# StateAct: Program State, before Pixels, for Long-Horizon Computer-Use Agents

> [← Daily summary](../2026-07-28.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2607.22798) · [arXiv](https://arxiv.org/abs/2607.22798)


## One-sentence takeaway

StateAct improves long-horizon computer-use performance and cost by making code-accessible program state the main action and verification interface, while reserving GUI interaction for irreducibly visual subgoals.

## Problem and motivation

Screenshot-driven agents act on lossy renderings that can hide task-critical details such as formulas, hidden rows, backend records, and whether an artifact was saved correctly. According to the authors, these ambiguities compound across long sequences of dependent actions, while screenshots provide weak evidence about the final persisted deliverable. The identified gap is therefore not merely visual perception: agents need direct state manipulation, independent completion checks, and context management over hundreds of steps (§§1, 3).

## Approach and contributions

- **State-grounded action:** The main agent uses persistent bash, Python, file editing, and structured state access. GUI operations are delegated to a specialist only when no state path is available or the subgoal is intrinsically visual (§4.1).
- **State-grounded verification:** A narration-blind, read-only finish gate independently locates and checks the persisted deliverable. It can reject structural failures and request up to three correction rounds (§4.2; Figure 4).
- **Long-horizon context management:** Fresh-context specialists, automatic context compaction, and an externalized plan preserve task facts across episodes of up to 200 main-agent turns (§4.3).
- **Empirical and diagnostic contribution:** The authors evaluate the harness on OSWorld 2.0, ablate its components and delegation depth, test shorter-horizon and alternative-backbone settings, and manually audit failures (§§5–6).

The results support the authors’ claim that state-first action is the largest measured contributor within this harness, while GUI fallback, verification, and context management remain useful. They also show that the verifier catches some structural defects but does not reliably establish value correctness.

The evidence does not isolate every architectural mechanism independently, prove that state-grounding caused all cross-system differences, or establish general superiority outside the tested benchmarks and backbones. Public-system comparisons additionally involve different systems and potentially different cost profiles, whereas the same-backbone reference is the cleaner comparison.

## Limitations and validity risks

- **Author-stated scope boundary:** State access offers little leverage for render-only objectives such as image editing, layout, chart appearance, canvas manipulation, or information available only on screen (§3).
- **Author-stated verification ceiling:** The finish gate checks structural completion without expected answers. It passed 68 of 76 non-perfect gated tasks, largely because it could reproduce the agent’s mistaken interpretation rather than independently establish value correctness (§6.1; Table 5).
- **Author-stated reasoning bottleneck:** Reasoning errors were the largest audited failure category, accounting for 38 of 79 non-perfect tasks (Figure 8).
- **Author-stated modality and ambiguity limits:** Twenty-two failures involved modality bottlenecks or ambiguous instructions, and five were not decomposed (§6.1; Figure 8).
- **Author-stated GUI dependence:** A weaker GUI specialist worked similarly on four reported benchmarks but substantially hurt OSWorld 2.0, so difficult long-horizon visual subgoals still require strong GUI capability (§6.2; Table 6).
- **Analyst inference — limited causal isolation:** The component ablations remove broad mechanisms rather than individually testing state discovery, code execution, compaction, planning, or specialist freshness. Their separate effects therefore remain uncertain.
- **Analyst inference — audit subjectivity:** Failure categories come from manual trajectory inspection; the supplied text does not report multiple annotators, agreement statistics, or a blinded labeling protocol.
- **Analyst inference — reproducibility:** The text describes prompts and tools conceptually but does not provide complete prompts, implementation details, repeated-run variance, statistical uncertainty, or evidence of a public release.

## Open research questions

1. **Can value correctness be verified without task-specific ground truth?** The finish gate mainly detects structural errors and shares interpretation failures with the acting agent. A next experiment could compare independent source re-derivation, heterogeneous verifier models, and task-specific oracle checks on the 68 wrongly passed tasks.

2. **Which context-management mechanism contributes most?** Removing compaction and planning together lowers partial score, but their individual effects are not reported. A factorial ablation could separately disable compaction, externalized planning, and fresh-context delegation while measuring accuracy, cost, and task-fact retention.

3. **When should an agent choose state access versus GUI interaction?** The current routing rule relies on probing and an “irreducibly visual” judgment. A next experiment could benchmark learned or confidence-based routing against fixed code-first, GUI-first, and oracle routing across state-addressable, hybrid, and render-only task strata.

4. **Does the advantage grow predictably with task horizon?** Similar performance on short-horizon OSWorld-Verified and larger gains on OSWorld 2.0 are consistent with this hypothesis but do not establish a scaling law. An experiment could bucket matched tasks by dependency length and hidden-state requirements, then measure relative performance as horizon increases.
