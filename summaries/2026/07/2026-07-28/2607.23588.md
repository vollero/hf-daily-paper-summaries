# JarvisHub: An Open Harness for Canvas-Native Multimodal Creative Agents

> [← Daily summary](../2026-07-28.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2607.23588) · [arXiv](https://arxiv.org/abs/2607.23588)


## One-sentence takeaway

JarvisHub is an open, canvas-centered harness that represents evolving multimodal projects as editable graphs, enabling agents and users to inspect, revise, recover, and trace long-horizon creative workflows.

## Problem and motivation

Creative production involves references, alternatives, revisions, failures, dependencies, and feedback—not merely isolated prompt-output exchanges. The authors argue that prompt-based systems discard intermediate state, chat interfaces poorly represent spatial and branching relationships, and node-based tools often require manually specified workflows. Closed commercial platforms further prevent researchers from inspecting state representation, tool scheduling, validation, and failure recovery. JarvisHub addresses the resulting need for an open runtime built around persistent, editable project state (Introduction; Figure 1).

## Approach and contributions

- **Project-state formalization:** Models long-horizon multimodal creation as an agent process over an editable, typed artifact graph containing content, provenance, user interactions, layout, dependencies, and runtime status (Section 2.2, Equations 1–2).
- **Three-layer harness:** Combines a persistent canvas-state layer, a protocol bridge that validates granted operations, and an agent runtime that plans, invokes capabilities, and commits evidence-backed updates (Sections 2.1–2.4; Figures 2–3).
- **Controlled orchestration and recovery:** Supports canvas, generation, native-execution, recovery, and MCP tool families, supplemented by skills, memory, and subagents (Section 2.4; Table 2).
- **Process traceability:** Records requests, canvas states, capability manifests, execution grants, actions, observations, feedback, repair decisions, and resulting states as trajectories (Section 2.5, Equation 5).
- **Cross-domain demonstrations:** Presents qualitative cases in narrative media, interactive web development, and presentation-deck generation (Sections 3.2–3.3; Table 3).

The evidence establishes feasibility through selected qualitative demonstrations and illustrates inspectable project traces. It does not establish superiority over prompt-, chat-, or node-based alternatives, quantify reliability or artifact quality, isolate the value of individual architectural components, or measure recovery and feedback adherence systematically.

## Limitations and validity risks

- **Author-stated:** The experiments are qualitative demonstrations, not a completed benchmark or leaderboard (Section 5).
- **Author-stated:** Artifact quality depends on external models and tools because JarvisHub focuses on orchestration and state management (Section 5).
- **Author-stated:** Protocol checking makes actions explicit and recoverable but cannot guarantee semantically correct creative decisions (Section 5).
- **Author-stated:** Trajectories require consent, anonymization, quality filtering, and copyright review before research or training use (Section 5).
- **Analyst inference:** With no baselines, quantitative metrics, repeated trials, or user study reported, comparative effectiveness and run-to-run robustness remain unestablished.
- **Analyst inference:** No ablation isolates contributions from the canvas representation, protocol bridge, memory, skills, subagents, or recovery tools.
- **Analyst inference:** Reliance on one listed backend configuration limits conclusions about portability across models and tool stacks.

## Open research questions

1. **Does canvas-native state improve performance over chat or manual node workflows?** The paper provides no controlled comparison. A next experiment could hold models and tools fixed while comparing task success, context preservation, repair success, and human effort across interface/state representations.
2. **Which harness components drive any gains?** No component ablation is reported. Disable typed dependencies, protocol grants, trajectory history, memory, or recovery individually and measure degradation on standardized long-horizon tasks.
3. **How reliable is JarvisHub across repeated and adversarial workflows?** Selected examples do not reveal variance or failure rates. Run multiple seeds across tasks containing broken tools, contradictory feedback, missing assets, and long version branches.
4. **Can trajectory data safely improve future agents?** The paper proposes this possibility but identifies governance requirements. A next study could curate consented trajectories, apply filtering and anonymization, then compare training utility and privacy leakage against appropriate controls.

## Confidence and missing information

**Confidence: high** for the architecture, intended capabilities, evaluation scope, and stated limitations because the supplied text covers them directly.

Materially missing are quantitative metrics, baseline results, repeated-trial statistics, human-evaluation procedures, ablations, failure-case analysis, resource and latency measurements, detailed task counts or sampling criteria, and empirical evidence that recorded trajectories improve training. Repository details referenced by the paper are outside the supplied text and were not consulted.
