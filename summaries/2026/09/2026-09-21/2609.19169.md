# SiliconBench: Speed, Memory, and Fidelity for LLM Serving on Unified-Memory Desktops

> [← Daily summary](../2026-09-21.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.19169) · [arXiv](https://arxiv.org/abs/2609.19169)


## One-sentence takeaway
SiliconBench’s nine-engine Apple Silicon audit shows that concurrent throughput, memory headroom, and task-level fidelity can diverge, with only llama.cpp, vllm-metal, and omlx passing its completion, fidelity, and model-coverage gates (§7, Table 5).

## Problem and motivation
Local LLM servers share unified memory with the operating system and foreground applications. Single-request speed therefore misses practical failures: concurrency can inflate memory use, delay responses, or expose output-quality regressions. The authors identify a gap in benchmarks that jointly assess these effects across Apple Silicon serving engines (§§1–2).

## Approach and contributions
- **Joint serving audit:** Fixed chat and agent prompt sets measure throughput, latency, system memory, and completion; a separate classification task measures fidelity against NVIDIA A100 vLLM. The main comparison uses Qwen3-0.6B, with newer architectures, larger models, and a DGX Spark performance track extending coverage (§§4, 6).
- **Evaluation framework:** Architecture readiness, memory discipline, and multi-node scaling organize the findings. These are evaluation desiderata, rather than newly introduced serving algorithms (§3).
- **Maintained benchmark assets:** The authors report releasing code, per-run results, and maintenance journals. Their workflow permits bounded agent-proposed adapter fixes while reserving workload changes, scoring, and official-result review for maintainers (§5, Appendix A).

## Evidence and main results
| Finding | Evidence / setting | Location in paper |
|---|---|---|
| vllm-metal scales across both serving splits | Qwen3-0.6B BF16, 64 GB M5 Pro, 100 prompts per split: concurrency 1→16 raises throughput **3.65× on chat and 2.71× on agent**; agent median TTFT at concurrency 16 is **219 ms**. | §6.1.1; Figure 6 |
| Completion does not establish memory discipline | On the same main audit, sglang and vllm-mlx each complete **600/600 requests** despite high memory use. vllm-metal’s agent peak system memory stays at **34.7–34.9 GB** across concurrency levels. | §6.2; Figures 5, 7 |
| Fidelity regressions are configuration-specific | GMRID, BF16, Qwen3-0.6B: ollama’s five-shot weighted F1 is **0.4462**, versus **0.7364** for A100 vLLM; vllm-mlx’s zero-shot F1 is **0.3592**, versus **0.4094**. | §6.3; Table 3 |
| Newer-model fidelity agrees within the observed band | All five evaluated Apple stacks fall within **1.4 percentage points** of reference weighted F1 for Qwen3.5-0.8B and Gemma-4-E4B-it, using GMRID zero-/five-shot BF16 evaluation. | §6.3; Table 3 |
| Only three engines pass the combined gates | llama.cpp, vllm-metal, and omlx satisfy completion of **at least 90/100 requests** at every tested concurrency on both splits, reference-band fidelity, and coverage of all three model releases. Speed and memory are reported but are not gates. | §7; Table 5 |
| Larger-model throughput rankings depend on caching | For nominal four-bit Qwen3.6-35B-A3B on the M5 Pro, agent concurrency 4, vllm-metal’s throughput advantage over omlx ranges from **4% to 17%** across archived cache configurations. | §6.1.2; Appendix F.2 |
| CUDA implementations show stronger scaling | DGX Spark, Qwen3-0.6B BF16, identical prompt sets: concurrency 1→16 yields **7.7×/4.3×** chat/agent scaling for vLLM and **6.9×/4.6×** for SGLang. Hardware and configuration differences prevent causal attribution. | §6.1.3; Table 12 |
| Tested multi-node paths diverge | Qwen3.5-35B-A3B eight-bit, 512 generated tokens, two versus one 64 GB M4 Pro: TP/RDMA decode speedups are **1.28–1.32×** for mlx_lm and **1.30–1.37×** for EXO; llama.cpp PP/TCP achieves **0.80–0.84×**, across tested context lengths. | §6.4; Table 4 |

These results establish differences among the tested configurations and demonstrate why throughput alone is insufficient. They do not isolate the causal contribution of batching, cache layout, hardware, or transport. Fidelity agreement concerns one classification task; the reported agreement band is explicitly not a statistical noise estimate (§6.3).

## Limitations and validity risks
- **Author-stated scope:** The main audit uses one Apple M5 Pro; larger-model studies cover selected engines. Main serving splits omit very long contexts and long-form generation (§4; Appendix H).
- **Author-stated uncertainty:** There is no designed repeat study or formal variance estimate. Larger-model follow-ups use later builds, differing quantization formats, and single measurements per configuration (§6.1.2; Appendices F, H).
- **Measurement caveats:** Structured tool calls can be scored as failures when content is empty; ollama throughput can include content-free tokens. Missing telemetry includes mlx_lm’s main agent memory trace and omlx’s memory-ceiling study trace (§§6.1.1, 6.3; Appendices A, F).
- **Reproducibility gaps:** Historical records lack a complete engine-version manifest and exact maintenance-agent model IDs. The demonstrated maintenance incidents do not establish sustained publication cadence (§5; Appendix A).
- **Analyst inference:** Passing the gates does not establish acceptable foreground-application responsiveness: memory is not gated, and changing foreground memory demand was not tested (§7).

## Open research questions
1. **Can servers preserve responsiveness as foreground memory demand changes?** This was not evaluated (§7). Replay serving workloads while varying controlled foreground allocations and measuring both inference and application latency.
2. **Which serving mechanisms cause the concurrency gains?** Shared architectural features produce different scaling (§6.1.1). Ablate packed queries, paging, and mixed prefill/decode within one engine under matched settings.
3. **Do fidelity findings generalize to agent tasks?** Fidelity uses only GMRID, while speed prompts are not accuracy-scored (§4). Add scored tool-use and generation tasks with controlled templates and repeated runs.
4. **Does multi-node serving help when distribution is required for capacity?** The tested model fits on one machine (§6.4). Evaluate models exceeding single-node memory and expand beyond two nodes.

## Confidence and missing information
**Confidence: medium.** The supplied text supports the descriptive findings, but causal explanations and generalization remain limited.

Material missing information includes formal uncertainty estimates, complete historical software provenance, the identified memory traces, isolated fidelity-regression causes, dynamic foreground-memory tests, and capacity-required multi-node results.
