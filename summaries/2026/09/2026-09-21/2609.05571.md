# Grounded Skill Synthesis from Code at Scale for Agentic Intelligence

> [← Daily summary](../2026-09-21.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.05571) · [arXiv](https://arxiv.org/abs/2609.05571)


## One-sentence takeaway
Code2Skill converts repository code into retrievable procedural guidance, with reported gains in 57 of 72 matched evaluations, although its grounding checks establish LLM-assessed consistency rather than executable correctness (§§3.2, 5.2).

## Problem and motivation
Agents need reusable procedures that specify applicability, steps, constraints, and failure handling. The authors argue that trajectory-derived skills depend on the generating agent’s experience and environment, while document-derived skills can lack implementation evidence. They propose source code as an existing, inspectable substrate for acquiring procedural knowledge before downstream agent interaction (§1).

## Approach and contributions
- **Code2Skill construction pipeline:** Select reusable source units, extract atomic operations, composite workflows, or recurring patterns, and preserve invariants, failure cases, anti-goals, and provenance (§3.2).
- **Reconstruction-based filtering:** An LLM reconstructs code without seeing the source body; a source-aware judge checks consistency. An adjudicator can retain a faithful skill despite failed reconstruction. This is explicitly not a substitute for testing (§2; Appendix C.2).
- **CodeSkillBank:** The pipeline produces 1,006,822 accepted records from 19,769 repositories, with separate retrieval annotations and deterministic purpose-based representative selection (§§3–4; Appendix C.3).
- **Utilization studies:** Experiments examine skill source, workflow placement, compact rendering, coding reinforcement learning, and skills extracted from tested AI-generated implementations (§5).

These results support the usefulness of the constructed bank under the tested workflows. They do not establish universal gains, formal skill correctness, or equivalence between code origins. Macro-averages combine different benchmark evaluators and task counts; they are descriptive scores, not pooled success rates (Appendix D.1).

## Limitations and validity risks
- **Authors’ qualifications:** Workflow comparisons change more than insertion point; RL reports one checkpoint without repeated seeds or learning curves; the small code-origin score difference does not establish equivalence (§§5.4, 5.6–5.7).
- **Analyst inference—grounding:** Construction stages share one model configuration, and judges receive no tests or execution traces. Correlated judgment errors remain possible; acceptance does not demonstrate executable equivalence (Appendix C).
- **Analyst inference—causal attribution:** Separately sampled annotation pools do not isolate filtering effects. No reported ablation establishes the downstream contribution of reconstruction, adjudication, or record granularity. Shared-interface bank comparisons also do not isolate source type from bank scale and construction resources (Appendix B; §5.3).
- **Analyst inference—generalization:** Default evaluation retrieves from a sampled fraction of the bank. Repository-to-benchmark overlap controls are not reported, so offline construction alone does not establish contamination-free transfer (§5.1; Appendix D).
- **Analyst inference—annotation precision:** Sample sizes, annotator agreement, and accepted-branch weighting are unavailable, limiting interpretation of the accepted-bank quality summary (Appendix B).

## Open research questions
- **Does reconstruction filtering improve downstream utility?** Outcome-pool comparisons are not causal. Compare size-matched banks built with and without reconstruction/adjudication, using independent executable checks and downstream evaluation.
- **Does code origin explain the bank-comparison advantage?** Construction resources and bank sizes are not matched in the reported comparison. Equalize budgets, record counts, retrieval, and context across code- and trajectory-derived banks.
- **Do gains survive repository-disjoint evaluation?** Source overlap controls are unspecified. Remove benchmark repositories and related code before construction, then repeat matched evaluations.
- **Can tested AI code sustain bank expansion?** The provenance study covers a small paired sample. Repeat across more behaviors and generators, with source-disjoint tasks and paired uncertainty estimates.

## Confidence and missing information
**Confidence: medium.** The supplied text supports the pipeline description and reported outcomes, but stronger causal and reproducibility conclusions remain limited.

Material missing information includes the construction model identity and cost, exact selection gates and repository caps, default retrieval implementation, baseline bank sizes and budgets, annotation sample details, main-evaluation uncertainty, repository-overlap audits, and usable release links or licensing details.
