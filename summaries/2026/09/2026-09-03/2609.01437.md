# HarnessDev: Can LLMs Create and Evolve Their Own Agent Harness?

> [← Daily summary](../2026-09-03.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.01437) · [arXiv](https://arxiv.org/abs/2609.01437)


## One-sentence takeaway

HarnessDev shows that frontier LLMs can build and locally improve runnable agent harnesses, but their quality is domain-dependent, evolution is noisy, and improvements often fail to generalize across tasks or executor models.

## Problem and motivation

Agent performance depends substantially on model-external infrastructure governing execution loops, tools, context, state, recovery, and verification. Yet conventional evaluations treat this harness as fixed configuration and score only task outputs. The authors address the resulting gap: evaluating whether an LLM can create a persistent harness from a weak seed and subsequently improve it using execution feedback, while separating harness quality from executor capability and measuring both task success and token cost (Sections 1 and 3.1).

## Approach and contributions

- **HarnessDev benchmark:** Changes the evaluated artifact from a one-off answer to frozen, runnable infrastructure reused across downstream tasks (Sections 1 and 3.1).
- **Creation stage:** Six creator LLMs receive a zero-scoring compatibility seed, a task-family specification, and one to three development cases, then construct harnesses for code, data/ML experimentation, writing, and search/research (Sections 3.2–3.3).
- **Evolution stage:** Creators revise their own code harnesses using feedback from SWE-Pro-100 and Terminal-Bench-89; every official revision is later tested on 630 withheld SWE-Pro tasks (Sections 3.2 and 4.3).
- **Creator–executor separation:** Self-Eval runs a harness with its creator model, while Unified-Eval uses Gemini 3.1 Pro for all generated harnesses to test portability and isolate executor effects (Sections 3.4 and 4.1).
- **Artifact and trajectory analysis:** The evaluation records execution-token cost, edit behavior, component reachability, regressions, feedback use, and cross-executor transfer, alongside native benchmark scores (Sections 3.5, 4.2, and 4.3).

The evidence supports the authors’ claim that runnable harness construction is feasible and that targeted evolution can yield modest gains. It also demonstrates substantial executor dependence, inactive machinery, noisy feedback, and weak version selection. It does **not** establish parity with human engineering generally: the references are uneven external system results rather than paired controls, and the evaluated domains, models, and evolution trajectories are limited.

## Limitations and validity risks

- **Author-stated:** Four categories do not cover all deployments, and human-engineered references are uneven and potentially suboptimal (Section 6.1).
- **Author-stated:** Human-reference scores come from different harness–executor combinations, so comparisons are not controlled estimates of the effect of human versus generated harness design (Sections 4.1 and 6.1; Appendix B.2).
- **Author-stated:** Unified-Eval cannot fully remove model–harness interaction effects (Section 6.1).
- **Author-stated:** Evolution has only one trajectory per creator–runtime cell, including one unfinished main-runtime cell, preventing uncertainty estimates and population-level comparisons (Section 6.1).
- **Author-stated:** Post-freeze held-out evaluation covers only SWE-Pro, while Evolution itself covers only code harnesses (Sections 3.3 and 6.1).
- **Author-stated:** The development environment remains fixed; recursive use of an evolved harness as its own future development environment is untested (Section 6.1).
- **Analyst inference:** Many reported score changes are difficult to attribute causally to edits because repeated-run variation reaches approximately ±4.75 pair-score points and only two switches exceed that noise band (Section 4.3).
- **Analyst inference:** Reproducibility cannot be fully assessed from the supplied rendering because the numerical bodies of several referenced tables, including Tables 2–9, are absent even though their captions are present.
- **Analyst inference:** Container execution was designed for reproducibility rather than strong containment, so the released generated harnesses require stricter isolation before reuse; the authors explicitly characterize them as untrusted code (Ethics statement).

## Open research questions

1. **Can evolution generalize beyond code and SWE-Pro?** Held-out evolution testing is confined to SWE-Pro. A next experiment could evolve writing, research, and ML harnesses using one feedback subset and evaluate every revision on disjoint tasks from the same and different benchmarks.

2. **How can final versions be selected reliably under noisy feedback?** Only 2/9 declared revisions were held-out optimal, and switch directions agreed with held-out results only 53.1% of the time. A next experiment could compare repeated evaluation, confidence-aware selection, regression suites, and simpler search baselines under matched budgets.

3. **Can harness changes transfer across diverse executor models?** Fixed-Gemini results show strong runtime dependence but test only one common executor. A next experiment could run identical frozen revisions across a matrix of executor models and explicitly optimize worst-case or average cross-model performance.

4. **Do state, memory, and verification mechanisms causally improve results?** Many such components were absent, dead, or rarely changed, and the paper’s analysis is descriptive. Controlled component ablations with reachability checks and matched execution budgets could test their causal contribution.

## Confidence and missing information
