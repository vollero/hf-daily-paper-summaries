# Repo-To-Skill: Distilling GitHub Repositories Into AI4AI Skills

> [← Daily summary](../2026-09-03.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.02749) · [arXiv](https://arxiv.org/abs/2609.02749)


## One-sentence takeaway

The authors report that verified, selectively loaded skills distilled from repositories, papers, and task feedback substantially improve a fixed GPT-5.5 Codex research agent across four benchmarks, though skill construction adds substantial offline cost and the evaluation does not isolate which distillation components drive the gains.

## Problem and motivation

Autonomous ML-research agents usually combine a language-model backbone with a harness for planning, execution, memory, and verification, but lack explicit domain-specific “operational knowledge”: guidance about which tools and methods apply, how to configure them, and how to avoid implementation or evaluation failures (§§1–2).

The authors argue that this knowledge exists in repositories and papers but is too dispersed, declarative, and voluminous to load directly. Agents therefore repeatedly rediscover package behavior through budget-consuming trial and error. Existing manually authored skills do not scale with the number of domains, software versions, and tools. The identified gap is an automatic, scalable way to turn static technical sources into compact, executable, verifiable, and reusable agent context (§§1–2.2).

## Approach and contributions

1. **Operational-knowledge formulation.** The paper extends the conventional model-plus-harness account of an agent with an explicit operational-knowledge component, \(\mathcal K\), separating domain guidance from control-loop design (§2, Eqs. 2–4).

2. **DisCo distillation pipeline.** DisCo transforms a source or task anchor through four stages: scope capabilities, ground them in evidence, construct a candidate skill graph, and verify or repair it (§3.2, Eq. 8; Figure 2). It supports:

   - Task-agnostic distillation from repositories, papers, or tutorials.
   - Task-oriented distillation driven by a particular problem and its capability gaps.

3. **Progressively disclosed skill graphs.** Each skill can include a `SKILL.md` usage interface, deeper references, and executable scripts; linked skills encode routing, dependencies, or composition so only relevant branches enter context (§3.1, Eqs. 5–7).

4. **AREX-Skill Library.** The released repository snapshot contains 5,353 verified skills from 1,000 ML repositories, routed through 20 areas and 178 capability families (§4.1; Figure 3). Separate evaluation collections include 636 skills distilled from 153 papers, 75 MLE-bench task graphs, and shared graphs for FrontierCS and PassNet (§4.3).

5. **Controlled downstream evaluation.** The authors compare GPT-5.5 Codex with and without skills while holding the backbone, harness, and downstream execution budget fixed across MLE-bench, PaperBench, FrontierCS, and PassNet (§5.1). Offline construction budgets are separate.

These results support the authors’ claim that added operational context can improve a fixed agent configuration across several kinds of research work. The matched comparisons are stronger evidence for the complete skill-equipped condition than comparisons with unrelated leaderboard systems.

They do **not** establish that every skill helps, that performance comes specifically from verification rather than added information or extra offline computation, or that gains generalize to other backbones, harnesses, domains, and budgets. Near-zero usage correlations on FrontierCS do not by themselves prove that additional computation had no causal role.

## Limitations and validity risks

- **Separate construction cost:** Skill construction is excluded from matched runtime budgets. MLE-bench permits up to 24 GPU-hours of exploration per task before a separate 24-GPU-hour run, while repository construction averages about \$40 per repository (Appendix A.1–A.2.1). The results therefore demonstrate amortized downstream benefit, not lower total cost for one-off tasks.

- **Occasional negative transfer:** PaperBench performance declines on `sample-specific-masks` by 5.07 points and `stay-on-topic` by 4.52 points. The authors suggest imperfect retrieval precision or distraction by poorly matched guidance (§5.3), but do not experimentally verify that explanation.

- **Resource use is not strictly matched on FrontierCS:** Time limits are shared, but skill-equipped runs consume more steps, calls, and tokens (Table 3). The correlation analysis weakens a simple resource-scaling explanation but is observational rather than a compute-matched ablation.

- **Curated, non-exhaustive library:** Repository selection uses visibility and practical-use signals, including GitHub stars, and represents a snapshot rather than the entire ML ecosystem (§4.1). Coverage of obscure, private, or rapidly changing software is not established.

- **Verification is heterogeneous:** Repository skills use native tests and smoke checks; PaperBench uses isolated tests and bounded recovery; task-oriented skills use diagnostic trajectories and evaluator feedback (Appendix A). These procedures do not imply uniform correctness guarantees.

- **Analyst inference — component attribution is unresolved:** The supplied experiments do not ablate grounding, scripts, references, verification, graph links, routing, or task-oriented versus generic skills. Thus the source does not show which component is necessary or sufficient.

- **Analyst inference — possible development/evaluation adaptation:** FrontierCS and PassNet graphs were iteratively refined on selected development or training problems before freezing (Appendix A.2.3–A.2.4). Although task text and identifiers were excluded for FrontierCS and PassNet reports a held-out evaluation list, the supplied text does not quantify distribution overlap or sensitivity to graph-development choices.

- **Analyst inference — limited model generalization:** Main evaluations use one GPT-5.5 Codex configuration with xhigh reasoning (§5.1). Construction uses additional models, including GPT-5.6-sol, but downstream benefits for weaker models or different harnesses are not tested.

## Open research questions

1. **Which skill components actually produce the gains?**  
   The paper evaluates the complete operating-context package without component ablations. A next experiment could independently remove verification, scripts, references, graph links, or router metadata under matched total compute.

2. **When should an agent ignore a retrieved skill?**  
   Two PaperBench regressions suggest harmful mismatches, but the proposed retrieval-precision explanation remains untested. A next experiment could compare confidence-gated retrieval, explicit “no suitable skill” decisions, and an unguided fallback against the current router.

3. **Do skills remain beneficial after accounting for their full construction cost?**  
   Offline costs are intentionally separated and assumed to amortize across reuse. A next experiment could measure break-even reuse counts and total score per dollar or GPU-hour across repeated, related, and unrelated tasks.

4. **How portable are the skills across agents and software versions?**  
   The paper argues that compatible harnesses can reuse them, but downstream tests use GPT-5.5 Codex, and repository drift is identified as a challenge. A next experiment could cross-evaluate unchanged skill graphs across multiple models, harnesses, and newer repository releases.

## Confidence and missing information

**Confidence: high** for the reported experimental values and described protocols because the supplied text includes the full main paper and implementation appendices.

Material missing or insufficiently specified includes:

- Component-level ablations for distillation, routing, verification, and skill representation.
- Total monetary, token, and compute cost for all benchmark-specific skill construction.
- Variance or repeated-run uncertainty for PaperBench, FrontierCS, and PassNet.
- Cross-model and cross-harness downstream evaluations.
- Detailed benchmark contamination checks beyond the stated source exclusions.
- Longitudinal evidence about maintaining skills as repositories change.
- Direct measurements of retrieval accuracy, skill-use fidelity, or context overhead.
