# Miles v0.1: Production-Level Post-Training

> [← Daily summary](../2026-09-09.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.08368) · [arXiv](https://arxiv.org/abs/2609.08368)


## One-sentence takeaway
Miles integrates rollout fidelity, asynchronous scheduling, memory offload, and weight synchronization into a post-training system that runs GLM-5.2 744B-A40B across 64 GB300 GPUs, although its single-run evidence does not establish reliable task-quality gains (§9).

## Problem and motivation
Frontier agentic RL combines long, variable-duration tool interactions with memory-intensive training. Synchronous execution leaves hardware idle, while differences in token reconstruction, expert routing, and numerical computation can make the trainer optimize trajectories differently from how they were sampled. The authors identify a need for an integrated, verifiable, customizable system addressing both efficiency and rollout–training fidelity (§§1–2).

## Approach and contributions
The contribution is primarily **system integration and implementation** built on slime, SGLang, Megatron-LM, and FSDP; the report credits prior work for algorithms including R3, LoRA, and on-policy distillation.

- **Rollout orchestration:** Session-affinity routing preserves cached prefixes; asynchronous generation feeds a bounded, group-aware buffer with filtering and weight-staleness checks. Evaluation scores retain their policy-version attribution (§§2.1–2.3).
- **Trajectory and numerical fidelity:** A token-in-token-out session server preserves sampled token IDs across turns and branches. Expert-routing replay, shared quantization contracts, and narrowly supported deterministic alignment address additional mismatch sources (§§2.4–2.5, 3.1, 5.3).
- **Memory and synchronization:** Actor offloading and disk-streamed optimizer state reduce GPU-memory requirements. Broadcast, RDMA peer-to-peer transfer, and shared-storage byte deltas support different deployment topologies (§§3.2, 4).
- **Reusable training infrastructure:** Typed interfaces support alternative objectives, LoRA, distillation, supervised training, and a diffusion extension, with explicit recipe-verification levels (§§3.3–3.4, 5–8).

These results support configuration-specific feasibility and component-level speed improvements. They do not establish superiority over another complete post-training framework, general scaling behavior, or reliable downstream accuracy gains. Several additional claims, including low-precision reward parity, are qualitative in the supplied text.

## Limitations and validity risks
- **Author-stated coverage limits:** Session-server image/video inputs and screenshot recording are unavailable; connectors are experimental; MXFP8/NVFP4 remain beta; backend, model, and transport support differ (§§2.3–2.4, 3.1, 4–7).
- **Author-stated correctness boundaries:** Loose history matching can silently merge different tool calls. Exact alignment covers sampled-token probabilities only and does not remove stale-policy effects (§§2.4.2, 5.3).
- **Author-stated operational tradeoffs:** P2P can be slower on single-node deployments. Streamed optimizer checkpoints require the same parallel layout and can block training during saving (§§3.2.2, 4.2).
- **Analyst inference:** The reference run lacks repeated seeds, reported held-out evaluation scores, and component ablations, so reward generalization and each mechanism’s causal contribution remain unresolved (§9).
- **Internal ambiguity:** Section 3.2.2 describes the reference run as having DP = 4, whereas §9.1 describes a single data-parallel replica. The optimizer-sharding configuration needs clarification.

## Open research questions
- **What asynchronous staleness policy best balances learning and throughput?** The buffer exposes controls, but no sweep is reported. Compare staleness limits and synchronous execution at fixed compute, measuring discarded groups and held-out reward (§§2.2, 9).
- **When does numerical exactness justify its cost?** Exact alignment slows rollout without demonstrated reward improvement in the documented run. Compare exact alignment, standard corrections, and routing replay across supported models using repeated seeds and matched compute (§§2.5, 5.3).
- **How do synchronization choices generalize across topology?** P2P comparisons vary model and fleet width together, and disk-delta lacks timing results. Hold the model fixed while varying fleet width and network/storage conditions across all transports (§4).

## Confidence and missing information
**Confidence: medium.** The architecture and reported measurements are explicit, but broad effectiveness claims have limited experimental support.

Material missing information includes repeated-run uncertainty, held-out reference-run scores and task counts, the precise KL estimator, a resolved DP configuration, complete settings for several component timings, quantitative low-precision and exact-alignment tradeoffs, and disk-delta performance measurements.
