# ProgramDistill: From Interactive Web Apps to Verifiable Reference-Guided SWE Tasks

> [← Daily summary](../2026-09-17.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.18805) · [arXiv](https://arxiv.org/abs/2609.18805)


## One-sentence takeaway

ProgramDistill automatically converts working web applications into replay-verifiable coding tasks and shows that frontier agents’ success declines sharply as they must discover and restore more dependent behaviors.

## Problem and motivation

Most coding benchmarks provide the desired behavior through issues, instructions, or tests. The authors target a different setting: an agent receives a working reference application with hidden source and an incomplete editable application, then must discover the intended behavior through interaction, implement it, and validate the result (Introduction, Figure 1).

Interactive applications pose an additional challenge because behaviors depend on earlier actions and persistent state. Existing whole-program behavioral reconstruction does not expose these prerequisite relationships or provide controlled task granularity. The authors therefore seek a scalable way to factor working applications into verifiable tasks ranging from atomic repairs to complete reconstruction (Section 1, pp. 1–2).

## Approach and contributions

1. **ProgramDistill benchmark.** The benchmark contains 4,063 repair tasks derived from 1,975 replay-verified behaviors across 26 self-contained web applications. Tasks cover atomic repair, cumulative repair, and full-application reconstruction (Section 1; Figure 5).

2. **Mine–craft–patch pipeline.**
   - **Mine:** LLM agents discover browser-interaction traces, associate dependent traces through parent links, and retain only traces that replay successfully.
   - **Craft:** LLM agents remove the source implementation responsible for each behavior. Counterfactual validation requires the application to build, prerequisites to remain functional, and the target behavior to fail.
   - **Patch:** Evaluated coding agents inspect the working reference, edit the incomplete application, and are graded by replaying the original traces (Sections 2.2–2.4; Figures 2 and 4).

3. **Application-to-task factorization.** Verified behaviors become individual tasks and can be composed along prerequisite lineages. Each accepted task has a gold patch obtained by reversing the mask and verified through full-lineage replay (Sections 2.3 and 2.3, “Gold patches”).

4. **Restoration depth.** The number of masked behaviors in a lineage provides a controlled difficulty axis. Binary scoring requires the complete lineage to pass, while chain scoring credits the recovered prefix (Sections 2.3–2.4, Equation 1).

5. **Diagnostic trajectory analysis.** The paper studies how observation, validation, and editing effort changes with depth and categorizes failures in full reconstruction (Section 3.2.2; Figures 9–13).

The results establish performance under the paper’s replay-based, deterministic web-application environment. They support the authors’ claim that deeper cumulative restoration and full reconstruction remain difficult, and the trajectory evidence associates deeper tasks with reduced effort per required behavior.

They do not establish that restoration depth alone causes the decline: depth also changes workload and potentially other task characteristics. The context-band analysis weakens one alternative explanation but is observational rather than a controlled intervention. Likewise, Astra’s observation-heavy behavior is correlated with stronger performance; the experiments do not isolate observation activity as its cause. Failure categories also depend on an LLM-assisted post hoc analysis.

## Limitations and validity risks

**Author-stated limitations**

- Solver agents receive structured text and accessibility observations without screenshots, and replay checks do not measure visual fidelity (Section 5).
- The experiments cover self-contained web applications rather than external services, nondeterministic systems, desktop software, or mobile applications (Section 5).
- GPT-5.6 Sol constructs every benchmark stage, so behavior coverage and task quality may depend on one construction model (Section 5).
- Results may be sensitive to selector stability, observation quality, replay infrastructure, and the agent harness (Section 5).
- Training with the generated tasks and trajectories is proposed but not evaluated (Section 5).
- The benchmark is described as being prepared for public release, so availability at the time of the supplied text is not established (p. 1 footnote).

**Analyst inferences**

- **Construction-model bias:** Using one model for mining and crafting may favor behaviors and source structures that it can recognize; no cross-constructor comparison is reported.
- **Replay coverage:** Passing recorded traces demonstrates agreement on sampled workflows and expected signals, not complete behavioral equivalence. The authors explicitly evaluate selected atomic behaviors and lineages.
- **Depth confounding:** Cumulative tasks grow in code size and trace actions alongside restoration depth (Figure 10), so depth is not experimentally isolated from total workload.
- **Failure-label reliability:** The 977 failures were categorized using GPT-6 Astra, but the supplied text reports no human validation, inter-rater agreement, or classifier accuracy (Section 3.3.2).
- **Limited full-reconstruction sample:** Full reconstruction covers three models, 12 applications, and one run per model-application pairing as implied by the 36 analyzed runs; run-to-run variance is therefore not established.
- **Merge-agent dependence:** Of 1,201 cumulative tasks, 572 required an LLM merge agent. All reportedly retained every intended mask, but the supplied text does not describe an independent manual audit (Section 2.3).

## Open research questions

1. **Does restoration depth remain predictive when workload is controlled?**  
   Depth covaries with lines to restore and behavior-trace actions. A matched experiment could compare tasks with equal code-change size and trace length but different numbers of dependent behaviors.

2. **Which observation strategy causally improves repair success?**  
   Astra observes more and edits less, but the evidence is correlational. An intervention could impose observation budgets or require targeted reference and current-app validation, then compare success and cost.

3. **How sensitive is benchmark quality to the construction model?**  
   All mining and crafting use GPT-5.6 Sol. Running the pipeline with several construction models and measuring behavior overlap, mask validity, diversity, cost, and downstream model rankings would test robustness.

4. **Can multimodal observations improve behavioral and visual reconstruction?**  
   Solver agents do not receive screenshots, and visual fidelity is outside the verifier. A follow-up could add screenshot access and visual metrics while retaining the same replay checks to measure complementary gains.
