# Can Agents Design Libraries for Agents?

> [← Daily summary](../2026-09-30.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.36730) · [arXiv](https://arxiv.org/abs/2609.36730)


## One-sentence takeaway
LibraryDesignBench finds that agent-designed libraries can outperform production libraries for fixed downstream coding agents, but interface rigidity, verbosity, and incomplete reuse constrain their value (Table 1; §3.2).

## Problem and motivation
Agents increasingly consume code written by other agents, yet often reimplement existing functionality. The authors argue that library correctness tests cannot establish whether a design helps downstream agents write correct, simpler programs; prescribed interfaces also remove the design freedom being evaluated (§1).

The gap is an evaluation of library design through actual agent use, rather than implementation correctness, static library metrics, or human preferences.

## Approach and contributions
- **LibraryDesignBench:** A designer builds a packaged library from capability requirements with open interfaces and abstractions. Three fixed downstream implementers solve programming problems using it. The benchmark contains 15 library tasks and 242 expert-validated problems across Python, TypeScript, Rust, and Haskell (§§2.1, 2.4; Table 7).
- **Downstream utility measurement:** Each program receives its squared test-pass fraction multiplied by simplicity: the average of four capped reference-to-program ratios for source lines, cyclomatic complexity, cognitive complexity, and Halstead volume. References use production libraries. Results average three independent runs and weight library tasks equally (§§2.2–2.3).
- **Design and reuse analysis:** The authors inspect generated abstractions, audit excess code and failed tests, and introduce LibraryUseBench to evaluate implementers with production libraries (§§3.1–3.3).
- **Combined design intervention:** Consumer-first sketches, runnable examples, and testing with fresh agents are evaluated together as guidance for GPT-6 Astra; their individual effects are not isolated (§3.4; Appendix I).

These results establish downstream utility under the benchmark’s specified consumers, prompts, tasks, and budgets. They do not establish a universal library ranking or prove that interface redesign caused the audit’s attributed failures. Lower exported-name overlap measures naming divergence, not necessarily deeper architectural novelty.

## Limitations and validity risks
**Author-stated limitations:** The benchmark measures tested downstream correctness and static consumer-program complexity, not full library correctness, security, runtime efficiency, or maintainability. References are not uniquely optimal; workloads emphasize reuse opportunities; confidence intervals describe reruns of the fixed benchmark, not new domains (§5). With three runs per task, nominal confidence-interval coverage is not guaranteed (§2.3).

**Audit limitations:** One model audits each selected cell without human labels, agreement checks, or executing its proposed better path. Fully passing solutions are excluded, and attribution includes library changes that could prevent implementers’ own task-logic errors (Appendix F).

**Analyst inferences:** The bundled guidance experiment cannot identify which component helps (§3.4). Including visible example problems in scored evaluation leaves uncertainty about performance on wholly unseen use cases (§2.1). Harness sensitivity also limits conclusions about models independent of their execution setup (§3.1).

## Open research questions
- **Which guidance component improves reuse?** The intervention is bundled (§3.4). A factorial experiment could separate consumer sketches, runnable examples, and fresh-agent testing.
- **Do better designs transfer to unseen consumers and tasks?** Scores are explicitly configuration-dependent (§5). Evaluate frozen libraries with held-out model families and new downstream workloads.
- **Do simpler consumer programs retain broader software quality?** Security, runtime efficiency, and maintainability are unmeasured (§5). Add targeted security tests, runtime benchmarks, and change-request evaluations.
- **How reliable is the failure taxonomy?** Current labels lack agreement checks and executable counterfactual validation (Appendix F). Independently relabel a stratified sample and implement the proposed library fixes.

**Confidence: high** for the reported benchmark setup and results; **medium** for causal interpretations of failures and guidance effects.
