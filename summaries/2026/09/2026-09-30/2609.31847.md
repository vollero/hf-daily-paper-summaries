# Omni-IO Skills: Harnessing Your Agent Omni-Native

> [← Daily summary](../2026-09-30.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.31847) · [arXiv](https://arxiv.org/abs/2609.31847)


## One-sentence takeaway
Omni-IO Skills combines hierarchical procedures, multimodal tools, dependency graphs, and persistent assets to expand two unchanged host agents’ input coverage and output scores on UniM-90, although the evaluation does not isolate which components drive the gains (§§4–6).

## Problem and motivation
Multimodal production requires coordinating dependent artifacts, shared content, and later revisions across text, images, audio, video, documents, 3D assets, and code. The authors argue that expanding foundation models requires costly updates, while connecting specialist tools alone leaves procedural coordination and asset continuity unresolved. They propose a harness between agent reasoning and execution backends to address this gap (§1).

## Approach and contributions
- **Hierarchical procedural knowledge:** Atomic Skills implement individual operations; Expert Skills assemble one deliverable; Scenario Skills coordinate application-level outputs. The implementation contains 19 Atomic, 2 Expert, and 6 Scenario Skills, covering 38 representative tasks (§§1, 4.2; Table 1).
- **Separated execution architecture:** Four layers separate Skills, standardized MCP tool interfaces, provider configuration, and persistent asset records. Specialist services remain replaceable without rewriting Skill procedures (§4; Figure 3).
- **Dependency and artifact coordination:** Declare Execution Graphs validate dependencies, schedule independent nodes concurrently, and cancel descendants of failed nodes while preserving independent outputs. An append-only Asset Registry supplies stable references and provenance for downstream and cross-turn reuse (§5).
- **System-level evaluation:** The authors compare each host’s default environment with the same environment plus the harness, holding other built-in configurations, prompts, and execution budgets unchanged (§6.1).

The proposed novelty is the integration of these mechanisms into a multimodal production harness; the supplied experiments evaluate the combined system rather than each mechanism separately.

## Evidence and main results
All quantitative comparisons below are **Base Agent → Agent + Omni-IO Skills** on the fixed 90-instance UniM-90 evaluation.

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Full benchmark input support | Input-support rate: GPT-5.6 Sol **40.00% → 100%**; Claude Sonnet 5 **38.89% → 100%**. | §6.2, Table 3 |
| Higher semantic-quality scores over the complete test set | Relative SQCS: GPT **26.99 → 74.94**; Claude **27.82 → 77.78**. Relative scores incorporate input coverage. | §§6.1–6.2, Table 3 |
| Higher interleaved coherence over the complete test set | Relative ICS: GPT **34.61 → 93.98**; Claude **32.00 → 83.28**. | §6.2, Table 3 |
| Stronger output structure and modality coverage | Relative StS: GPT **19.14 → 100.00**; Claude **20.30 → 99.78**. Relative LeS: GPT **28.89 → 100.00**; Claude **26.67 → 100.00**. | §6.2, Table 3 |
| Higher absolute SQCS, with different evaluation subsets | GPT **67.49 → 74.94**; Claude **71.53 → 77.78**. Baselines are scored only on supported inputs; harness scores cover all instances. | §§6.1–6.2, Table 3 |
| Qualitative production examples | Authors report both hosts completed an art tutorial and a product-promotion package while maintaining content consistency. | §6.3, Figure 6 |

These results support broader input coverage and improved aggregate performance for the complete harness on this benchmark. Input support does not imply perfect task completion. **Analyst interpretation:** absolute-score increases are not matched-instance evidence of quality improvement because the scored subsets differ. Relative gains combine coverage and output quality; they do not isolate orchestration quality or establish a ranking between hosts.

## Limitations and validity risks
The supplied text contains no explicit limitations discussion.

- **Analyst inference—component attribution:** No ablations or comparison with the same specialist tools without the hierarchical harness are reported. Gains cannot be assigned separately to Skills, backend access, graph scheduling, or asset persistence.
- **Analyst inference—evaluation scope:** Evidence comes from one fixed benchmark subset and two hosts. Per-modality results, repeated-run variability, and statistical uncertainty are not reported (§6).
- **Analyst inference—operational claims:** Cross-turn reuse, failure containment, and provider replacement are described, but dedicated quantitative tests are absent (§§4–6).
- **Reproducibility gaps:** The referenced subset-selection protocol is unavailable in the supplied text. Concrete backend configurations, evaluator details, costs, and latency measurements are also unavailable. Appendix B contains its heading and column labels but no task-mapping rows.

## Open research questions
- **Which components provide the gains?** The bundled comparison leaves attribution open. A next experiment could hold specialist backends fixed while removing hierarchical Skills, graph scheduling, and persistent asset state separately.
- **Does quality improve on identical inputs?** Absolute scores use different supported subsets. Re-score both configurations on the shared supported instances, with modality-specific breakdowns.
- **How reliable is cross-turn reuse under failure?** The runtime describes persistence and branch cancellation without dedicated evaluation. Test revision sequences with injected backend failures, measuring completion, provenance correctness, and unnecessary regeneration.

## Confidence and missing information
**Confidence: medium.** The architecture and aggregate results are explicit, but causal attribution and reproducibility remain uncertain.

Material missing information includes the subset-selection protocol, complete task mappings, concrete providers and settings, detailed scoring procedures, repeated-run uncertainty, component ablations, runtime costs, and confirmed code or benchmark release availability.
