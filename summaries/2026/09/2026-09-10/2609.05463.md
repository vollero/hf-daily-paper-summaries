# A Three-Layer Caching Architecture for Low-Latency LLM Web Search on Commodity CPU Hardware

> [← Daily summary](../2026-09-10.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.05463) · [arXiv](https://arxiv.org/abs/2609.05463)


## One-sentence takeaway
The authors integrate session persistence, semantic response caching, and URL embedding reuse in a CPU-hosted search stack, but their production snapshot measures Redis behavior rather than establishing end-to-end latency or inference-cost improvements.

## Problem and motivation
Multi-turn web search accumulates conversation history, repeats work for paraphrased queries, and recomputes embeddings for shared URLs. The authors seek to reduce this overhead while preserving resumable conversations on inexpensive local infrastructure; LLM synthesis remains remote. They identify a gap in lightweight systems that unify all three caching concerns (§§I-B–I-D).

## Approach and contributions
The contribution is an integrated engineering architecture and implementation, rather than a new similarity or compression algorithm:

- **Persistent session context:** A Redis window retains the latest 20 messages by default; overflow and idle sessions move to Huffman-compressed disk archives, with restoration on demand (§§III-B, IV-C–IV-D).
- **Semantic response reuse:** Queries use 384-dimensional embeddings and cosine matching within a session–URL pair. Defaults are a 0.90 similarity threshold, up to 50 entries per pair, and a five-minute TTL (§§III-C, V-E).
- **Cross-session embedding reuse:** A global URL cache stores float32 embeddings with a 24-hour TTL (§§III-D, V-F).
- **Unified implementation:** Separate Redis logical databases and a coordinator expose the layers through one interface. The reusable implementation is named `lix-open-cache`; the authors describe the answer engine as open source (§§I-C, III-A, III-E).

The claim that no prior system combines these capabilities is the authors’ positioning; the supplied evidence does not independently establish that claim (§II).

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Aggregate Redis hit rate was 89.3% | 2,182 hits and 262 misses over six days; internal lookups across all layers, not user-query cache hits | §VI-E |
| Fast Redis reads are reported | Abstract reports 0.1 ms; text describes roughly two orders of magnitude separation from disk. Largest reported archive, 133 turns, took approximately 107 ms to read | Abstract; §§VI-B, VI-C1; Fig. 8 caption |
| Reported memory footprint reflects a sparse snapshot | 1.38 MB total Redis memory; semantic and URL caches held zero keys, while session context held 16 keys | §VI-D |
| Huffman compressed less effectively than zlib-1 | At 2 KB, compressed/raw size was 68.8% for Huffman versus 63.2% for zlib-1; production-archive comparison excludes the application header from the ratio | §§VI-C–VI-C1; Table V discussion |
| Layer-level savings are exploratory estimates | Authors report approximately 15–20% within-session semantic near-duplicates, estimating 3–8 seconds saved per avoided pipeline call; URL embedding hits save approximately 200 ms each | §VI-E1 |
| Cost estimate is not a measured caching benefit | Approximately $0.015 per standard uncached query, combining amortized infrastructure and remote inference for roughly 10K input and 2.5K output tokens | §VI-A |

These observations support the feasibility of the integrated storage design in the reported deployment. They do not establish query-level cache effectiveness, controlled end-to-end speedups, answer quality, or avoided provider spending. The authors explicitly distinguish Redis hits from inference-skipping queries (§VI-A, §VI-E).

## Limitations and validity risks
- **Author-stated:** Evaluation covers one historical workload and hardware configuration; semantic lookup scales linearly with cached entries; pure-Python compression limits throughput; archives lack encryption at rest (§VII).
- **Author-stated:** Layer contributions are exploratory, request-level token savings remain unmeasured, and GPTCache was not directly benchmarked (§§II, VI-A, VI-E1).
- **Analyst inference:** The mostly empty memory snapshot cannot demonstrate footprint under sustained populated-cache load (§VI-D).
- **Analyst inference:** No reported correctness or freshness evaluation establishes whether similarity-based reuse preserves answers as conversation context or web content changes (§§III-C–III-D, VI).
- **Analyst inference:** Thread-lock descriptions do not establish coordination across the reported worker processes and replicas; concurrency and failure-recovery validation are absent (§§V-G, VI).
- The retrieved text contains table captions without table bodies and figure descriptions without plotted values, limiting verification of detailed comparisons.

## Open research questions
1. **How much does each layer improve user-visible performance?** Contributions are estimated rather than isolated (§VI-E1). Replay a fixed workload with each layer disabled in turn, measuring latency distributions, provider tokens, and query-level hits.
2. **When does semantic reuse return an incorrect or stale answer?** No quality evaluation accompanies the fixed threshold and TTL (§III-C). Test labeled paraphrases, context-dependent follow-ups, and changing facts while varying both settings.
3. **Does persistence remain reliable under concurrency and failure?** The deployment uses multiple processes, but no stress or fault tests are reported (§§V-G, VI). Exercise simultaneous session writes, eviction, worker termination, and Redis outages while checking archive integrity and message recovery.

## Confidence and missing information
