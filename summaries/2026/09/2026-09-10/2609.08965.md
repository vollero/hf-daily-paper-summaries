# PlannerForge: LLM Agents for Scenario-Based Testing of Motion Planners in Autonomous Driving

> [← Daily summary](../2026-09-10.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.08965) · [arXiv](https://arxiv.org/abs/2609.08965)


## One-sentence takeaway
PlannerForge integrates language-driven scenario creation, retrieval, editing, execution, and planner tuning, retaining 165/200 commercial-backend and 156/200 open-backend queries through its tested pipeline, but establishes reliability only in open-loop simulation (Table 1; Limitations).

## Problem and motivation
Motion-planner testing requires coordinated scenario generation, selection, modification, execution, and interpretation. The authors describe existing workflows as fragmented and manually scripted, and identify a gap in LLM systems that predominantly address individual stages rather than the complete testing lifecycle (§§1–2).

## Approach and contributions
- **Integrated agent workflow:** A conversational router dispatches requests to scenario editing, configuration tuning, testing, analysis, or question answering. The authors claim novelty in unifying the testing lifecycle and extending it with enhancement and benchmarking (§§3–4).
- **Language-to-tool interfaces:** LLMs produce structured intents, edits, and configurations. Generation delegates map geometry and traffic dynamics to OSM and SUMO; retrieval combines metadata filtering with semantic fallback; trajectory, behavior, and population edits use CommonRoad–SUMO conversion. Goal edits directly change the planning problem (§§4.3–4.6).
- **Evaluation and planner interface:** The study compares ten model variants under five prompting conditions and integrates Frenetix and MP-RBFN through a shared execution interface. The main contribution is system integration and empirical evaluation; it does not introduce a newly trained language model (§§4.6, 5.1; Appendix A.1).

## Evidence and main results
| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Modules compose with substantial attrition | On 200 seed queries under CP+ICL+CoT, Qwen3.6-plus retains 165 and Qwen3.6:35b retains 156 through enhancement; reported mean costs are approximately 126/99 seconds and 42.5k/32.6k tokens per scenario. | Table 1 |
| Generation improves executability at higher latency | Across 200 queries covering 50 cities, PlannerForge produces 193 planner-executable scenarios versus Scenario Factory 2.0’s 144; latency is 21.6 versus 2.2 seconds. PlannerForge receives full language requests; the baseline receives the target city. | Table 3 |
| Retrieval improves rank-one satisfaction | On 200 queries over a shared database of 500+ scenarios, PlannerForge versus BM25 achieves 92.0% versus 67.5% Satisfy@1 and 96.5% versus 86.0% Any@5, at 21.6 versus <0.01 seconds per query. | Table 4 |
| Edits are more often physically valid | On the same 200 base scenarios, reported physical validity is 94.8–100% across PlannerForge edit types versus 31.0% for From-Words-to-Collisions; planner-runnable counts are 192–200 versus 200. | Table 5 |
| Configuration matching does not ensure safe execution | GPT-5.4-mini with CP+ICL+CoT achieves 100% full-YAML matching on 191 configuration queries, but only 155/191 configurations run without crashing; this includes reaching the simulation horizon without reaching the goal. | Table 18; Appendix A.6 |
| Cost tuning reportedly improves Frenetix outcomes | At batch size 400, Qwen3.6-plus with CP+ICL+CoT raises success from 50.4% to 70.2±0.4% and lowers collisions from 19.0% to 8.4±0.4%, versus Default; reported uncertainty is SD across three tuning rounds. | Table 2 |
| Extra reasoning scaffolds can hurt retrieval | On 200 selection fixtures, reasoning-enabled Qwen3.6:35b falls from 65.0% to 40.0% all-returned satisfaction when adding CoT to CP; its non-thinking variant rises from 63.5% to 83.0%. | Table 9 |

The evidence supports useful language interfaces and executable pipeline integration. It does not establish real-world driving safety, reliable natural-language diagnosis, or general superiority across planners. Scores also measure different contracts: schema matching, semantic correctness, execution, and safe goal completion are not interchangeable.

## Limitations and validity risks
- **Author-stated scope:** Traffic does not react to the ego vehicle; quantitative safety and tuning results use Frenetix. The Analysis module lacks ground-truth evaluation and can produce claims unsupported by logs (Limitations; Ethical Considerations).
- **Author-stated failure modes:** Selection suffers from invented tags; trajectory and population edits can fail during simulation conversion despite correct semantic edits (Limitations; Appendix A.3.3).
- **Analyst inference—unresolved tuning uncertainty:** Table 2 says the planner is deterministic, the LLM is the only stochastic component, and all tuning calls return identical configurations, yet reports nonzero variation across rounds. The supplied text does not reconcile this, weakening interpretation of its uncertainty estimates.
- **Analyst inference—comparison ambiguity:** Table 4’s 92.0% rank-one result differs from Table 9’s Qwen3.6-plus results under the listed prompt conditions. Appendix A.7 describes cross-planner evaluation as qualitative/ongoing despite Figure 12 showing numerical outcomes.
- **Analyst inference—limited generalization evidence:** Modification queries emphasize short reroutes and Germany-based scenarios, and the tuning comparison uses Default without an established held-out evaluation or alternative optimization baseline (Table 2; Appendix A.4).

## Open research questions
1. **Do the gains survive reactive traffic?** Open-loop execution excludes ego–traffic feedback. Repeat paired scenario tests with reactive agents and compare validity, collisions, and pipeline completion.
2. **Does tuning generalize beyond the evaluated batches?** Held-out performance and stronger tuning comparisons are not established. Tune on one scenario set, freeze configurations, and compare against Default and a non-LLM optimizer on unseen scenarios.
3. **Can analysis become evidence-grounded?** Diagnostic responses are unscored. Build an expert-annotated log benchmark and measure factual accuracy and support for parameter recommendations.
4. **Can constrained edits reduce execution failures?** Correct edit semantics still permit conversion failures. Compare current XML editing with validated route operators on longer and geographically broader reroutes.

## Confidence and missing information
**Confidence: medium.** Architecture and module results are extensively documented, but important outcome claims have reporting ambiguities.

Material information unavailable or unresolved includes the exact generation composite-score formula, reconciliation of tuning variance, held-out tuning splits, detailed physical-validity scoring for Table 5, validated Analysis outputs, and full prompt contents—the text points to released files rather than reproducing them.
