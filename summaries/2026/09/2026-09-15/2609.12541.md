# Agent as Policy for Robotic Manipulation

> [← Daily summary](../2026-09-15.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.12541) · [arXiv](https://arxiv.org/abs/2609.12541)


## One-sentence takeaway
AGP demonstrates that a frozen general-purpose coding agent can perform varied real-robot manipulation through runtime programming and physical feedback, but execution remains slow and evidence for reliability and experience-driven improvement is limited (§§3–4).

## Problem and motivation
The authors identify two constraints in existing agentic robot systems: programs generated before execution must anticipate runtime contingencies, while agents orchestrating learned policies remain limited by those policies’ motion capabilities. Manipulation failures can require revising perception, geometry, and motion together. AGP therefore keeps the agent responsible for these decisions throughout execution (§1).

## Approach and contributions
- **Runtime agent policy:** A preparation agent produces a reusable task definition; an execution agent interprets observations, writes and revises programs, requests motions, and handles recovery with fixed model weights (§§3.1–3.3).
- **Grounded robot interface:** Calibrated images, depth, robot state, and execution errors support geometric computation. A separate controller performs inverse kinematics, trajectory execution, and motion-limit enforcement. Thus, “agent as policy” operates through motion requests rather than direct motor-level control (§3.2; Appendix A.1).
- **Physical evaluation:** The study tests assembly, construction, dice reorientation, throwing, and towel folding, with additional model comparisons and qualitative execution traces (§4; Appendices E–H).
- **File-based experience reuse:** Saved measurements, scripts, procedures, and corrections support subsequent executions and transfer from Astra to Terra without parameter updates (§4.3).

The proposed distinction is the agent’s continuing authority to revise both programs and decisions during execution; the paper does not experimentally establish superiority over prior policy architectures (§2; §4).

## Evidence and main results
| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Strong observed performance on rigid-object tasks | Fresh-session Astra: four-pair assembly **8/10**; pyramid **10/10**; two towers **10/10**; six-block tower **9/10**; dice flipping **10/10**. | Table 1; §4.1 |
| Dynamic and deformable tasks have uneven evidence | Potato throwing **2/2**; sequential towel folding **5/5**; simultaneous folding **3/5**. | Table 1 |
| Successful execution is expensive | Mean time/API-equivalent cost: assembly **37.2 min / $16.62**; dice **37.9 min / $21.07**; sequential folding **50.8 min / $24.14**. Means exclude failed trials. | Table 1; Appendix B.3 |
| Model choice matters on two-pair assembly | Astra low/medium/high effort each **5/5**; Sol **5/5**; Terra **1/5**; Luna **0/5**; Opus **5/5**; Fable **3/5** under shared task references, interfaces, and budgets. | Table 2; §4.2.2 |
| Repeated experience accompanies faster assembly | Across five dependent Astra executions, first-to-fifth two-pair task time decreases **29.3%**; estimated reasoning/programming time decreases **47.0%**, while tool execution increases **9.3%**. | §4.3.1; Table 7 |
| Transferred experience improves observed Terra outcomes | Two-pair success rises from **1/5 to 4/5**; successful-trial mean time decreases **34.3%**, and token usage **11.4%**. Collection costs for Astra experience are excluded. | §4.3.2; Figure 3; Appendix D.3 |
| Cross-embodiment evidence is qualitative | A P7 arm and L6 hand grasp and lift a bottle, which subsequently slips during holding. | Appendix G; Figures 11–12 |

These results support feasibility within the supplied interfaces and task settings. They do not establish superiority over learned robot policies or pre-generated programs, broad deployment reliability, or a causal benefit from experience accumulation. The authors explicitly acknowledge that the repeated-execution sequence needs an empty-experience control (Appendix D.2).

## Limitations and validity risks
- **Author-stated:** Latency, inference cost, and coordinated deformable manipulation remain obstacles (§5). Deployment around people or unfamiliar environments needs additional safety evaluation (Appendix I).
- **Author-stated:** Experience trials are ordered and dependent; transfer resource averages compare only one successful baseline trial with four successful experience trials (Appendices D.2–D.3).
- **Analyst inference:** Small samples, especially throwing, constrain reliability estimates. Successful-trial resource averages do not measure expected cost per attempted task (Table 1).
- **Analyst inference:** No controlled ablations isolate runtime programming, feedback, or individual memory components. Appendix E likewise states that program examples alone cannot measure their performance contribution.
- **Analyst inference:** Folding success permits visible residual errors and qualitative alignment judgments; a successful sequential example is described as only a partial visual match (Table 3; Appendix F.5).
- **Analyst inference:** The main evidence comes from a prepared tabletop platform. The bottle’s later slip limits what the supplementary embodiment example establishes (Appendix G).

## Open research questions
- **Which runtime capabilities cause the gains?** Component effects are not isolated. Compare full AGP with fixed programs and restricted-feedback variants on matched scenes and budgets.
- **Does memory improve performance across changing conditions?** Existing accumulation trials are dependent. Randomize memory access across repeated scenes, then test altered object poses and geometries (Appendix D.2).
- **When does strong-to-weak transfer repay its collection cost?** Reported savings exclude Astra preparation. Measure cumulative cost and success across repeated deployments, including collection and failures (§4.3.2).
- **Can deformable manipulation become reliably precise?** Simultaneous folding has failures and successful folds retain skew. Test more towel configurations using explicit edge-alignment measurements and failure annotations (Table 1; Appendix F.5).

## Confidence and missing information
**Confidence: medium.** The supplied text gives detailed methods and outcomes, but supports narrower conclusions than general-purpose robotic reliability.

Material information unavailable includes public code/data release details, exact numerical trial budgets, complete model/software/host configurations, raw per-trial records, uncertainty estimates, quantitative folding tolerances, and controlled comparisons against alternative policy architectures.
