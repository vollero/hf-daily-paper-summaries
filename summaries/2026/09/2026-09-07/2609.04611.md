# τ^τ-Bench: An Environment for End-To-End, Realistic Agent Construction

> [← Daily summary](../2026-09-07.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.04611) · [arXiv](https://arxiv.org/abs/2609.04611)


## One-sentence takeaway
τ^τ-Bench evaluates agents that build customer-service agents from business records and client interviews, with the strongest tested configuration scoring 23.9% against an expert oracle reference of 82.2% under budget-adjusted evaluation (Table 2; §4).

## Problem and motivation
Building a deployable agent requires recovering scattered requirements, questioning stakeholders, integrating imperfect APIs, repairing inherited code, and allocating serving resources. The authors argue that existing benchmarks largely evaluate finished agents or construction from explicit specifications, leaving this combined engineering task insufficiently measured (§§1–2).

## Approach and contributions
- **Agent construction as the deliverable:** Developers implement a complete agent; evaluation measures its behavior with simulated customers through database outcomes and judged communication. Scores subtract serving-budget overages from mean reward, with a floor at zero (§3.1).
- **Recoverable business evidence:** Domain policies become atomic facts distributed across multimodal records or retained by an interactive client. Machine checks and human audits assess coverage and grounding (§3.2).
- **Configurable construction environment:** Seven task dimensions cover evidence format, client access, API defects, starting code, model/budget constraints, limited live experiments, and response phrasing. The release contains 53 construction tasks across airline, retail, telecom, and banking; another 53 are designated private (§3.2; Appendix A).
- **Empirical diagnosis:** Six model–harness configurations are evaluated, with trajectory analysis identifying incomplete requirement recovery, limited design exploration, budget mistakes, and misleading self-tests (§§4–6).

## Evidence and main results
| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Large gap to oracle reference | Claude Opus 5 + Claude Code scores **23.9%**, GPT-5.6-sol + Codex **22.0%**, and the expert reference **82.2%**. Overall scores average budget-adjusted rewards across **53 construction tasks**, with one build per configuration per task. | Table 2; §4 |
| Banking dominates aggregate difficulty | Banking contributes **35 of 53 tasks**. Opus + Claude Code scores **5.9%** there, versus **55.9%** airline, **72.8%** retail, and **48.2%** telecom. | Table 2 |
| Client questioning correlates with success | On client-enabled tasks, builds asking no questions average **0.16** evaluation score; those asking four or more average **0.50**. This is an observational comparison. | §5; Figure 4 |
| Architecture hint improves one probe | A telecom probe reports score increasing from **31% to 67%** after a hint to route by intent and review tool calls; replication and configuration details are not supplied. | §5, p. 9 |
| Budget violations can erase useful behavior | Authors report **21 builds** exceeding budget, with penalties reducing otherwise positive scores to zero for **10**; the passage does not specify the audited denominator. | §6, p. 11 |
| Passing self-tests does not establish coverage | In retail release task **010**, Codex/GPT-5.6-sol passes all **10** self-authored scenarios but scores **59.7%** on the held-out suite against an **85.8%** reference, while remaining under budget. | Appendix C; Figure 8 |

The results establish a substantial performance gap within this benchmark. Although the abstract calls the headline numbers pass rates, §4 defines the reported metric as a mean of task-level, budget-adjusted scores—not a pooled conversation pass rate. The reference uses ground-truth access and expert–model collaboration, so it is an oracle comparison rather than average human performance. Trajectory observations suggest failure mechanisms but generally do not isolate their causal contributions.

## Limitations and validity risks
- **Author-stated:** Single-LLM clients and users simplify stakeholder behavior; requirements are fixed; repeated-build variance is unmeasured; every requirement is recoverable; maintenance after deployment is excluded (§7).
- **Analyst inference—aggregation:** Banking’s large task share and repeated domain variants make overall scores sensitive to benchmark composition rather than equally representative of the four domains (Tables 2–4).
- **Analyst inference—causal attribution:** Most configurations change both model and harness. Questioning correlations and trajectory audits cannot independently establish which intervention would close the gap (§§4–6).
- **Evaluation access exception:** Five tasks allow one live experiment whose sampled traffic remains in the scored suite, qualifying the general description of evaluation as fully withheld (Appendix A).
- **Reporting ambiguities:** §5 reports serving-budget usage of 0.45–0.72×, while Table 2 spans 0.38–0.76×. Latency gates are mentioned, but concrete thresholds and aggregate latency results are not supplied (Appendix F).

## Open research questions
- **Does systematic requirement recovery improve outcomes?** Audits implicate unread evidence and unasked questions without a broad controlled intervention. Compare ordinary builds with fact-coverage tracking and structured client interviews under matched budgets.
- **Does architecture search generalize beyond the telecom probe?** The reported hint result is narrow. Repeat controlled routing and tool-review interventions across domains, with multiple construction trials.
- **Can independent test generation reduce blind spots?** The worked example and weakened assertions expose self-test failures. Compare builder-authored tests with separately generated, evidence-grounded tests, keeping evaluation hidden.
- **How well does construction transfer to changing requirements?** Evaluation ends at submission. Introduce staged policy and API changes, then measure adaptation and regression rates (§7).

## Confidence and missing information
**Confidence: medium.** The supplied text supports the benchmark design and headline comparisons clearly. Material gaps include repeated-run uncertainty, full architecture-probe details, judge–human agreement measurements, complete reference implementations and selection procedures, concrete latency settings, and a repository or release-access link.
