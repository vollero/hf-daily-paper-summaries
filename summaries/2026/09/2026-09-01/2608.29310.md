# Super Library Agent: Joint Generation and Maintenance of Multiple Applications Beyond the Single Codebase

> [← Daily summary](../2026-09-01.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2608.29310) · [arXiv](https://arxiv.org/abs/2608.29310)


## One-sentence takeaway

The authors propose an agent workflow that incrementally extracts and migrates shared components across related applications, reducing portfolio-wide code duplication and size without statistically significant functionality loss in their benchmark suites.

## Problem and motivation

LLM coding agents typically generate or maintain one codebase at a time, even when organizations operate portfolios of independently deployable but related applications. This duplicates domain logic, UI patterns, utilities, and maintenance work while allowing each codebase to accumulate dead code and structural debt independently (Introduction, pp. 1–2).

The authors identify an unaddressed online, multi-repository setting: applications arrive sequentially, new shared abstractions should be added to a common library, and earlier applications must then be migrated safely. Existing library-learning and refactoring methods are described as primarily post-hoc or single-project approaches (Sections 2–3.1, pp. 2–3). A minimal shared-library agent performs poorly because it misses semantically equivalent code and incompletely updates dependencies (Section 3.3, pp. 3–4).

## Approach and contributions

- **New problem formulation:** The Super Library Agent (SLA) jointly generates a sequence of related applications and maintains a shared library, including retroactive migration of earlier applications when reusable components emerge (Section 3.1; Figure 1).

- **Candidate-guided extraction:** AST-delimited code blocks are summarized in natural language, and an LLM selector matches summaries across applications to find semantically similar implementations. Each new codebase is also consolidated locally before cross-application extraction (Section 3.3.1; Algorithm 2).

- **Context-aware migration:** Separate extraction and migration agents communicate through structured extraction traces containing source locations, generalization rationale, and replacement guidance. File-level caller/import relationships are added to migration prompts to help update dependent code (Section 3.3.2; Appendix H.4–H.5).

- **Portfolio-level evaluation:** SLA-FULL is compared with isolated generation, post-hoc Librarian, and two naive sequential-library variants on WebGen-Bench and PaperBench, including initial construction, one shared maintenance update, ablations, reuse analysis, cost analysis, a different backbone, and a low-reuse stress test (Sections 4–5; Appendices A–F).

The results support the authors’ claim that structured extraction and migration can reduce static redundancy and the size of one cross-application patch in these adapted suites. They do not establish lower real-world maintenance cost, long-term reliability, security, or superiority on functionality: functionality differences were generally nonsignificant, the low-reuse stress test showed degradation, and only one post-construction update was evaluated.

## Limitations and validity risks

- **Author-stated:** There is no SLA-native benchmark. The paper converts single-task benchmarks into related sequences, so the evaluation lacks real users, production constraints, and commit histories (Limitations, p. 10).

- **Author-stated:** Maintenance is tested for only one update. The study therefore does not reveal whether errors compound or library abstractions remain suitable through repeated requirement drift (Limitations, p. 10).

- **Author-stated:** LOC, duplication, verbosity, and utilization are proxies; they do not directly demonstrate that humans find the resulting systems easier to understand or modify (Limitations, p. 10).

- **Author-stated:** Centralization creates correlated risk: an undetected fault in one shared symbol can affect many applications. The released applications were not reviewed for security, accessibility, licensing, or data-handling suitability (Ethical Considerations, p. 10).

- **Author-stated:** SLA-FULL incurs high inference cost—8.3× Zero-Shot on WebGen—and fewer migration rounds trade cost for quality (Tables 15 and 17).

- **Analyst inference:** Evaluation depends heavily on LLM-based generation, selection, and judging. Although the paper standardizes backbones across principal comparisons and reports one backbone-robustness experiment, the supplied evidence does not quantify judge agreement with humans.

- **Analyst inference:** The selected main WebGen suites are topically clustered and favorable to reuse. The low-reuse stress test usefully probes this assumption, but its functionality decline limits generalization to heterogeneous portfolios (Appendix E; Table 19).

- **Analyst inference:** Ablations cover local consolidation and call-graph conditioning, but the supplied tables do not isolate extraction traces independently or compare natural-language summaries against other semantic retrieval methods within the complete SLA-FULL pipeline.

## Open research questions

1. **Does SLA remain beneficial over many maintenance cycles?** Only one policy update is evaluated. A next experiment could run a controlled sequence of changing, conflicting, and reverting requirements while measuring regressions, cross-application consistency, patch effort, and library churn.

2. **When is shared extraction preferable to keeping code local?** The low-reuse suite loses functionality despite remaining compact. A next experiment could vary measured semantic overlap and introduce an extraction threshold or rollback policy, then estimate the point at which reuse becomes harmful.

3. **Can migration safety be strengthened against correlated failures?** Passing benchmark tests does not cover every behavior affected by a shared component. A next experiment could add differential tests, static analysis, mutation testing, and staged per-application rollout before accepting a library migration.

4. **Can comparable maintainability gains be obtained at lower cost?** SLA-FULL costs up to 8.3× Zero-Shot, while fewer rounds degrade quality. A next experiment could selectively invoke migration only for applications implicated by extraction traces or dependency analysis and compare cost, recall, and regression rates.

## Confidence and missing information

**Confidence: high** for the method description and reported benchmark results because the supplied text includes the main procedures, metrics, aggregate results, ablations, significance tests, and limitations.

Material missing or unresolved in the supplied text includes human validation of maintainability and LLM-judge scores, repeated real-world maintenance histories, security and regression audits, an independent ablation of extraction traces, and complete numerical results for some appendix analyses referenced but not reproduced here.
