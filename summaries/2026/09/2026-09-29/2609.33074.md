# KernelZero: Co-Evolving Proposer and Coder for Continuously Improved GPU Kernel Generation

> [← Daily summary](../2026-09-29.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.33074) · [arXiv](https://arxiv.org/abs/2609.33074)


## One-sentence takeaway
KernelZero alternates training a task Proposer and kernel Coder to improve CUDA and Triton correctness on KernelBench, with substantially stronger speedup results for Triton than CUDA (Table 1; Figure 5).

## Problem and motivation
Generating GPU kernels requires both functional correctness and hardware efficiency. The authors identify two training gaps: insufficient data matched to a model’s current weaknesses, and unstable optimization when correctness and speed compete. They propose adaptive task generation and correctness-gated performance rewards to address these gaps (§1).

## Approach and contributions
- **Co-evolving curriculum:** A Proposer generates Torch modules from API combinations, while a Coder translates them into kernels. Training alternates with the other model fixed; failed modules inform subsequent API inputs (§§2.1–2.2).
- **Frontier-oriented generation:** API co-occurrence sampling encourages realistic compositions; AST, execution, and numerical checks filter modules. The Proposer reward peaks when half the Coder’s sampled kernels are correct (§2.2).
- **CA-GRPO:** Correct kernels receive a base reward; within-group normalized speedup contributes only after group correctness reaches a threshold (§2.3).
- **Supporting components:** Teacher distillation uses tiling, fusion, pipelining, and reordering principles. The Keck evaluator isolates executions and aligns model parameters before correctness and timing checks (§2.3; Appendix A).

Both models start from Qwen2.5-Coder-7B; separate CUDA and Triton Coders receive backend-specific distilled traces (§3.1.1).

## Evidence and main results

All accuracy and fast metrics below are percentages. Main evaluations use one-shot kernel-generation prompts on KernelBench Levels 1 and 2; fast1 counts correct kernels exceeding PyTorch Eager speed.

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| High sampled correctness | CUDA L1/L2: pass@1 **75.8/69.6**, pass@10 **100/97**. Triton: pass@1 **77.2/72.5**, pass@10 **99/98**. | Table 1, p. 8 |
| Foundation-model comparison is metric-dependent | CUDA Claude-4.5-Sonnet has higher L1 pass@1 (**76.4**), but lower L2 pass@1 (**66.5**) and pass@10 (**97/93**). Triton DeepSeek-V4-Pro reports pass@1 **49.7/63.4**, below KernelZero. | Table 1 |
| Stronger speedup coverage for Triton | Triton L1/L2 fast1@1: **43.9/65.4**; CUDA: **17.6/2.4**. fast1@10: Triton **87/96**, CUDA **29/12**. | Figure 5; §3.2 |
| Updating the Proposer improves final correctness | Against freezing it from Step 40, CUDA L1/L2 pass@1 rises **74.9→75.8 / 64.4→69.6**; Triton rises **74.9→77.2 / 68.3→72.5**. | §3.3; Figure 3 |
| Threshold results show a trade-off | At Step 80 on combined L1/L2 tasks, α=1.1 gives pass@1 **74.85**, fast1.5@1 **9.75**; α=0.9 gives **73.15**, **11.00**. The backend is not explicitly identified in this paragraph. | §3.3, p. 9 |
| Selected operators favor α=0.5 | Best correct kernel among ten generations: α=0.5 wins among four threshold variants on six displayed operators; Tensor-MM improves from SFT **0.12×** to **4.42×**. | Figure 4; §3.3 |
| RL resource requirements are disclosed | Each 20-step Proposer update takes approximately **3.1 hours using 12 A100-80GB GPUs**, including services; Coder update takes **4.5 hours using 8 GPUs**. | Appendix C, pp. 17–18 |

The evidence supports improved benchmark correctness and benefits from continued Proposer updates. It does not establish universal superiority: Claude leads CUDA L1 pass@1, and three-turn Dr.Kernel-8B leads Triton L2 pass@1 at **73.0%** (Table 1). Accuracy also does not imply acceleration, particularly for CUDA fusion tasks. The authors attribute part of that difficulty to prohibiting vendor-library calls while PyTorch uses optimized libraries (§3.2).

## Limitations and validity risks
- **Author-described boundary:** Large speedups over vendor-library-backed operators remain difficult; standalone CUDA faces a demanding reference (§3.2).
- **Analyst inference—generalization:** Reported aggregate evaluations cover KernelBench Levels 1/2. Other benchmarks, Level 3, and hardware transfer are not demonstrated (§3.1.2; Appendix D).
- **Analyst inference—validation strength:** Correctness means passing numerical tests with absolute and relative tolerances of **10⁻²**. Timing uses two warm-ups and three measured iterations; uncertainty estimates are absent (Appendix A).
- **Analyst inference—ablation coverage:** No isolated ablation establishes the benefit of optimization-principle distillation or failure-driven API sampling. Threshold evidence combines aggregate metrics with selected operator examples (§3.3).
- **Analyst inference—implementation consistency:** The cross-entropy example divides a tensor outside the custom kernel, despite stated native-kernel constraints (Appendix F.1.2 versus Appendix A). The transposed-convolution example sums all input/kernel contributions without visible spatial-boundary corrections, warranting adversarial boundary tests (Appendix F.1.6).
- **Analyst inference—efficiency claim:** RL runtime is reported, but total cold-start cost and matched-budget comparisons are unavailable; overall training-cost superiority remains unproven.

## Open research questions
- **Does the curriculum transfer beyond this benchmark and hardware?** Current evidence is narrow; evaluate frozen models on unseen operator compositions, shapes, and GPU targets.
- **Which curriculum component causes the gains?** The freeze ablation bundles adaptive effects; compare fixed, random, failure-driven, and frontier-reward generation under equal execution budgets.
- **How robust are accepted kernels?** Tolerance-based tests and appendix examples leave semantic edge cases unresolved; rerun with stricter tolerances, boundary inputs, varied shapes, and an independent constraint audit.
- **What threshold best balances correctness and speed?** Selected examples favor α=0.5, while reported aggregate fast1.5 favors α=0.9; run repeated backend-specific sweeps and report full correctness–speed trade-offs.

## Confidence and missing information
**Confidence: medium.** Core methods and benchmark numbers are clearly supplied, but broad superiority and efficiency claims need qualification.

Missing material information includes release status, training/evaluation overlap checks, complete distillation costs, repeated-run uncertainty, detailed test-input coverage and software versions, and the backend plus complete aggregate results for the threshold ablation.
