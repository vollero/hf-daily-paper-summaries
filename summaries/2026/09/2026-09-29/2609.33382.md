# WideSWE: Can Coding Agents Coordinate Changes Across Repositories?

> [← Daily summary](../2026-09-29.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.33382) · [arXiv](https://arxiv.org/abs/2609.33382)


## One-sentence takeaway
WideSWE evaluates coordinated changes across multiple repositories and finds that the best tested agent configuration solves 42.50% of tasks, while separate repository runs recover some omitted work without improving overall success (Table 1; §4.3).

## Problem and motivation
A shared feature or bug fix can require changes to SDKs, dependencies, consumers, or parallel implementations. The authors identify a gap in coding-agent benchmarks: completing work within one repository does not establish that an agent can identify and satisfy requirements across all affected repositories (§1, §5).

WideSWE therefore scores the complete shared request, rather than treating progress in individual repositories as task completion.

## Approach and contributions
- **Cross-repository benchmark:** 120 real-world tasks across 41 ecosystems, balanced between bug fixes and features. Tasks require substantive changes in two or three scored target repositories; historical workspaces may also contain context repositories (§2; Appendix A).
- **Requirement-aligned test review:** The authors revise inherited tests to remove implementation-specific restrictions and unrequested functionality checks while retaining required behavior. Revised suites must fail on the original code and pass on reference solutions (§2.2; Appendix A.8).
- **Empirical coordination study:** Seven model–scaffold configurations are evaluated using hidden functional and regression tests. Failure trajectories and a paired joint-versus-independent comparison examine scope identification, delivery, and implementation correctness (§3–4).

Task success requires every target repository to pass all applicable fail-to-pass (F2P) and pass-to-pass (P2P) tests, with no missing or invalid results (§2.3).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Benchmark covers coordinated development | 120 tasks: 60 bug fixes and 60 features; 41 ecosystems; 253 target-repository instances; 2,815 F2P and 22,139 P2P tests | §2.2, §4.1 |
| Complete success remains limited | Across seven configurations on all 120 tasks, task success ranges from 10.83% to 42.50%; Codex CLI–GPT-5.6-sol is highest | Table 1 |
| Repository progress exceeds complete resolution | Codex CLI–GPT-5.6-sol succeeds on at least one target repository in 83.33% of tasks, versus 42.50% complete task success | §4.1 |
| Failures include both scope omissions and incorrect implementations | Among 69 unresolved Codex CLI–GPT-5.6-sol runs: 37.68% scope failures, 2.90% recognized work without delivery, and 59.42% post-edit failures | Table 2; Figure 3 |
| Scaffold pairing changes observed performance | With GPT-5.6-sol fixed, task success is 42.50% with Codex CLI versus 32.50% with Claude Code; mean recorded API requests are 86.7 versus 134.8 per task | Table 1; §4.1 |
| Independent execution does not improve overall paired success | On 89 identical-prompt tasks, joint execution solves 36/89 (40.45%), versus 32/89 (35.96%) independently; mean API requests are 94.7 versus 296.6 per task | Table 3; §4.3 |
| Execution effects differ by task intent | On the paired subset, independent versus joint success is 44.83% versus 34.48% for 29 bug fixes, but 31.67% versus 43.33% for 60 features | Table 3; Appendix B.1 |
| Independent runs more often recover omitted work | Of joint-failed repositories, independent runs recover 12/20 unmodified repositories (60.00%), versus 5/53 modified repositories (9.43%) | Table 6 |
| Test alignment required extensive review | Revisions affect 88/120 tasks: implementation constraints relaxed in 87, unrequested checks removed in 16, with 15 overlapping | Appendix A.8 |

These results establish difficulty under the tested benchmark and configurations. Selected trajectories support the authors’ interpretation that related repositories can supply implementation facts and behavioral references. They do not establish causal mechanisms or a generally superior execution strategy: total budgets differ, recovery groups have different task composition, and task subgroups are observational (Appendix B.1; C).

## Limitations and validity risks
- **Author-stated scope:** Evaluation covers two or three target repositories on Linux; performance with larger repository sets or other platforms is not established (Appendix D).
- **Author-stated comparison boundary:** Independent execution receives a full run per target repository. The comparison matches per-run limits, not total task budget, so it does not isolate execution scope (Appendix B.1).
- **Author-stated descriptive boundaries:** Recovery differences are noncausal; intent-specific reversals should not be generalized beyond the sample; selected trajectories do not establish model-wide rankings (Appendix B.1; C.4).
- **Analyst inference—selection bias:** Popular GitHub organizations, explicit cross-repository links, runnable Linux environments, test availability, and manual feature selection constrain representativeness (§2.2; Appendix A.1–A.2).
- **Analyst inference—test validity:** Base/Gold validation and independent review support test consistency, but do not prove acceptance of every valid alternative implementation. The paper supplies no measured agent-performance comparison before versus after test revisions (Appendix A.8).
- **Analyst inference—measurement uncertainty:** The supplied text reports no repeated-run variability, confidence intervals, or significance tests for configuration differences.

## Open research questions
- **Does joint execution retain its advantage under equal total budgets?** The current comparison gives independent execution more resources. A next experiment could match aggregate token, time, or request budgets across execution modes.
- **Can explicit scope tracking reduce omissions?** Trajectories show both missed targets and recognized work left unfinished. A next experiment could compare the same agent with and without a persistent repository-and-requirement checklist.
- **Does cross-repository verification reduce post-edit failures?** Successful examples compare behavior or pass exchanged data between components, but these mechanisms are not ablated. A next experiment could add systematic contract tests and measure changes in post-edit failure rates.

## Confidence and missing information
**Confidence: high** in the benchmark description and reported outcomes; **medium** in generalization and mechanism interpretations.

Material information unavailable in the supplied text includes exact timeout and resource-limit values, repeated-run uncertainty, model training-data overlap or contamination assessment, the effect of test revisions on agent scores, and an equal-total-budget execution comparison. Artifact contents are described, but were not independently inspected.
