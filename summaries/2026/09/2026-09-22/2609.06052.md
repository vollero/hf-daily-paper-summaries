# SkillSpec: Intent-Masked Specification Reasoning for Agent Skill Correctness

> [← Daily summary](../2026-09-22.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.06052) · [arXiv](https://arxiv.org/abs/2609.06052)


## One-sentence takeaway
SkillSpec compares intent-derived specifications with behavior-derived specifications to detect agent-skill defects, finding 763 manually confirmed defects across 515 skills at 61.2% precision among sandbox-validated findings, without establishing recall (Table III; §V-A).

## Problem and motivation
Agent skills combine natural-language instructions, code, and supporting resources, allowing defects such as conflicting requirements and implementation drift that conventional code checks cannot fully capture. Runtime success can also hide defects when an agent compensates for faulty instructions. The authors identify a gap in checking whether reusable skill artifacts consistently implement their declared capabilities across reachable, intended scenarios (§§I, III).

## Approach and contributions
- **Specification-based correctness:** Represent expected and encoded behavior as textual Hoare-style preconditions and postconditions. Differences produce defect hypotheses, not formal proofs (§III).
- **Unified artifact graph:** Combine an LLM-reconstructed workflow DAG with parsed code graphs and bidirectional workflow–implementation bindings. Code support covers Python, JavaScript/TypeScript, and Shell (§IV-A).
- **Intent-masked reasoning:** Derive ExpectSpec from surrounding intent while excluding the target implementation; derive FactSpecs with self, neighborhood, lineage, and holistic visibility. Joint reasoning checks incompatible requirements, weakened guarantees, and additional effects (§IV-B).
- **Validation and empirical assets:** Use executable probes for code and source-grounded triggering scenarios for workflows, followed by manual review for evaluation. The authors report releasing source code and a skill-defect dataset (§§I, IV-C, V-A).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Substantial confirmed defect yield | GPT-5.6-Sol analysis of 515 skills: 763 manually confirmed defects in 239 skills (46.4%); 61.2% confirmed among 1,246 sandbox-validated findings. | §V-B; Table III |
| Code findings have higher confirmation precision | Code: 417/621 validated findings confirmed (67.1%); workflows: 346/625 (55.4%). | Table III |
| Specifications improve candidate quality with lower confirmed counts | SkillsBench-S, GPT-5.6-Sol: workflow confirmed/candidate rises from 29/102 (28.4%) for direct detection to 21/55 (38.2%); code rises from 101/179 (56.4%) to 97/152 (63.8%). | Table VII |
| Joint views improve confirmed yield and rate | SkillsBench: multi-view confirms 261/541 candidates (48.2%); individual views confirm 228–236, with rates of 42.9%–45.8%. | Table VIII |
| Backend robustness concerns automated acceptance | On frozen GPT-5.6-Sol graphs, five backends achieve total code validated/candidate rates of 81.2%–90.8%, versus 40.1%–67.4% for workflows; these are not manual precision estimates. | §V-D; Table VI |
| Reported operational cost | Main pipeline uses GPT-5.6-Sol and Grok 4.6: 223 minutes with up to 30 concurrent repositories; $1,331 total, averaging $2.585 per skill without discounts. | §V-F; Table IX |

The evidence supports useful defect discovery and improved candidate confirmation rates from specifications and joint views. It does not establish exhaustive detection, formal correctness, or downstream task-success improvements after repairs. Workflow scenario corroboration provides weaker behavioral evidence than executable reproduction. Main precision uses **validated findings** as its denominator; ablation confirmation rates use **all candidates**.

## Limitations and validity risks
- **Authors’ stated limitations:** Declared intent is assumed faithful; textual specifications are not machine-checkable proofs. Creative and underspecified workflows lack reliable oracles, and recall is unavailable (§§III, VI-A, VII).
- **Sampling and coverage:** Popular repositories and executable benchmark skills may not represent the broader ecosystem. Short code definitions are excluded from direct analysis; unresolved and external calls are omitted from graph edges (§§IV-A–B, VII-C).
- **Residual validation errors:** Workflow false positives commonly arise from treating optional guidance as mandatory; code false positives commonly involve triggers excluded by realistic workflow conditions (§VI-B; Table X).
- **Analyst inference—comparison limits:** Frozen graphs isolate backend reasoning but do not test robustness of graph construction across models. The specification ablation covers only SkillsBench-S, and no head-to-head evaluation against another complete defect detector is reported (§§V-D–E).
- **Analyst observation—claim/table mismatch:** The claim that multi-view improves results “without increasing the candidate pool” is not uniformly supported: its 541 candidates exceed lineage’s 504 and holistic’s 517 (Table VIII).

## Open research questions
- **Can workflow oracles reduce over-inference?** Textual findings remain ambiguous. Compare scenario corroboration with replayed end-to-end tasks and independent human labels (§VI).
- **How many defects do eligibility filters miss?** Recall is unknown and short definitions are pruned. Exhaustively audit a small corpus, then vary filtering and call-resolution policies (§§IV-B, VII-D).
- **Does graph reconstruction materially affect findings?** Backend experiments freeze one graph set. Repeat graph generation across models and runs, measuring binding accuracy and confirmed-defect overlap (§V-D).
- **Do repairs preserve generalization?** Preservation is part of the defect definition but lacks a reported repair evaluation. Test repaired skills on triggering cases and held-out in-scope tasks (§III).

## Confidence and missing information
**Confidence: medium.** The supplied text provides detailed methods and quantitative comparisons, but material gaps include exhaustive defect labels, inter-rater agreement statistics, repeated-run uncertainty, manual precision across all backends, and measured post-repair task performance. The reported code and dataset releases were not independently inspected.
