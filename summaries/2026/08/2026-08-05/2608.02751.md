# Search, Inspect, Fetch: Exploiting Boolean Retrieval for Deep-Research Agents

> [← Daily summary](../2026-08-05.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2608.02751) · [arXiv](https://arxiv.org/abs/2608.02751)


## One-sentence takeaway

Sieve lets research agents filter documents with fielded Boolean queries, inspect structured result cards, and fetch only relevant sections, yielding higher observed QA accuracy than conventional page-level Search–Visit while using substantially fewer tokens.

## Problem and motivation

Deep-research agents typically inspect short search snippets and then load entire pages. This discards addressable document structure—such as headings, sections, dates, and authors—and introduces irrelevant text into the agent’s context. The authors identify a gap between structured web sources and page-level agent workflows: ranking can prioritize documents, but cannot guarantee eligibility constraints or control which sections are read (§1).

## Approach and contributions

- **Search–inspect–fetch workflow:** The paper formulates a workflow that preserves document structure from retrieval through reading (§1, Figure 2).
- **Sieve:** An agent-generated Boolean Query Language filters eligible documents by fields, Boolean operators, phrases, wildcards, and dates. BM25, dense retrieval, or their fusion then ranks only the eligible set (§3).
- **Structured inspection and selective reading:** Result cards expose titles, headings, matched fields, metadata, and a 25-token query-focused snippet; the agent subsequently fetches a named section rather than a complete page (§3).
- **Controlled evaluation assets:** The authors derive paired flat and structured versions of HotpotQA, MuSiQue, and BrowseComp-Plus, preserving questions and emitted text while changing whether structure is addressable (§4).
- **Empirical analysis:** Matched controls isolate BQL candidate selection, snippets, retriever choice, and transfer across three agent backbones (§§5–6). The implementation is included in the SkimSearchAgent library (§4.1.3).

The evidence supports the authors’ system-level claim that combining Boolean candidate selection, structured inspection, and section fetching improves the observed accuracy–context trade-off under these benchmarks and budgets. It does not establish that Boolean operators alone cause the gains, that every reported accuracy difference is statistically significant, or that the results generalize to open-web deployment, non-English sources, or documents without usable structure.

## Limitations and validity risks

- **Author-stated:** The comprehensive comparison grid uses one primary backbone; the two additional backbones appear only in transfer experiments (Limitations).
- **Author-stated:** Only three QA collections are evaluated, and Wikipedia evaluation primarily uses exact match because judge coverage is incomplete (Limitations).
- **Author-stated:** Sieve jointly changes candidate construction, result presentation, and reading granularity; not every component combination is crossed. The evidence therefore supports the complete workflow rather than an independent causal effect of Boolean operators (Limitations).
- **Author-stated:** Answer-recovery overlays are incomplete for Wikipedia Sieve and other Search–Fetch conditions, creating an evaluation asymmetry (Limitations; Appendix C.2).
- **Author-stated:** Agent manuals and actual indexes disagree: Wikipedia instructions advertise an unavailable infobox search field, while BCP-S instructions incorrectly discourage section use (Appendix B.2.4).
- **Author-stated:** BCP-S sections are model-generated, with possible heading or boundary errors; some overlong documents were truncated before section-boundary generation (Limitations; Appendix A).
- **Author-stated:** Wikipedia articles were matched by normalized title without content checks, so snapshot drift may introduce noise (Limitations; Appendix A).
- **Author-stated:** The frequent zero-hit fallback uses an approximate BM25 ranker with substantial divergence from Lucene, so the system is neither pure strict Boolean retrieval nor a pure Lucene implementation (Limitations; Appendix C.4).
- **Analyst inference:** Because the supplied rendering omits the numerical cells of Tables 1 and 7–12, many per-system absolute scores, costs, uncertainty values, and pairwise significance outcomes cannot be independently checked from this text.
- **Analyst inference:** BCP-S accuracy depends on a single named LLM judge, but the supplied text does not report judge validation, agreement, or sensitivity analysis.

## Open research questions

1. **Which Sieve component contributes most independently?** The paper does not fully cross Boolean filtering, structured cards, snippets, and section fetching. A factorial ablation across these components with matched prompts and rankers could estimate their individual and interaction effects.

2. **How well does Sieve transfer to live, noisy web search?** Evaluation uses fixed corpora with parsed or generated structure. A next experiment could compare Sieve and Search–Visit on time-bounded live-web tasks while measuring parser failures, source coverage, latency, and answer quality.

3. **Can better query relaxation replace the divergent zero-hit fallback?** More than one-third of search calls invoke fallback, whose rankings differ substantially from Lucene. A controlled comparison could test learned constraint relaxation, operator removal, and a matched Lucene fallback.

4. **Can retrieval and synthesis failures be addressed jointly?** BCP-S is mainly retrieval-bound, whereas the Wikipedia collections are mainly synthesis-bound. A next experiment could combine retrieval improvements with evidence-grounded answer extraction and report gains separately by failure category.
