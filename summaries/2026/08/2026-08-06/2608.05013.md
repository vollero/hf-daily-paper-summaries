# OneDayAgent: Towards a Long-Horizon Harness for Autonomous Agents

> [← Daily summary](../2026-08-06.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2608.05013) · [arXiv](https://arxiv.org/abs/2608.05013)


## One-sentence takeaway

OneDayAgent combines subtask decomposition, compressed execution memory, and final-deliverable verification and repair, achieving a reported 0.821 on AgentIF-OneDay with GLM-5.2, though comparisons to official baselines use a substituted judge.

## Problem and motivation

Open-ended everyday requests may span many steps, tools, environments, and modalities while requiring a concrete artifact such as a report or presentation. Over long trajectories, agents can lose earlier constraints, fail to transfer intermediate state, or exhaust usable context. The authors argue that prior methods usually address these failure modes separately; the unmet need is a single backend-transferable harness that manages them jointly (Introduction; Figure 1).

## Approach and contributions

- **Managed long-horizon workflow:** The original request remains the global intent while a planner creates up to six bounded subtasks, each executed through a ReAct loop (Sections 2.1–2.2; Appendix Table 6).
- **Execution memory:** Tool observations are summarized or truncated, subtask answers and result-file handles serve as checkpoints, and earlier dialogue is compressed near the context limit (Section 2.2.3).
- **Artifact-level verification and repair:** After synthesis, a verifier checks the output against the original request, subtask results, and attachments; detected defects trigger localized repair rather than full re-execution (Section 2.2.2).
- **Unified environment interface:** Web, academic-search, computation, filesystem, and multimodal operations share one action space, with artifacts persisted in a workspace (Section 2.2.4; Appendix Table 5).
- **Evaluation and release:** The authors evaluate the unchanged harness with five backend LLMs and state that the harness and trajectories are open-sourced (Introduction; Section 3.5).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Best reported overall score | OneDayAgent with GLM-5.2 scored **0.821** on all 104 AgentIF-OneDay tasks; AutoClaw, the strongest listed baseline, scored **0.799**. Scores are normalized to [0,1]. | Table 2; Sections 3.1–3.2 |
| Improvements from decomposition and verification | With GLM-5.2 and memory always enabled: DIRECT **0.771**, decomposition only **0.8039**, verification only **0.8044**, and FULL **0.821** on the same 104 tasks. | Section 3.3; Table 3 |
| Simpler variants sometimes outperform FULL | VERIFY beat FULL on **17** tasks, DECOMP on **13**, and DIRECT on **12**. | Section 3.3; Table 3 |
| Repair recovered some verification failures | **95/104** tasks passed first verification; **9** entered repair, of which **6** recovered and **3** remained failures. | Section 3.4; Figure 3(c–d) |
| Context compression was frequently needed | **35/104** tasks triggered compression; the highest-pressure task accumulated roughly **350K context tokens** across compression rounds, with reported near-zero correlation between compression count and score. | Section 3.4; Figure 3(e–f) |
| Performance transferred but varied across backends | Under the same harness and 104-task suite, five backends scored from **0.613 to 0.821** overall. | Table 2; Section 3.5; Table 4 |
| Backend efficiency differed substantially | GLM-5.2 averaged **53.6 minutes**, **51.6 tool calls**, and **585.7 KB context** per task; Gemini-3.1-Pro-Preview averaged **21.4 minutes**, **18.7 calls**, and **118.1 KB**. | Section 3.5; Figure 4 |
| Judge substitution changed scores | On the same earlier run, Gemini-3-Pro-Preview assigned **80.39%**, versus **77.27%** from Gemini-3.1-Pro-Preview—a **3.12 percentage-point** difference. | Section 3.1.2; Appendix F |

The ablation supports the authors’ claim that decomposition and verification each improve scores when execution memory remains fixed, with their combination performing best. Cross-backend results show operational compatibility across the tested models, but do not establish transfer to unseen model families or other benchmarks. Compression quality was not causally isolated, and the near-zero correlation with score does not prove that compression prevents degradation. The state-of-the-art claim is also not a fully judge-controlled comparison: official baselines and the new runs were evaluated with different judge versions, although the authors provide a paired judge comparison suggesting that the replacement judge is stricter.

## Limitations and validity risks

- **Author-stated scope limitation:** All primary results come from AgentIF-OneDay; broader benchmark generalization remains untested (Conclusion).
- **Author-stated security limitation:** The implementation runs on the host without workspace isolation, while permitting arbitrary shell commands, file modification, network access, and processing of untrusted content (Appendix E).
- **Author-stated memory risk:** Prompt-injected instructions could survive compression and propagate into later subtasks, verification, or repair (Appendix E).
- **Memory ablation is absent:** The authors say disabling memory prevents completion because of overflow or state loss, but provide no controlled quantitative memory ablation (Section 3.3).
- **Analyst inference—comparison validity:** The 0.821 result and official baseline scores use different LLM judges. The paired comparison supports the authors’ “conservative” interpretation but does not replace rescoring every baseline and system output with one judge (Section 3.1.2; Appendix F).
- **Analyst inference—backend generalization:** Five models from three families demonstrate limited transferability, not universal backend independence; quality and latency vary widely (Section 3.5).
- **Analyst inference—resource trade-off:** The strongest configuration is expensive—GLM-5.2 averages 53.6 minutes per task—and full harness composition has the lowest reported score-per-latency ratio (Sections 3.3 and 3.5).
- **Reproducibility gap in supplied text:** Runtime configuration and tool services are documented, but Appendix Table 7’s actual service-traffic totals and the numerical contents of Tables 3 and 4 are not included in the retrieved text.

## Open research questions

1. **How much does execution memory causally contribute?** Memory remained enabled in every ablation, so its independent effect is unknown. A next experiment could compare checkpointing, summarization, deterministic truncation, and no-memory variants on tasks that fit within a controlled context budget.

2. **Can module activation be selected adaptively?** Simpler variants outperform FULL on several tasks, while verification-only offers a better cost trade-off. A next experiment could train or evaluate a task-level router that predicts whether decomposition, verification, or both are warranted.

3. **Does the harness generalize beyond AgentIF-OneDay?** The authors explicitly limit their findings to one benchmark. A next experiment could evaluate the unchanged harness on additional long-horizon, cross-environment suites using matched tools and budgets.

4. **How robust is compressed memory to adversarial content?** Appendix E identifies persistence of injected instructions as a risk but reports no attack evaluation. A next experiment could insert controlled prompt injections into web pages and attachments, then measure survival through compression and effects on later actions.

## Confidence and missing information

**Confidence: medium.** The supplied text gives detailed method descriptions, configurations, headline results, and qualitative ablation findings. Material missing information includes the numerical bodies of Tables 3, 4, and 7; per-task scores and variance or uncertainty estimates; full baseline rescoring under a common judge; detailed failure examples; quantitative memory ablations; and evaluation beyond AgentIF-OneDay.
