# Repo0: Design-Driven Zero-to-All Code Generation

> [← Daily summary](../2026-08-21.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2608.19854) · [arXiv](https://arxiv.org/abs/2608.19854)


## One-sentence takeaway
Repo0 improves whole-repository generation by iteratively refining a requirement-to-component Dual-DAG with cohesion- and coupling-based actions before using the converged architecture for test-driven code generation.

## Problem and motivation
Zero-to-all code generation must infer both functionality and repository architecture from natural-language requirements. Existing approaches often assume a supplied architecture or freeze a one-shot plan before implementation, which can produce low-cohesion components, tangled dependencies, and poor cross-file coordination when later evidence exposes design flaws. The authors argue that repository design should instead evolve continuously until component boundaries stabilize (Introduction, pp. 1–2; Fig. 1).

## Approach and contributions

- **Persistent Dual-DAG state:** Repo0 separately represents requirement-level functional coordination, component-level implementation dependencies, and their many-to-many alignment, preserving requirement-to-code traceability without conflating two kinds of relationships (Section II-A, p. 3).

- **Modularity-guided evolution:** Components undergo `split`, `merge`, `revise`, or `save` actions. Splits use requirement-graph cohesion and partitioning; merge candidates use responsibility overlap, connectivity, and LLM validation. Evolution stops when a full round yields no eligible split or merge (Sections II-C, pp. 4–5).

- **Design-guided implementation:** The converged graph determines packages, files, symbols, dependencies, and generation order. Each component is implemented through skeleton creation, test synthesis, code generation, validation, and localized repair (Section II-D, p. 5).

- **Empirical contribution:** The authors compare Repo0 with direct-agent, staged-generation, and static graph-planning baselines, plus ablations and alternative convergence strategies (Sections III–IV, pp. 5–8).

The controlled comparison supports the claim that architecture construction—not merely the shared implementation scaffold—contributes to performance. The ablations further associate several design elements with improvements, but they do not isolate all interactions among those elements.

The evidence does not establish generality beyond Python or RepoCraft. The full six-repository numerical results are only said to appear in supplementary material, which is not included here. There is also an unresolved discrepancy for GPT-5-mini `django` Coverage: Table II reports 80.50%, whereas Table III reports 87.50% for the full Repo0 setting.

## Limitations and validity risks

- **Author-stated:** Structural updates still depend on the backbone LLM’s architectural reasoning, even though metrics select split and merge candidates (Section VI, p. 10).

- **Author-stated:** Evaluation is limited to six Python repositories from one benchmark; effectiveness in other languages and ecosystems remains unknown (Section VI).

- **Author-stated scope constraint:** Thresholds were selected manually on two held-out Commit0 Lite repositories by comparing evolved structures with golden architectures (Section III-E, p. 6). This introduces human judgment and leaves sensitivity to alternative thresholds unclear.

- **Analyst inference:** Only three repositories appear in the main result and ablation tables; claims covering all six rely on unavailable supplementary results.

- **Analyst inference:** The Table II/Table III `django` Coverage disagreement weakens confidence in that specific result and may reflect different runs or a reporting error; the supplied text does not explain it.

- **Analyst inference:** The convergence comparison covers only `statsmodels` with GPT-5 mini, so it does not demonstrate that metric-guided convergence dominates fixed-round refinement across repositories or backbones.

- **Analyst inference:** Results are averages over three Repo0 runs, but variability statistics are absent, and equivalent repetition details for baselines are not stated (Section III-E).

## Open research questions

1. **Does structural evolution generalize beyond Python?** The study evaluates only Python repositories. A next experiment could apply the same architecture-level actions and metrics to matched Java, TypeScript, and multilingual repository-generation tasks.

2. **How robust are the split and merge thresholds?** The thresholds were manually selected on two held-out repositories, but no sensitivity analysis is reported. A next experiment could sweep both thresholds and measure architecture size, modularity, accuracy, and cost.

3. **Which interactions among Dual-DAG context, ordering, and evolution drive performance?** One-at-a-time ablations do not expose synergies. A factorial ablation could remove combinations of these components across all repositories and both backbones.

4. **Do the proposed metrics correspond to independently assessed architectural quality?** The paper primarily evaluates generated functionality and tests. A next experiment could compare evolved architectures using blinded expert review and static cohesion/coupling measures, then test whether those judgments predict downstream correctness.

## Confidence and missing information
**Confidence: medium.** The supplied text provides detailed methodology, main results, ablations, and stated threats, but omits the supplementary six-repository results, prompts, complete cost tables, variance or significance tests, baseline repetition details, threshold-sensitivity results, and an explanation for the conflicting GPT-5-mini `django` Coverage values.
