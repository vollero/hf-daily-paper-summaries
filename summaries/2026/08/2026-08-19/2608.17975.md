# aDSL: Agentic 3D Creation via Joint Agent-Program Design

> [← Daily summary](../2026-08-19.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2608.17975) · [arXiv](https://arxiv.org/abs/2608.17975)


## One-sentence takeaway

The authors jointly design a relational 3D programming language and a training-free Plan–Execute–Critic agent workflow that improves structured text- and image-conditioned 3D generation over other code-generation systems while retaining executable, editable programs.

## Problem and motivation

LLM-driven 3D program synthesis is brittle because general-purpose modeling interfaces require precise coordinates and low-level API choices that language models handle inconsistently. This can produce disconnected parts, violated spatial constraints, or degradation during edits. Existing 3D DSL work emphasizes expressiveness but, according to the authors, gives less attention to making program structure directly usable for planning, verification, and repair. The paper addresses both the representation and agent workflow together so that semantic intent, spatial constraints, implementation, and critique share one vocabulary (Sections 1 and 3).

## Approach and contributions

- **Agent-centric DSL:** aDSL embeds hierarchical assets in Python and combines geometric primitives, CSG operations, transformations, named part attachments, articulation, and declarative spatial operators based on bounding boxes, anchors, support points, alignment, placement, and repeated layouts (Section 3.1; Table 5).
- **Shared relational interface:** the Planner specifies hierarchical components and checkable relations, the Coder implements them, and the Critic verifies those same relations after execution. This is the paper’s central joint agent–program design claim (Sections 3 and 5).
- **Role-specialized workflow:** Planner, Coder, Executor, Debugger, Image Critic, and Code Critic participate in an iterative generate–execute–inspect–repair loop, with selective memory separating persistent requirements from transient code, logs, and renderings (Section 3.2; Figure 4).
- **Training-free structured generation:** no task-specific model training is used; the system relies on a proprietary multimodal LLM and execution feedback. Its programs also support localized editing, joints and URDF export, multi-object scenes, and conditioning of an external high-fidelity generator (Sections 3.1, 4.4, and Appendix A).

These results support the authors’ claim that relational operators, explicit planning, and iterative repair improve code-based 3D generation under the tested protocols. They do not establish superiority over every 3D-generation paradigm: Trellis remains better on several image-to-shape metrics, field and code systems have materially different training and output properties, and no uncertainty estimates or significance tests are reported.

## Limitations and validity risks

- **Author-stated:** output quality is bounded by aDSL’s primitives and expressiveness, especially for complex geometry, appearance, and materials (Section 5).
- **Author-stated:** critique relies largely on 2D renderings and can suffer from perspective ambiguity (Section 5).
- **Author-stated:** reliable long-horizon reasoning and repair depend on strong proprietary LLMs, limiting accessibility (Section 5).
- **Author-stated comparison caveat:** field and mesh methods use large-scale 3D training data and are treated only as reference comparisons; LL3M is qualitative, while BlenderMCP is quantitatively evaluated only on a subset because of API quotas (Section 4 and page 6).
- **Analyst inference:** application demonstrations for articulation, editing, high-fidelity refinement, and scenes are primarily qualitative, so their robustness and generality are not quantified (Section 4.4; Figures 7 and 9–11).
- **Analyst inference:** all agents use the same proprietary Gemini 3 Pro model, so the experiments do not isolate whether the results transfer across model families or weaker open models (Appendix A).
- **Analyst inference:** the ablation table covers core workflow components but does not separately test the Image Critic, Code Critic, Debugger, or selective-memory policies, leaving their individual contributions uncertain (Section 3.2; Table 4).
- **Analyst inference:** the user study’s participant demographics, per-participant trial allocation, uncertainty, and statistical testing are not supplied, limiting interpretation of the preference percentages (Section 4.1).

## Open research questions

1. **Can open models reproduce the repair performance?** This remains open because all agents use Gemini 3 Pro. A next experiment could repeat Tables 1 and 4 with multiple open and proprietary models while holding prompts, tools, and stopping criteria fixed.

2. **Would direct 3D verification outperform multi-view visual critique?** The authors acknowledge perspective ambiguity from 2D renders. An experiment could add mesh-level collision, contact, topology, and articulation checks, then compare semantic scores, false critiques, and refinement rounds.

3. **How much does each critic and memory component contribute?** Existing ablations cover planning, refinement, spatial utilities, and Blender scripting but not critic roles or memory policies individually. A factorial ablation could remove or substitute the Image Critic, Code Critic, Debugger, sliding-window memory, and visual-history reset.

4. **Can high fidelity and program editability be combined systematically?** SpaceControl integration is shown qualitatively. A larger study could measure geometry fidelity, constraint preservation, edit locality, and failure rates before and after external refinement across objects and scenes.
