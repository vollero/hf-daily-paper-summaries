# OpenART: Scaling Agent Red Teaming via Open-Ended Environment Evolution

> [← Daily summary](../2026-08-13.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2608.00677) · [arXiv](https://arxiv.org/abs/2608.00677)


## One-sentence takeaway

OpenART evaluates agent safety by evolving persistent, target-visible environment state while holding tasks and safety contracts fixed, and the authors report that its EMHA attack increasingly outperforms instruction-only attacks as workflow complexity grows.

## Problem and motivation

AI agents modify and repeatedly consume shared state across long workflows, so an initially benign change can propagate into a much later unsafe action. The authors argue that existing safety benchmarks emphasize short, static or resettable tasks and benchmark-specific runtimes, limiting their ability to test delayed, cumulative failures or compare heterogeneous agents under equivalent conditions (Introduction, pp. 1–2).

OpenART addresses this gap by treating the executable environment trajectory—not an isolated prompt—as the unit of red teaming.

## Approach and contributions

- **OpenART arena:** More than 10K validated, stateful scenarios across 50 domains, constructed from a corpus of over 500K Tools, MCPs, and Skills. Scenarios have fixed benign objectives, hidden safety contracts, executable workflows, and deterministic evaluators (Sections 3.1–3.2; pp. 5–7).

- **Cross-runtime projection:** Target-specific adapters project the same scenario semantics into 15 deployed agents paired with five foundation models, producing 75 agent–model configurations. Adapters expose supported subsets of eight state surfaces: workspace, instructions, Skills, Tools, MCPs, short-term memory, plan state, and long-term memory (Section 3.3; Table 4).

- **Controlled environment evolution:** Only authorized target-visible state changes; the objective and evaluator remain fixed across rounds. Attacker and target run in separate containers, with the adapter projection as their communication channel (Sections 3.3–4.1).

- **EMHA:** The Evolutionary Markov Hypergraph Attack is a black-box policy that represents coordinated attack subgoals as hypergraphs, learns path values from evaluator feedback, and evolves a quality-diversity archive without updating attacker or target model parameters (Section 4.2).

These results support the authors’ claim that persistent state evolution can reveal failures missed by instruction-only or early-round evaluation, especially in complex workflows. They do not establish that EMHA finds all relevant failures, that the observed attacks transfer to uncontrolled production environments, or that agent implementation causally explains the reported variance.

## Limitations and validity risks

- **Author-stated qualification:** The agent-identity analysis establishes an association after model and benign-completion controls but does not identify which runtime mechanisms cause the difference (Section 5.4).

- **Author-stated scope distinction:** The MCP capability-rebinding example is a controlled construction and is explicitly excluded from the empirical results (Appendix E.6).

- **Analyst inference — judge dependence:** Strict ASR requires agreement with a GLM-5.2 judge, while GLM-5.2 is also one evaluated target model. The supplied text does not report alternative judges, judge calibration, or sensitivity analysis.

- **Analyst inference — incomplete evaluation detail:** The retrieved text does not state per-configuration sample counts, the attack budget beyond the five-round analysis, uncertainty intervals for the main pooled ASR, or statistical details for the variance decomposition.

- **Analyst inference — baseline breadth:** Search ablations compare full EMHA mainly with its restricted or component-removed variants. No matched comparison against an independently implemented environment-search method is reported.

- **Analyst inference — validation coverage:** The 99.3% evaluator-correctness result comes from a 10% audit, but sampling procedure, expert count, disagreement resolution, and error categories are not supplied.

- **Analyst inference — representativeness:** Scenarios are synthesized from capability registries and admitted through deterministic checks. This supports scale and executability, but the text provides no external study showing that their state distributions or attack conditions match production deployments.

## Open research questions

1. **Which runtime features cause agent-specific vulnerability?** Agent identity adds 7.6 points of explained ASR variation, but mechanisms are unidentified. A next experiment could toggle memory, planning, instruction loading, and capability-validation components within the same agent–model pair.

2. **How robust is Strict ASR to the choice of judge?** The metric depends partly on GLM-5.2 judgments, with no reported judge-sensitivity study. Re-score identical trajectories using multiple blinded judges and human adjudication.

3. **Does EMHA outperform other black-box environment search policies?** The paper ablates EMHA internally but does not report a broad external-policy comparison. Evaluate random search, Bayesian optimization, evolutionary baselines, and alternative quality-diversity methods under identical budgets.

4. **Do OpenART failures predict real deployment incidents?** The scenarios are executable but synthesized, and production validity is not established. A prospective study could test whether OpenART vulnerability profiles correlate with failures in permission-controlled staging deployments.

## Confidence and missing information

**Confidence: high** for the method description and reported results because the supplied text includes the full experimental and appendix material.

Material information not available includes per-cell sample counts, full attack-budget and compute costs, confidence intervals for most headline results, variance-decomposition methodology, evaluator-audit protocol, judge calibration, contamination controls, and evidence of transfer to production environments.
