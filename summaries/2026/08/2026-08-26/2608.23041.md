# AutoSaddler: Automatic Harness Optimization with Durable Updates from Agent Execution Traces

> [← Daily summary](../2026-08-26.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2608.23041) · [arXiv](https://arxiv.org/abs/2608.23041)


## One-sentence takeaway

AutoSaddler automatically improves long-horizon LLM-agent harnesses by diagnosing failed execution traces, applying structured changes to prompts, tools, or middleware, and selecting updates using held-out development performance.

## Problem and motivation

Long-horizon agents can fail when small errors compound across many reasoning, tool-use, and environment-interaction steps. External harnesses can improve reliability, but manually tuning their prompts, tools, and runtime logic requires costly search and detailed analysis of lengthy traces.

The authors identify a gap between prompt-only optimization or trajectory-specific repair and broader, persistent harness optimization that explicitly tests whether changes generalize beyond the failures that motivated them (Sections 1–2, pp. 1–3).

## Approach and contributions

- **Offline harness optimization:** The method treats prompts, tool interfaces and implementations, and middleware control logic as non-differentiable parameters optimized from batches of execution traces under a rollout budget (Sections 3–4, pp. 3–5).
- **Diagnosis and structured patching:** A diagnosis–patch agent investigates traces and harness source code, then makes constrained capability or steering patches using a taxonomy spanning prompt, tool, and middleware changes (Section 4 and Table 1, pp. 5–6).
- **Generalization-aware update selection:** Same-batch verification tests the proposed intervention; qualifying patches receive development-set evaluation, reflection, and storage in an evolutionary DAG (EvoDAG) containing changes, outcomes, and lessons (Section 4, pp. 4–6; Algorithm 1, p. 17).
- **History-aware evolution:** An evolution agent can rebase or recombine useful changes from multiple previously explored harnesses rather than following only the latest candidate (Section 4, p. 6).
- **Empirical evaluation and released artifacts:** The framework is evaluated on GAIA2, SWE-Bench Pro, and Terminal-Bench 2.0; the paper says a project website and code will be available (Abstract, p. 1).

The results support the claim that the complete pipeline can outperform the tested base harnesses and automated baselines in these three benchmark configurations. Component ablations also associate diagnosis, structured intervention, and generalization-aware selection with higher GAIA2 performance.

They do not establish improvement for stateful tasks, unlabeled deployment data, or a broad range of optimizer and task-agent model families. They also do not isolate every interaction among components, and most optimization comparisons rely on only one costly search run per method.

There are numerical inconsistencies in the paper: the Abstract and Conclusion report a **9.6-point** SWE-Bench Pro base gain, while Table 3 and Section 5.2 support **8.4 points**. Section 5.2 also swaps the SWE-Bench Pro and Terminal-Bench baseline-gain labels: Tables 2–3 support **+4.4** and **+6.7 points**, respectively.

## Limitations and validity risks

- **Author-stated:** The approach assumes labeled training tasks, gold answers, and a clear task-level success metric; these signals may be unavailable or expensive in real deployments (Appendix R, p. 44).
- **Author-stated:** Tasks are assumed to be stateless and independent, excluding memory and skill curation from the optimization space (Section 3, p. 4; Appendix R, p. 44).
- **Author-stated:** Evaluation across a broader set of LLM families remains future work, and automated changes should receive human review or security validation before production use (Appendix R, p. 44).
- **Author-stated:** Two GAIA2 optimization trajectories are insufficient for comprehensive statistical characterization (Appendix C, pp. 20–21).
- **Analyst inference:** Most methods receive one optimization run followed by three repeated test executions, so reported test deviations primarily capture execution stochasticity, not variability in the harness-search process (Section 5.1, p. 7).
- **Analyst inference:** Baselines required benchmark-specific adaptations and Meta-Harness received train–development unions because it lacks native split support; these differences complicate perfectly controlled comparisons (Section 5.1, p. 7; Appendix B, pp. 18–20).
- **Analyst inference:** Terminal-Bench 2.0 uses a random split of only 89 tasks rather than a group-shifted split, making its generalization evidence narrower than that of GAIA2 and SWE-Bench Pro (Table 6, p. 20).
- **Analyst inference:** The conflicting headline numbers reduce confidence in narrative summaries; the tables should be treated as the clearest supplied evidence.

## Open research questions

1. **Can harnesses be optimized without gold outcomes?** The current method requires supervised success signals. A next experiment could replace labels with tool-error, trace-consistency, or multi-rollout agreement signals and compare held-out Pass@1 against supervised AutoSaddler.

2. **How does AutoSaddler behave on stateful workloads?** The evaluation assumes independent tasks and excludes memory and skill curation. A next experiment could optimize a harness over multi-session tasks with persistent state and measure both task success and harmful cross-task interference.

3. **How stable is the optimizer across repeated searches and model families?** Only limited independent-search and cross-model evidence is provided. A factorial experiment could repeat optimization with several optimizer/task-agent model pairings and report the distribution of final performance, cost, and regressions.

4. **Which selection mechanism contributes most under equal compute?** Development filtering, reflection, and EvoDAG interact, while the reported ablations do not exhaustively separate their compute-adjusted effects. A next experiment could compare all combinations under matched rollout and optimizer-token budgets.

## Confidence and missing information

**Confidence: medium.** The supplied text includes detailed methods, tables, appendices, splits, costs, and ablations, but confidence is reduced by contradictory headline improvements and limited repetition of the optimization process.

Material missing or unresolved information includes significance tests or confidence intervals for between-method differences, exhaustive multi-seed optimization results, results across more LLM families, real-world stateful evaluations, security assessments of generated patches, and confirmation that the promised code and website were actually released.
