# TorchMorph: CUDA-accelerated Morphological Transforms

> [← Daily summary](../2026-08-26.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2608.24738) · [arXiv](https://arxiv.org/abs/2608.24738)


## One-sentence takeaway
TorchMorph packages 22 SciPy-compatible morphological, distance-transform, and optimal-transport operators as batched N-dimensional CUDA kernels, achieving large single-core CPU speedups while preserving tested reference outputs to float32-level precision.

## Problem and motivation
Morphological transforms remain important for mask cleanup, shape processing, watershed seeding, skeletonisation, and boundary-aware losses, but `scipy.ndimage` operates on CPU arrays and requires costly GPU-to-host transfers and per-sample loops in modern PyTorch pipelines. Existing GPU libraries do not jointly provide native PyTorch tensors, batching, higher-dimensional support, full SciPy semantics, exact Euclidean distance transforms, and differentiable optimal transport (Introduction; Table 1).

## Approach and contributions

- **Unified operator library:** 22 public operators cover binary and greyscale morphology, exact and approximate distance transforms, and entropy-regularised optimal transport on `(B, C, Spatial...)` CUDA tensors with one to eight spatial dimensions (Sections 2.1–2.2; Figure 1).
- **SciPy-compatible interface:** Image operators mirror `scipy.ndimage` argument conventions, border behavior, origins, iteration semantics, and preallocated outputs, facilitating import-level migration (Section 2.2.1; Listing 1).
- **CUDA implementation:** Fused morphology kernels use host-resolved offsets and an interior fast path; the exact Euclidean transform uses separable lower-envelope passes; Sinkhorn uses batch tiling, single-pass log-domain updates, and CUDA-graph replay (Sections 2.3.1–2.3.3).
- **Testing and release:** The MIT-licensed implementation is validated through 78 test functions against SciPy and POT, including layout, dimensionality, boundary, solver, stream, and device cases (Section 2.4; Section 3). The authors explicitly characterize the contribution as implementation availability rather than new algorithms (Conclusion).

The evidence supports numerical agreement on the tested configurations and substantial throughput gains against the specified single-threaded SciPy and POT baselines. It does not establish superiority over optimized multicore CPU implementations, competing GPU libraries, other GPUs, or end-to-end training pipelines. Exact agreement is established only for the tested binary and chamfer cases, not universally.

## Limitations and validity risks

- **Author-stated:** Morphology and distance kernels are forward-only; only optimal transport supports differentiation (Conclusion).
- **Author-stated:** Morphology and distance transforms require CUDA, while only transport has a pure-PyTorch CPU fallback (Conclusion).
- **Author-stated:** Kernels use float32 with `--use-fast-math`, and NaN propagation is not guaranteed to match SciPy (Section 3; Conclusion).
- **Author-stated:** Performance was measured on one machine against single-threaded CPU baselines; brute-force distance-transform timing is intended as an oracle comparison, not a competitive CPU benchmark (Section 3, protocol and threats).
- **Analyst inference:** Because no direct benchmarks against Kornia, cuCIM, or other GPU implementations are reported, Table 1’s coverage comparison does not establish comparative GPU performance.
- **Analyst inference:** The text reports operator microbenchmarks but no downstream accuracy or end-to-end training-time measurements, so practical impact inside full learning pipelines remains unquantified.
- **Analyst inference:** No component-level ablation isolates the contribution of offset precomputation, interior fast paths, Sinkhorn tiling, or CUDA graphs, although batch-size comparisons expose aggregate batching effects.

## Open research questions

1. **How much do the individual kernel optimizations contribute?** The paper reports only combined implementations. An ablation could disable the morphology interior fast path, Sinkhorn batch tiling, and CUDA-graph replay separately across representative shapes.
2. **How does TorchMorph compare with alternative GPU libraries where capabilities overlap?** Only CPU references are timed. A matched benchmark against Kornia, cuCIM, and pure-PyTorch implementations could compare latency, memory, semantics, and dimensional coverage.
3. **Can morphology and distance transforms support useful gradients?** The authors identify their forward-only status as a limitation. A follow-up could implement arg-min/arg-max subgradients and test gradient correctness, stability, and downstream segmentation training.
4. **Do microbenchmark gains translate into end-to-end pipeline gains?** No complete training workload is evaluated. An experiment could measure wall-clock time, memory, and task quality when replacing CPU preprocessing or loss computation in a volumetric segmentation pipeline.
