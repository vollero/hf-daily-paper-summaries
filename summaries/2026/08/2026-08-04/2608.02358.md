# ScrambleToolBench: Agents Search Exhaustively Even When Their Own Map Points to the Next Step

> [← Daily summary](../2026-08-04.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2608.02358) · [arXiv](https://arxiv.org/abs/2608.02358)


## One-sentence takeaway

ScrambleToolBench shows that leading language-model agents can discover obfuscated tools but largely fail to adapt deductively when mappings change, with memory improving recall and additional reasoning funding broader search rather than reliable cycle-tracing recovery.

## Problem and motivation

Tool-use evaluations commonly expose meaningful API names and assume stable behavior, allowing agents to rely on pretrained semantic knowledge. The authors argue that this does not test whether agents can infer undocumented behavior from interaction, distinguish transient failures from structural changes, and revise established beliefs efficiently.

ScrambleToolBench targets this gap with semantically obfuscated tools and non-stationary conditions: identifier drift, stochastic timeouts, and time-limited execution sequences (Sections 1 and 2.4).

## Approach and contributions

- **Interactive benchmark:** Agents discover anonymized function identifiers, parameter keys, output fields, and success/failure tokens through trial and error in a stateful terminal simulator (Sections 2.1–2.2).

- **Continuous curriculum:** Each episode contains sequential procedural tasks sharing context, so agents must retain and reuse tool knowledge rather than restart discovery (Section 2.3; Figure 1).

- **Controlled environmental dynamics:** The benchmark separately and jointly evaluates 25% mapping drift, 15% stochastic action failure, and 10-action temporal windows (Sections 2.4 and 3.1).

- **Persistent-memory baseline:** Structured databases store task recipes and inferred tool mappings, parameters, and confidence, with model-generated updates injected at every step (Section 3.1; Appendix A).

- **Recovery analysis:** The authors derive cycle tracing, which exploits the bijective drift mapping and requires at most six extra calls for each seven-identifier drift cycle in this benchmark; evaluated agents generally do not discover or apply it (Section 4.2).

The evidence supports the authors’ claim that tested agents often retain enough information to reuse tools but do not reliably transform that information into an efficient structural recovery policy. It also supports a partial benefit from external memory.

It does not establish that cycle tracing is optimal outside the benchmark’s cyclic-permutation construction, that these results transfer to live software systems, or that every possible prompting, memory, or agent architecture would behave similarly.

## Limitations and validity risks

- **Author-stated scope:** Semantic obfuscation is intentionally a worst-case construction rather than a claim that real APIs are always fully anonymous (Section 2.1).

- **Limited evaluation budget:** Results use only 20 episodes of five tasks per condition, 100 inference steps per task, and memory evaluation on four model pairs because of inference constraints (Section 3.1; Table 2).

- **Simulator rather than live systems:** The environment is a lightweight Python simulator, so real latency, side effects, tool diversity, and operational failures are not represented (Section 2.3).

- **Cycle-tracing assumptions:** Its guaranteed six-call overhead assumes a current full mapping before a seven-element cyclic drift; unresolved mappings from earlier tasks can change the cost (Section 4.2.3, Equation 2 footnote).

- **Incomplete initial discovery:** Gemini 3.1 Pro and Claude Sonnet 5 never observed all 28 functions during the analyzed Task 1 drift runs, weakening direct comparison with a reference strategy that assumes full operational discovery (Section 4.2.4).

- **Analyst inference — narrow structural drift:** Because drift is implemented as one cycle over selected identifiers while outputs retain stable fingerprints, the benchmark may make a particular deductive recovery strategy unusually available. Performance under arbitrary many-to-one changes, schema changes, or changing tool semantics remains unknown.

- **Analyst inference — exact-match outcomes:** Exact string matching provides a clear metric but may undercount semantically correct or partially correct work; no alternative answer-quality evaluation is reported (Sections 2.1 and 3.2).

## Open research questions

1. **Can agents be taught to derive cycle tracing rather than merely given more reasoning tokens?**  
   This remains open because higher reasoning reduced failed searches but did not improve chain-following. A next experiment could compare an explicit bijection-aware planning prompt, a learned recovery controller, and the existing unassisted baseline under identical drift.

2. **How robust is deductive recovery under less structured drift?**  
   The current drift is a known benchmark construction based on cyclic permutation. A follow-up could vary cycle sizes and introduce multiple cycles, schema changes, or non-bijective replacements while measuring recovery cost and belief updating.

3. **Which memory-update policies prevent stale beliefs?**  
   Memory sometimes reduced stale calls but increased them for Claude Sonnet 4.5. An experiment could ablate confidence decay, contradiction-triggered invalidation, automatic cycle updates, and periodic pruning.

4. **Do these failure modes persist in live tool environments?**  
   The evaluation uses a deterministic simulator with injected noise. A next study could reproduce matched tasks against sandboxed real command-line tools and APIs, tracking success, latency, side effects, and recovery behavior.
