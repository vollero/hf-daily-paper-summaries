# SWE-Touch: Benchmarking Coding Agents When Users Touch the Code

> [← Daily summary](../2026-08-04.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2608.02499) · [arXiv](https://arxiv.org/abs/2608.02499)


## One-sentence takeaway

SWE-Touch finds that injecting small, task-conflicting user edits into a coding agent’s live workspace reduces average SWE-bench Verified resolve rate by 7.7 percentage points, exposing robustness failures not predicted by autonomous performance.

## Problem and motivation

Repository-level coding benchmarks generally assume a static workspace or restrict users to messages, whereas real users can directly modify code while an agent is working. The authors identify this as an important evaluation gap: their analysis reports user-attributed repository changes in 59.0% of SWE-chat sessions, yet existing coding benchmarks do not test agents against live user code changes (Figure 1, pp. 2–3).

The paper asks whether agents notice, interpret, reconcile, and validate changes to their evolving workspace—capabilities distinct from solving a repository task alone.

## Approach and contributions

- **Shared-workspace benchmark:** SWE-Touch augments repository-repair tasks with simulated user edits applied during an agent trajectory, accompanied by contextual user messages (§3.1–§3.4).

- **Counter-Edit construction:** Three models’ read/edit trajectories identify up to eight task-critical regions. A separate GPT 5.5-backed generator creates small, plausible but task-conflicting implementation patches (§3.2–§3.3; Appendix B.3).

- **Validation and delivery:** A candidate must not solve the fail-to-pass tests, and either remains incompatible with the reference repair or prevents it from applying cleanly. On SWE-bench Verified, delivery is triggered by access to the edited region and attempted up to \(K=3\) times (§3.3–§3.4; Appendix E).

- **Multi-model evaluation and diagnostics:** Nine models are compared under autonomous and Counter-Edit conditions, supplemented by longer-horizon experiments, message/code ablations, a helpful Co-Edit control, and trajectory-level failure analysis (§4–§5).

The matched conditions, component ablation, and Co-Edit control support the authors’ claim that task-conflicting repository state creates a robustness challenge beyond message wording or interruption alone. They do not establish performance under the full range of real human collaboration, nor do the model-level correlation and audited trajectories prove a causal mechanism.

## Limitations and validity risks

- **Author-stated:** The interventions represent controlled, simulated, task-conflicting edits rather than the full distribution of user behavior, such as helpful, partially correct, ambiguous, or requirement-changing contributions (§7).

- **Author-stated:** Triggering is scripted rather than full-duplex; the simulated user does not continuously observe and adapt to the agent’s behavior (§7).

- **Coverage limitation:** The main cohort is a conditioned sample of 200 tasks for which all three region-mining models produced complete trajectories; this may limit representativeness (Appendix B.1).

- **Delivery variability:** Eight tasks receive only messages, and 6.4% of scored Counter-Edit runs receive no repository-changing application. Effective exposure also varies when agents rewrite target regions (Appendix B.3).

- **Validation heterogeneity:** Only 150 of 192 code edits pass the full three-state validation; for 42, the reference patch no longer applies cleanly after the Counter-Edit (Appendix E).

- **Analyst inference:** Longer-horizon results are not directly comparable with the main experiment because they use only 25 tasks per benchmark, two runs, distinct edits, and fixed-fraction rather than region-triggered delivery (§4; Appendix B.2).

- **Analyst inference:** The message/code component ablation is based on one run, making its model-specific differences less stable than the three-run main evaluation (Appendix B.3).

- **Analyst inference:** Failure labels are produced by GPT 5.5 judges rather than human annotators. Two calls agreed on 93.9% of primary labels, but shared-model biases could remain (Appendix D).

## Open research questions

1. **How do agents handle realistic mixtures of helpful, partial, ambiguous, and conflicting edits?** SWE-Touch primarily tests deliberately conflicting edits. A next experiment could stratify interventions by semantic correctness and measure acceptance, clarification, and recovery separately.

2. **Would explicit workspace-change detection improve robustness?** The paper diagnoses weak state awareness but does not test a dedicated detection mechanism. A controlled experiment could add filesystem-diff notifications or mandatory post-change inspection and compare resolve rate and cost.

3. **Which validation strategies actually prevent failed reconciliation?** Test volume alone does not separate success from failure. A next study could require targeted test generation for the modified code path and compare it with generic regression testing.

4. **Do adaptive users change agent behavior relative to fixed triggers?** The current simulator controls message wording but uses predetermined delivery rules. A full-duplex simulator could choose when and how to intervene based on live diffs, commands, and test outcomes.

## Confidence and missing information

**Confidence: high.** The supplied text includes the complete methodology, primary tables, controls, appendices, and stated limitations.

Material uncertainties remain: no human validation of patch plausibility or failure labels is reported; the exact task lists and full trajectory artifacts are referenced but not reproduced; complete per-run longer-horizon and ablation uncertainty estimates are absent; and no evaluation with actual users is provided.
