# SemaPLC: A Project-Grounded, Verification-Gated Agent Harness for PLC Code Generation

> [← Daily summary](../2026-08-20.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2608.18565) · [arXiv](https://arxiv.org/abs/2608.18565)


## One-sentence takeaway

SemaPLC grounds LLM-generated PLC logic in existing projects and permits completion only after logged external checks, substantially improving runtime behavior while incurring many more model interactions on project tasks.

## Problem and motivation

Existing PLC code-generation evaluations largely test isolated program organization units or demonstrate execution in a few cases. Production code must instead reuse an existing project’s interfaces, variables, modules, and operational conventions, while behaving correctly across scan cycles, timers, resets, interlocks, and state transitions. The authors argue that compilation and static checks cannot establish runtime correctness and identify a lack of unified, benchmark-scale evaluation across project integration, static behavior, and live execution (Introduction, pp. 2–3).

## Approach and contributions

- **Project-grounded generation:** The agent retrieves relevant project structure, declarations, interfaces, function blocks, and conventions, then makes bounded edits rather than regenerating the project (Sections 4.1–4.2).
- **Multi-source verification:** Separate specification audits, compilation checks, and live-runtime tests provide external feedback for repair (Sections 4.3–4.4).
- **Verification-gated completion:** A candidate is accepted only when logged results satisfy track-specific criteria. Edits invalidate all earlier verdicts, unlogged claims become unchecked, and each check permits at most two repair rounds (Algorithm 1; Section 4.5).
- **Two evaluation tracks:** A 117-task function track measures strict verified pass rate; a 65-task project-context track independently measures integrated compilation, static assertions, and golden-trace runtime behavior (Sections 3 and 5.2).
- **Empirical contribution:** The experiments show that methods clustered by static scores can differ substantially under live execution (Section 6.3).

These results establish stronger performance under the paper’s repaired function benchmark and hidden project-track scoring setup. The cumulative ablation supports—but does not fully isolate—the value of successive verification layers because it uses only one model. The evidence does not establish correctness outside the tested scenarios, equivalence to exhaustive verification, or generalization beyond the selected projects, models, and PLC infrastructure.

## Limitations and validity risks

- **Author-stated:** Dynamic scoring covers a bounded scenario set, leaving unseen operating conditions unmeasured (Conclusion; Appendix E).
- **Author-stated:** SemaPLC’s advantage narrows on the strongest model; on GPT-5.5 its dynamic lead over Agents4PLC is 1.8 points, and it trails some baselines statically (Section 6.2).
- **Author-stated:** Project-track reliability requires substantially more model requests, and request counts vary considerably by backbone (Section 6.4; Table 6).
- **Author-stated:** Sampled traces do not observe every scan cycle; transient events are addressed through persistent assertions (Section 4.4).
- **Analyst inference:** The layer ablation is limited to DeepSeek-V4-Flash, so layer effects are not shown to hold independently across all seven models (Section 6.3; Table 3).
- **Analyst inference:** Bare versus full removes both knowledge artifacts and verification tools, so it cannot attribute gains to a particular harness component; the authors explicitly acknowledge this conflation (Section 6.1).
- **Analyst inference:** The project corpus covers ten industrial plants derived from one source corpus, limiting evidence for other project conventions or runtime environments (Section 5.2).
- **Analyst inference:** Forty-three function tasks required oracle repairs. Although the paper describes a three-round engineering audit, the supplied text does not report inter-reviewer agreement or an independent external validation of those repairs (Appendix A).

## Open research questions

1. **Does verification-gated repair generalize to unseen operating conditions?** The benchmark scores only bounded hidden scenarios. A next experiment could generate additional adversarial or simulation-derived scenarios after development and evaluate them without exposing them to the agent.

2. **Which harness component produces the most reliable gain across models?** The full-versus-bare comparison conflates skills and tools, while the layer ablation uses one backbone. A factorial ablation across all seven models could independently vary grounding, specification audit, compilation feedback, and runtime feedback.

3. **Can comparable runtime reliability be achieved with fewer interactions?** Project tasks require 34.1 requests per task on average. A next experiment could compare batched tool execution, scripted verification plans, or non-model-controlled repair scheduling at matched dynamic scores.

4. **How can timer-heavy logic receive stronger verification coverage?** The reported formal pipeline was inconclusive for every timer-bearing property. A next experiment could combine runtime testing with a timer-aware formal backend and measure conclusive coverage and defect detection on the same programs.

## Confidence and missing information

**Confidence: high** for the method, experimental design, and reported results because the supplied text includes complete definitions, tables, appendices, and evaluation-isolation details.

Material missing information includes statistical uncertainty or significance tests, per-task result distributions, inter-reviewer agreement for oracle repairs, hardware/runtime configuration details, exact interaction and token budgets beyond reported averages, and evaluation on unseen projects, alternative PLC toolchains, or unbounded operating conditions.
