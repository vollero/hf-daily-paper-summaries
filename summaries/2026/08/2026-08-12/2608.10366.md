# DSAgentBench: Can Agents Automate End-to-End Data-Science Workflows in Real Computer Environments?

> [← Daily summary](../2026-08-12.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2608.10366) · [arXiv](https://arxiv.org/abs/2608.10366)


## One-sentence takeaway

DSAgentBench shows that current agents remain unreliable at end-to-end data science in real desktop environments: the best evaluated agent reaches 56.70% task success, versus 85.09% for human participants.

## Problem and motivation

The paper addresses whether agents can autonomously complete long-horizon data-science workflows spanning acquisition, wrangling, exploration, modeling, visualization, and validation while operating real applications and operating-system interfaces.

The authors argue that existing evaluations split this problem into isolated code-generation, analytical, or generic GUI tasks. They therefore miss the combined demands of grounding actions in desktop state, coordinating several tools, interpreting intermediate results, recovering from errors, and producing analytically correct artifacts (Introduction; Table 1).

## Approach and contributions

- **End-to-end benchmark:** DSAgentBench contains 275 human-authored tasks across six lifecycle categories, each represented by an initial system configuration, a natural-language instruction, and an evaluator (Sections 3.1–3.3; Tables 5–6).
- **Real-computer environment:** The benchmark extends OSWorld with Ubuntu, Python, VS Code, Jupyter, Chrome, Kaggle and OpenML access, and SQLite support. Agents interact through screenshots or screenshots plus accessibility trees and standard GUI actions (Section 4.1; Figure 4).
- **Outcome-based evaluation:** Task-specific evaluators inspect scripts, numerical results, files, visualizations, and trained models rather than merely checking whether code executes. About 10% of tasks additionally use a visual-language-model judge after deterministic gates (Section 5.2; Appendix C).
- **Broad empirical assessment:** The authors evaluate 15 closed-source, hybrid, and open-source systems and analyze performance by lifecycle stage, difficulty, workflow length, tool, observation modality, step budget, and failure type (Sections 5–6).
- **Released asset:** The authors state that the benchmark is released through its project repository and that datasets, prompts, configurations, evaluators, and inference scripts will be provided (Abstract; Appendix B.3 and B.6).

These results establish that the evaluated systems have a large success gap relative to the small human reference group under this benchmark’s specific environment, tasks, and scoring rules. The breakdowns also associate failures with longer workflows, task difficulty, grounding, and executable-code production.

They do not establish performance in organizations, on unrestricted real-world projects, on operating systems other than the evaluated Ubuntu setup, or with larger action budgets and alternative agent scaffolds beyond the limited ablations. The failure taxonomy is diagnostic rather than causal: Table 10 reports assigned root causes but does not isolate each capability experimentally.

## Limitations and validity risks

- **Author-stated:** Open-source systems do not support accessibility-tree input and are therefore compared only in the screenshot setting. Their results are not modality-matched to the strongest closed-source results (Limitations; Table 13).
- **Author-stated:** Detailed error analysis covers 604 closed-source and 150 sampled open-source runs rather than all trajectories, so uncommon failure types may be missed (Limitations; Section 6).
- **Author-stated:** Visualization evaluation emphasizes final-artifact correctness and quality. A model-based visual judge is used for roughly 10% of tasks after deterministic gates, leaving some dependence on judge validity (Limitations; Section 5.2; Appendix B.6 and C).
- **Analyst inference:** Generalization is constrained by the evaluated Ubuntu configuration, Python-centered workflows, 15-action default budget, and heavily tabular task mix. Portability to other operating systems and tools is described but not experimentally demonstrated (Table 2; Sections 4.2 and Appendix B.6).
- **Analyst inference:** The human reference is based on only three participants, so 85.09% should not be treated as a precise population-level estimate (Section 5.3).
- **Analyst inference:** Difficulty labels combine step count, analytical sophistication, and tool coordination. Consequently, Table 4 cannot determine which factor causes the observed degradation (Section 3.3).
- **Analyst inference:** Some reporting is internally ambiguous: the text says A11y generally gives modest gains, yet changes vary substantially by model; Table 15 also contains an apparent malformed Gemini entry. These issues warrant checking the released artifacts before reusing every value.

## Open research questions

1. **Which capability bottleneck is most causal: UI grounding, planning, coding, or analytical reasoning?**  
   The manual taxonomy assigns failures to these categories but does not independently manipulate them. A next experiment could provide oracle UI actions, oracle code, or oracle intermediate plans one at a time and measure the resulting success gains.

2. **How well does DSAgentBench transfer beyond its Ubuntu and Python setup?**  
   The authors describe potential portability but report experiments only on Ubuntu. Re-instantiating a matched task subset on Windows, macOS, RStudio, and cloud notebooks would test environment and tool robustness.

3. **Can agents improve through structured recovery rather than larger raw step budgets?**  
   Raising the budget from 15 to 50 produces little gain, while the error analysis highlights persistent unrecovered mistakes. A controlled comparison could test checkpointing, error classifiers, execution verification, and rollback under an equal action budget.

4. **How stable are rankings across repeated runs and judge choices?**  
   Only GPT-4o and Claude-4.5-Sonnet receive reported repeat evaluations, and some visualization tasks use model judges. Repeating every model across several seeds and cross-validating visual judgments against blinded humans would quantify ranking uncertainty.

## Confidence and missing information

**Confidence: high** for the benchmark design and reported headline results because the supplied text includes detailed methods, tables, appendices, and evaluation definitions.

Material missing or unresolved information includes confidence intervals for most model scores, full per-task results, repetition counts for most models, complete human-participant protocol, detailed sampling rules for error analysis, inter-rater agreement on failure labels, empirical cross-OS validation, and a human validation study of the visual judges. The supplied text also contains minor table-label and formatting inconsistencies that prevent complete confidence in every appendix entry.
