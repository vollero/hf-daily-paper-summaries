# SWE-Bench ProMax: Benchmarking Agents on Large-Scale Multilingual Code Refactoring

> [← Daily summary](../2026-08-11.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2608.09802) · [arXiv](https://arxiv.org/abs/2608.09802)


## One-sentence takeaway

SWE-Bench ProMax is a 170-instance, expert-curated benchmark of large, multilingual repository refactors on which the best tested model resolves 41.2%, with incomplete cross-file propagation emerging as the principal observed failure pattern.

## Problem and motivation

Existing coding benchmarks increasingly risk saturation, contamination, ambiguous specifications, and tests that either reject valid solutions or enforce unstated requirements. They also emphasize bug fixes and feature additions, often in Python and at limited file scope.

The authors argue that behavior-preserving refactoring is a harder, more realistic evaluation target because it requires sustained understanding and coordinated edits across many files. Prior refactoring benchmarks do not jointly provide multilingual coverage, large-scale changes, execution-based evaluation, and expert-reviewed specifications and tests (Sections 1 and 2.1).

## Approach and contributions

- **A large-scale multilingual benchmark:** 170 real-commit instances from 70 repositories in Python, Java, TypeScript, Go, C, C++, and Rust. Gold source patches average 11.4 files and 261.6 lines (Section 3.3; Tables 2 and 5).
- **A three-stage construction pipeline:** candidates are mined from qualifying GitHub repositories, reproduced in Docker, and filtered and rewritten through expert review. Only 170 of 29,782 initial candidates remain (Section 3.2; Figure 3).
- **Specification and test curation:** experts rewrite issue descriptions and remove tests judged overly narrow or overly broad, then review alignment among the description, test suite, and gold patch (Section 3.2).
- **Execution-based agent evaluation:** six models are evaluated on all instances using mini-swe-agent and OpenHands, with identical 300-step and $10-per-instance limits; success requires passing every test (Sections 3.1 and 4).
- **Behavioral and efficiency analysis:** results compare scaffolds, languages, steps, and API cost, while trajectory analysis examines modified-file coverage and interaction rounds (Sections 5.1–5.3).

These results establish that the tested model–scaffold combinations leave a majority of instances unresolved and that outcomes vary substantially by scaffold, language, and cost. Figure 5 supports an association between failures, lower file coverage, and longer trajectories for two representative models.

They do not prove that file under-coverage is the universal or causal failure mechanism, that the benchmark measures all forms of real-world refactoring, or that language-level differences arise from training data. The latter is explicitly offered only as a possible explanation in Section 5.1.

## Limitations and validity risks

- **Restricted source population — analyst inference:** repositories must have at least 500 stars, an approved license, and at least 80% of their code in one of seven languages. Results may not transfer to small, private, mixed-language, or unsupported-language projects (Section 3.2).
- **Uneven repository concentration — source-stated:** TypeScript has 28 instances but only two repositories, 25 from Angular, creating a project-specific concentration risk (Appendix A).
- **Commit-mining selection bias — analyst inference:** requiring post-January-2025 commits whose messages contain “refactor,” exclude “bug fix,” and modify both test and non-test files can omit refactors described differently or committed without test changes (Section 3.2).
- **Task-label uncertainty — analyst inference:** task categories and required skills in Appendix B were classified by Claude Sonnet 4.6; the text does not report independent validation or classifier reliability.
- **Curation subjectivity — analyst inference:** experts determine complexity and whether tests are overly narrow or broad, but inter-reviewer agreement and detailed adjudication statistics are not provided.
- **Gold-patch framing — analyst inference:** descriptions are checked against the original developer patch, while success is test-based. The supplied text provides no study of how many materially different correct implementations remain admissible.
- **Limited behavior analysis — source-supported scope:** Figure 5 examines only Claude Sonnet 4.6 and Kimi-K2.5, so its failure-pattern conclusions are not directly demonstrated for all six models.
- **No uncertainty estimates:** Table 3 reports single Pass@1 rates without confidence intervals or repeated-run variance.
- **Cost comparability is unclear:** reported API cost is useful within the experiment, but the supplied text does not document pricing dates, token accounting, or normalization across providers.
- **Potential issue–task mismatch:** although collection excludes commit messages containing “bug fix,” the LLM-based analysis labels 41.2% of instances as also involving bug fixes and 43.5% as involving new features (Appendix B, Figure 6). Thus, the benchmark is not a pure test of isolated behavior-preserving refactoring.

## Open research questions

1. **Can explicit repository-wide planning reduce incomplete refactors?** Figure 5 links failures to insufficient file coverage for two models, but does not test a planning intervention. A follow-up could randomize agents between the existing scaffolds and a dependency-aware plan-and-check workflow, measuring resolve rate and recall of gold-patch-affected files.

2. **How robust are results across repeated stochastic runs?** The paper reports Pass@1 without run-to-run variability. Repeating each model–instance pair with several seeds would permit confidence intervals and reveal whether model rankings are stable.

3. **What causes the large language-specific variation?** Section 5.1 suggests training-data differences but does not establish them. A controlled experiment could match tasks across languages by patch size, repository complexity, and refactoring category, then test whether performance gaps persist.

4. **How sensitive are scores to curation and test design?** The benchmark removes tests judged too narrow or broad, but no ablation quantifies the effect. An evaluation using pre-curation, partially curated, and final test suites could measure score changes and manually audit disagreements.

## Confidence and missing information

**Confidence: high** for benchmark construction, reported dataset statistics, protocol, and Table 3 results because the supplied text is detailed and internally consistent; **medium** for broader interpretations of failure causality and real-world generalization.

Material missing information includes benchmark access and licensing details for the assembled artifact, annotator counts and expertise, inter-reviewer agreement, per-stage candidate attrition, exact low-LOC thresholds, classifier-validation results for Appendix B, repeated-run uncertainty, contamination checks on evaluated models, cost-accounting details, and systematic analysis of alternative correct patches.
