# A^2E : An End-to-End Agent Auditing Engine

> [← Daily summary](../2026-08-11.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2608.07346) · [arXiv](https://arxiv.org/abs/2608.07346)


## One-sentence takeaway

A²E unifies benchmark execution, standardized agent tracing, and lifecycle-aligned evaluation, showing that harness choice materially affects effectiveness and efficiency even when the underlying model and tasks are held fixed.

## Problem and motivation

Deployed agent performance depends not only on the LLM but also on the harness’s prompts, tool interfaces, context management, execution loop, and error handling. The authors argue that existing systems cover only parts of harness-level evaluation: benchmark runners may require harness-specific adapters or alter native execution, while observability platforms collect traces without providing end-to-end task orchestration and verification. A²E targets this gap with a minimally invasive, harness-agnostic pipeline for composing benchmarks and harnesses, recording faithful trajectories, and evaluating both outcomes and execution processes (Introduction; Sections 2 and 5).

## Approach and contributions

- **Agent Task Protocol (ATP):** Separates benchmark adaptation from harness execution through shared task, binding, runner, and trace objects, avoiding distinct integration code for every benchmark–harness pair (Section 4.1; Figure 1a).
- **Automatically instrumented monitoring:** Maps framework-specific model calls, tools, chains, skills, errors, timing, and resource use into standardized OpenTelemetry-compatible span trees (Sections 3.1–3.2).
- **Lifecycle-Aligned Evaluation:** Organizes rule-based and LLM-judged metrics across reasoning, action, final-answer, and runtime-quality stages rather than relying only on correctness (Sections 5.1–5.2; Figure 5).
- **Persistent, incremental evaluation:** Stores trajectories, configurations, outputs, and metric results in a centralized database so new or revised metrics can be applied without rerunning agents (Section 5.3).
- **Cross-harness empirical study:** Evaluates nine harnesses over 23 benchmarks under matched configurations and separately compares model–harness combinations on three benchmarks (Section 6; Table 1; Figures 6–7).

The evidence supports the authors’ central claim that harness implementations can alter success, token consumption, and trajectories under controlled model/task settings. It does not establish a stable global ranking: each Table 1 cell contains only five tasks, Figure 7’s underlying numerical values are not supplied, and the detailed diagnostic comparison is a single case. The claim that remaining controlled-run differences are attributable to the harness is plausible within the experimental setup, but causal attribution to particular harness components is not isolated by intervention or ablation.

## Limitations and validity risks

- **Author-stated limitations:** Table 1 uses only five tasks per cell, producing 0.20 score granularity and high per-cell variance; the authors explicitly say it should not rank frameworks (Section 6.1).
- **Author-stated limitations:** Full trajectory analysis covers only the 19 non-sandbox benchmarks, not all 23; CrewAI is omitted from token analysis because its LLM spans lack token counts (Figure 6).
- **Author-stated limitations:** `tool_invocation` and `hallucination` in Figure 6 are instrumentation-set and should not be interpreted as harness behavior. Several process metrics move little, and actionable design guidance is left for future work (Section 6.1; Figure 6).
- **Analyst inference:** Table 2 is internally inconsistent: its task-outcome row labels LangGraph “Successful” and CrewAI “Failed” but displays `task_succeeded=1.0, correctness=0.0` for both, whereas the surrounding prose reports correctness 1.0 versus 0.0. This weakens confidence in that table’s metric annotations.
- **Analyst inference:** The normalized \(Q_h\) score depends on the harnesses included in each comparison and imposes a particular Euclidean trade-off between normalized tokens and success; no robustness analysis for alternative weighting or normalization is reported (Equation 1).
- **Analyst inference:** No component ablations isolate ATP, instrumentation, metric taxonomy, or individual harness design choices. Thus, the study diagnoses differences but does not identify which implementation features cause them.
- **Analyst inference:** Reproduction requires matching dataset versions, model endpoints, and run settings, but the supplied text does not fully specify these items or report repeated-seed uncertainty (Section 4.3).

## Open research questions

1. **Which harness mechanisms cause the observed performance gaps?** The comparisons hold the model fixed but do not ablate prompts, context policies, tool conversion, termination, or recovery logic. A next experiment could swap these components individually between two harnesses on identical tasks.

2. **Are harness rankings stable across task samples and model backends?** Table 1 uses five tasks per cell, while the GLM-5.2 comparison covers only three benchmarks. Repeating the full grid with larger samples, multiple seeds, and several fixed models could estimate confidence intervals and ranking stability.

3. **How reliable are lifecycle metrics across instrumentation and judge choices?** Some metrics are instrumentation-set, and the text does not report agreement or calibration for LLM judges. A next study could compare human annotations, multiple judge models, deterministic checks, and instrumentation adapters on the same traces.

4. **Can trajectory diagnostics predict or improve future task success?** The paper shows descriptive differences but does not demonstrate that its process metrics guide effective harness changes. A plausible experiment would optimize a harness using selected trajectory metrics and test the modified version on held-out benchmarks.

## Confidence and missing information

**Confidence: medium.** The supplied text gives substantial architectural and experimental detail, including controls, sample counts, and several quantitative comparisons. Material missing or ambiguous information includes full Figure 6 and Figure 7 numerical data, per-run variance or confidence intervals, judge prompts and judge-model details, complete metric definitions, dataset/model endpoint versions, repeated-seed results, resource overhead of A²E itself, repository contents and licensing, and resolution of the Table 2 metric inconsistency.
