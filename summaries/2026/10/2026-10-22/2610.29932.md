# FrontierCS 2: A Benchmark for Computer Science R&amp;D

> [← Daily summary](../2026-10-22.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.29932) · [arXiv](https://arxiv.org/abs/2610.29932)


## One-sentence takeaway
FrontierCS 2 evaluates agents on 48 research-code improvement tasks, with the strongest tested model–harness pair passing 58% of runs under task-specific thresholds and 16 tasks remaining unpassed across all tested agents (§§1, 4).

## Problem and motivation
The authors ask whether LLM agents can improve published computer-science research implementations. They identify a gap between benchmarks that score a single standalone program and research workflows involving an existing repository, iterative experiments, and comparison against the original authors’ code. Existing environment-based benchmarks, they argue, either concentrate on machine learning or use tests, rubrics, or reimplementations as their reference (§§1–2).

## Approach and contributions
- **Tasks built by subtraction:** Remove a paper’s central implementation while retaining its dependencies; agents reconstruct or improve the component within permitted files. The removed code supplies the human reference. Structured LWE is an explicit exception (§3; Appendix A).
- **Private, interactive judge:** Agents receive development scores and sanitized threshold feedback during a five-hour run. The evaluator, reference, and final workloads remain private; agents select their own final patch. Passing requires meeting every metric’s threshold across every final workload (§4).
- **Benchmark and evaluation:** The suite contains 48 tasks across 13 domains and evaluates 12 model–harness pairs. The authors also describe a private collection exceeding 100 tasks, reserved for future announcement (§1; Appendix A).
- **Capability and difficulty estimation:** FCI and FDI adapt an item-response model to combine metric outcomes and normalized score margins on a shared scale, with uncertainty intervals (§5.2; Appendix D).

These results establish performance within the supplied repositories, permitted edits, resources, and thresholds. “Beating the reference” means satisfying task-specific thresholds, which may permit quality tolerances (§§3–4). **Analyst inference:** the results demonstrate bounded research-engineering capability; they do not independently establish novel scientific discovery or superiority to researchers working under matched conditions.

## Limitations and validity risks
- **Author-identified metric blind spots:** Pass rates obscure improvement magnitude, while final scores can ignore material side costs, illustrated by QuarterPIR communication and BBQ circuit size (§§6–7).
- **Author-identified uncertainty:** Individual task FDI estimates are too uncertain for task ranking; many agent FCI intervals overlap (§5.2).
- **Analyst inference—limited repeatability evidence:** One run per agent–task pair leaves within-pair variability unmeasured. Task bootstrapping does not replace repeated executions (§5.1; Appendix D).
- **Analyst inference—model and harness effects are confounded:** Each reported model uses one harness, sometimes with different settings; rankings describe complete agents rather than isolated models (§5.1; Appendix C).
- **Analyst inference—budget curves have restricted interpretation:** They censor completed runs by cost rather than testing agents explicitly instructed to stop and submit at each budget (§5.3; Appendix D).
- **Scope exception:** Structured LWE uses public instances without a held-out final component, unlike the general protocol (Appendix A).

## Open research questions
- **How stable are agent rankings across repeated runs and harnesses?** The evaluation uses one run and one harness per reported model. Repeat tasks across seeds and cross selected models with multiple harnesses.
- **How should evaluations reward improvement while retaining safeguards?** The case studies expose conflicts between passes, scores, and side costs. Compare current rankings with multi-objective reporting that includes communication, circuit size, and workload-level quality.
- **What performance is achievable under explicit spending caps?** Current curves treat unfinished runs as failures. Run budget-aware agents that must select and submit a patch before each cap.
- **Which protocol components improve held-out performance?** No controlled ablation isolates subtraction or development feedback. Compare matched tasks with altered feedback access and starting-code completeness.
