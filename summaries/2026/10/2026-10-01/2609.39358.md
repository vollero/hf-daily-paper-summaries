# Working Around the Compute Ceiling: Byte-Exact Memory in Galahad Makes LLM Reading a One-Time Cost LLM Reading a One-Time Cost

> [← Daily summary](../2026-10-01.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.39358) · [arXiv](https://arxiv.org/abs/2609.39358)


## One-sentence takeaway
Galahad reports exact persistent KV reuse and faster document answering with section retrieval, but efficiency depends on runtime and cache settings, and its strongest accuracy comparison uses a context-truncated baseline (§§3–4).

## Problem and motivation
Repeated questions about the same documents repeatedly incur prompt processing costs. The authors identify a persistence gap: engine-local caches can be evicted or lost on restart, while existing offloading approaches do not necessarily require exact reuse. Galahad aims to charge computation primarily for previously unseen text without changing model weights or increasing the model’s computational capacity (§§1, 6–7).

## Approach and contributions
- **Taliesin:** Stores model KV state under fingerprints of input bytes, model and tenant; restores whole blocks when token positions match. Failed checks trigger recomputation (§§2.1–2.2, 5).
- **Blaise:** Keeps exact document text, selects a section on the CPU and supplies that section to the model. Its selection algorithm is undisclosed; the evaluated mode selects outside the model (§2.3).
- **Integrated system and validation:** A shared library connects to vLLM, SGLang and llama.cpp. Contributions include restoration-exactness checks and separate measurements of KV persistence and section selection (§§1, 3–4).

The authors position exact acceptance checks and persistence across process lifetimes as differentiators. The supplied text does not establish novelty over competing systems through direct performance comparisons (§6).

These author-reported results support exact restoration in specified tests and substantial savings in selected repeated-document workloads. They do not establish universal output equivalence across all supported models or uniformly faster KV loading. The recall accuracy gains also reflect access to text unavailable to the truncated baseline; they do not isolate memory effects under equal information access.

## Limitations and validity risks
- **Author-disclosed:** Storage format, Blaise internals and security implementation details are withheld because of pending patents. Raw logs and an accompanying dataset are promised (§§1, 8).
- **Author-disclosed:** Blaise was developed on the hidden-fact test. On unseen sources it reduces accuracy relative to Taliesin-only; upstream PDF extraction can remove answers entirely (Table 2 footnote, §4.2, Table 3).
- **Analyst inference:** Retrieval comparisons remain incomplete: RAGFlow uses a different GPU, lacks latency/energy results, and no Blaise-only row isolates its contribution from Taliesin (§4.1, Table 2).
- **Analyst inference:** Named benchmark sources do not establish standard benchmark performance. Question construction and scoring details for the seven-source sample are insufficiently specified (§4.2).
- **Analyst inference:** Generalization is uncertain: all experiments were run by the developer-founder, real-world evaluations have one run per runtime, and broad compatibility tests check operation rather than full logit identity (§4.4, Disclosure).
- **Analyst inference:** Claims of attending to the whole corpus need clarification: llama.cpp averages 53,219 prompt tokens/question despite the 96,726-token corpus; request assembly and block handling are not fully explained (§4.1).

## Open research questions
1. **How much does persistence save under equal context access?** The principal baseline is truncated. Compare full-corpus recomputation, engine caching and Taliesin with matched hardware, context and cache policies.
2. **When does Blaise lose answer-bearing sections?** Held-out accuracy drops and the selector is undisclosed. Measure section-selection recall and downstream accuracy, including a Blaise-only condition.
3. **How broadly does exactness survive serving changes?** Compatibility coverage exceeds full-logit validation. Repeat fresh-versus-restored logit comparisons across models, batching, precision and hardware configurations.

## Confidence and missing information
**Confidence: medium.** The supplied text gives concrete settings and useful component comparisons, but all evidence is author-reported.

Material missing information includes Blaise’s algorithm, storage and verification internals, full model lists, seven-source question/scoring protocols, detailed request assembly, uncertainty estimates for most results, published raw logs, and matched comparisons against other persistent KV systems.
