# QuantCode Model: Specializing Language Models for Executable Algorithmic Trading Code

> [← Daily summary](../2026-10-06.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.39420) · [arXiv](https://arxiv.org/abs/2609.39420)


## One-sentence takeaway
Validated strategy SFT after domain pretraining substantially improves executable Backtrader code generation, but specialization damages structured tool calling, and recovery training restores formatting without recovering base-model repository performance (§§4.1–4.4).

## Problem and motivation
Trading-code generation requires more than valid Python: implementations must use framework APIs correctly, execute, produce trades, and preserve the requested strategy. The authors investigate whether framework-code pretraining and validated request-to-code SFT improve these distinct capabilities, while retaining the tool-use behavior needed by deployed agents (§1).

## Approach and contributions
- **Sequential specialization study:** Compare base → domain pretraining at two Qwen model scales, and base → domain pretraining → SFT for Qwen3.6-35B-A3B. Pretraining uses approximately 5–6B tokens of filtered, MinHash-deduplicated trading repositories (§§3.2–3.3).
- **Executable target construction:** Build approximately 800 request-to-Backtrader-code pairs from Reddit, StackExchange, and GitHub material, with agent-generated, validated implementations. The contribution is target construction and validation, rather than a new SFT objective (§3.4).
- **Capability-retention evaluation:** Add a repository issue-resolution track and investigate malformed tool calls through weight merging and trajectory recovery SFT. This separates parser compatibility from effective agent behavior (§§3.6–3.7, 4.4).

QuantCode-Bench itself comes from earlier work; this report contributes the training study and additional evaluations (§1).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Pretraining improves single-turn semantic success at both scales | On 400-task QuantCode-Bench with greedy decoding and GPT-5.4 judging: Qwen3.5-397B-A17B Judge Pass **41.5% → 47.5%**; Qwen3.6-35B-A3B **27.8% → 33.0%**, each against its own base | §3.5; §4.1, Table 2 |
| Subsequent SFT improves execution and semantics | Same single-turn setting, Qwen3.6-35B-A3B pretrained → pretrained+SFT: Backtest **53.8% → 83.5%**, Trades **36.8% → 60.0%**, Judge **33.0% → 58.2%** | §4.2, Table 2 |
| Pretraining weakens final agentic success despite a better first attempt | Qwen3.6-35B-A3B base → pretrained, cumulative Judge Pass: T1 **22.3% → 32.3%**; T10 **47.5% → 32.5%**, with feedback and up to 10 attempts | §4.3, Table 4 discussion |
| SFT improves both agentic endpoints | Same lineage and protocol: pretrained+SFT reaches **58.3% T1** and **79.5% T10**, versus base **22.3%** and **47.5%** | §4.3, Table 4 discussion |
| Formatting recovery does not recover repository performance | Approximately 200 verified repository tasks, reasoning disabled: Qwen3.6-35B-A3B base solves **23.7%**, recovery SFT with 16k sequence limit **16.3%**, and 32k **13.0%** | §§3.6–3.7; §4.4, Table 6 discussion |
| Tool-call recovery is supported qualitatively | Specialized checkpoints and the tested linear merge emit malformed calls; both recovery-SFT variants pass qualitative serving-parser checks. No retained quantitative parse-success rate | §4.4 |

These results support improvements within the reported checkpoint lineages and distinguish executable strategy success from agent-harness compatibility. They do not establish profitability, broad framework transfer, or statistical reliability across training runs. The authors’ explanation that raw-code pretraining damages conversational feedback processing is plausible but explicitly unablated (§4.3).

## Limitations and validity risks
- **Author-stated:** SFT is tested at only one model scale, without an SFT-only baseline; its dependence on prior pretraining remains unknown (§6).
- **Author-stated:** Semantic judging is an automated proxy, and repository-code contamination remains a concern despite excluding benchmark tasks from the SFT request pool (§§3.4, 6).
- **Author-stated:** No profitability, market-regime robustness, transaction-cost, market-impact, or production-risk evaluation is performed (§6).
- **Author-stated:** The evolving internal snapshots lack a complete public reproduction package; repository coverage is limited and still developing (§6).
- **Author-stated:** Recovery initialization and alternative merge ratios are unablated; quantitative parser-validity measurements are missing (§§3.7, 4.4).
- **Analyst inference:** Without reported repeated runs or uncertainty intervals, the stability of the score differences cannot be assessed. Higher first-turn success suggests possible operational savings, but latency and compute savings are not measured.

## Open research questions
1. **Is pretraining necessary for the SFT gain?** The SFT-only condition is absent. Compare base+SFT against pretrained+SFT using identical examples and evaluation (§6).
2. **Can specialization preserve structured tool use?** The proposed forgetting mechanism is untested. Mix instruction/tool-call data into pretraining and separately measure parser validity, argument validity, and task success (§§4.3–4.4).
3. **Why does recovery restore syntax but underperform on repository tasks?** Teacher-policy mismatch, token weighting, and trajectory length remain hypotheses. Compare on-policy and teacher trajectories with matched token budgets and outcome filtering (§5).
4. **Do gains transfer beyond this setting?** SFT scale and framework coverage are narrow. Repeat the sequence at additional scales and on held-out frameworks under frozen, decontaminated evaluations (§§6–7).

## Confidence and missing information
**Confidence: medium.** The supplied text supports the main within-lineage comparisons, but causal explanations and generalization remain uncertain.

Missing information includes public asset availability, frozen dataset/framework versions, seeds and repeated-run uncertainty, exact repository filters, detailed historical-data settings and validation procedures, recovery-data size and full training configuration, and quantitative parser-success rates.
