# Unsupervised Tool Evolution for Coding Agents in Data-Lake Analytics

> [← Daily summary](../2026-10-21.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.27327) · [arXiv](https://arxiv.org/abs/2610.27327)


## One-sentence takeaway
TEAL evolves reusable tools and usage guidance without answer labels, improving data-lake analytics under tight action budgets, although its verification checks do not guarantee correctness (§§3.2.2, 4.2).

## Problem and motivation
Coding agents repeatedly discover, clean, and join the same data because they discard intermediate programs after answering each question. This repetition consumes limited action budgets. The authors identify a gap between descriptive catalogs, task-specific code generation, and reusable executable tools backed by persistent data artifacts. Ground-truth validation is expensive, while successful execution alone cannot detect incorrect parsing, table granularity, or joins (§1).

## Approach and contributions
- **Complementary tool discovery:** An Explorer inspects the lake without seeing questions; a Critic diagnoses Worker trajectories. A Toolsmith implements and unit-tests proposals, and a Skill Writer maintains invocation guidance. Evolution changes the library, not model weights; the library is frozen for testing (§§3.1–3.2.1).
- **Label-free rerun verification:** Acceptance checks tool adoption, task completion, step growth, and evidence when answers change. Importantly, inconclusive answer comparisons pass, and one passing rerun suffices. Extra steps are permitted within a tolerance, despite stricter wording in the abstract (§3.2.2).
- **TEAL-Q:** Synthetic questions are drafted from files, hardened, checked through executable solution pipelines, and rewritten. Only questions enter tool evolution; generated answers are not training labels (§3.3).
- **Budget-pressure finding:** The authors report that libraries evolved under tighter budgets transfer effectively to looser deployment budgets, sometimes outperforming libraries evolved directly under those looser budgets (§4.2).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Strong gains under tight budgets | Against the no-library Sonnet-5 Worker, accuracy gains are **22.6/30.4 percentage points** on KramaBench/LakeQA at **10 steps**, and **9.3/21.7 points** at **15 steps**. All four Workers improve on both benchmarks at these budgets. Main curves summarize three test repeats. | §4.2; Fig. 3 description |
| Tighter-budget evolution transfers | Sonnet-5 on LakeQA at **30 deployment steps** scores **68.3%** with a library evolved at **20 steps**, versus **59.6%** baseline and **64.2%** with evolution at **30 steps**. | Abstract; §1.1; §4.2 |
| Execution-only retention can hurt | With the same Worker and **15-step budget**, TEAL exceeds ISE by **5.7 points** on KramaBench; ISE is **10.0 points below baseline** on LakeQA. One retained ISE search tool times out on **121 of 126 test calls**. | §4.3; Table 1 discussion |
| Synthetic questions support evolution | Libraries evolved on **50 synthetic questions per lake** improve Sonnet-5 over baseline and are described as comparable to real-question evolution at **15 steps**, using the same held-out tests; the authors report the same pattern across Workers. Numerical table cells are absent. | §4.4; Table 2 discussion; Appendix D |
| Skills and verification matter | Removing skills causes a larger drop than removing the Explorer; answer-label oracle verification performs comparably to label-free verification. Full solution access enables more targeted tools. Numerical ablation scores are absent. | §4.5; Table 3 discussion |
| Harness transfer is reported | The unchanged OpenHands-evolved library improves Sonnet-5 under Google ADK, Prime Agent, and Codex CLI. Per-harness scores are unavailable. | §4.5 |
| Fewer steps do not imply proportional token savings | On KramaBench at **15 steps**, uncached input per episode falls **37–63%** for Sonnet-5 and the two Gemini Workers; the fixed prompt prefix is approximately **2–3×** baseline length. | Appendix C.2 |

The evaluation uses disjoint questions over the same lakes: KramaBench has 51 training and 53 test tasks; tables-only LakeQA has 50 training and 80 test tasks (§4.1). “Accuracy” means LakeQA’s deterministic score or KramaBench’s mixed exact-match/partial-credit score.

These results support useful reuse within an already accessible lake. They do not establish transfer to unseen lakes, guaranteed correctness, or quantified equivalence between verification methods. Many referenced tables and plots lack their actual values in the supplied text.

## Limitations and validity risks
- **Author-stated overhead:** Longer tool/skill prompts increase input tokens; reasoning per step also tends to increase. Cost estimates assume optimal caching and are lower bounds, rather than billed costs (§5; Appendix C.2).
- **Analyst inference—permissive acceptance:** Inconclusive answer comparisons pass, and only one rerun must succeed. A retained change therefore need not improve every motivating question or be correct (§3.2.2).
- **Analyst inference—limited generalization scope:** Tests cover new questions on the same lakes; LakeQA excludes direct non-table reasoning. Cross-harness transfer does not establish cross-lake transfer (§§3.1, 4.1, 4.5).
- **Analyst inference—comparison limits:** Existing agents retain their original, differing budgets and configurations, so those comparisons are not uniformly resource-matched (§4.3).
- **Evidence gaps:** Three test repeats are reported, but variation across independent evolution runs is not established. Total offline evolution cost and numerical ablation results are unavailable in the supplied text (§4.2; Appendix A).

## Open research questions
1. **How often does verification accept harmful changes?** Inconclusive comparisons and single-rerun acceptance leave this unresolved. Next experiment: audit accepted/rejected changes with held-out labels and compare stricter acceptance rules (§3.2.2).
2. **Which evolution budget offers the best total cost–accuracy trade-off?** Tighter budgets help, but full offline costs are unavailable. Next experiment: sweep evolution budgets while measuring construction cost, deployment cost, and amortization across question volumes (§4.2; Appendix C).
3. **Can libraries remain useful as a lake changes?** Frozen, same-lake evaluation does not test artifact freshness. Next experiment: add or modify files and compare frozen libraries with incremental rebuilding (§3.1; Appendix A).
4. **How dependent is TEAL-Q on seed quality?** Synthetic evolution is promising, but seed-selection effects are not quantified. Next experiment: vary seed diversity and quantity while holding generation and evolution budgets fixed (§§3.3, 4.4).

## Confidence and missing information
**Confidence: medium.** The method and headline findings are clearly described, but numerical table bodies, plotted uncertainty values, complete ablation scores, seed-question details, independent evolution-run variability, total offline costs, and public release information are unavailable in the supplied text.
