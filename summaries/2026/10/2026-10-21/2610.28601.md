# Evolving Agent Interfaces

> [← Daily summary](../2026-10-21.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.28601) · [arXiv](https://arxiv.org/abs/2610.28601)


## One-sentence takeaway
Agent S4 evolves reusable computer-use interfaces from ungraded synthetic trajectories, improving a fixed model’s benchmark performance, although gains over the seed repository are smaller than comparisons against a different harness suggest.

## Problem and motivation
Human-designed computer-use interfaces require manual maintenance and can force agents into inefficient actions, such as editing cells individually or reading program output through screenshots. The authors argue that reusable skills composed from fixed actions cannot expand the underlying observation and action space; interface design itself should therefore become an agent capability (§1).

## Approach and contributions
- **Evolve interfaces and usage knowledge together.** A meta-agent examines synthetic-task trajectories without success labels and edits a persistent repository containing executable operations, documentation, and workflows. Repositories stay frozen during task execution (§§2–3).
- **Separate construction evidence from selection evidence.** Population search uses mutation, crossover, and validation-based tournament selection. The meta-agent sees training trajectories but cannot access validation instructions, trajectories, diagnostics, or scores (§3).
- **Evaluate interface evolution and its mechanisms.** Experiments compare seed and evolved repositories, population and linear search, and construction with or without a scratch VM. Analyses illustrate structured browser access, application operations, and verification helpers (§§5–7; Appendix B).

“Verifier-free” describes the construction trajectories: repository selection still requires scored validation tasks (§3.3).

## Evidence and main results
| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Evolution improves the seed on OSWorld V2 | Across 108 tasks, Qwen3.8-27B in Prime Agent improves from **19.44% to 21.30% binary success** and **44.90% to 46.90% partial score** with population evolution without a scratch VM. | Table 4; §7.1 |
| Larger improvement against Qwen CUA includes a harness change | Qwen CUA obtains **5.56% binary**, **20.69% partial**, and **$1.39/task**; the evolved repository without scratch VM obtains **21.30%**, **46.90%**, and **$1.10/task**. Qwen CUA uses GUI control; Prime Agent exposes persistent code execution. | Table 2; Appendix A.2 |
| Reported frontier comparisons favor binary success and model-call cost | On full OSWorld V2, evolved Qwen obtains **21.30% binary at $1.10/task**, versus externally reported GPT-5.5 **13.00% at $25.50** and batched Opus 4.8 **20.60% at $72.40**. | Table 2; §§4–5 |
| Scratch access and population search show metric-dependent differences | With scratch VM, population and linear evolution both reach **19.44% binary**; partial scores are **51.06% versus 47.17%**. Population without scratch VM has higher binary but lower partial score. | Table 4 |
| Separate evolution improves ScienceBoard over the seed | Across 169 tasks, seed success is **55.03% (93 tasks)** and evolved success **58.58% (99 tasks)**; Qwen CUA obtains **41.4%**. Average model calls fall from **61.7 to 58.9** for seed versus evolved. | Table 3; §6 |
| Aggregate efficiency does not show uniform acceleration | Across 108 OSWorld V2 tasks, mean tool calls are **163.2 seed versus 162.1 evolved**. On the **11 jointly full-credit tasks**, calls increase from **87.8 to 103.2**. | Table 6; Appendix B.2 |

The strongest evidence for evolution itself comes from seed-versus-evolved comparisons within Prime Agent. Comparisons with Qwen CUA also change execution access and harness. ScienceBoard demonstrates a fresh search in another domain, rather than transfer of the OSWorld-evolved repository (§6). Qualitative examples support plausible mechanisms but do not isolate individual helpers’ causal effects.

## Limitations and validity risks
- **Selection and final evaluation overlap:** Each full benchmark includes its validation tasks. **Analyst inference:** reported full-set scores are not entirely independent of repository selection (§4; Appendix A.2).
- **Unequal comparison settings:** External OSWorld results use reference harnesses and a 500-step budget; Prime Agent uses 300 assistant responses that may contain multiple actions. These are not matched model-and-harness comparisons (Appendix A.2).
- **Incomplete cost accounting:** Reported costs exclude repository construction and infrastructure and assume an 80% input-cache hit rate (§4; Appendix A.2).
- **Run variability:** The authors show that repeated ScienceBoard validation changes repository rankings; OSWorld validation is not repeatedly denoised because of cost (§§4, 7.3). Full-evaluation uncertainty and repeated independent searches are not established in the supplied text.
- **Mechanism attribution:** Repository changes combine code and knowledge. Population-versus-linear comparisons also change parent selection and crossover together, leaving their separate contributions unresolved (§§3, 7.1).
- **Configuration ambiguity:** Although the model and harness are described as fixed, the builder prompt permits editing context-compaction configuration. Whether evolved candidates changed it is unclear (Appendix C.1).
- **Coverage limitation:** The supplied source is truncated, including a substantial middle omission; this analysis does not imply complete paper coverage.

## Open research questions
- **Do gains persist on tasks untouched by selection?** Final sets include validation tasks. Next experiment: report a strictly separate test partition with repeated evaluations.
- **Which repository components produce the gains?** Code and usage knowledge evolve jointly. Next experiment: ablate executable additions, documentation changes, and configuration changes separately.
- **Does population search reliably outperform linear search?** Reported differences depend on the metric, and independent search replication is not established. Next experiment: repeat matched-budget searches with and without crossover.
- **When does evolution repay its construction cost?** Current cost comparisons omit search and infrastructure. Next experiment: measure total cost amortized over increasing numbers of deployment tasks.

## Confidence and missing information
**Confidence: medium.** Core methods and reported results are explicit, but interpretation is constrained by source truncation and evaluation design.

Material missing information includes independent-search variability, full-test confidence intervals, results excluding validation tasks, total evolution cost, component-level ablations, cross-model repository transfer, and whether compaction settings actually evolved.
