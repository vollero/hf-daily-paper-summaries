# EdgeKernelBench: Unified LLM-Driven Kernel Generation for Edge Backends

> [← Daily summary](../2026-10-21.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.24648) · [arXiv](https://arxiv.org/abs/2610.24648)


## One-sentence takeaway

EdgeKernelBench evaluates LLM-generated edge kernels through a shared compiler interface, while its layered agent LEKA outperforms a budget-matched coding agent on a small, three-backend evaluation subset (§5.3).

## Problem and motivation

Edge kernel development must accommodate fragmented hardware, backend-specific programming rules, and limited memory and compute. The authors identify a gap between existing evaluations focused on server GPUs or individual mobile operators and deployment workloads requiring cross-operator optimization and graph-level planning (§1).

The central difficulty is preserving correctness while coordinating algorithms, fusion, scheduling, and memory decisions as program scope grows.

## Approach and contributions

- **Benchmark and deployment framework:** EdgeKernelBench contains 331 canonical PyTorch tasks spanning basic computations, composed operators, and compact model graphs. A shared IR expresses computation, scheduling, and memory decisions; backend adapters handle lowering and deployment (§§3.1–3.2).
- **Layered optimization agent:** LEKA assigns graph, scheduling, and target-source optimization to separate agents. A shared candidate tree preserves alternatives and lineage, while a hardware-sensing agent routes measured bottlenecks to the relevant layer (§4; Appendix F.2).
- **Cross-backend evaluation:** The TVM-based implementation evaluates five one-shot models over 650 task instances and compares iterative agents on a stratified subset. The contribution combines existing compiler infrastructure with a shared evaluation contract and layered agent search (§5.1).

## Evidence and main results

Fast@1.0 counts tasks with correct outputs, valid timings, and median paired speedup above one over the specified baseline (§5.1).

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Correctness substantially exceeds performance success | Across 650 one-shot instances, the strongest model achieves 73.5% Compile@1, 64.5% Correct@1, and 25.5% Fast@1.0 against tuned TVM. | §1 |
| Larger graphs remain difficult | Highest one-shot Fast@1.0 across backend/model configurations falls from 51.0% at Level 1 to 16.2% at Level 2 and 4.0% at Level 3, against TVM. | §5.2.1 |
| LEKA improves over direct generation | On 69 instances using GLM-5.3-Flash, Correct@1 rises from 42.0% to 100.0%; Fast@1.0 against TVM rises from 13.0% to 43.5%. | §5.3.1; Fig. 6 |
| LEKA beats the matched coding-agent baseline | Same base model, evaluator, task contracts, and time budgets: Fast@1.0 against TVM is 43.5% versus Claude Code’s 26.1%; geometric mean speedup relative to Claude Code is 3.8×. | §5.3.1; Appendix B.4 |
| Production-engine gains concentrate on simpler tasks | Against TensorRT on supported CUDA tasks, highest one-shot Fast@1.0 is 43.2% at Level 1 and 5.3% at Level 2; no Level 3 candidate wins. | §5.2.2; Appendix C.3 |
| Memory legality is a major failure source | Memory errors constitute 34.0% of pooled one-shot failures, primarily allocation-legality problems rather than insufficient capacity. | §5.2.3; Fig. 5 |

The reported results support LEKA’s effectiveness on the evaluated subset. They do not isolate the causal benefit of layered agents from its other search components or establish generalization to unseen hardware. Timing uses paired measurements, warm-up, synchronization, and stability checks; correctness testing uses three random input seeds (Appendices B.2–B.3).

## Limitations and validity risks

- **Author-stated scope:** Evaluation excludes NPUs and cooperative CPU–GPU execution (Appendix G.1).
- **Analyst inference—limited agent coverage:** LEKA uses one base model and 69 instances, including four Level 3 tasks per backend. Its reported perfect correctness therefore has a narrow demonstrated scope (§5.1; Appendix B.4).
- **Analyst inference—confounded backend comparison:** Each backend uses a different application domain and corresponding shapes, preventing clean attribution of cross-backend differences solely to hardware (§5.1).
- **Analyst inference—mechanism remains unisolated:** No reported ablations separately remove layer specialization, candidate lineage, or hardware-feedback routing.
- **Analyst inference—memory claims exceed aggregate measurement:** Memory optimization is central to the motivation, but aggregate metrics emphasize compilation, correctness, and latency. Case studies demonstrate avoided intermediates, without a benchmark-wide memory-budget evaluation (Appendices D.1, E.2).
- **Evidence availability:** Table 1 and several other tables appear only as captions in the supplied text, limiting inspection of detailed comparisons.

## Open research questions

- **Which LEKA components produce the gains?** Component ablations are absent. Compare layered and single-agent search while matching feedback, candidate retention, and time budgets.
- **Do high-level optimizations transfer to new backends?** Portability is an architectural claim rather than a demonstrated transfer experiment. Reuse optimized upper-layer candidates on a held-out backend and measure adaptation cost.
- **How should agents balance latency and memory?** Aggregate memory trade-offs remain unmeasured. Sweep explicit memory caps and report peak memory, feasibility, and latency.
- **Where should representation boundaries fall?** The authors identify layer organization as future work. Compare alternative layer boundaries and context-sharing policies under matched budgets (Appendix G.2).

## Confidence and missing information

**Confidence: medium.** The supplied text supports the architecture and headline results, but lacks detailed table contents, exact task-specific tolerances, full task inventories, actual optimization costs, repeated-run uncertainty, component ablations, aggregate memory measurements, and confirmed code/data release information.
