# Fewer Tokens, Better Action: GPT-6 Astra Robot Agents with 14% Higher Success Rate but 65% Fewer Tokens

> [← Daily summary](../2026-10-02.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.01939) · [arXiv](https://arxiv.org/abs/2610.01939)


## One-sentence takeaway
Across 700 simulated robot-task instances, the authors report that PyRUA-Lean raises success from 63.1% to 71.7% under equal model-call budgets while reducing input tokens by 65% on instances both agents solve (Table 2).

## Problem and motivation
Robot agents repeatedly invoke a vision-language planner to coordinate primitives, inspect feedback, and recover from failures. Tool calling can accumulate redundant camera images and conversation history, increasing inference overhead. The authors investigate whether executable primitive composition and selective observations can improve success while reducing that overhead over the same underlying robot stack (§1).

## Approach and contributions
- **Interactive execution interface:** PyRUA-Lean exposes existing RPent primitives through a Python robot object. Generated cells compose actions, check outcomes, retry locally, and perform geometric computations; variables and helper functions persist within an episode (§§3.1–3.2).
- **Selective feedback:** Intermediate results stay in the runtime; explicitly printed outputs and requested images return to the planner at cell end. This controls incoming context rather than deleting conversation history (§3.3).
- **Controlled comparison and analysis:** The authors compare complete interfaces using the same planner, primitives, frozen VLA policies, and task instances, then analyze token accounting and ablate policies, guides, and automatic images (§4).

The contribution is the interface and its evaluation, rather than new robot primitives or a newly trained policy; executable robot programs already appear in the related work (§2).

## Evidence and main results
| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Higher overall success | Across 700 instances, tool calling achieves 63.1% versus 71.7% for code: +8.6 percentage points, approximately 14% relative. Both receive 40 calls per episode, or 100 for RoboCasa365 composite tasks, plus a two-hour limit. | Table 2; §§4.1–4.2 |
| Gains across benchmark groups | Tool → code success: LIBERO-PRO 83.0% → 94.0%; RoboTwin 60.0% → 69.2%; RoboCasa365 atomic 78.9% → 86.7%; composite 34.4% → 39.4%. | Table 2 |
| Lower overhead on shared successes | Mean whole-episode calls fall from 17.0 to 8.7 (49%); input tokens from 788k to 276k (65%); estimated cost from $1.63 to $0.74. Counts include cached input and post-success calls. | Table 2; §4.1; Appendix E |
| Fewer calls explain much of the savings | On jointly solved LIBERO-PRO instances, the 4.48× token ratio decomposes into 2.55× fewer calls and 1.76× fewer tokens per call. RoboCasa365 atomic code calls are larger on average. | §4.3; Figure 5 |
| Removing automatic images alone does not reproduce gains | On 200 LIBERO-PRO instances, baseline success falls from 83.0% to 68.5%. On 131 instances all configurations solve, both baseline variants average 1.07M input tokens, versus 222k for code. | Table 8; Appendix G |
| Benefits persist in component ablations | Without VLA policies but with guides, RoboTwin success is 42.8% for tool calling versus 68.8% for code; shared-success mean input tokens are 1.03M versus 316k. | Table 3 |
| Failed attempts narrow some cost advantages | Including failures, the tool-to-code estimated cost ratio is only 1.1× on RoboCasa365 atomic tasks. | §4.5; Appendix E |

These results support the complete interface comparison in the evaluated setting. They do not isolate which feature causes the success gains, establish efficiency across arbitrary task distributions, or demonstrate faster execution. The pooled token reduction is strongly influenced by longer LIBERO-PRO episodes (§4.2).

## Limitations and validity risks
**Author-stated limitations:** Evaluation uses one planner, RPent’s stacks, simulation, and one run per agent per task instance. Other planners, repeated-run variability, physical robots, and execution latency remain untested. Composition, persistent state, and selective feedback are not fully isolated (§5).

**Additional evidence-backed risks:**

- Equal call budgets do not equalize primitive executions: code can perform multiple actions per invocation (§4.1; Table 6).
- Some exclusive successes reflect different VLA outcomes rather than demonstrated recovery advantages (§4.5; Appendix D).
- Shared-success subsets change between ablations, preventing clean component-cost comparisons on a fixed subset (§4.4).
- Baseline descriptions can trigger post-success recipe/audit writes, whose calls count toward reported overhead (Appendix E).

**Analyst inference:** The reported 65% reduction is conditional on shared successes and should not be interpreted as the reduction in deployment-wide spending.

## Open research questions
- **Which interface features drive gains?** The comparison bundles several mechanisms. A factorial experiment independently varying composition, persistent state, and selective feedback could estimate their contributions (§5).
- **How stable are success differences?** Single runs leave variability unresolved. Repeated paired runs on identical task instances could measure uncertainty and separate stochastic policy outcomes (§5; Appendix D).
- **Do token savings translate into faster physical execution?** Latency and physical performance are untested. A robot experiment could measure completion time, recovery, and inference usage together (§5; Appendix E).

## Confidence and missing information
**Confidence: high** in the descriptive summary of the supplied results; **medium** in causal attribution or generalization.

Material missing information includes confidence intervals or significance tests, repeated-run estimates, independent feature ablations, physical-robot results, execution-latency measurements, and verification of the linked repository’s contents.
