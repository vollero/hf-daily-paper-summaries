# Triadic Linear Attention: Three-Dimensional Recurrent States for Long-Context Sequence Modeling

> [← Daily summary](../2026-10-05.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.36529) · [arXiv](https://arxiv.org/abs/2609.36529)


## One-sentence takeaway
Triadic linear attention enlarges recurrent memory through a second key/query pair, improving long-context perplexity and recall in the tested language models with small parameter overhead but higher training cost.

## Problem and motivation
Linear attention compresses context into a fixed-size matrix, limiting how many associations it can retrieve without interference. Enlarging heads, values, or head counts can increase memory but also consume substantial parameter budgets. The authors seek a more parameter-efficient way to expand recurrent memory for long-context language modeling and recall (§§1–2.1).

## Approach and contributions

- **Triadic memory:** Write the outer product of a key, second key, and value into a state of shape \(d\times E\times d\); retrieve values by contracting both key axes with separate queries. This multiplies state size by \(E\) through two additional projections (§2.2).
- **Modern recurrence extensions:** Apply forgetting separately to state slices and extend the delta rule to erase and replace associations addressed jointly by both keys (§2.4).
- **Efficient training:** Factor joint-key interactions and tile the state along the value axis, enabling chunkwise training with custom CuTe kernels (§2.5; Appendix A).
- **Adaptation and hybrid experiments:** Convert pretrained ordinary linear-attention models during context extension and compare enlarging recurrent memory against enlarging attention caches in hybrid models (§§3.3–3.4).

The paper acknowledges earlier third-order tensor memories; its contribution is their integration into modern linear-attention layers and scalable language-model training, rather than inventing higher-order associative memory (§5).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|

| Stronger state-matched GDN results | At approximately 400M parameters and 25.2 MB state, triadic \(E=4\) achieves PG19 16k–64k perplexity **13.79** and recall **31.1%**; alternative enlargements yield **14.24–14.44** and **27.3–28.5%**. Three-seed averages. | Table 1 |
| Gains persist at the larger scale | At the 1.3B scale, scratch-trained GDN \(E=8\) improves PG19 16k–64k perplexity from **10.20 to 9.94** and six-task recall from **36.1% to 44.4%**; parameters increase from **1360.2M to 1378.3M**. Single-seed results. | Table 2 |
| Upcycling recovers part of the gain | At approximately 400M parameters, upcycled GDN \(E=8\) reaches long-range PG19 perplexity **13.86** and recall **29.7%**, versus base **14.15 / 26.2%** and scratch-trained triadic **13.74 / 33.1%**. Three-seed averages. | Table 2 |
| Hybrid memory allocation improves perplexity and NIAH | In the 400M hybrid comparison, triadic memory versus enlarged KV cache gives PG19 4k–64k perplexity **13.39 vs 13.47**, RULER-NIAH average **56.3% vs 53.0%**, and state at 64k **220 vs 407 MB**; recall is lower, **44.5% vs 45.3%**. Three-seed averages. | Table 3 |
| Training overhead accompanies long-context speed gains | For one 1.3B-model block, batch size 4 on one H100, \(E=8\) adds **28–30%** forward/backward time over GDN but is **5.1 times faster** than the tested Transformer implementation at 64k. | §3.5, Fig. 4 |

Recall scores average six tasks, with correctness determined by whether generation contains the answer. Table 3’s NIAH score averages eight tasks across context lengths from 1k to 64k (Appendix D).

These results support improved memory use within the tested training regimes. They do not establish universal Transformer superiority or end-to-end deployment speed. State-matched comparisons also preserve different MLP capacities: some alternative enlargements shrink the MLP to meet the parameter budget (§3.2).

## Limitations and validity risks

- **Author-stated:** Larger states slow training; some recall tasks still favor Transformers; only GDN and sGLA receive the triadic construction (§4).
- **Analyst inference:** Parameter matching changes MLP width for several baselines, so Table 1 measures the resulting architecture tradeoff rather than isolating memory addressing alone (§§3.1–3.2).
- **Analyst inference:** Larger-scale Table 2 results use one seed, limiting evidence about variability. Smaller-scale tables report averages without numerical uncertainty estimates.
- **Analyst inference:** Timing uses individual blocks and different kernel implementations; full-model training cost and autoregressive decoding performance remain unestablished (§3.5).

## Open research questions

- **Does the advantage persist under matched compute?** Table 1 matches state and parameters, while triadic training costs more. Train competing enlargements with equal accelerator-time budgets and compare perplexity and recall.
- **How far can the construction scale?** Evaluation stops at the reported model scales and contexts through 64k. Test larger models and longer contexts while tracking recall saturation and memory cost.
- **How much benefit comes from slice-specific forgetting?** The fixed-state factorization ablation uses one gate per head, but does not directly isolate gating at an otherwise identical configuration. Compare scalar and per-slice gates with the same key dimensions and training setup.
- **Can staged enlargement close the upcycling gap?** Upcycled models improve but trail scratch-trained triadic models. Compare gradual enlargement and longer adaptation under matched total training budgets (§3.3).

## Confidence and missing information
**Confidence: high** in the reported method and tabulated comparisons; **medium** in broader generalization.

Material gaps include numerical uncertainty estimates, exact plotted values unavailable in the extracted figures, full-model and decoding benchmarks, results beyond the tested scales and contexts, and confirmation of released checkpoints or repository contents.
