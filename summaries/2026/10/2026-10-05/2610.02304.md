# SimuVerity: Benchmarking Agents for Engineering-Grade Simulink Model Generation

> [← Daily summary](../2026-10-05.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.02304) · [arXiv](https://arxiv.org/abs/2610.02304)


## One-sentence takeaway
SimuVerity evaluates requirement satisfaction through native simulation on 101 Simulink generation tasks, finding that the strongest tested agent system scores 42.86/100 despite delivering models on 94.72% of runs (Table 2).

## Problem and motivation
Generating a model that compiles and runs does not establish that it meets engineering requirements. The authors identify a gap in cross-domain evaluation: existing benchmarks emphasize execution or reference similarity, potentially accepting defective reference-like models and penalizing valid alternative implementations (§1; Appendix A).

SimuVerity instead tests physical mechanisms, control relationships, robustness, and dynamics across prescribed operating conditions.

## Approach and contributions
- **Benchmark:** 101 text-to-executable `.slx` tasks across ten engineering domains. Experts reconstruct reference systems, run them to build executable-system profiles, and derive consistent engineering specifications (§§3.1–3.2).
- **Evaluator:** 595 native simulation scenarios cover operating envelopes, interactions and faults, temporal processes, and mechanism/causal checks. Delivery, executability, and engineering-qualification gates precede six-dimensional scoring; task-specific weighted geometric aggregation penalizes critical weaknesses (§§3.3–3.4; Table 7).
- **Empirical diagnosis:** Six model-plus-harness systems are evaluated over three runs per task, with additional analyses of structural diversity, diagram readability, expert agreement, and tool access (§4; Appendices C–G).

The contribution is a benchmark and evaluation framework, rather than a new generation agent.

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Engineering performance remains limited | Across 101 tasks and three runs per task, Opus 4.8 + Claude Code scores 42.86, GPT-5.5 + Codex 41.72; reference systems average 96.01. | Table 2 |
| The top pair is statistically unresolved | Opus–GPT paired difference: 1.13 points, task-bootstrap 95% CI [−5.80, 7.68], Wilcoxon p=0.86. | Table 14 |
| Execution success exceeds qualification | Opus delivers on 94.72%, executes on 86.47%, and passes engineering qualification on 76.90% of task-runs. | Table 2 |
| Qualification leaves substantial weaknesses | Opus post-G output quality is 82.21, versus robustness 60.73 and dynamics/recovery 58.65; dimensions average over their applicable tasks. | Table 3 |
| Structural proximity does not reliably rank quality | Among 95 delivered Opus Run 1 models, reference-aligned and structurally distinct post-G means are 59.80 and 61.20; seven reference-aligned models score zero. | §4.3; Table 4 |
| Evaluator rankings agree with sampled experts | For 30 stratified Opus Run 1 candidates, evaluator–mean-expert Spearman ρ=0.94, 95% CI [0.88, 0.98]; for 18 nonzero candidates, ρ=0.88. | Appendix C.4; Table 11 |
| Tool restrictions sharply reduce selected-task performance | On ten tasks selected for strong Full MCP performance, three-run mean scores are 78.46 with Full MCP, 7.88 without simulation, and 18.23 with batch-only access. | Tables 5, 16; Appendix G |
| High engineering scores can coexist with poor layouts | Experts judge eight of 31 Opus Run 1 models scoring at least 70 severely disordered; layout-only reorganization removes overlap in all eight. | §4.5; Table 22 |

These results support separating artifact execution, engineering qualification, and subsequent performance. They also demonstrate valid structural alternatives within the tested tasks. They do not establish industrial deployment readiness, a definitive winner between the top systems, or universal tool benefits outside the selected ablation subset.

## Limitations and validity risks
- **Author-stated:** Evaluation depends on MATLAB/Simulink, and native simulation can be slow (§5).
- **Analyst inference—system comparisons:** Results evaluate model-plus-harness combinations. GPT uses Codex while the others use Claude Code; model capability cannot be isolated from harness effects (Appendix D.1).
- **Analyst inference—selected analyses:** Expert validation, structural analysis, and readability inspection use Opus Run 1 candidates. Tool ablations use ten tasks selected for strong baseline performance, limiting generalization (§§3.4, 4.3–4.6).
- **Analyst inference—coverage:** Finite expert-designed scenarios establish behavior under tested conditions, not exhaustive correctness or real-world physical fidelity (§3.3).
- **Analyst inference—resource comparability:** Runs stop when agents declare completion; the supplied text provides no common time/token budget or cost and runtime measurements (Appendix D.1).
- **Analyst inference—scoring dependence:** Experts set task-specific utilities and weights. Alternative aggregation checks support broad ranking stability, but do not establish robustness to every threshold or metric choice (Appendix C.3; Table 15).

## Open research questions
- **Do simulation benefits generalize to difficult tasks and other agents?** The ablation covers one system’s selected strong tasks. Repeat it on a randomly sampled, difficulty-stratified subset across systems.
- **How much do harnesses affect engineering performance?** Current comparisons combine model and harness. Run compatible models across matched harnesses with fixed resource budgets.
- **Can models pass formal scenarios yet fail nearby conditions?** Evaluation uses finite prescribed tests. Add withheld perturbations and adversarial operating conditions, then measure performance retention.
- **Can agents produce readable diagrams without sacrificing engineering quality?** Readability improvements here are expert layout interventions. Compare automated layout methods using both native performance checks and blinded readability ratings.

## Confidence and missing information
**Confidence: high** for the reported benchmark design and numerical findings; **medium** for broader generalization.
