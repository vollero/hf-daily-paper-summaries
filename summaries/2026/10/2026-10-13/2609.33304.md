# Relevance Does Not Imply Applicability: Experience Activation for Personal GUI Agents

> [← Daily summary](../2026-10-13.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2609.33304) · [arXiv](https://arxiv.org/abs/2609.33304)


## One-sentence takeaway
ExpActivator improves personalized GUI action prediction and proactive suggestion on AndroidIntent by selecting historical actions for the current screen and gating recurring intents by time and scenario, without training the encoders or policy (§§2–3).

## Problem and motivation
Personal GUI agents must recover omitted preferences from interaction history and recognize when recurring routines warrant a suggestion. The authors identify a gap between **task relevance** and **decision-time applicability**: a retrieved trajectory may identify the right application without identifying the action appropriate for the current screen, while a familiar routine may be inappropriate now (§1).

Their experiments find that existing history mechanisms mainly help the opening application decision, with much weaker benefits during subsequent interface interactions (§3.3).

## Approach and contributions
- **Step-level activation:** Retrieve task-relevant trajectories using goal embeddings, then match each current screenshot against historical states using centered, spatially pooled features from the frozen GUI backbone. Supply the matching historical action as a reference that the policy can adopt, adapt, or reject (§2.2).
- **Task-level activation:** Group similar historical intents into overlapping routine neighborhoods. Require sufficient total, same-scenario, and time-weighted support; rank eligible routines by normalized contextual support and abstain when none qualifies (§2.3).
- **Controlled diagnosis:** Separate opening from subsequent decisions and compare selecting versus appending the same history, plus current versus stale screen matching. These experiments support decision-time selection rather than simply adding more historical context (§§3.3–3.4).

The fixed-history ablations support the value of selecting and refreshing references. Cross-backbone results support transfer across the tested frozen policies. They establish recorded-action prediction performance, rather than live task completion: evaluation uses recorded screens and benchmark action prefixes, and CSR is an early-step-weighted score rather than an episode completion rate (Appendices C.2–C.3, D.1). Lower prompt-token cost does not establish lower total latency or compute.

## Limitations and validity risks
The supplied text contains no dedicated author limitations section. The authors do document a coverage constraint: stricter repetition requirements leave more queries without eligible routines (Appendix E).

**Analyst inferences:**

- Generalization beyond AndroidIntent remains untested; all reported evaluations use one mobile benchmark (§3.1).
- Recorded-screen evaluation does not establish resilience to errors that change subsequent screens or action histories (Appendices C.2, D.1).
- Proactive selectivity remains imperfect: activation before verbalization has a **37% false-alarm rate** at the declared operating point (Appendix E).
- LLM-UM profiles were regenerated because the original profiles were unavailable, limiting comparison with that original implementation (Appendix C.4).
- Visual matching adds encoding and search work, but measured runtime, storage, and total compute comparisons are absent (Appendix A.2).

## Open research questions
- **Do gains survive agent-induced errors?** Recorded inputs do not test recovery. Run live episodes using each policy’s own actions and measure completion and recovery.
- **How robust is activation to interface changes?** Matching is evaluated on historical and target screens from one benchmark. Test application-version shifts and altered layouts.
- **Can sparse or changing routines support reliable suggestions?** Eligibility requires repeated observations. Evaluate progressively shorter histories and changing habits, measuring coverage and false alarms.
- **Does token reduction improve actual efficiency?** Additional visual encoding is required. Measure end-to-end latency, GPU use, and storage against the same baselines.

## Confidence and missing information
**Confidence: high** in the reported method and benchmark findings; external validity remains uncertain.

Material missing information includes public code/run-artifact availability, live rollout results, measured latency and storage costs, and evaluation beyond AndroidIntent. Several supplied tables contain captions without their bodies, including Tables 2, 7, and 12, so some detailed comparisons and intervals cannot be independently checked from this text.
