# SPLATIFY: Reproduce, Discover, Innovate! From Papers and Ideas to Trainable 3DGS Code

> [← Daily summary](../2026-10-13.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.09116) · [arXiv](https://arxiv.org/abs/2610.09116)


## One-sentence takeaway

Splatify combines domain-constrained agent code generation, repository dependency recovery, and rendering feedback to reproduce and improve 3D Gaussian Splatting methods, with reported expert-level fidelity but incomplete detailed results in the supplied text.

## Problem and motivation

Reimplementing 3DGS papers requires coordinating rendering, Gaussian attributes, optimization, and density control across incompatible repository forks. The authors argue that generic paper-to-code systems lack this domain knowledge and produce code that fails during training (§1).

Their broader motivation is to make published techniques composable: faithful reproduction alone does not identify useful combinations or adapt rendering assumptions to new physical domains (§§1, 3.1).

## Approach and contributions

1. **Constrained implementation template.** A context-free grammar specifies valid gsplat/Nerfstudio plugins with nine extension points. Agents fill relevant hooks while inheriting the training and rendering skeleton; the grammar also supplies verification contracts (§3.2).
2. **3DGS-specific reproduction pipeline.** Retrieval selects verified paper-code examples; citation resolution extracts function-level changes from repository forks; Graph-of-Thought generation follows dependency order. Smoke tests, Gaussian structural checks, rendering critiques, and PSNR trajectories guide repairs (§3.3).
3. **Compositional search.** Explorer agents mutate combinations of losses, densification, appearance, anti-aliasing, and schedules, using staged training to filter candidates (§3.4).
4. **Cross-domain synthesis.** Agents retrieve external physical priors and generate domain-specific modifications, demonstrated for nebulae and iridescent bubbles (§4.5.2).
5. **Splatify-Bench.** A benchmark separates papers without code, papers with public code, and papers selected for component-level novelty evaluation (§4.1).

The authors explicitly build on Nerfify’s reproduction architecture; their claimed additions center on fork recovery, Gaussian-specific verification, compositional improvement, and cross-domain synthesis (§2).

## Evidence and main results

All findings below are author-reported.

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Close reproduction without public code | Set 1 contains 10 papers; average quality reportedly within ±0.5 dB PSNR and ±0.02 SSIM of commissioned expert implementations. Each paper follows its reported protocol; all automated baselines reportedly fail to produce trainable code. | §4.3.1; Tables 1–2 captions |
| Close reproduction with public code | Set 2 contains 10 papers; average PSNR deviation from original implementations reportedly under 0.3 dB under identical training conditions. | §4.3.2; Table 3 caption |
| Faster implementation | Splatify reportedly takes 10–30 minutes per paper, versus typically 1–2 weeks for expert implementations. What the timing includes is not fully specified. | §§4.2–4.3.1 |
| Strong component preservation | Across 10 Set 3 papers, weighted semantic scores exceed 0.94. Blind human assessment agrees with the LLM judge at κ=0.87 for component labels and Spearman ρ=0.92 for semantic scores. | §4.4; Table 4 caption |
| Compositional gains | Best validated configurations improve PSNR by up to 2.4 dB over reproduction-only implementations on Set 1/2 scenes. Uniform random search reportedly uses 8× the tokens for one-quarter of the PSNR gain; detailed aggregates are unavailable. | §4.5.1; Table 5 caption |
| Nebula improvement | On planetary-nebula imagery with 157 training and 23 test views, NebulaGS obtains 32.52 dB PSNR / 0.914 SSIM versus vanilla 3DGS’s 31.19 dB / 0.862. | §4.5.2, Scenario 1; Fig. 5 |
| Bubble improvement with speed cost | BubbleGS obtains 27.81 dB PSNR / 0.869 SSIM / 0.244 LPIPS versus vanilla 3DGS’s 26.97 dB / 0.858 / 0.264. Speed falls from 99.1 to 69.1 FPS; view counts are unspecified. | §4.5.2, Scenario 2; Fig. 5 |
| Components affect trainability | On 10 Set 1 papers, full-system trainability is 100%; removing CFG constraints gives 70%, smoke tests 50%, and Gaussian structural checks 80%. Removing fork recovery lowers correct-component fraction from 1.00 to 0.70. | §4.6; Table 6 |

The reproduction protocol generally uses 30k training iterations, held-out viewpoints, A6000 GPUs, and multiple seeds (§4.2), although Set 1 also invokes paper-specific protocols (§4.3.1). These results support the authors’ claim that domain structure and verification help within the selected benchmark. They do not establish universal paper reproduction, broad physical validity, or independent reproducibility: Tables 1–5 contain captions but no result cells in the supplied text.

## Limitations and validity risks

- **Author-stated adaptation requirement:** Extending the system to another framework requires a new grammar and curated verified paper-code pairs (§5); transfer is proposed rather than evaluated.
- **Analyst inference—selection scope:** Set 2 explicitly selects gsplat-portable methods, limiting evidence for methods requiring unsupported renderer or backend changes (§4.1).
- **Analyst inference—contamination claim:** Absence of public implementations does not itself prove that all relevant implementation knowledge was absent from model training; the authors’ claim of uncontaminated evaluation is stronger than the supplied evidence (§4.3.1).
- **Analyst inference—search validity:** §3.1 describes held-out-view improvement, but §3.4 ranks candidates on training views. The separation between search selection and final testing is insufficiently explained.
- **Analyst inference—physical validation:** Image metrics and code verification do not establish physical correctness. NebulaGS retains the rasterizer despite motivating the method through a mismatch with alpha compositing (§4.5.2).
- **Reporting inconsistencies:** §4.5.2 announces three domains but describes two. §4.6 calls CFG removal the largest trainability impact, although Table 6 shows a larger drop without smoke tests.
- **Reproducibility status:** Code and data release are promised; availability is not established by the supplied text (§5).

## Open research questions

1. **Do compositional gains generalize beyond search scenes?** Training-view ranking leaves generalization unclear (§3.4). A next experiment could freeze discovered configurations and evaluate untouched scenes with a separate validation split.
2. **How much performance depends on seed-library overlap?** Retrieved verified implementations are central, but leave-family-out results are absent (§3.3.1). A next experiment could remove examples sharing each target’s technique family and measure trainability and fidelity.
3. **Are cross-domain methods physically faithful?** The demonstrations measure rendering quality rather than recovered physical quantities (§4.5.2). A next experiment could use controlled scenes with known emission or film thickness and ablate each physical modification.

## Confidence and missing information

**Confidence: medium.** The pipeline and headline claims are clear, but detailed verification is limited.

Material omissions include Tables 1–5 result cells, supplementary per-scene results, full grammar and extension-point definitions, exact seed counts and uncertainty estimates, prompts and repair/search budgets, API costs, cross-domain data provenance and bubble splits, and release artifacts.
