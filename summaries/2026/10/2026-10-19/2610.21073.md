# Skip the Compressor: Coding Agents Fix More Issues When They Pick Whole Files

> [← Daily summary](../2026-10-19.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.21073) · [arXiv](https://arxiv.org/abs/2610.21073)


## One-sentence takeaway
On 300 Python SWE-rebench issues with matched per-issue context budgets, CQ2-CARE’s selected verbatim files outperform the tested general compressors and retrievers, but its small lead over trained function retrieval does not establish superiority (Table 1).

## Problem and motivation
Repository code exceeds coding models’ context budgets, yet successful patches need both the relevant files and accurate source text. Retrievers can select code that resembles an issue without containing the fix; token compressors can corrupt lines that edits must match. The authors identify a missing comparison of retrieval, pruning, and file selection under matched per-issue budgets and executable issue tests (§1).

## Approach and contributions
- **CQ2-CARE:** The coding model predicts files from an issue and a ranked path inventory. Agreement between two localization samples selects files, with a single-sample fallback; requested grep searches add supporting spans. Selected source files appear verbatim, subject to size caps (§2; Algorithm 1).
- **Controlled evaluation:** Context methods share a patch-generation pipeline and benchmark grader. Each baseline targets the selector’s realized context size for that issue and model (§§3.1–3.2).
- **Failure analysis:** Gold-file recall and verbatim-line share characterize context quality; corruption and shared-candidate controls probe file selection versus text preservation (§§4.1–4.2). Ablations indicate that selecting few files matters more than sample agreement (§4.4).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Selected files beat general compressors and retrievers | On 300 issues, GPT-5.6 resolves **43.7%**, versus **37.3%** for LongCodeZip and **34.3%** for file-level BM25; Claude resolves **46.7%**, versus **40.3%** for LLMLingua-2 and **34.0%** for the best general retrievers. Budgets matched per issue. | Table 1; §3.3 |
| Trained retrieval is competitive | SweRank resolves **43.0% / 45.0%** versus CQ2-CARE’s **43.7% / 46.7%**, for GPT-5.6 / Claude; neither lead is statistically significant. SWE-Pruner resolves **41.7% / 39.3%**, significantly lower only for Claude. | Table 1; §3.3 |
| Altering source text independently hurts | Deleting **20% of tokens from every line** of CQ2-CARE contexts, with files fixed, lowers GPT-5.6 applicability from **98.0% to 78.7%** and resolution from **43.7% to 34.0%** on 300 issues (**p<0.001**). | §4.2; Table 8 |
| Good candidate selection removes LongCodeZip’s deficit | Compressing the union of CQ2-CARE’s localization draws plus evidence to the same budgets yields **44.7%** GPT-5.6 resolution versus **43.7%** for CQ2-CARE; difference **+1.0 points**, 95% interval **[−2.7, 4.7]**. | Table 8; Appendix G |
| Agreement is not the essential contribution | GPT-5.6 localization F1 is **0.613** for agreement, **0.430** for a single draw, and **0.600** after trimming a single draw to the same file count; the trimmed variant resolves about as many issues with both models. | §4.4 |

The evidence supports careful file selection and source fidelity in this single-call setting. It does not establish that whole files universally beat whole functions or code-aware pruning: SweRank is close, and LongCodeZip performs comparably when supplied the selector-derived candidates.

## Limitations and validity risks
- **Author-stated scope:** One benchmark, Python repositories, and one patch call; agents cannot reopen files or run tests during generation.
- **Comparison design:** Budgets come from CQ2-CARE’s operating point. Matching is approximate; several baselines and the mechanism analyses were added after the main results. The written plan was not preregistered (§2; Appendix D; Limitations).
- **Sampling uncertainty:** Most settings use one patch sample. Authors report substantial outcome changes under resampling and flag small gaps as fragile (Limitations).
- **Contamination:** Model training overlap is unknown; SweRank may have seen other pull requests from evaluated repositories, and some repositories may have appeared during selector development.
- **Analyst inference:** Gold-file recall measures whether any span from a gold file appears, not whether all necessary code is visible. Changed-line coverage helps diagnose this, but its estimator required a post-hoc adjustment after underpredicting SweRank (Appendix H).
- **Implementation boundary:** “Whole files” can be truncated or skipped under size caps; the method also includes supporting spans (Appendix B).

## Open research questions
- **Can rereading recover compression losses economically?** The paper excludes interactive recovery. Compare full agent loops under equal total token, tool-call, and cost budgets (§5).
- **Which context unit works best under externally fixed budgets?** Budgets primarily follow CQ2-CARE, and trained function retrieval is close. Compare files, functions, and whole-line pruning across prespecified budgets with shared candidate localization.
- **Does the finding generalize beyond Python?** Evaluation covers one Python benchmark. Repeat the shared pipeline on other languages and repository structures (Limitations).
- **Do the diagnostics predict unseen methods reliably?** The estimator misses SweRank before a post-hoc coverage revision. Freeze both versions and evaluate new context methods on held-out repositories (Appendix H).

## Confidence and missing information
**Confidence: medium.** Main results and controlled tests are explicit, but broader conclusions face narrow scope and sampling uncertainty. The supplied text omits many referenced tables’ numerical bodies, exact prompt templates, the pinned benchmark revision identifier, and confirmation that promised artifacts are available; training overlap remains unknown.
