# OS-Helix: Unifying GUI Interaction and Code Execution in Native Computer-Using Agents

> [← Daily summary](../2026-10-19.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.22234) · [arXiv](https://arxiv.org/abs/2610.22234)


## One-sentence takeaway
OS-Helix learns a unified GUI/code desktop policy through synthetic-task supervision and action-step-balanced reinforcement learning, reaching 66.44% success on OSWorld-Verified versus 46.50% for its matched hybrid backbone (Tables 1, 4).

## Problem and motivation
Desktop tasks combine visual interface interaction with precise manipulation of files and system state. GUI-only agents can struggle with grounding and repetitive operations, while code-only agents lack access to some visual and application-specific behavior.

The authors identify a policy-learning gap: exposing a GUI agent to code does not necessarily teach effective routing between modalities. For example, adding code access to Qwen3-VL-32B-Instruct reduces OSWorld success from 34.17% to 32.68%, although other backbones benefit from code access alone (Table 14). The motivation is therefore to learn coordination rather than assume tool availability supplies it.

## Approach and contributions
- **Unified hybrid policy:** A single multimodal policy selects GUI actions, episode-control actions, or Python/Bash execution. Code runs in fresh processes, with stdout and stderr returned as context (§3.1).
- **Executable task synthesis:** An application–artifact compatibility graph combines versioned applications and file artifacts into reproducible Ubuntu states. An exploration agent proposes grounded tasks; a separate evaluator agent compiles frozen success conditions into rule-based or visual checks (§3.2).
- **Hybrid training:** Teacher-generated trajectories undergo evaluator and quality filtering before SFT. Online RL then uses live desktop environments and rule-based terminal rewards (§3.3).
- **Step-balanced GSPO:** The method averages token log-importance ratios within each action, then averages across actions with equal GUI/code weights. This removes action-length weighting from the sample-level ratio; it does not guarantee equal parameter-gradient norms or correct routing (§3.3.2; Appendix E).
- **Planned research assets:** The authors promise models, environments, pipelines, generated instructions, and filtered/unfiltered supervision; the supplied text does not establish completed release (§1).

| RL adds a smaller aggregate gain after SFT | OSWorld success rises from 62.75% to 66.44%. Paired task-bootstrap RL−SFT difference is reported as +3.68 percentage points, 95% CI [0.93, 8.33]. | Tables 4, 16 |

| Hybrid supervision contributes beyond inference-time access | At a fixed 10K-sample SFT budget and hybrid evaluation harness, hybrid supervision achieves 60.61% versus 57.56% for GUI-only supervision. | Table 5(b) |
| Gains persist after removing benchmark-related application data | Removing nine OSWorld application domains reduces desktop SFT data from approximately 31K to 17K samples; success changes from 62.75% to 62.31%. | Table 3(b) |
| Windows transfer is positive but smaller against the hybrid baseline | With Python-only prompt adaptation and a 50-step budget, WindowsAgentArena success is 56.41% for the hybrid backbone, 57.95% after SFT, and 63.87% after RL; GUI backbone success is 40.82%. | Table 12; Appendix D.1 |
| Repeated-attempt coverage improves | OSWorld Pass@3 rises from 70.88% after SFT to 76.44% after RL; paired-bootstrap gain is +5.56 points, 95% CI [2.24, 8.97]. | Figure 4(b); Table 16 |

These results support learned hybrid behavior and an empirical benefit from step-balanced optimization under the tested configuration. They do not establish optimal modality selection, universal transfer, or safety in deployment. Higher Pass@3 establishes improved repeated-attempt coverage; it does not directly demonstrate greater trajectory diversity.

## Limitations and validity risks
- **Author-stated coverage limits:** Fixed-version applications, curated artifacts, and controlled VMs cannot represent personalized machines or private workflows. Structured cross-application synthesis remains a small prototype (Appendices A, B.4).
- **Author-stated evaluator limits:** Rule checks can reject semantically valid solutions, while visual judges can miss details. Excluding visual rewards from RL restricts training-task diversity; reward-hacking robustness remains unresolved (Appendix A).
- **Author-stated scaling limits:** RL covers only the dense 27B model under constrained compute. MoE RL stability and broader scaling behavior are untested (Appendix A).
- **Observed execution weaknesses:** Case studies show lost unsaved GUI changes during code handoffs and failed preservation of rendered formatting. Windows failures include incompatible command patterns (Appendices D.1, F.5).
- **Analyst inference—attribution:** Controlled ablations support hybrid supervision and the RL objective, but do not separately quantify the contributions of the compatibility graph, exploration memory, and decoupled evaluator generation.
- **Reporting inconsistencies:** Table 2 gives 56.41% for the Windows backbone, while §4.2 describes the larger improvement against a GUI baseline; Table 12 clarifies that GUI is 40.82% and hybrid is 56.41%. Table 16 also differs slightly from rounded main-table differences. The abstract’s “42.9%” improvement refers to the hybrid backbone comparison, not the incremental gain over SFT.
- **Deployment validity:** The authors explicitly state that isolated experiments do not resolve prompt injection, privacy, or unintended code-execution risks (Ethics Statement).

## Open research questions
1. **Does step balancing generalize across model architectures and training scales?** RL is limited to dense 27B. A next experiment could compare standard and step-balanced GSPO across dense/MoE backbones, budgets, and multiple training seeds.
2. **Can evaluators recognize valid alternative solutions without rewarding shortcuts?** Verification brittleness remains unresolved. A next experiment could compare generated judges with independent human judgments on correct, near-correct, and adversarial terminal states.
3. **Can explicit state reconciliation prevent GUI/code handoff failures?** The paper documents unsaved-state loss. A next experiment could test save/reload or conflict-detection mechanisms on tasks with concurrent GUI-resident and disk-side edits.
4. **How robust is transfer beyond controlled Ubuntu states?** Windows requires adaptation and retains command failures. A next experiment could evaluate held-out operating systems, application versions, and user configurations while measuring side effects alongside success.

## Confidence and missing information
**Confidence: high** for the reported methods and benchmark outcomes; **medium** for broad coordination and generalization claims.

Material gaps include confirmed asset-release status, complete teacher-distillation prompts, independently measured evaluator error rates, systematic component ablations for task synthesis, variation across RL training seeds, and deployment-level safety measurements.
