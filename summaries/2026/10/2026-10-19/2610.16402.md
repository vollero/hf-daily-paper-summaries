# EvoWeb: A Benchmark for Coding Agents on Evolving Web Applications

> [← Daily summary](../2026-10-19.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.16402) · [arXiv](https://arxiv.org/abs/2610.16402)


## One-sentence takeaway
EvoWeb evaluates coding agents across persistent web-development trajectories and finds that integrating features across requests is consistently harder than implementing new functionality or delivering earlier functionality.

## Problem and motivation
Web applications evolve through successive feature requests, so agents must extend their own implementations while preserving existing behavior. The authors identify a gap between this setting and benchmarks centered on fixed specifications, specification refinement, or developer-facing software tasks: those settings do not directly measure cumulative, user-facing web-product development with explicit functional dependencies (§§1–2).

## Approach and contributions
- **Benchmark:** 32 applications with ten cumulative requests each, covering 16 application domains. Follow-up features derive from real websites; generated requests, tests, and dependency graphs undergo automated verification, repair, and human curation (§3.1; App. B).
- **Evaluation methodology:** Agents retain the repository and conversation across requests, while a hidden dependency DAG supports cross-request integration tests. Each follow-up has three functional tests, one integration test, and one backward test, executed through a multimodal browser agent (§§3.1–3.3).
- **Trajectory metrics:** Grade integrates delivered functionality across user quality thresholds; Survival integrates the number of consecutively satisfactory requests. All requests run before thresholds are replayed offline, avoiding a single fixed stopping rule (§3.4).
- **Empirical study and assets:** The authors evaluate 14 models and report releasing requests, tests, DAGs, pinned seeds, and execution/scoring code. The supplied extraction does not expose usable release URLs (§4; reproducibility statement, p. 10).

These results support integration difficulty and runtime reliability as useful evaluation targets within this benchmark. They do not establish that dependency complexity causes failures, that simulated tolerance reflects actual abandonment behavior, or that these rankings generalize to production development. Survival is averaged over thresholds, rather than an observed user retention measure.

## Limitations and validity risks
- **Authors acknowledge limited repetition:** Closed-source models receive three runs; open-source models receive one. Variability estimates exclude application-sampling uncertainty, and language/DAG analyses lack confidence intervals (App. F).
- **Backward tests only sample preservation:** One earlier test per follow-up cannot exhaustively detect regressions. Failures can reflect previously missing functionality, and verdict transitions can include judge variability (§3.1; App. D.1).
- **Metric conventions matter:** Uniform threshold weighting and assigning PARTIAL a score of 0.5 are choices. Early evaluator errors affect more of a trajectory, and strict fail-stop scoring changes some rankings (App. H).
- **Evaluation scope is constrained:** Applications exclude external services, authentication, live data, and several browser interactions. Agents receive no test feedback between requests (App. D.1; §3.2).
- **Analyst inference:** Grounding realism is supported by model preferences and lexical diversity, rather than observed user development sessions. Browser-judge validation also leaves material disagreement, particularly when screenshots are insufficient (Apps. C.1, D.3).

## Open research questions
- **Can agents recover through explicit feedback?** The current protocol withholds test outcomes. Compare matched trajectories with and without failure reports and repair requests, measuring recovery and subsequent integration (§3.2; §6).
- **Does dependency complexity independently drive failures?** Late-request restriction reduces position confounding but does not isolate causality. Construct matched requests varying DAG depth or in-degree while holding feature content and trajectory position fixed (§5.1).
- **How robust are scores to user and judge assumptions?** Actual tolerance distributions are unknown, and early grading errors propagate. Re-score trajectories under empirically measured tolerance weights and human-adjudicated early outcomes (App. H).

## Confidence and missing information
**Confidence: high** in the reported benchmark design and descriptive findings; lower in causal interpretations and close model rankings.

Material gaps include usable release URLs in the extraction, detailed per-model configuration values, uncertainty for open-source runs and DAG/language analyses, observed user-tolerance data, and results for longer or feedback-driven trajectories.
