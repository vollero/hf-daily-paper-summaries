# DuoDiscover: Scaling Autonomous Discovery Beyond the Evaluation Bottleneck

> [← Daily summary](../2026-10-19.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.17184) · [arXiv](https://arxiv.org/abs/2610.17184)


## One-sentence takeaway

DuoDiscover jointly discovers code optimization targets and cheap proxy evaluators, using repeated fidelity checks and coordinated coding agents to improve performance under expensive evaluation budgets.

## Problem and motivation

Autonomous code optimization slows when each full evaluation takes minutes or hours. The authors identify a gap in discovery systems that treat evaluators as fixed: effective search must also discover inexpensive ways to measure progress, while detecting proxies that become misleading during optimization (§§1–2).

## Approach and contributions

- **Target–evaluator co-discovery:** Each coding agent selects a code region and constructs a target-specific proxy, called a *yardstick*, then hill-climbs its score. Yardsticks include reduced inputs, profiling harnesses, filtered test suites, and static cost models (§2.2; Appendix F.2).
- **Continual fidelity testing:** The system compares yardstick rankings with true evaluations using noise-filtered Kendall rank correlation, invalidating unreliable yardsticks. Benchmark validation requires at least six resolved states, correlation ≥0.5, and a significance test; every accepted gain requires true evaluation (§2.4; Appendix A.1).
- **Bottom-up coordination:** An LLM orchestrator terminates stalled agents, redirects exploration, transfers confirmed changes, and combines complementary edits without a predefined problem decomposition (§2.3; Appendix A).

The authors claim novelty in discovering optimization solutions and cheap evaluators together while validating evaluators during search (§5); the supplied text alone cannot independently establish priority.

The evidence supports improved optimization and evaluation efficiency on the tested workloads, with component ablations supporting the proposed mechanisms. It does not establish universal proxy reliability, lower total cost at every budget, or general scientific discovery beyond executable systems optimization.

## Limitations and validity risks

- **Author-stated:** Without a faithful yardstick, search falls back to expensive true evaluations; proxy construction and validation impose warmup costs that reduce benefits under very short budgets (§6).
- **Analyst inference—limited replication:** Main results are single-run. Three-seed replication covers only the repository and kernel analysis samples, leaving broader outcome variance uncertain (§§3–4).
- **Analyst inference—weaker case-study validation:** Case studies reduce the fidelity-test state floor from six to two, providing less ranking evidence than benchmark validation (Appendix D).
- **Analyst inference—architecture comparison:** Prefetcher search includes targeted human interventions, asynchronous official evaluations that do not gate subsequent search, and baselines taken from prior reports. Its time advantage is therefore not a fully controlled comparison of search systems (Appendices B, D.5).
- **Analyst inference—workload dependence:** SQLite changes include disabling default mutexes for a single-threaded workload; zstd uses instruction count and AVX2-targeted compilation. These results do not establish equivalent gains across deployment conditions (Appendices D.3–D.4).
- **Evidence ambiguity:** FormulaCode’s aggregation description differs between prose and Table 10’s caption. Many tables appear only as captions in the supplied retrieval, limiting verification.

## Open research questions

1. **When does proxy construction repay its overhead?** Short-budget disadvantages are acknowledged without a precise crossover. A next experiment could sweep evaluation duration and total budget while accounting for proxy construction costs (§6).
2. **How reliable is fidelity testing with sparse feedback?** Case studies use fewer validation states, and Appendix F.1 acknowledges selection effects in measured correlations. Test frozen yardsticks on independently sampled edits across validation sample sizes.
3. **Do gains transfer beyond searched workloads?** Several solutions depend on workload and hardware settings. Evaluate final patches on held-out arrival patterns, input distributions, concurrency levels, and hardware without further search.
4. **How much architecture improvement requires human steering?** The prefetcher study changes objectives and editable regions through interventions. Compare prespecified autonomous and human-steered protocols under matched compute budgets (Appendix D.5).

## Confidence and missing information

**Confidence: medium.** The supplied text gives substantial method and evaluation detail, but many numerical tables are absent beyond captions. Material gaps include full per-task results and uncertainty intervals, complete orchestration prompts and implementation, a confirmed general code release, comprehensive compute-cost accounting, and clarification of FormulaCode aggregation.
