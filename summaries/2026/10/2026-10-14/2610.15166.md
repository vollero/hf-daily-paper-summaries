# ExeWorldBench: Benchmarking Code-Based Executable 3D World Modeling

> [← Daily summary](../2026-10-14.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.15166) · [arXiv](https://arxiv.org/abs/2610.15166)


## One-sentence takeaway
ExeWorldBench evaluates whether models can construct executable 3D mechanisms from images or textual goals, with reported results showing that runnable code often fails to deliver coherent mechanical and causal behavior (§§3–4).

## Problem and motivation
The authors identify a gap between understanding physical systems and implementing them as executable worlds. Existing evaluations separately emphasize physical question answering, visual reconstruction, or behavioral reproduction; these can miss whether geometry, contacts, constraints, and interactions actually produce the intended mechanism (§1).

This matters because plausible appearance or motion can coexist with an incorrect underlying mechanism. The benchmark therefore targets integrated structural, mechanical, and causal construction in 3D (§1).

## Approach and contributions
- **Task formulation:** Executable world modeling combines physical world understanding with its realization in code (§§1, 3.1).
- **Benchmark:** Three task families progressively reduce guidance: image-based individual mechanism reconstruction (T1), image-based multi-stage composition (T2), and text-based synthesis (T3), divided into component-constrained and goal-constrained settings (§3.1). The authors claim novelty for this integrated benchmark; priority is not independently established here.
- **Construction and evaluation pipeline:** Mechanical references, a reusable atomic-component code library, model-assisted feasibility checks, and human review support task construction (§3.2). Evaluation separates visual structure, mechanical motion, causal execution, and goal satisfaction, using Opus 5.5 as the visual judge (§4.1).
- **Empirical analysis:** API and coding-harness evaluations, execution-error repair, horizon analysis, and added motion references examine where executable construction fails (§§4.2–4.7). The paper introduces a benchmark rather than a new trained world-generation model.

## Limitations and validity risks
- **Author-reported capability limits:** Multi-stage propagation, longer execution horizons, and synthesis from high-level intent remain difficult (§§4.5–4.7).
- **Analyst inference—causal validity:** Dynamic scores come from sampled rendered frames (§4.1). The supplied text does not establish code-level checks or intervention tests that distinguish genuine physical mechanisms from scripted behavioral imitation.
- **Analyst inference—selection dependence:** Models generate or filter tasks, and T1 inferability validation uses model-generated evidence before human review (§3.2). This may favor systems and mechanisms those models can interpret; no selection-bias analysis is supplied.
- **Analyst inference—comparison confounds:** Harness and API settings differ, while one coding agent repairs API outputs (§4.2). Missing budgets and repair audits limit attribution of differences to underlying models.
- **Reporting gaps:** No dedicated limitations discussion, judge–human agreement study, uncertainty estimates, or repeated-run analysis appears in the supplied text.

## Open research questions
- **Do high scores certify physical causality?** Frame-based judging leaves this unresolved (§4.1). A next experiment could perturb component positions or remove a causal link and compare scored behavior with simulator traces and code inspection.
- **What causes long-chain failures?** Horizon trends do not separate layout, component-motion, and handoff errors (§4.6). Controlled chains with fixed components and systematically varied stage counts could localize failures.
- **How much does the coding harness contribute?** Existing comparisons lack supplied resource controls (§4.2). Evaluate the same model through API and harness interfaces under matched tool, token, and repair budgets.
- **How reliable is the automated judge?** Human verification concerns data construction, while scoring uses Opus 5.5 (§§3.2, 4.1). Compare blinded expert ratings and instrumented physical checks with judge scores.

## Confidence and missing information
**Confidence: medium.** Task definitions and narrative findings are clear, but quantitative verification is limited.

Material missing information includes dataset sizes and splits, full table values and plot data, component statistics, prompts, execution and sampling settings, harness budgets, repair logs, judge calibration, statistical uncertainty, and public asset availability.
