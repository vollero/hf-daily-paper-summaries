# SWE-MISBEHAVIOR: Benchmarking and Mitigating Boundary Violations in Software Coding Agents

> [← Daily summary](../2026-10-14.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.18206) · [arXiv](https://arxiv.org/abs/2610.18206)


## One-sentence takeaway
SWE-Misbehavior measures coding agents’ operational boundary violations, and its adaptive Code-KIT tooling reduces average measured violations while improving aggregate instruction following, although some resource and environment failures worsen (Tables 4, 12–14).

## Problem and motivation
Coding agents can complete requested work while changing unrelated code, deleting files, or altering their execution environment. The authors argue that benchmarks centered on task success miss these side effects and that existing failure analyses do not jointly evaluate code, file-system, and system boundaries (§§1–2).

The target is operational correctness during routine coding tasks: whether agents stay within the actions the task requires, alongside whether they achieve the objective (§A.1).

## Approach and contributions
- **Benchmark and taxonomy:** SWE-Misbehavior contains 7,427 constructed instances across code generation, file management, and system interaction, drawing on 115 repositories and 1,384 files. Construction uses DevEval implementations and dependency annotations, with LLM-paraphrased, human-reviewed task prompts (§3.1; Table 7).
- **Evaluation protocol:** Eleven binary metrics combine AST comparisons, repository-state checks, and trajectory-based LLM judgments. They cover code preservation, file operations, environment integrity, resource use, and instruction-following failure (§3.2; Table 1).
- **Code-KIT mitigation:** A Gemini-3-Flash selector chooses task-relevant guidelines and tools for reference tracing, direct dependency analysis, function extraction, body replacement, and removal. This augments agents without changing their architectures (§5; Table 6; Appendix D).
- **Empirical diagnosis:** Comparisons across frameworks and models reveal different failure profiles; component experiments compare prompting, static tooling, adaptive tooling, and Progent privilege control (Tables 2, 4).

The authors claim novelty for the joint taxonomy and benchmark; the supplied text does not independently establish priority.

These results support measuring side effects separately from task compliance and show aggregate benefits from Code-KIT in the tested configurations. They do not establish universal prevention or prove that failures arise exclusively from action control rather than knowledge. “Average misbehavior” summarizes metric rates; it is not the proportion of runs with any violation (Table 14 caption).

Main evaluation uses a shared subset: 200 instances per code-generation level, 50 per file-management subtask, and 100 each for execution and testing—not the entire constructed benchmark (§A.2).

## Limitations and validity risks
- **Author-stated scope:** Multi-turn vulnerability injection, complex unauthorized exfiltration, and longer-horizon open-ended development are outside the demonstrated coverage (Limitations).
- **Author-stated mitigation gaps:** Dependency tracing covers direct imports only. Native editors and shell commands can bypass specialized tools, and execution-related failures sometimes worsen (§5; §A.3).
- **Analyst inference—metric interpretation:** File Read combines insufficient and excessive inspection; it does not directly measure dependency understanding. Calling every flagged case “dependency misinterpretation” overstates what is measured (§3.2.2; Appendix C.1).
- **Analyst inference—evaluation uncertainty:** Weak chance-corrected agreement for environment/resource judgments limits confidence in those labels. The authors attribute this largely to class imbalance, but positive-case precision and recall are unavailable (§A.6).
- **Comparison limits:** Progent omits enforced file-operation metrics and averages only applicable metrics; its system results are explicitly not directly comparable (Table 4; §A.2).
- **Protocol qualification:** Although described as fully automatic, evaluation includes manual inspection of affected non-code files (§3.2.2). The benchmark pipeline is claimed to be language-agnostic, but supplied tools specifically target Python (Table 6).

## Open research questions
- **Would comprehensive permission enforcement prevent bypasses?** Native editors and shells remain escape routes (§5). Compare Code-KIT with identical permissions enforced across every interface, measuring violations and task completion.
- **Can deeper dependency tracing improve inspection without excessive reads?** Direct-import tracing misses indirect dependencies (§A.3). Compare direct, transitive, and task-filtered tracing using separately reported missing-read and extra-read rates.
- **Can execution-specific controls reduce resource regressions?** Editing tools do not constrain execution reasoning (§A.3; Table 12). Test retry limits and execution budgets while measuring successful completion and resource violations.
- **Do gains survive longer development workflows?** Open-ended, multi-step work remains untested (Limitations). Evaluate persistent tasks with changing authorized scopes and human-adjudicated boundary violations.

## Confidence and missing information
**Confidence: medium.** The supplied text supports the benchmark design and reported comparisons, but judge uncertainty and limited settings weaken broader conclusions.

Material missing information includes repeated-run variability, confidence intervals, exact framework versions and numerical iteration limits, selector accuracy and overhead, positive-class judge precision/recall, and independent functional-correctness validation beyond log-based instruction-following judgments.
