# Doc2Harness: Benchmarking LLMs on Long-Horizon Harness Engineering of Coding Agents

> [← Daily summary](../2026-10-15.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.20344) · [arXiv](https://arxiv.org/abs/2610.20344)


## One-sentence takeaway
Doc2Harness evaluates specification-driven construction of coding-agent harnesses with scripted behavioral tests, and the best evaluated model achieves only 53.05% mean pass rate across three builds (§4.1).

## Problem and motivation
Coding-agent performance depends on infrastructure that manages tools, permissions, context, sessions, and recovery. The authors argue that existing benchmarks mostly measure downstream success with an existing harness, leaving the ability to build that infrastructure insufficiently tested (§1).

Harness evaluation also requires distinguishing correct restrictions from broken functionality: a prohibited read might appear blocked simply because all reads fail. Doc2Harness targets behavioral conformance directly while controlling the model used to drive evaluation (§§1, 2.4).

## Approach and contributions
- **Construction benchmark:** A build model uses fixed OpenCode infrastructure to implement a harness from a consolidated development document and an interface-only skeleton adapted from mini-swe-agent. The document combines and disambiguates functionality from twelve harnesses (§§2.1–2.2).
- **Behavioral evaluator:** Each frozen implementation runs complete scripted sessions in separate containers. Assertions inspect model requests, disk contents, exit codes, and command output. Positive controls gate tests whose apparent success could otherwise be vacuous (§§2.1, 2.4).
- **Test suite and empirical study:** The authors construct 328 tests through public-issue mining, cross-harness source comparison, and single-variable expansion, then evaluate nineteen models with three independent builds each and analyze implementation structure (§§2.3–2.5, 3–4).

The authors claim this is the first deterministic benchmark specifically measuring harness-development ability; the supplied text does not independently verify that priority claim (§5.3).

## Evidence and main results
| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Substantial headroom remains | Across nineteen models, each scored on three builds and 328 tests, GPT-6 Astra averages 53.05% pass rate versus Hy3’s 27.44%; positive controls are excluded from denominators. | §4.1; Table 2 caption |
| Boundary behavior separates the top models | On ordinary scenarios, Opus 5 scores 80.68% versus Astra’s 72.46%; on boundary scenarios, Astra scores 48.97% versus Opus 5’s 37.02%. Scenario counts are unavailable. | §4.1 |
| Permissions discriminate strongly | Permissions average 43.7% pass rate, with a 50.8-percentage-point strongest–weakest gap; 51 of 61 tests discriminate among evaluated implementations. | §4.2; Table 3 |
| Some cases provide no cohort separation | All scored candidate harnesses fail 56 tests, concentrated in direct drive, session state, permissions, and headless categories. | §4.2 |
| Positive controls cover a substantial subset | Of 328 tests, 130 are gated by at least one positive control; controls do not themselves contribute to pass rate. | §§2.4–2.5 |
| Test responses have high internal consistency | KR-20 is 0.913 across fifty-seven candidate harnesses and all tests. | §4.2 |
| Module fragmentation correlates with lower scores | Controlling for code lines, module count has partial correlation −0.423 with pass rate; leave-one-model-out values range from −0.484 to −0.309. | §4.3 |

These findings establish differences in specification conformance under this particular construction and evaluation protocol. They do not establish downstream coding effectiveness, iterative self-improvement, or a causal benefit from reducing module count. High internal consistency also does not by itself establish broad validity, especially given the correlated test variants acknowledged by the authors (§6).

## Limitations and validity risks
- **Author-stated:** This measures a single construction episode, allowing submission revisions but no build–evaluate–repair loop using behavioral feedback. Early submission can limit observed performance (§6).
- **Author-stated:** Variants derived from a shared seed can fail together because of one defect, creating correlated failures (§6).
- **Analyst inference:** Rankings are conditional on OpenCode and the supplied resource limits: two hours, up to twenty-four turns and three submissions per build, plus a 900-second limit per evaluation case. Robustness to other builders or budgets is untested in the supplied text (§3).
- **Analyst inference:** Scripted sessions isolate harness behavior but do not demonstrate effectiveness with real-model interaction or downstream tasks (§§2.1, 5.3).
- **Analyst inference:** Architecture correlations are observational. They do not isolate fragmentation from model identity or implementation quality (§4.3).
- **Evidence gap:** The text describes positive-control coverage but provides no ablation quantifying how much controls change scores or rankings (§§2.4–2.5).

## Open research questions
1. **How much does behavioral feedback improve construction?** The protocol freezes implementations before behavioral evaluation (§6). A next experiment could compare matched-budget single builds against iterative test-feedback repair.
2. **Do conformance scores predict downstream usefulness?** Evaluation uses scripted mock responses (§2.1). Test the same frozen harnesses on shared coding tasks with a fixed real model and compare task success with conformance scores.
3. **Does fragmentation cause failures?** The evidence is correlational (§4.3). Refactor matched implementations to centralize selected cross-cutting behavior, then rerun unchanged tests.
4. **How stable are rankings across construction settings?** Only one builder configuration is reported (§3). Repeat construction with alternative builders and matched budgets to measure ranking sensitivity.

## Confidence and missing information
**Confidence: medium.** The supplied narrative supports the protocol and reported findings, but numerical bodies of Tables 1–4 and plotted figure data are absent.

Material missing information includes complete per-model scores and standard deviations, ordinary/boundary scenario counts and classification rules, full clauses and test scripts, model sampling and reasoning settings, detailed test-selection thresholds, and confirmation of artifact release and reproducibility.
