# Cortex: Measurement-Gated Evolution and Pruning of Coding-Agent Skills and Rules

> [← Daily summary](../2026-10-15.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.14216) · [arXiv](https://arxiv.org/abs/2610.14216)


## One-sentence takeaway
Cortex’s repeated, exposure-aware testing produced large convention-following gains for Claude Haiku 4.5 in a synthetic repository, but harmful-instruction detection and benefits on real projects remain unestablished.

## Problem and motivation
Developer-written instructions, skills, and rules accumulate as coding agents make mistakes, yet a successful attempt does not establish that an instruction helps: task outcomes vary across repeated runs. Unnecessary instructions can also consume context or degrade behavior. The author identifies a need for repository-specific measurement that determines which instructions earn their place under a limited context budget (§1).

## Approach and contributions
- **Session-to-experiment loop:** `/harvest` extracts replayable tasks and corrections; `/evolve` proposes one skill or rule for a recurring problem; `/prune` measures removal of existing items. Tasks include a broken commit, original request, reference fix, and validated check (§§3.1–3.3).
- **Exposure-aware acceptance and deletion:** Repeated comparisons score tasks where the item entered context. Unknown exposure blocks a verdict; never-fired candidates cannot be accepted, and never-fired existing items cannot be deleted. Skill-description visibility counts as exposure, while opening the body counts as firing (§3.4).
- **Scripted measurement gates:** A cheap screen precedes confirmation across valid tasks. Confirmation requires improvement, sufficient net wins, bounded individual-task losses, and protection of tasks that passed every baseline attempt; regression-only failures receive a recheck (§3.5, Table 2).
- **Claimed distinctive contributions:** The author emphasizes applying exposure rules symmetrically to addition and deletion, testing the acceptance pipeline with planted candidates, and studying automatically loaded rules versus agent-chosen skills inside the selection loop. Individual gate components have acknowledged precedents (§1; related-work discussion, “What is new”).
- **Released assets:** The paper reports an open-source tool, evaluation lab, exported data, and offline analysis scripts; underlying session records are not released (§8).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Large held-out convention gain | Evolved versus minimal CLAUDE.md without skills/rules: **+55.0 percentage points**, 95% CI **[+34.1, +74.1]**, permutation **p=0.0001**; Haiku 4.5, four independent runs, 23 common valid rule-family scenarios, five attempts per arm/scenario. CI resamples runs and scenarios. | §5.1, Table 5 |
| Limited control-family change | Same primary evaluation: **−0.8 points**, 95% CI **[−5.0, 0.0]** on plain bugs; no run retained a control-family item. | §5.1 |
| Rules dominated retained items | **16 of 18** retained items were rules. Across candidate sweeps and gate tests, path-gated skills opened in **28/66** rollouts where listed; always-on candidates opened in **0/198**. These are observational comparisons. | §5.2, Figure 19 |
| No added always-on instruction text | Every retained item had paths; evolved and baseline shared the same **559-character CLAUDE.md** and common skill listing. This concerns always-on context, not total execution cost. | §1; Appendix A, Table 7 caption |
| Known-answer gates incompletely validated | No **20 placebo** or **5 harmful** candidates were retained, but placebo/harmful skills never opened and harmful-rule screens were inconclusive. Only **2/4 known-good** candidates were retained. | §1; §8 |
| Smaller benefit under stronger model | R1 harness versus none on rule-family held-out tasks with Sonnet 5, three attempts per scenario: **+5.6 points**, 95% CI **[−2.8, +13.9]**; the corresponding reported Haiku gain was **+66.7 points**. | §4; §7 |
| Scope overfitting blocked transfer | R3’s narrowed money rules loaded in **0/30** held-out money rollouts; both arms passed **26.7%**. | §5.2, Figure 18 |
| Real-project benefit untested | On structlog, corrections did not recur and no item was retained, leaving identical harnesses to compare. | §7 |

The evidence supports transfer to unseen tasks within the synthetic repository’s convention families. It does not establish general software-engineering gains, reliable detection of harmful loaded instructions, or real-project effectiveness. Loading-tier observations suggest a delivery bottleneck, but do not isolate delivery from candidate content and task differences.

## Limitations and validity risks
- **Author-stated scope limits:** The lab was deliberately calibrated to expose the model’s mistakes; conventions were mechanically checkable, the developer was scripted, and evaluation used few independent runs. Some held-out scenarios were written after the development harness was known (§7).
- **Incomplete gate validation:** Never-opened placebos do not test rejection of useless text that actually loads. Harmful screens omitted the passing-task coverage needed to test regression detection (§1; §8).
- **Execution deviated from intended procedure:** The evolution agent buried candidates receiving RERUN instead of repeating their sweeps (§5.2).
- **Leakage and reproducibility:** Git history exposed fixes or removed harness text; leakage was particularly evident in the stronger-model and structlog experiments. Exported rows are released, but original session records are unavailable (§7).
- **Analyst inference:** Exposure-conditioned comparisons should not be interpreted as causal estimates of invocation effects, because exposure is determined within the arm containing the item; the supplied related-work discussion explicitly acknowledges this concern.
- **Coverage limitation:** The supplied source is truncated, omitting substantial middle results; several tables appear only as captions.

## Open research questions
1. **Can the gates detect harmful instructions that load?** Existing screens did not establish this. Run harmful and length-matched placebo rules through full confirmation on both passing and failing tasks (§8).
2. **Does Cortex improve real developer work?** The structlog attempt produced no learned harness. Evaluate projects with documented recurring corrections and prospective held-out tasks (§7).
3. **How should scope balance precision and transfer?** R3’s narrow paths missed new tasks. Compare file-level and directory-level scopes on tasks touching unseen files (§5.2).
4. **Do gains survive stricter isolation?** Git exposed excluded information. Repeat benchmarks and pruning with single-commit repositories and untracked harness files (§§7–8).
