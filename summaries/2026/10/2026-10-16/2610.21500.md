# When the KV Cache Is Slower Than the GPU: Scaling Remote KV Tiers for Context-Parallel Prefill

> [← Daily summary](../2026-10-16.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.21500) · [arXiv](https://arxiv.org/abs/2610.21500)


## One-sentence takeaway
For GLM-5.3 on an eight-B300 prefill engine, rank-sharded remote caching reduces hit-heavy p99 latency from 83.32 s to 0.67 s, but its 0.40 s median still exceeds recomputation’s 0.31 s (§6.3, Table 2).

## Problem and motivation
Remote KV caches allow engines to reuse prompt prefixes across requests and restarts, but loading cached state must compete with increasingly fast GPU recomputation. In the reported production deployment, enabling a remote LMCache/Valkey tier increased 16k-token p99 TTFT from 3.96 s to 17.3 s without improving the median (§1).

The author identifies three interacting problems: insufficient remote bandwidth, synchronous loads that stall every context-parallel rank, and client bugs that cause prolonged or permanent stalls. The gap addressed is how to assess and scale a remote tier for MLA-based, context-parallel prefill rather than assuming cache hits are beneficial (§§1, 4–5).

## Approach and contributions
- **Load-versus-recompute model.** Model recomputation as \(n/R\) and loading as \(T_0+ns/B\). This exposes both a bandwidth requirement, \(B>sR\), and a fixed overhead that bandwidth alone cannot remove (§4).
- **Rank-sharded MLA storage.** Assign chunks deterministically across prefill ranks. A proof shows that the existing minimum-over-ranks lookup still returns the longest cached prefix; a coordinated load protocol gives every rank the same collective sequence despite reported local failures (§5.1, Proposition 1, Algorithm 1).
- **Rank-partitioned remote servers.** Give each rank its own Valkey instance, preserving cross-engine reuse through consistent ownership and remote keys without inter-server coordination (§5.2).
- **Asynchronous loading and client repairs.** Extend asynchronous prefetch to sharded storage and fix lost completions, missing-key reads, and inconsistent asynchronous keys, with regression tests (§§5.3–5.4).

The author reports submitting these changes upstream to LMCache; acceptance or release is not established (Availability). The additional throughput improvement from a FlashInfer kernel rewrite uses a separate upstream contribution (§6.4).

| Finding | Evidence / setting | Location in paper |

| Bandwidth and fixed overhead impose separate thresholds | For GLM-5.3 FP8 on one eight-B300 node, the model gives \(B^*\approx2.53\) GB/s. A fitted \(T_0\approx0.33\) s predicts that prompts below approximately 17k tokens cannot benefit at any bandwidth. | §4, Eq. 1, Fig. 2 |

| Combined changes eliminate the observed queue buildup | On 450 requests with 98.5% of tokens served from L2, H1b single-instance synchronous loading has p99 83.32 s and 7% GPU utilization; H5b sharded asynchronous loading with all fixes has p99 0.67 s. | §6.3, Table 2 |

| Sharding improves computed-token throughput | One eight-B300 node, eight concurrent approximately 200k-token prompts over three rounds: throughput rises from 43.2k to 49.4k tokens/s (+14%); adding the separate kernel fix reaches 57.3–58.0k tokens/s (+34%). | §6.4, Fig. 7 |
| Targeted semantic checks pass | Six needle prompts evaluated through four execution paths recover the hidden code in 24/24 answers; a synchronous-store soak completes 1,549 requests over 30 minutes without errors. | §6.5 |

These results support the reported bandwidth bottleneck and queue instability in this deployment. They do not establish universal cache speedups: optimized loading remains slower at the median, and the predicted prompt-length crossover was not directly tested. Most replay “latency” measurements cover prefill completion and omit decode handoff (§§3, 8). The end-to-end deployment reportedly passes its SLA, but its comparison changes several architectural factors (§6.6).

## Limitations and validity risks
- **Author-stated:** Each condition ran once; differences below approximately 10%, including synchronous versus asynchronous loading after scale-out, are not established (§8).
- **Author-stated:** Replay uses one engine as the only remote client and omits decode handoff. Shared-server contention across engines is estimated rather than measured (§8).
- **Author-stated:** Latency evaluation covers 14.7k–17.9k-token prompts. The fixed overhead is fitted from one point, and the resulting crossover length remains a prediction (§8).
- **Author-stated:** The primed subset fits in the private cache; production eviction would introduce more misses and lookup-to-load races (§8).
- **Analyst inference:** The combined tail improvement cannot be assigned independently to every component because Table 2 is not a complete factorial ablation.
- **Analyst inference:** Needle recovery and soak tests provide targeted correctness evidence, but do not establish general semantic equivalence; bit-exact comparison was unavailable because cold execution was itself nondeterministic (§6.5).

## Open research questions
- **Where does loading actually overtake recomputation?** The crossover is predicted from one fitted point (§8). Sweep prompt lengths and bandwidth, repeating cold and cached runs to measure the crossover and uncertainty.
- **How does the tier behave under shared production contention?** Multi-engine contention and eviction are not measured in replay (§8). Run several engines against shared shards while varying offered load, cache capacity, and hit rate.
- **Can collective batching reduce the fixed overhead?** Per-chunk broadcasts remain in the load path (§7). Compare the current protocol with batched owner-wise exchanges, measuring latency by prompt length.
- **Can per-request load-or-recompute decisions improve performance?** The paper proposes such a policy but does not evaluate it (§7). Compare model-based selection with always-load and always-recompute under mixed lengths and changing bandwidth.

## Confidence and missing information
**Confidence: medium.** The supplied text gives concrete configurations, mechanisms, and substantial measured effects, but single runs limit statistical confidence and generalization.

Material missing information includes numerical contents of Tables 1 and 3, repeated-run uncertainty, measured multi-engine contention, direct crossover validation, public availability of replay traces and analysis scripts, and whether the submitted patches were accepted.
