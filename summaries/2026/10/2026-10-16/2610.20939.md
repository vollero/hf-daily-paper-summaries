# MAI-Gym: An Open All-in-One Platform for GUI Agent Evaluation and RL Training across Mobile and Computer Environments

> [← Daily summary](../2026-10-16.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.20939) · [arXiv](https://arxiv.org/abs/2610.20939)


## One-sentence takeaway
MAI-Gym combines shared GUI-agent evaluation and RL infrastructure with executable task synthesis, producing a joint mobile–desktop agent that improves on held-out tasks and shows partial clone-to-real transfer.

## Problem and motivation
GUI RL requires isolated, reliably resettable devices and many screenshot-based model calls, making interactive training expensive. Separate evaluation and training harnesses can also drift, confounding model comparisons. The authors identify a complementary data gap: realistic workflows need coherent information across applications, while existing task synthesis often uses isolated files or fixed sample data (§1).

## Approach and contributions
- **Unified infrastructure:** Evaluation, data collection, and RL share a rollout path and agent harness. Environment adapters handle mobile, desktop, and web execution; the platform supports ten benchmarks and reports operation with 20,000 concurrent instances (§§3.1–3.3).
- **Environment and task synthesis:** Coding-agent skills generate resettable app clones, novel apps, and coherent cross-app worlds. Task requirements precede independently generated completion and verifier code; acceptance includes initial–completed–reset tests and review of agent attempts (§3.4).
- **Joint training and efficiency:** MAI-Gym-9B starts from Qwen3.5-9B, receives supervised warm-up, then joint mobile–computer GRPO training. Adaptive task sampling and overlapping history windows reduce wasted rollouts and repeated training computation (§§3.5, 4.1).
- **Released assets, as reported:** Framework and training code, synthesis skills, model checkpoint, 49 mocked apps, and 2,000 verified MobileWorld/OSWorld tasks (§1; §3.4).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Strong held-out-task performance | MAI-Gym-9B achieves **78.4% MobileWorld** and **76.2% OSWorld-Verified** success, versus UI-Venus-2-9B’s **75.2% / 70.8%**. These environments appear in training, but benchmark tasks do not. | Table 4; §§4.1–4.2 |
| RL adds gains beyond SFT | Joint RL adds **14.1 / 7.8 percentage points** on MobileWorld/OSWorld-Verified and improves all five environment-OOD benchmarks. Environment-OOD average rises by **4.2 points**, using the paper’s mixed-metric averaging convention. | Figure 6; §4.2 |
| Joint RL beats tested merges | At the combined budget of two domain experts, joint RL scores **78.4% / 76.2%**; the best tested merge for each benchmark scores **76.4% / 74.8%**, respectively. | Table 7; §4.3.2 |
| More synthesized tasks help | With algorithm, hyperparameters, and rollout budget fixed, increasing the total pool from **500 to 5,000 tasks** raises MobileWorld success **69.2%→78.4%** and OSWorld-Verified **69.7%→76.2%**. | Figure 8; §4.3.3 |
| Clone training partially transfers | On **52 paired 12306 tasks**, clone-only RL raises physical-phone real-app success **28.8%→48.1%**; clone success rises **36.5%→73.1%**. | Figure 9; §4.3.4 |
| Reward-only adaptation improves novel-app performance | Training on **252 tasks**, evaluated on **62 held-out tasks**, one attempt each with a **60-step limit**, raises success **25.8%→45.2%** and reduces mean trajectory length **33.3→16.4 steps**. | §4.3.5 |
| History windows trade rollout speed for training efficiency | Window-wise versus step-wise history reduces training input tokens per trajectory **566,375→86,855** and update time **2,166.4→810.9 seconds**, while rollout throughput falls **2.3→1.9 steps/s**. | Table 6; §4.3.1 |
| Large-scale execution is reported | The main run uses **512 GPUs**, approximately **96 hours**, and peak concurrency of **20,000 environments**. Bringing up **1,000 GUI-ready instances** takes **328.4 s mobile**, **88.9 s computer**, and **94.2 s browser**. | §4.1; Table 5 |

These results support the authors’ claims of useful joint training, synthesized-task scaling, and partial transfer. They do not establish universal superiority: some baseline scores come from external reports, environment-OOD performance remains uneven, and the reported real-app transfer covers one service.

## Limitations and validity risks
- **Author-acknowledged:** Repeated evaluation–diagnosis–synthesis–retraining rounds are supported but not evaluated (§3.3). Clone transfer is incomplete: the clone–real success gap widens after training (§4.3.4).
- **Analyst inference—comparison validity:** Most baseline entries use published reports or leaderboards rather than a fully shared evaluation setup; harness effects therefore remain a comparison risk (§4.1).
- **Analyst inference—causal attribution:** The supplied experiments do not isolate the contributions of coherent-world construction, failure-driven synthesis, verifier auditing, and adaptive sampling. Most overall improvement comes from SFT, whose data composition is only broadly described (§4.2; Figure 6).
- **Analyst inference—scope and uncertainty:** The trained model is evaluated on mobile/computer benchmarks, despite web infrastructure support. No confidence intervals or seed variability are supplied for the key comparisons.
- **Analyst inference—reproducibility:** Training uses 5,000 synthesized tasks, while the reported release contains 2,000 MobileWorld/OSWorld tasks; Appendix A.5 also leaves several run-specific configuration values as placeholders.

## Open research questions
1. **Does repeated failure-driven synthesis outperform static task scaling?** Repeated rounds are unevaluated (§3.3). Compare iterative synthesis against a fixed pool under matched generation and rollout budgets.
2. **Which synthesis components drive generalization?** The paper evaluates the combined pipeline. Ablate coherent cross-app worlds and failure targeting while holding task count and training budget fixed.
3. **How broadly does clone-to-real transfer hold?** Only 12306 receives a quantitative real-app transfer study. Repeat paired evaluations across other released clones and measure sensitivity to interface differences.
4. **Can the recipe retain its gains at smaller compute budgets?** The main run is resource intensive (§4.1). Measure benchmark performance against GPU-hours and environment concurrency.

## Confidence and missing information
**Confidence: medium.** The supplied text provides clear methods and result tables, but lacks detailed SFT data provenance, complete main-run configuration, uncertainty estimates, component ablations, a full account of the unreleased training-task subset, and broader real-app transfer evidence.
