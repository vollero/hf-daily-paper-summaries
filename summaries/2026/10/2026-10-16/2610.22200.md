# OpenGCUA: Toward a Fully Open Stack for Generalist Computer Use

> [← Daily summary](../2026-10-16.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.22200) · [arXiv](https://arxiv.org/abs/2610.22200)


## One-sentence takeaway
OpenGCUA combines executable GUI–shell programs with model-selected observations and task tracking, improving reported performance across eight models on offline OSWorld-v2 while leaving real-device reliability preliminary (Table 2; §4.3.3).

## Problem and motivation
The authors argue that computer-use research should study agents that choose among visual and programmatic interfaces, rather than restrict interaction to screenshots and clicks. They identify limited access to frontier systems’ prompts, harnesses, SDKs, and trajectories as an obstacle to reproducible design comparisons. Real computers also introduce shared control, background windows, existing files, and evolving user requests that controlled benchmarks only partly capture (§§1, 4.1).

## Approach and contributions
- **Decision-based formulation:** A generalist computer-use agent chooses what to observe, how to act, and how to organize its work. This is a conceptual framework, rather than a newly trained policy (§2).
- **Executable interaction:** The benchmark harness executes Python programs combining GUI operations, shell commands, loops, conditions, and checks on intermediate results (§3.1).
- **Selected workflow decisions delegated to models:** Models request screenshots, update a persistent task ledger, and describe action intent. Context retention and compaction remain harness-controlled (§3.2).
- **Open research infrastructure:** The authors report releasing implementations, prompts, and eight-model evaluation trajectories, plus preliminary real-device and cross-device infrastructure. A trained model and real-device benchmarks remain planned (§§4–5).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Full configuration improves all evaluated models | On 82 offline OSWorld-v2 tasks across eight models, mean partial score rises from 45.3 to 64.9; average within-model step reduction is 53.0% versus batched GUI-only execution. | Table 2; §§3.3.1–3.3.2 |
| Strongest baseline also benefits | GPT-6 Astra’s partial score rises from 67.1 to 75.7, binary success from 36.6% to 46.3%, and steps/task fall from 102.1 to 33.5 under the same comparison. | Table 2 |
| Code execution adds value beyond shell access | With GUI and CLI available in both settings, GLM-5.3-Flash’s partial score rises from 55.8 to 63.2; Qwen3.8-Max’s steps/task fall from 66.1 to 54.9 versus batched GUI–CLI execution. | Fig. 6; §3.3.4 |
| On-demand screenshots improve cache reuse in selected runs | Added to code execution, cache-hit rates rise from 75.6% to 86.1% for Qwen3.8-Max and 61.9% to 76.3% for DeepSeek-V4.1-Flash; partial scores also increase. | Table 4 |
| Workflow features have mixed effects | Adding intent alone lowers partial scores from 62.4 to 61.5 and 56.7 to 53.3 for those two models; the authors position intent primarily as a user-understanding feature. | Table 4; §§3.3.5 |
| Real-device token usage differs substantially | Across four macOS tasks using selected run 1, Qwen3.8-Max averages 50.2K reported reasoning tokens versus GPT-6 Astra’s 2.6K—reported as 19.4×—with completion counts of 3/4 versus 4/4. | Table 5; §4.3.3; Fig. 1 |
| Artifact checks reveal incomplete task coverage | In the workbook example, GPT fills 125/125 required Level answer cells; Qwen fills 85/125 despite using executable functions and loops. | Fig. 11; §4.3.4 |

The benchmark evidence supports improved task completion and fewer model calls for the evaluated configurations. It does not isolate every component’s causal contribution, establish lower end-to-end latency, or demonstrate reliable operation across real-device environments. The authors explicitly treat timing comparisons as exploratory because execution conditions differed across models (§3.3.6).

## Limitations and validity risks
- **Authors’ stated scope:** The harness and SDK are preliminary; this release contains no newly trained model. Cross-device functionality is described architecturally without a reported cross-device task evaluation (§§4.2, 5).
- **Limited real-device evidence:** Aggregate results use one selected run per model on four macOS tasks. The authors caution against interpreting these as a general model ranking (§4.3.3).
- **Analyst inference—uncertain stability:** Results use selected attempts; Appendix A retains the latest evaluator-bearing attempt rather than the best. No confidence intervals or across-run variability are reported.
- **Analyst inference—component attribution:** The main comparison changes interface access, executable control, workflow mechanisms, and context policies together. Component ablations cover fewer models (Tables 2–4).
- **Evaluation ambiguity:** The text says both selected workbook runs satisfy evaluation criteria, while Fig. 11 documents missing required cells in Qwen’s artifact; the relationship between these records is unclear. Appendix B also gives task summaries and full instructions with differing deliverable scope (§§4.3.3–4.3.4; Appendix B).
- **Verification boundary:** Ledger statuses represent model assessments, and successful action delivery does not establish task completion (§§3.2, 4.3.1).

## Open research questions
- **How stable are the gains across repeated runs?** Selected-run results lack variability estimates. Repeat matched configurations with fixed budgets and report paired task-level uncertainty.
- **When should workflow decisions remain with the harness?** Individual mechanisms produce mixed score and step changes. Compare fixed, model-directed, and adaptive policies under identical interface and context settings.
- **Does cross-device coordination work reliably under interruption?** The SDK supports such workflows, but empirical evaluation remains absent. Test phone–desktop–browser tasks with window changes, user interruptions, and recoverable failures.
- **Can reasoning tokens be reduced without losing task coverage?** Real-device examples show large generation differences but no controlled reasoning intervention. Vary reasoning settings while independently auditing artifact completeness and correctness.

## Confidence and missing information
**Confidence: medium.** The supplied text supports the benchmark findings and implementation description, but broader reliability claims remain weakly established.

Material missing information includes repeated-run uncertainty, complete benchmark execution budgets and model configurations, detailed real-device completion rubrics, reconciliation of workbook evaluation and artifact coverage, controlled latency measurements, and empirical cross-device results.
