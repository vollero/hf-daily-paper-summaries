# RouteWeaver: Weaving Mode Selection and Execution into Unified LLM Routing

> [← Daily summary](../2026-10-23.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.19705) · [arXiv](https://arxiv.org/abs/2610.19705)


## One-sentence takeaway
RouteWeaver jointly learns execution-mode selection and model coordination, reporting 61.4% average accuracy versus Router-R1’s 55.3% across five benchmark domains, with cost savings measured only for Worker inference (§5.2–5.3).

## Problem and motivation
Existing LLM routers typically commit to single-round, multi-round, or agentic execution before receiving a query. The authors argue that selecting models within a fixed paradigm cannot accommodate queries requiring different computation structures. Unified routing must learn both which execution mode suits a query and how to execute that mode effectively, while avoiding early training collapse onto one mode (§1).

## Approach and contributions
- **Unified routing policy:** A shared grammar represents mode selection, Worker calls, observations, and final answers. Agentic calls additionally specify roles and dependencies. Only the Qwen3-4B-Instruct-2507 router is trained; six heterogeneous Workers remain frozen (§4.1, §5.1).
- **COMET-GRPO:** Group-relative feedback is split into an across-mode advantage for mode tokens and a within-mode advantage for subsequent routing and answer tokens. Separate token-count normalization balances these decision levels; task and efficiency signals are normalized separately before mixing (§4.2).
- **Progressive exploration:** Training moves from externally assigned modes through a forced/free transition to autonomous selection. A temporary batch-level support penalty discourages premature mode concentration (§4.3).
- **Empirical evaluation:** The authors compare unified routing against ten fixed-paradigm routers, test component ablations, and examine cost preferences and held-out benchmarks (§5).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Higher main-task accuracy | With α=0, RouteWeaver reports **61.4%** versus strongest baseline Router-R1’s **55.3%**, an author-reported **11.03% relative improvement**. | Adjustable Worker-cost trade-off | Relative to α=0, α=0.1 reduces fixed-reference Worker cost/query by **23%** with **1.0 percentage-point** accuracy loss; α=0.3 gives **61% / 3.1 points**; α=0.5 gives **86% / 11.2 points**. Each α uses a separately trained run. | §5.3, Figure 3; Appendix C.3 |
| COMET-GRPO ablation | Under the same training budget and α=0, ordinary GRPO lowers average accuracy from **61.4% to 58.8%**. Single/multi/agentic usage changes from **35%/41%/24%** to **13%/82%/5%**. | §5.4; Table 2 accompanying prose |
| Exploration ablation | Removing progressive exploration lowers average accuracy from **61.4% to 55.6%** and yields **100% single-round** selection. This variant also disables the support penalty. | §5.4; Appendix C.3 |

These results support improved benchmark performance and sensitivity to training components in the reported setup. Mode frequencies show specialization but do not establish that the chosen mode is optimal for each query. Cost results establish a Worker-token accounting trade-off, not total deployment savings. ## Limitations and validity risks
- **Author-stated scope:** Worker biases, unsafe behavior, and factual errors can propagate across calls; safety-critical deployment is not evaluated (Ethics statement). Richer execution structures and tool-augmented environments remain future work (§6).
- **Analyst inference—cost coverage:** Router computation is excluded, reference prices differ from actual payments, and α=0 cost is reconstructed from token usage. End-to-end cost and latency benefits therefore remain unestablished (§5.3; Appendix C.1).
- **Analyst inference—ablation attribution:** Removing progressive exploration also removes its support penalty. The reported ablation cannot isolate the schedule’s effect from that penalty’s effect (Appendix C.3).
- **Analyst inference—evaluation uncertainty:** Workers sample, providers may ignore the fixed seed, and each question receives one system rollout. No repeated-run uncertainty estimates are supplied (Appendix C.3).
- **Analyst inference—scoring and scope:** LiveCodeBench and TACO may use truncated test suites; SimpleQA-Verified permits whole-word reference matching. These operational scores have limits beyond their stated protocols (Appendix B.2). Transfer is tested within existing task domains, with the same Worker pool (§5.5).

## Open research questions
1. **Which exploration component prevents collapse?** Schedule and support penalty are removed together. A factorial ablation could vary cold start, forced-mode decay, and support penalty independently.
2. **Does unified routing improve total deployment efficiency?** Router cost and latency are outside the reported cost measure. Measure full-system expense and wall-clock latency at matched accuracy.
3. **Does the policy transfer to changed Workers?** Held-out testing changes benchmarks rather than the model pool. Replace or add Workers and compare zero-shot routing with retraining.
4. **Are selected modes better for individual queries?** Aggregate usage does not answer this. Execute each mode on the same queries under controlled budgets and compare selected-mode outcomes with alternatives.

## Confidence and missing information
**Confidence: medium.** The supplied text clearly describes the method and headline results, but lacks numerical table bodies, exact dataset sampling details, Worker capability descriptions and price entries, detailed baseline configurations, held-out scoring/sample sizes, and uncertainty estimates. Code availability is author-reported and was not independently checked.
