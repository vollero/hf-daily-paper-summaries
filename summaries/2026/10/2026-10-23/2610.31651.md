# BrickWright: Agentic Creation of Physically Feasible Brick Builds

> [← Daily summary](../2026-10-23.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.31651) · [arXiv](https://arxiv.org/abs/2610.31651)


## One-sentence takeaway
BrickWright combines a connector-aware Python assembly API with iterative validation, achieving 100% collision-free and floater-free builds across four agents on BrickNet-512, while leaving stability and assembly-sequence feasibility untested (Table 1; §3).

## Problem and motivation
Coding agents can generate visually convincing brick models that contain intersecting, unsupported, or disconnected parts. The authors identify a gap between tools for digital geometry creation and tools for assemblies made from fixed physical parts: the latter require explicit connector rules and physical checks. Writing raw LDraw also requires absolute part poses, making construction cumbersome and error-prone (§§1, 3.1).

## Approach and contributions
- **BrickLayer assembly toolkit:** A Python API for catalog search, nested subassemblies, relative placement, connector mating, and LDraw conversion. It uses existing BrickNet connector annotations and adds construction helpers (§3.1).
- **Executable feasibility checks:** Collision, ground-support, and connectivity checks return actionable feedback. Collision testing uses inset meshes to accommodate tight snap connections; annotated articulations can be checked at sampled poses (§3.1; Listings 2, 4).
- **BrickWright agent framework:** A pretrained agent writes and repairs a Python build program, runs fixed and self-written tests, inspects renders, and finalizes the result without task-specific training (§3.2).
- **Comparative evaluation:** Experiments separate the effects of the assembly API and validation tools, and compare against general coding agents, adapted Articraft, and specialized brick generators (§4).

The contribution is the domain-specific toolkit and its integration with an established iterative agent workflow; the paper does not introduce a newly trained generator.

These are author-reported, post-human-review results. They support strong improvements under the paper’s geometric and support-based definition of validity. Connectivity is reported separately: a valid build need not be connected (§3; Table 1).

The results do not establish universal success, statistical equivalence of fidelity, stability under forces, or successful physical assembly. Image conditioning, editing, articulation, and large scenes receive example-based demonstrations rather than comparable quantitative evaluation (§4.3; Fig. 5).

## Limitations and validity risks
- **Authors’ stated scope:** Stability and executable assembly sequences are excluded from feasibility. Agentic generation is generally slower and more costly than specialized generation (§5).
- **Analyst inference—shared verifier:** BrickLayer both guides generation and measures validity. Human review checks selected potential false positives, but the text reports no systematic independent audit for missed violations (§4, Metrics).
- **Analyst inference—ablation confound:** The “without validator” condition also removes rendering, so its effect cannot be attributed exclusively to physical feedback. Astra component ablations are omitted for budget reasons (§4.2).
- **Analyst inference—limited generalization evidence:** Quantitative evaluation uses one dataset of captions generated from human-made builds. Other input modalities and extension tasks are demonstrated qualitatively (§4).
- **Documented articulation limits:** Posing requires a tree structure; motion checking is optional and samples poses rather than certifying continuous motion. Unannotated connections remain rigid (§3.1; Listings 2, 4).
- **Analyst inference—comparison boundaries:** Agent tool access differs across conditions, and Articraft is adapted with its original collision checks disabled. Results therefore compare complete configured systems (§4, Technical details).

## Open research questions
1. **Do validator-passing designs survive physical construction and handling?** Stability and assembly order remain excluded (§5). A next experiment could physically assemble a sampled set and measure assembly completion and failure under specified loads.
2. **How much benefit comes from physical feedback versus visual inspection?** Their removal is bundled in the ablation (§4.2). A factorial experiment could independently enable validation and rendering with the assembly API fixed.
3. **Does validity generalize to image inputs and complex articulation?** These receive qualitative demonstrations (§4.3). A held-out benchmark could measure prompt adherence, static validity, and motion violations across specified joint ranges.

## Confidence and missing information
**Confidence: high** in the reported benchmark findings and method description; physical-world feasibility remains unestablished.

Material information unavailable in the supplied text includes repeated-run variability or confidence intervals, systematic false-negative rates for the validator, physical assembly tests, quantitative extension benchmarks, and detailed prompt-adherence rendering/scoring settings. Code availability is claimed but was not independently verified.
