# nanoMuse: An Open-Source Personal Agent for Every Device You Own

> [← Daily summary](../2026-10-08.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.08699) · [arXiv](https://arxiv.org/abs/2610.08699)


## One-sentence takeaway
nanoMuse presents an open-source, device-resident personal-agent system with cross-device coordination, readable memory and approval-gated GUI actions, but reports no task-success or safety evaluation.

## Problem and motivation
The authors argue that persistent personal agents need access to a person’s accounts, devices and history, making deployment, inspectability and control central design choices. They identify two gaps in existing systems: dependence on vendor-hosted infrastructure and limited access to native phone applications without APIs or web interfaces (Secs. 1–2).

Their proposed alternative runs the agent on user-owned devices, permits model choice and makes the shared relay self-hostable. These are architectural motivations; the paper does not experimentally establish their benefits.

## Approach and contributions
- **Integrated open system:** nanoMuse combines Android, iOS, desktop and web clients with an optional open relay under GPL-3.0. Devices run their own agents and expose capabilities to peers; delegated jobs require permission on the acting device (Sec. 5, Fig. 5).
- **GUI operation with approval gates:** the agent prefers skills, command-line tools, MCP and browser access before using a screenshot-driven action loop. A Sentinel evaluates each tool call, with scoped grants, conversation-level taint and warnings for sensitive actions. GUI screening uses the model’s action description and, on Android, available accessibility text (Sec. 5).
- **Persistent personal-agent interface:** editable memory, scheduled tasks, Feed, Ideas and Goals support ongoing interaction. Memory provenance and reconciliation remain future work (Secs. 5–7).
- **Conceptual framework and comparative account:** the report organizes personal-agent requirements into five questions and three horizons, and analyzes Muse using explicitly labeled documented, prompt-derived, observed and inferred statements (Secs. 3–4).

The technical contribution is primarily system integration and deployment design. The authors acknowledge substantial reuse from OpenMinis, the DeepSeek harness, UI-TARS-desktop and MemGUI-Bench; they introduce no evaluated new model or benchmark.

The evidence supports a described implementation and limited footprint observations. It does not establish task reliability, safety against attacks, cross-device consistency, comparative superiority or typical operating cost. Table 1 compares reported architectural features rather than benchmark performance.

## Limitations and validity risks
**Author-stated limitations:** Sentinel is a policy boundary rather than a privilege boundary; device compromise compromises the agent. GUI safety screening depends on action descriptions and available labels, leaving unlabeled icons problematic. Linux GUI control requires X11, and iOS cannot operate other apps. Memory lacks writer-model provenance, confidence and a reconciliation rule. The shared relay stores synced conversation text, and community-model training collection defaults on for new community-relay accounts (Sec. 7).

The Muse analysis also relies partly on a production-prompt copy whose provenance the authors cannot verify; prompt-derived and inferred descriptions may not match deployed behavior (Sec. 7).

**Analyst inference:** without task evaluations, adversarial tests or component ablations, the supplied text cannot determine whether the hybrid access ladder, Sentinel rules or peer delegation improve reliability or safety. Resource observations from a fresh relay and one workstation do not establish performance under sustained or concurrent use.

## Open research questions
- **How reliable are the Hands across applications?** Success and takeover rates are absent. Run repeated AndroidWorld and OSWorld tasks, reporting completion, takeovers and failures by interface type.
- **How often can unsafe actions evade description-based screening?** Unlabeled controls and dependence on model-generated words remain unresolved. Test misleading labels, icons and prompt-injection scenarios, measuring unauthorized actions and unnecessary approvals.
- **Can memory provenance reduce persistent errors?** Current memory lacks confidence and rechecking. Compare the existing store with provenance-aware reconciliation on longitudinal tasks containing conflicting updates and user corrections.
- **How robust is cross-device delegation?** The paper describes permission checks but reports no coordination evaluation. Test multi-device workflows under disconnects and permission revocations, measuring completion and unintended actions.

## Confidence and missing information
**Confidence: medium.** The architecture and acknowledged limitations are explicit, but empirical evidence is sparse.

Material missing information includes task-level results, evaluated model configurations, safety-test outcomes, component ablations, longitudinal memory performance, relay load measurements, real usage costs and a verifiable provenance record for the Muse prompt.
