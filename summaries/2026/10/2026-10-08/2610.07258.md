# Lineage-Aware Memory Governance: A Derivation-Gated Framework for Privacy-Preserving Column-Level Access Control in Enterprise AI Agents

> [← Daily summary](../2026-10-08.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.07258) · [arXiv](https://arxiv.org/abs/2610.07258)


## One-sentence takeaway
AMU attaches derivation lineage to cached analytical results and conditionally prevents unauthorized sensitive-column reuse, with favorable simulator results but limited real-agent validation.

## Problem and motivation
Shared agent memory can serve an apparently harmless result whose computation used columns the requester cannot access. Departments can also reuse a same-named KPI computed with incompatible definitions. The authors identify a gap between source-layer access controls and memory retrieval: content, ownership, and role tags do not necessarily capture a cached result’s derivation (§§I–II).

## Approach and contributions
- **Derivation-aware memory:** The Analytical Memory Unit stores a metric, result, producing department, epoch, and table/column/filter lineage. Retrieval selects the freshest candidate whose recorded **sensitive-column** dependencies fit the requester’s permissions; otherwise it returns an already authorized fresh computation (§III).
- **Conditional safety proof:** Theorem 1 proves sensitive-column safety under complete lineage and authorized fallback computation. Policy changes require refreshing cached sensitivity tags (§IV).
- **Metric-definition governance:** Definition hashes flag cross-department derivation differences without blocking writes. An extended study evaluates exact and fuzzy detectors and proposes an unevaluated composite detector (§§III-B, VI-C).
- **Threat and feasibility analysis:** An eight-threat model, simulator experiments, runtime measurements, and SQL-lineage integration characterize protection and its boundaries (§§V–VI).

The claimed novelty is applying column-level derivation checks at shared analytical-memory retrieval; comparisons with existing systems concern documented features, not independently measured performance (§II).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Conditional safety | No returned result depends on a forbidden sensitive column if lineage is complete and fallback computation is authorized. | §IV, Theorem 1 |
| Leakage–reuse tradeoff | Across 30 seeds per schema, naive versus lineage-aware leak rates were **18.8 ± 3.7% versus 0.0 ± 0.0%** on the synthetic schema and **25.5 ± 4.5% versus 0.0 ± 0.0%** on TPC-H. Reuse was **95.8 ± 0.0% versus 82.6 ± 2.3%**, and **95.8 ± 0.0% versus 81.5 ± 4.8%**, respectively; ± denotes population SD. Authors report bootstrap intervals excluding zero and Mann–Whitney **p < 0.001** for naive–LA differences. | §VI-A, Table VI |
| Incomplete lineage weakens protection | At completeness **ρ = 0.50**, leaks were **16.3 ± 3.3%** synthetic and **10.3 ± 4.7%** TPC-H over 30 seeds. Measured leaks reached zero at **ρ ≥ 0.75** and **ρ ≥ 0.90**, respectively. | §VI-B, Figure 4 |
| Conflict detectors have different failure modes | On **43 hand-labelled pairs**, D3 missed all **8** logic-operator changes and achieved **F1 = 0.833**; exact-hash D1 caught all eight but had **precision = 0.651**, flagging threshold recalibrations. | §VI-C, Figure 5 |
| Retrieval cost grows with candidate count | Mean all-blocked retrieval latency increased from **0.66 μs at n = 1** to **13.82 μs at n = 50**, measured over **2,000 iterations** in a single-threaded container on an ARM64 VM using CPython 3.10.12. | §VI-D |
| Small integration demonstrates feasibility | Northwind with LangChain, Ollama, SQLGlot, and real/canned SQL: **9 round-trips**, **zero observed leaks**, **5 fresh queries**, **4 cache-served requests**, and **2 blocks coinciding with 2 conflicts**; reported cache-hit latency **0.009 ms**. | §VI-E |

These findings establish the gate’s conditional correctness and characterize its behavior in controlled workloads. They do not establish universal leak rates, production security, or comparative performance against implemented named memory systems. Zero measured leakage below complete lineage is workload-specific; it does not satisfy the theorem’s completeness assumption.

## Limitations and validity risks
- **Author-stated:** Protection depends on lineage completeness and integrity. Undeclared sensitive dependencies, cross-metric inference, and departmental collusion remain outside the gate’s protection (§V).
- **Author-stated:** Evaluation uses simulator workloads, a small hand-labelled conflict corpus, one runtime platform, and a short integration mixing generated and canned SQL. Production-scale viability remains untested (§§VI–VII).
- **Author-stated:** Views, procedures, UDFs, deep aliases, and wildcard expansion can hide dependencies from static SQL extraction (§VII-B).
- **Analyst inference:** The fail-closed claim is incompletely substantiated. Extraction failures can trigger maximal sensitivity, but silently omitted dependencies may not signal failure; §VII-B both describes hidden-column omissions and claims these cases cause only over-blocking.
- **Analyst inference:** The implementation enforces registered sensitive columns, not every forbidden column, despite broader wording elsewhere; Table V explicitly states this boundary.
- **Reproducibility:** Supplementary protocols and several table bodies are absent from the supplied text. Section VIII promises public assets but supplies no repository link.

## Open research questions
1. **Can extraction detect silent lineage omissions?** The SQL integration does not establish completeness for opaque dependencies. Test catalog-aware extraction against adversarial views, procedures, nested aliases, and wildcard queries with known ground-truth lineage.
2. **How do workload factors independently affect leakage and reuse?** The schema comparison changes several factors together (§VI-A). Run the proposed factorial sweep over join depth, registry size, and sensitive-variant proportion.
3. **Can conflict detection distinguish semantic changes from benign recalibration?** Existing detectors trade missed logic changes against false alerts; D4 is unevaluated (§VI-C). Compare D4 and existing detectors on a larger, independently labelled analytics corpus.
4. **Does the tradeoff persist in sustained deployment?** The integration and hardware coverage are narrow (§VII-B). Measure end-to-end leakage, reuse, query cost, and policy-update behavior over weeks on a real warehouse and multiple platforms.

## Confidence and missing information
**Confidence: medium.** The supplied text supports the conditional mechanism and reported results clearly, but leaves important validation details unavailable.

Missing information includes supplementary workloads and raw results, full detector specifications and table contents, a public code/data repository, the integration’s LLM identity and real-versus-canned query breakdown, and evidence that silent extraction omissions reliably trigger denial.
