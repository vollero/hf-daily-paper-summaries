# Embodied Turing Machines: Stateful Code for Robot Recursive Self-Improvement

> [← Daily summary](../2026-10-09.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.12369) · [arXiv](https://arxiv.org/abs/2610.12369)


## One-sentence takeaway
The authors report that an offline-developed, shared code policy with explicit sensor-derived state achieves 70.24% success on RoboDojo’s 42 simulated bimanual tasks without runtime model inference, while relying on benchmark assets and task-specific development (Table 2; §5.4).

## Problem and motivation
The authors target robot policies whose state and action decisions remain partly hidden inside runtime VLA or VLM inference. They argue that this makes failures difficult to inspect, correct, and recover from, while adding inference cost.

Their identified gap is that earlier code policies either generate code during execution or obtain state from learned perception or simulator oracles. COAP instead measures state through ordinary code and reuses fixed programs across episodes and a shared library across tasks (§§1–2).

## Approach and contributions
- **Code-Only-as-Policy:** Frozen code maintains environment, robot, and task state and computes trajectory segments from observations. NumPy/OpenCV perception fits known object geometry to RGB regions; proprioception updates robot state (§§3.1–3.2).
- **Shared manipulation library:** Task programs compose or inherit object, manipulation, perception, and motion modules. Default-off extensions preserve existing callers’ code paths, with compatibility checked on test fixtures (§3.3).
- **Offline agent-driven improvement:** Coding agents inspect failed development runs, propose parallel code branches, and select changes using validation success margins. Simulator ground truth is available for development debugging, but not runtime control (§3.4).
- **Proposed data engine:** Explicit states, decisions, and successful trajectories could supervise VLAs or agent harnesses; downstream training benefits are proposed rather than evaluated (§5.5).

The claimed distinction is the combination of code-based measurement, persistent explicit state, episode-reusable programs, and offline improvement—not simply using code for robot control.

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Highest overall reported success | 70.24% whole-task SR versus PhysicalRSI’s 31.38%, a 38.86 percentage-point advantage; progress scores 75.45 versus 36.27. RoboDojo: 42 tasks, three seeds of 50 layouts per task | Table 2; §4.1 |
| Leads every task dimension | SR: Memory 89.9%, Precision 75.1%, Open 64.1%, Generalization 65.7%, Long-Horizon 56.4%; respective advantages over each category’s best baseline: 39.6, 41.6, 33.1, 35.2, 13.0 points | Table 2 |
| Randomization reduces success | Generalization-task SR is 77.3% on standard versus 54.1% on randomized layouts | §4.2 |
| Measurement remains a bottleneck | The same program achieves 63% success with measured state versus 83% with oracle state; task coverage and episode count are unspecified | §4.3.1; Figure 5 |
| Recovery sometimes saves failures | Among validation episodes where something went wrong, 12% reattempted and succeeded, 22% reattempted and failed, and 42% stopped with a reported reason | Appendix A.1; Table 3 |
| Runtime calls are usually cheap | Median decision call: 0.3 ms; approximately 25 perception/planning calls per episode account for 99.4% of decision time. Estimated episode compute: 0.8–2.4% of VLA compute and below 0.1% of agent-harness compute | §4.3.2; Appendix A.1 |
| Existing-task regression was limited in the measured setting | Unchanged old-task programs: 78.4% before versus 79.9% after library development on identical layouts; pooled test p=0.16, with sensitivity to roughly four-point shifts | Appendix A.2 |
| Failures involve both state and logic | Authors attribute 62% of failures to perception/contact and 37% to incomplete logic/poor design; classification is judgment-based | §5.3; Appendix C |

These results establish strong reported performance within this simulation protocol. They do not isolate which COAP component causes the gains, demonstrate real-world transfer, or establish downstream training benefits. Compute comparisons use model-size estimates rather than measured baseline execution; the median call latency also excludes the concentration of work in slower planning calls.

## Limitations and validity risks
**Author-stated:** Evaluation is simulation-only and perception depends on public benchmark calibration, meshes, and object dimensions. Real deployment would require measurement and contact tuning. Every new task incurs offline development cost, and hard-coded rules, perception errors, and poorly represented contact limit generalization (§§5.2–5.4).

**Analyst inferences from the supplied evidence:**

- The leaderboard comparison does not control task-development effort or asset access across methods; it supports a benchmark performance comparison rather than an isolated architectural advantage (§4.1).
- No systematic component ablation separates persistent memory, geometric perception, recovery, and library reuse. The measured/oracle comparison has unspecified coverage (§4.3).
- Non-regression guarantees cover exercised fixtures; they do not prove unchanged behavior for all possible observations. The empirical old-task test rules out large pooled regressions, not every regression (§3.3; Appendix A.2).
- Claims of exponential capability growth and slower agent-harness growth use schematic curves, not measured comparative scaling experiments (§4.3.3).
- Appendix A.2 describes a four-task development curve while also mentioning an additional zero-success task; Table 6 includes a success decrease at a merge. Their relationship to the monotonic acceptance rule is unclear.
- Branch gains are measured on selection layouts, and the authors acknowledge optimistic gain estimates and independence assumptions (Appendix B).

## Open research questions
- **Can COAP transfer to real robots?** Simulation assets underpin current perception. A next experiment could measure real calibration and geometry, then evaluate frozen programs under sensor and contact variation (§5.4).
- **Which components drive success?** The combined system leaves causal attribution open. Matched-budget ablations could remove persistent memory, recovery, and wrist remeasurement separately (§4.3).
- **How far does library reuse generalize?** Task-specific development remains necessary. Freeze the library and compare adaptation cost and held-out success across unfamiliar object families and tasks (§5.4).
- **Do COAP trajectories improve learned policies?** The data-engine benefit is unevaluated. Train matched VLAs with and without COAP trajectories and explicit state supervision, then compare held-out performance (§5.5).

## Confidence and missing information
**Confidence: medium.** The supplied text gives detailed methods, protocol, results, and caveats, but leaves material evaluation details unresolved.

Missing information includes public code availability, full offline development cost and agent prompts, validation split sizes, overall uncertainty intervals, oracle-comparison coverage, measured baseline runtime costs, and an explanation of the new-task timeline inconsistencies.
