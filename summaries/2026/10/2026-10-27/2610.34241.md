# Beyond Benchmarks: Can Small Open-Weight Models Get Real Coding Work Done?

> [← Daily summary](../2026-10-27.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.34241) · [arXiv](https://arxiv.org/abs/2610.34241)


## One-sentence takeaway
In bounded TypeScript studies, small open-weight workers delivered verified code, but success depended on the deployment and artifact contract, and direct frontier coding had lower measured frontier cost per verified success in both studies with a direct arm (§§9–10).

## Problem and motivation
A model that loads and produces coherent text may still fail to execute tools, maintain session state, preserve interfaces, or complete correct code. The author examines the engineering gap between an accessible checkpoint and trustworthy coding outcomes, including whether local-worker delegation reduces frontier spending. The identified gap concerns operational integration and outcome accounting rather than a new general theory of coding-agent reliability (§1).

## Approach and contributions
- **Retrospective systems account:** Traces deployment recipes, client/gateway interoperability, streaming failures, and cache continuity across several runtimes. Evidence includes 4,165 author-operated gateway turns and 623 selected debug jobs (§§3–7).
- **Bounded delegation evaluations:** Uses Claude Code with a fixed Claude Opus 5.5 parent to compare direct coding and open-weight delegation on two TypeScript suites, separating artifact production, acceptance, application, behavioral verification, and retained worker code (§9).
- **Outcome-based economics and contract diagnostic:** Accounts for frontier spending including failed attempts, and tests whether a strict parameter-name gate rejected behaviorally passing artifacts. Neither a new model nor a general-purpose benchmark is claimed (§§9.4–10, 13).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Workers completed bounded tasks in the first study | Across five task categories with three repetitions per arm: direct coding passed 15/15, optimized delegation 12/15, and batch-labeled adaptive delegation 14/15 using Qwen3-Coder 30B-A3B IQ3. All 26 verified delegated trials retained worker code; intermediate parent edits were not ruled out. | §9.1, Table 5 |
| Later outcomes were weaker under a different suite and fixed contract | Completed replacement cohort: direct 45/45; Nemotron 12/45 verified, including 11 worker substitutions; separate later Qwen follow-up 0/45. Studies used different configurations and were not pooled. | §9.3, Tables 5a–5c |
| Replacing interrupted sessions materially affected results | Sixteen pre-inference subscription-limit stops were replaced contrary to protocol. Counting the original stops as failures gives direct 37/45 and Nemotron 8/45 verified, with 8 substitutions. | §9.3 |
| A static gate excluded some behaviorally passing code | Of 36 selected artifacts rejected solely for dropping leading parameter underscores, 19 passed unchanged when only that validation rule was bypassed. Parent review and application were not replayed. | §9.4, Table 5d |
| Direct coding had lower frontier cost per verified success | First suite: $0.136 direct, $0.214 optimized delegation, $0.199 adaptive delegation. Second-suite replacement cohort: $0.153 direct versus $1.313 Nemotron delegation; Qwen’s value was undefined because none verified. Failed sessions are included; local-worker costs are excluded. | §10, Tables 6–7 |
| Cache state was associated with substantially different latency | Selected Gemma debug jobs: median TTFT 69.4 seconds for 85 no-reuse requests with 30k–36k input tokens, versus 2.8 seconds for 280 requests with ≥90% reuse and <2k fresh tokens. Cohorts span MLX and llama.cpp and are unmatched. | §7.1, Table 3 |

These results establish useful worker contributions and unfavorable frontier-spending outcomes for the tested workflows. They do not establish model rankings, general coding success rates, causal cache improvements, or total deployment economics. The signature diagnostic identifies rejected functional candidates, not additional end-to-end successes.

## Limitations and validity risks
- **Author-stated scope:** One practitioner’s evolving setup, selected TypeScript fixtures, few worker configurations, and one parent harness limit generalization to production repositories or complete products (§12).
- **Scorer provenance:** Tests were AI-assisted and not externally audited. The first suite lacks an independently preserved pre-run hidden-test snapshot; the second suite was frozen and hash-recorded before scoring (§12).
- **Comparison confounds:** Earlier worker inputs omitted separate constraints and sometimes suffered truncation. Later cohorts differed in dates and cache state; the Nemotron study included session replacements and a client-version change (§§9, 12).
- **Observational latency:** Cache cohorts differ in request composition and have incomplete hardware/runtime metadata; patch effects were not isolated (§§7, 12).
- **Audit and economics:** Raw artifacts are unavailable, and local hardware, energy, engineering time, and depreciation were unmeasured (§12; Data availability).
- **Analyst inference:** End-to-end failures combine contract compliance, parent acceptance, and coding behavior, so low workflow scores alone cannot isolate worker implementation ability (Table 5c; §9.4).

## Open research questions
- **Can bounded repair improve verified substitutions economically?** The paper proposes but does not run this intervention. Compare one-shot delegation with one validation-error repair attempt, counting all failures, time, and spending (§11).
- **Would a behavior-aligned signature gate improve operational outcomes?** The offline diagnostic omitted parent review. Prospectively compare strict and relaxed gates through the complete acceptance-and-application workflow (§9.4).
- **How much latency do cache-preservation changes cause?** Existing evidence is observational. Replay matched requests while varying prefix stability, session affinity, and auxiliary traffic individually (§7).
- **Do the findings transfer to other workflows?** Parent and task diversity are narrow. Repeat a frozen, randomized comparison across parent harnesses and independently reviewed repository tasks (§12).

## Confidence and missing information
**Confidence: medium** in the reported descriptive findings; low in broader causal or capability conclusions.

Material unavailable information includes raw logs, prompts, artifacts, harness and scorer code, task fixtures, complete hardware/runtime provenance, an independently preserved first-suite pre-run scorer snapshot, and measured local-worker costs. These gaps prevent independent audit and reproduction (§12; Data availability).
