# Do Language Models Need a Trainable Input Embedding Table? Fixed Minimal Token Codes at 1.7B-Class Scale

> [← Daily summary](../2026-10-07.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.04002) · [arXiv](https://arxiv.org/abs/2610.04002)


## One-sentence takeaway
At the tested 1.7B-class scale and target training budget, fixed binary token identities support substantial language-modeling capability without trainable input rows, although the learned-input control performs better on several informative benchmarks (§§5–6).

## Problem and motivation
Conventional embedding tables combine token identification with independently trainable token vectors. The paper asks whether that trainable parameterization is necessary for useful language modeling, rather than merely beneficial. Holding input coordinates fixed also creates a controlled boundary for studying downstream representation learning (§1).

The identified gap is empirical characterization of a restrictive interface—minimal binary identities with no learned input generator—at this scale using standard language-model evaluations. The author explicitly acknowledges earlier shared embeddings and embedding-free models (§2).

## Approach and contributions
- **Controlled input intervention:** Train three decoder-only models from scratch with the same tokenizer, contextual backbone, untied output-head architecture, and recipe: learned inputs, canonical binary codes, and one invertible GF(2) recoding (§§3–4).
- **Restricted fixed interface:** Encode 49,152 token IDs with 16 bits and repeat each code 128 times to width 2048, without a trainable input projection. Fixed codebook lookups remain, as does the trainable vocabulary-sized output head (§3).
- **Capability and quality-cost characterization:** Evaluate retained performance and losses relative to the learned-input control; this is a backbone-matched intervention, rather than an equal-parameter or measured-compute comparison (§§4–5).
- **Research instrument:** Establish a viable immutable input boundary for future representation studies, without identifying where lexical computation or capabilities reside (§§6–7).

The evidence supports the author’s feasibility claim for these checkpoints and interfaces. It does not establish performance parity, assignment invariance, broad reasoning ability, sample efficiency, or mechanistic localization. WikiText performance is discussed qualitatively, but its numerical scores are absent. The supplied text contains table captions without the corresponding score cells.

## Limitations and validity risks
- **Author-stated replication limit:** One run per interface and one recoding do not estimate training variability or robustness across code assignments. Evaluation standard errors cannot resolve this (§§3.4, 4.3–4.4, 8).
- **Author-stated confounding:** Trainability, parameter count, geometry, and input scale change together; recipes are not independently tuned. The quality gap cannot be assigned to one mechanism (§8; Appendix B).
- **Author-stated scope limit:** One tokenizer family, vocabulary, context length, data configuration, and main scale; multilingual, long-context, instruction-tuned, and other-budget behavior remain untested (§8).
- **Reproducibility qualification:** Resume does not restore complete sampler state, so nominally shared seeds do not establish identical sample order. Training and inference adapters can use different target-label conventions (§4.3; Reproducibility Statement).
- **Evaluation qualification:** Matching prompt multisets does not validate every adapter or likelihood-alignment path; five-shot MMLU includes truncation (Appendix C).
- **Boundary case and analyst inference:** All-zero-code sequences produce uniform next-token distributions in the stated architecture. Because actual special-token and empty-context handling is unavailable here, its practical evaluation impact cannot be assessed (Appendix D).
- **Author-stated systems limit:** A full trainable output matrix remains, and throughput, energy, and latency benefits are unmeasured (§8).

## Open research questions
- **What causes the quality loss?** Several interface properties change simultaneously. Compare norm-matched fixed codes, learned low-dimensional codes, and independently tuned recipes to separate scale, dimensionality, and trainability effects (§§7–8).
- **How sensitive is performance to code assignment?** Only one recoding is tested. Train multiple recodings across multiple initialization seeds and report task-level performance distributions (§§3.4, 8).
- **Where does lexical computation emerge?** Immutable inputs do not localize capabilities. Combine measurements across depth and training with layer ablations and controlled activation substitutions (§§6.3, 7).
- **Does viability generalize beyond this setting?** The architecture and data scope are restricted. Repeat the matched intervention with another tokenizer, multilingual data, or a different training budget (§8).

## Confidence and missing information
**Confidence: medium.** The method and qualitative conclusion are clearly supported, but quantitative comparison is incomplete.

Material missing information includes actual table cells, exact learned-control scores and evaluation errors, numerical WikiText results, realized checkpoint token counters, detailed audit counts, and the practical handling of zero-code special tokens. Multi-seed results, broader recoding tests, matched-scale ablations, and measured systems performance are explicitly unreported.
