# Scaling Lean Theorem Proving for Real-World Code Verification

> [← Daily summary](../2026-10-30.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.38174) · [arXiv](https://arxiv.org/abs/2610.38174)


## One-sentence takeaway
The authors report that EasyProver nearly saturates several Lean benchmarks, while proving only 52.7% of a sampled Aegis verification set built from translated Rust implementations (§4).

## Problem and motivation
Long proofs require decomposition, auxiliary lemmas, and recovery from failed strategies despite finite context and compute. Program verification adds implementation obligations involving arithmetic bounds, mutation, termination, and data representations (§1).

The authors identify an evaluation gap: existing verification benchmarks are small, static, and increasingly saturated. Aegis aims to generate harder tasks automatically, with independently checkable outcomes that could also support training rewards (§§1–2).

## Approach and contributions
1. **EasyProver:** A proving runtime around the off-the-shelf Anthropic Fable-5 model, without additional training. Recursive agents use isolated contexts and asynchronous returns; parallel tactic probing compresses local search feedback. InfiniLean supplies elastic, stateless Lean elaboration (§3.1).
2. **Aegis:** A pipeline that generates safe Rust solutions to competitive programming problems, translates them through Charon and Aeneas, checks Rust–Lean agreement on retained tests, and generates formal specifications separately from proof search (§3.2).
3. **Acceptance safeguards:** Statements are frozen before solving. Final proofs or refutations must compile without `sorry` and satisfy an axiom allowlist through Lean Comparator, independently of interactive search (§3.1).

The contributions concern orchestration and task generation; Aeneas translation and Lean checking are existing components. RLVR use is proposed, not evaluated (§§2–4).

## Evidence and main results

All results below are author-reported.

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| High mathematics coverage | PutnamBench: 669/672 proved (99.6%), versus a cited guidance-assisted configuration’s 597/672; also all six IMO 2026 and all twelve Putnam 2025 problems solved. | §4, Formal mathematics; Table 1 referenced |
| High verification resolution | VERINA: 189/189 resolved; AlgoVeri: 77/77; NTP4VC: 597/600 (99.5%), comprising 588 proofs and nine refutations. Resolution includes proving the negation. | §4, Code verification; Table 2 referenced |
| Lower coverage on CLEVER | 113/143 resolved (79.0%), restricted to tasks translating to Lean 4.32. | §4, Code verification; Table 2 note |
| Corpus construction succeeds on most attempted problems | 2,045/2,356 problems (86.8%) passed Rust tests, extraction, translation, Lean elaboration, and differential evaluation; 11,533 candidate specifications generated. | §§3.2–4 |
| Aegis remains challenging | Sample: 2,000 statements across 1,257 programs; 1,997 attempted under a 30-minute budget per statement, 1,054 proved (52.7% of the sample), 943 unresolved. Screen-refuted statements and requested-false specifications were excluded. | §4, Aegis |
| Difficulty varies by task category | Within that Aegis sample, proof rates were 84.1% for edge cases versus 31.0% for explicit contracts, and 66.7% for Easy versus 37.6% for Hard source problems. | §4, Aegis |
| Even totality can remain unresolved | Bottom-up merge-sort totality was unresolved within 30 minutes; the theorem requests successful termination under its input-length bounds, without sorting correctness. | Appendix H.1–H.2 |

The evidence supports strong performance by the complete system and substantial remaining difficulty on the selected Aegis sample. It does not isolate which runtime components cause the gains. Kernel checking establishes the frozen formal claim under the declared trust policy; it does not establish that the specification fully captures the informal problem or that Rust and Lean agree beyond tested inputs (§§2–4).

## Limitations and validity risks
- **Author-stated:** No component ablations or comparison against the same model using Lean without the harness were run (§4).
- **Author-stated:** The model’s training cutoff is unavailable, so exposure to informal competition solutions cannot be ruled out (§4).
- **Author-stated:** Aegis excludes stateful/class interfaces and unsupported features such as hash tables, closures, nested references, and unrestricted aliasing (§3.2).
- **Author-stated:** Other-prover evaluation, RLVR, distillation, and mutation-task evaluation remain future work (§§2–4).
- **Analyst inference:** The selected Aegis sample does not establish performance over all candidate specifications, particularly negative specifications and screen-refuted cases (§4).
- **Analyst inference:** Proof success is not uniformly full functional correctness: examples establish only output length or totality (Appendices B and G).
- **Analyst inference:** Published comparisons require caution because proof-only and proof-or-refutation metrics differ; complete table bodies and matched compute details are unavailable in the supplied text (§4).
- **Coverage limitation:** The supplied source is truncated, including a substantial middle portion of the appendices; this analysis does not provide complete paper coverage.

## Open research questions
1. **Which orchestration components improve success per unit compute?** No ablations isolate them (§4). Next experiment: compare the full system with individual components removed and a same-model Lean-tool baseline under matched budgets.
2. **Does Aegis challenge other provers similarly?** Only EasyProver is evaluated (§4). Next experiment: run several provers on the same frozen sample with common acceptance rules and compute accounting.
3. **How faithfully do generated specifications capture intended behavior?** Formal acceptance checks statements, while examples include weaker structural properties (§3.2; Appendices B and G). Next experiment: independently audit a stratified specification sample for semantic coverage and precondition quality.
4. **Do Aegis labels improve verification through RLVR?** Training use is proposed but untested (§4). Next experiment: train with these rewards and evaluate on held-out programs and independently generated specifications.

## Confidence and missing information
**Confidence: medium.** The supplied methods and headline results are explicit, but the source is truncated.
