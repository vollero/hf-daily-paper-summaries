# VibeGame: Prompt-to-Game Development with AI-Native Engine and Self-Evolving Adversarial Agent Team

> [← Daily summary](../2026-10-30.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.33106) · [arXiv](https://arxiv.org/abs/2610.33106)


## One-sentence takeaway
VibeGame combines an agent-oriented 2D engine, independent implementation and review roles, and reusable project experience, achieving higher overall scores than evaluated harnesses on an adapted GameCraft-Bench subset, although accumulated experience can also hurt performance.

## Problem and motivation
Creating a playable game requires coordinating code, scenes, assets, physics, animations, and configuration while checking their behavior during play. The authors identify three gaps in existing workflows: project dependencies are difficult for agents to inspect, build checks miss interaction-dependent failures, and validated development experience is lost between projects (§1).

Their target is an editable, runnable 2D game project generated from a natural-language request and optional reference images, with interactive verification inside the development loop.

## Approach and contributions
- **AI-native engine:** A Phaser-based engine organizes scenes, nodes, assets, and dependencies in schema-validated JSON. Agents can pause execution, advance frames, inject actions, inspect runtime properties, and capture screenshots; engine source is included in each project (§3.1).
- **Adversarial Agent Team:** Eight roles— orchestrator, designer, artist, architect, programmer, auditor, player, and reviewer—separate construction from static auditing, runtime testing, and final acceptance. Rejected work returns to repair loops (§3.2).
- **Training-free experience reuse:** Accepted projects yield runnable skeletons, reusable behavior modules, and role-coordination contracts. These initialize later projects without updating model weights (§3.3).

The central contribution is the integration of structured project state, controllable runtime verification, and independent review. Experience reuse is evaluated separately; the main comparisons use no accumulated experience (Appendix H).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Higher overall score with GPT-5.6-Luna | On 30 adapted tasks, VibeGame P2G scores **49.99**, versus **38.29** for the strongest baseline, Qwen Code P2G: **+11.70 points**. VibeGame leads all four categories. | Table 1; §4.2 |
| Higher overall score with GPT-6.1-Sol | Same subset: VibeGame P2G scores **72.99**, versus **68.80** for Codex P2G: **+4.19 points**. Content Depth improves by **4.76** and Art & Presentation by **7.72**; Core Mechanics and Functional Visuals are slightly lower. | Table 1; §4.2 |
| Human preference supports the overall ranking | Blind study: **30 participants**, **150 game pairs**, **300 judgments** across all tasks and five GPT-6.1-Sol baselines; reported average overall VibeGame win rate is **72.7%**. | §4.2; Fig. 4(b) |
| Engine and review roles contribute | On the **10-task GPT-5.6-Luna ablation set**, full VibeGame scores **53.45** overall; removing the engine gives **43.12**, and removing auditor/player/reviewer gives **48.82**. | Table 2 |
| Engine also helps another harness | GPT-6.1-Sol Codex, PA2G, all **30 tasks**, same asset library: adding the engine increases overall score from **64.44 to 67.13**. | Appendix G; Table 5 |
| Selected experience transfers across models | Experience from GPT-6.1-Sol on **five tasks outside the ablation set** increases GPT-5.6-Luna’s ablation score from **53.45 to 56.37**. Content Depth and Functional Visuals nevertheless decline. | Table 2; Appendix C.1 |
| Judge choice affects effect size | Under GPT-5.5 judging, GPT-6.1-Sol VibeGame scores **78.57** versus Codex P2G’s **77.44**; VibeGame remains best overall, but scores and rankings change. | Appendix A; Table 3 |

Overall scores combine task-specific category weights with a build/playability gate. Model evaluation uses recorded input-trace replays and averages three judge passes (Appendix A).

The evidence supports better rubric scores and human preferences within this adapted 2D setting. It does not establish commercial readiness, long-term playability, or comparability with original GameCraft-Bench results; the authors explicitly reject that last comparison because the engine and instructions changed (Appendix C.2).

## Limitations and validity risks
- **Author-stated scope:** No validation on complex 3D scenes, complete commercial games sustaining long-term play, or operation on existing projects in established engines (Limitations, p. 10).
- **Author-stated negative transfer:** Accumulating experience across different game types can reduce performance. Appendix H gives no quantitative breakdown or tested remedy.
- **Analyst inference—component attribution:** Engine removal jointly removes multiple capabilities, while the review ablation removes three roles together. These experiments do not isolate schema validation, runtime control, source access, or individual review roles (Table 2).
- **Analyst inference—evaluation coverage:** Automated scoring sees submitted recordings rather than source or unrestricted gameplay. Short demonstrations and named scenario initialization may miss failures elsewhere in the game (Appendices A and C.2).
- **Analyst inference—uncertainty and resources:** The supplied text provides no confidence intervals, repeated development-run variability, or actual token, monetary, and compute usage. Equal time limits do not establish equal resource consumption.
- **Analyst inference—judge dependence:** GPT-6.1-Sol is both a generation model and the principal judge. Human preference and alternative-judge results provide supporting evidence, but do not resolve all judging biases (§4.2; Appendix A).

## Open research questions
1. **Which engine capability matters most?** The engine ablations bundle structured state, runtime control, and source access. A factorial experiment disabling these separately could identify their individual effects.
2. **How can experience reuse avoid negative transfer?** Appendix H reports degradation across game types without quantifying it. Compare unfiltered reuse with genre-conditioned retrieval and revalidation on held-out genres.
3. **Do gains survive longer, less scripted play?** Automated evaluation relies on submitted recordings. Test extended independent play sessions and unseen input sequences, measuring failures and gameplay completion.
4. **What quality–cost tradeoff does independent review provide?** Review improves scores, but resource usage is unavailable. Compare individual review roles under matched token or monetary budgets.

## Confidence and missing information
**Confidence: medium.** The supplied text supports the architecture and reported aggregate comparisons, including the negative self-evolution observation. Material gaps include run-to-run uncertainty, statistical significance, actual resource consumption, detailed human-study assignment and agreement, isolated capability ablations, quantified negative transfer, and verified repository contents.
