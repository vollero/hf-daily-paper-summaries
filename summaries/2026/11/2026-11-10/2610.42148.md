# Flide: Accelerating Decision Inference with Exact State Forking

> [← Daily summary](../2026-11-10.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.42148) · [arXiv](https://arxiv.org/abs/2610.42148)


## One-sentence takeaway

Flide jointly evaluates shared-context decision queries using exact state forking, reporting up to 9.5× lower latency than the better of vLLM and SGLang while preserving standalone-query semantics in exact arithmetic (§§3–4.2).

## Problem and motivation

Decision models answer several categorical questions about a shared passage or agent history. Generation-oriented engines process questions as separate sequences, incurring repeated prompt preparation and prefix computation or restoration. Concatenating questions with delimiters shares computation but changes their inputs and potentially their probabilities (§1).

The authors identify a mismatch between logical request trees and physical sequence execution. Hybrid models add a challenge: masking attention cannot isolate branches when recurrent states already incorporate preceding tokens (§§1, 3.1).

## Approach and contributions

- **ForkAttention:** Flatten requests into one token stream while recording request, branch, and position metadata. Attention exposes only the shared trunk and the current branch; Gated DeltaNet layers initialize each branch from its trunk’s recurrent state and convolution window (§3.2).
- **Flat-graph execution:** Store changing request topology in GPU buffers so different request mixtures reuse capacity-bucketed CUDA graphs. Selective readout reduces final-layer computation to required answer rows (§3.3).
- **Incremental reuse and determinism:** Save internal checkpoints for growing histories. An optional mode fixes reduction orders to preserve answer bits across batch compositions on the same hardware and software (§§3.4–3.5).
- **Correctness argument:** Proposition 3.1 establishes standalone-equivalent question hidden states for causal models in exact arithmetic; Appendix A supplies the layerwise proof.

The evidence supports substantial serving improvements when questions share context, including against a delimiter-based sharing method. It does not establish universal speedups: compute-bound single-question workloads can be effectively tied. Mathematical exactness concerns equivalence to isolated computation; it does not imply float32-identical outputs, calibrated probabilities, or better task accuracy.

## Limitations and validity risks

The supplied text contains no dedicated limitations section.

- **Numerical boundary:** The theorem assumes exact arithmetic. Default floating-point execution remains batch-sensitive; optional bitwise guarantees apply on the same hardware and software (§§3.2.3, 3.5).
- **Architectural boundary:** Some supported models let questions influence the whole prompt. Flide serves these with separate question sequences or a whole-request sequence, limiting shared-trunk forking benefits (Appendix H).
- **Analyst inference—comparison confounds:** SGLang and vllm-jev use different templates; MIS disables CUDA graphs and, in growing-history tests, its radix cache. These settings complicate attribution to state forking alone (§4.1; Appendices B–E).
- **Analyst inference—external validity:** Measurements use one H200 and closed-loop clients. Cross-request prefix reuse is intentionally suppressed in the main cold tests, although recurring-state tests are also reported (§4.1; Appendices C, F).
- **Incomplete retrieved evidence:** Many tables retain only captions, including detailed fidelity and main ablation results. Narrative claims remain available, but their individual cells cannot be audited.

## Open research questions

- **How portable are the speedups?** Only one GPU type is evaluated (§4.1). Repeat representative shared-state and single-question workloads across hardware and distributed serving settings.
- **How much benefit comes specifically from forking?** Ablations and token-ID comparisons help, but templates and execution settings still differ (§4.4; Appendix E). Compare identical prompts under matched graph and cache configurations.
- **How does checkpointing behave under realistic edits and reuse?** Growing trajectories and recurring states are tested, but checkpoint-placement trade-offs are not characterized (§3.4; Appendix F). Vary edit locations, checkpoint positions, and concurrent history counts while measuring latency and memory.
