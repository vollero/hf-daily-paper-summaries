# ToolSmith: An Automatic Tool-Generation Framework for Multimodal Search Agents

> [← Daily summary](../2026-11-24.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.31198) · [arXiv](https://arxiv.org/abs/2611.31198)


## One-sentence takeaway

ToolSmith turns failed multimodal search attempts into reusable Python tools, raising GPT-4o-judged accuracy over the base-tool workflow by 2.20 percentage points in-domain and 1.33 points out-of-domain for Qwen3-VL-8B-Instruct (§§1, 4.3, 5).

## Problem and motivation

Multimodal search agents combine visual evidence with live web retrieval over multiple turns. Their hand-built tool libraries are costly to maintain and can leave recurring query types or evidence formats unsupported. The authors identify a gap between improving how agents use existing tools and expanding what tools they can call. They argue that long trajectories mixing images, links, and tool outputs make tool generation especially challenging in multimodal search (§§1–2).

## Approach and contributions

- **Failure-driven tool generation.** The pipeline classifies failed trajectories, clusters those attributed to missing capabilities, and checks each representative against the existing catalog using TF–IDF similarity. An LLM writes a typed Python tool for gaps that pass this check (§§3.1–3.3, Fig. 2).
- **Verification and reuse.** Candidates undergo sandboxed sanity testing and LLM code review, with feedback-driven retries and a final redundancy check. At inference, the agent receives the base tools plus a query-specific shortlist of generated tools (§3.4).
- **Transfer and design analysis.** The authors present the integration as the first automatic tool-generation framework for multimodal search to their knowledge. They evaluate reuse across backbones and held-out benchmarks, and vary the generator, trajectory source, and cluster count (§§1, 5–7).

The results support average gains and some transfer to benchmarks excluded from tool generation under the reported judge and workflow. Adoption shows that agents used the new tools, but its correlation with gains cannot isolate the effect of tool execution from changes to the available schemas or routing. The conclusion’s claim of improvement on every benchmark is stronger than §5’s account, which describes two out-of-domain results for the 8B agent as essentially flat.

## Limitations and validity risks

- **Author-stated limitations.** The method excludes image-generating tools, leaves code-specialized generators untested, and depends on live search APIs and proprietary models that can change over time. The authors pin model snapshots and archive trajectories to reduce reproducibility drift (Limitations).
- **Reported failure modes.** Admitted tools can return incorrect evidence, misidentify visual entities, or override a correct base-tool result. GPT-5 identity refusals are scored as incorrect, which complicates comparisons across backbones (§7.3, Appendices F.2 and B.4).
- **Analyst inference.** The design ablations cover FVQA and MMSearch only. The supplied results do not isolate the effect of either verification gate or establish whether the smaller gains exceed run-to-run variation (§6, Appendix B.3).

## Open research questions

- **How much of the gain comes from executing generated tools?** The adoption analysis is correlational. Randomize generated-tool availability across matched queries and include an equal-size catalog control (§7.3).
- **Would behavioral testing catch failures missed by the admission gates?** Some candidates passed the gates despite logic defects. Compare the existing gates with added tests on held-out inputs, measuring both tool errors and downstream accuracy (§3.4, Appendix F.2).
- **Do generator and miner preferences hold across domains and consumers?** The ablations cover two benchmarks, and the miner sweep fixes the consumer at 8B. Repeat the sweeps across the broader benchmark suite with multiple consumers and matched generation budgets (§§6.1–6.2).

## Confidence and missing information

**Medium.** The supplied prose supports the pipeline and headline comparisons. Full result tables, run-level scores or dispersion, the exact judge and generation prompts, and executable tool listings are unavailable in the supplied text. The FVQA training count is also unresolved. Appendix B.1.1 reports **3,132** search-required training samples, while Appendix F.1 lists **3,312** as the first per-dataset count.
