# Let the Fixer Decide: Training a Code Localizer from the Fixer&#x27;s Likelihood

> [← Daily summary](../2026-11-24.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.12164) · [arXiv](https://arxiv.org/abs/2611.12164)


## One-sentence takeaway

Fixer-Guided Localization selected 27.5% less code than teacher localization with similar offline first-edit accuracy, but the Gemma 4 E4B evaluation did not establish a gain in issues solved (Tables 3–4).

## Problem and motivation

Code localizers are commonly trained to predict what a reference patch edits. A fixer may also need to read unchanged callers, base classes, or tests to make the right edit. The authors ask whether a fixer’s likelihood of a verified patch can provide a better training signal for selecting context, using supervised fine-tuning without executing tests for each candidate (§§1–2).

## Approach and contributions

- **Fixer-guided training.** A localizer proposes code locations, and a frozen fixer scores them by the average log-probability of the verified patch’s added-line tokens, with penalties for context size and extra reads. Per-task weights drive supervised fine-tuning, with the teacher localization retained as an anchor. Cross-fold proposal and scoring reduce task memorization. The experiment updates only the localizer for one round (§§2.2–2.4, §4).
- **Verified trajectories and replay pipeline.** The authors report releasing 1,629 test-verified Kimi K3 trajectories. Their pipeline converts single-agent traces into localizer and fixer records, reconstructs training prompts through the competition harness, and checks reconstructed reads against code the teacher actually saw (§3, §8, Appendix F).
- **Controlled evaluation and trace analysis.** The study compares likelihood-weighted targets with an extra-training control that reuses teacher targets, and examines how timeouts, repetition, and repository-path errors affect repair (§§4–5).

The offline comparison supports using the fixer’s score to select smaller contexts in this setup. The first-edit result is a measure of where editing starts, so it cannot establish equivalent repair success. The development runs show changes in agent behavior, while the matched solve-count discrepancy and lack of a statistically significant reported gain leave the effect on hidden-test success unresolved.

## Limitations and validity risks

- **Authors’ limitations.** The study uses one model size and one localizer-only update, with one run per system and setting. Offline candidates follow teacher exploration, and the signal test measures edit location. Four-way evaluation concurrency slows each task relative to the competition scorer (§7).
- **Analyst inference.** Context overflows were counted as stopped attempts and occurred more often for larger contexts. The offline comparison therefore combines the quality of the selected code with whether the context fits the rollout setup (Table 3, Appendix E).
- **Analyst inference.** A scoring job ended early and unscored tasks retained teacher targets, so the results describe a partially scored training round. The supplied prose and table also disagree on the matched solve count (§4, §5.2, Table 4, Appendix E).

## Open research questions

- **Does fixer likelihood predict test-passing repairs?** The offline check measures edit location. On held-out tasks, run the same fixer from teacher and ranked candidate contexts with repeated sampling, then compare paired hidden-test pass rates.
- **Does the signal hold after the localizer explores independently?** Candidate generation starts after teacher exploration. Compare candidates generated after independent and teacher-led exploration under the same context and tool budgets.
- **Do further rounds or fixer updates improve repair?** The experiment updates only the localizer once. Compare one-round training, repeated localizer-only updates, and alternating fixer updates across matched evaluation runs.

## Confidence and missing information

**Medium.** The method and offline comparison are documented. The correct solve count and paired task outcomes for the matched soft-FGL comparison remain unresolved. The text also provides no repeated runs at that exact setting to estimate run-to-run variation.
