# MAServeBench: Benchmarking Multi-Agent LLM Serving Systems with Hierarchical Collaboration Workloads

> [← Daily summary](../2026-11-03.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2610.40293) · [arXiv](https://arxiv.org/abs/2610.40293)


## One-sentence takeaway
MAServeBench separates collaboration-generated work from dependency-constrained execution, showing that better token throughput or memory efficiency need not improve timely completion of multi-agent tasks.

## Problem and motivation
Multi-agent collaboration changes which model calls occur, what context they consume, and when they become executable. Request counts, token lengths, and arrival traces alone cannot capture the collaboration rules producing these demands (§§1–2).

The authors identify a gap between evaluating agent task quality and understanding serving behavior: researchers need configurable native workloads, reproducible comparisons at fixed realized work, and measurements connecting GPU/NPU execution to complete-task deadlines.

## Approach and contributions
- **Composable workload construction:** Stages specify participants, coordination, and context construction. Spawn, Fork–Join, Refinement Loop, and Debate templates compose into workflows independently of task inputs and tools (§3).
- **Separate work generation from work exposure:** Native execution generates calls and artifacts. Hierarchical Semantic Traces retain resolved inputs, operations, and control/data/state dependencies; replay can add legal ordering constraints or vary resources while preserving recorded work (§4).
- **Task-linked evaluation:** Measurements connect task and stage identities to readiness, shared batches, operators, KV occupancy, latency, and deadline goodput. Validation combines source-workflow comparisons and replay checks; experiments examine GPU/NPU behavior (§§4–6).

The contribution is a benchmark and measurement framework; proposed hardware and distributed-serving designs remain discussion hypotheses (§6.7).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Realizations broadly track source task quality. | Seven paired native comparisons across six frameworks using Qwen3.5-9B: absolute quality differences of 1.2–3.8 percentage points on success/accuracy metrics and at most 0.019 on RACE. | §5.1; Table A.2 |
| Replay preserves audited work with limited timing differences. | Qwen3-8B/910C, Fork–Join and Fork–Join with Refinement, one or 16 concurrent roots, caching on/off: all 204 paired roots preserve payloads, token counts, operations, and dependencies; reported latency differences span −1.85% to +2.88%. | §5.2; Appendix B.2 |
| Smaller delivered context can generate more total work. | One native HTTP-binding Full/Selected pair: Selected lowers first-writer input by 7.5% but increases total input by 28.4%; calls grow from 25 to 30 and graph depth from 15 to 20. | §6.2; Appendix D.1 |
| Legal serialization increases latency at fixed work. | Four-call Full traces: Barrier reduces scheduled width from 24 to 12 and raises mean root latency by 26%. Three frozen GPT Researcher traces: width falls from 9 to 3 and root latency rises 40–54%, over three paired replay blocks. | §6.2; Figure 4 |
| GPU projection rankings depend on weight locality. | One-row 4096×4096 BF16 projection: RTX PRO 5000 is 1.78× faster than A800 with reused weights; A800 is 1.50× faster with eight rotating weights. These are operator probes. | §6.3; Figure 6 |
| More KV capacity reduces repeated work and task tails. | Fixed-work seven-workflow cohort, Qwen3-8B/910C, 64 roots/block: increasing nominal KV from 16 to 40 GiB reduces processed/source prefill factor by 51.97% and root P95 by 17.49%, using median within-block ratios across three blocks. | Figure 9; Appendix F.1 |
| Release rules strongly affect deadline attainment. | Spawn–Fork–Join–Refinement, Qwen3-8B/910C, second tested Poisson rate, shared 361.7-second deadline: DAG achieves 100% median attainment versus Barrier’s 4% under both KV budgets, without preemption. | §6.6; Figure 12; Appendix C.2 |
| Throughput gains can fail to improve deadline goodput. | At the highest rate in the same study, 40 versus 16 GiB raises DAG output TPS by 7.7% and lowers root P95 by 15.5%, while deadline goodput remains near zero; timely counts are unchanged in most paired comparisons. | §6.6; Appendix C.2 |

These author-reported experiments support distinguishing generated demand, legal release constraints, and backend execution costs. They do not establish universal effect sizes across models or deployments. Operator speedups are not end-to-end serving speedups, and fixed-work replay does not measure how changed generated answers would alter future collaboration.

## Limitations and validity risks
- **Author-stated replay boundaries:** HTTP and Ascend adapters use length-locked replay. Exact-token validation covers a bounded CUDA configuration; forced KV preemption and live cancellation require separate validation (Appendix B.3).
- **Author-stated state requirements:** Persistent-memory replay requires reproducible snapshots and restoration hooks. Tools return recorded results after recorded durations, limiting evaluation of live external-service variability (§4.2).
- **Analyst inference—deployment scope:** Main application experiments use one exposed accelerator per serving instance and tensor parallelism one. Multi-replica routing and prefill/decode disaggregation are proposed extensions, so distributed-serving conclusions remain untested (§§6.1, 6.7).
- **Analyst inference—coverage and attribution:** Explicit profiler joins cover 17.5% of pooled matrix time, and matched NPU probe shapes cover only part of sampled application matrix time. Hardware attribution is therefore partial (Appendix E).
- **Analyst inference—generalization:** Some controlled studies repeatedly execute frozen bindings; the native context-delivery comparison uses one pair per document binding. These support mechanism demonstrations more strongly than population-wide effect estimates (Appendices C.2, D.1).
- **Analyst inference—functional equivalence:** Similar task scores support approximate correspondence, not identical behavior or serving demand; Table A.2 explicitly shows differences in calls and token work.

## Open research questions
- **Does length-locked replay preserve configuration rankings under cache pressure?** Exact-token validation excludes forced preemption. Next experiment: compare both replay modes under constrained KV budgets, measuring cache hits, recomputation, and task goodput (Appendix B.3).
- **How do routing and phase placement affect task deadlines?** Distributed deployment is discussed rather than evaluated. Next experiment: hold traces and arrivals fixed while varying replica affinity and prefill/decode placement, including transfer and queueing costs (§6.7).
- **Can dependency-aware KV retention improve timely completion?** Capacity experiments show benefits, but do not evaluate the proposed retention policies. Next experiment: compare eviction policies at equal KV capacity using deadline goodput and recomputation as outcomes (§§6.4, 6.7).
- **How robust are context-delivery effects across native runs?** The HTTP example shows local input reduction causing additional work, but uses a single native pair. Next experiment: repeat across more bindings and seeds, measuring quality, generated graph structure, and total task cost (Appendix D.1).

## Confidence and missing information
**Confidence: medium.** The supplied text provides detailed protocols and internally consistent controlled findings, but many referenced tables and figures contain captions without their underlying values or graphics.

Material missing information includes complete trace-schema fields, several run-level result tables, full platform/protocol tables, uncertainty estimates beyond reported block ranges, and independently verified code or artifact availability.
