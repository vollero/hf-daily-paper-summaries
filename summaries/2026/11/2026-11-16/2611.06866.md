# GH-AWTrace: A Large-Scale Dataset of GitHub Agentic Workflow Execution Logs

> [← Daily summary](../2026-11-16.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.06866) · [arXiv](https://arxiv.org/abs/2611.06866)


## One-sentence takeaway
GH-AWTrace preserves linked GitHub agentic workflow configurations, run metadata, and execution logs for studying observable agent behavior, while explicitly treating logs as incomplete evidence rather than complete trajectories (§§II–V).

## Problem and motivation
Workflow definitions describe intended behavior, and run conclusions summarize outcomes, but neither explains intervening tool calls, access restrictions, infrastructure failures, or recovery attempts. The authors identify an execution-evidence gap and argue that archiving logs is urgent because GitHub retention policies make them disappear (§I).

## Approach and contributions
- **Verified workflow discovery:** Search generated YAML files using recursively partitioned file-size ranges, deduplicate by repository and path, and verify that the generator marker appears in an opening YAML comment (§II-A).
- **Linked execution archive:** Collect run metadata and available attempt-level ZIP archives; preserve raw content, checksums, file lists, and joinable indexes linking repositories, workflows, runs, and attempts (§§II-B–III-B).
- **Illustrative analyses:** Demonstrate access-policy failures, provider failures, adaptation after tool denial, and within-run delegation. These are examples of research uses, not a systematic behavioral evaluation (§IV).

The principal contribution is a dataset and preservation pipeline, rather than a new agent model or execution method.

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Large linked corpus | 25,014 verified workflows across 5,051 repositories, linked to 4,112,526 run records dated August 14, 2025–September 21, 2026. | §§II-A–B |
| Substantial log attrition | For 2,453,263 selected run records from June 23–September 21, 2026, collection saved 1,633,215 attempt ZIPs: 1,070,338 empty and 562,877 nonempty. Nonempty archives belong to 561,367 runs. Runs and attempt archives are different counting units. | §II-C; Fig. 1 |
| Uneven workflow coverage | Among 6,040 workflows with logs, median coverage is 16 archives per workflow, with an interquartile range of 6–60; each downloaded execution attempt contributes an archive. | §III-C; Fig. 3 |
| Failure-linked archive share | 178,151 of 562,877 nonempty archives (31.7%) link to run records whose conclusion is failure. This is an archive-level association, not an agent-caused failure rate. | §IV-A |
| Logs expose execution mechanisms | Selected examples show blocked issue access, provider authentication failure, changed behavior after tool denial, and delegation with missing reviewer responses. | §§IV-A–C; Examples 1–5 |

The evidence establishes the corpus’s reported scale and demonstrates that some logs reveal behavior unavailable from run conclusions alone. It does not establish representative frequencies of particular behaviors, causal failure attribution, or independently verified task completion. There is no comparative agent-performance evaluation.

## Limitations and validity risks
- **Authors’ stated limits:** Retention, retrieval failures, empty archives, and uneven coverage restrict observability; nonempty archives need not contain complete agent traces (§§II-C, V).
- **Configuration provenance:** Runs are linked to the YAML revision found during discovery, which may differ from the executed revision; run metadata retains `head_sha` (§II-B).
- **Interpretation boundaries:** Visible messages are not complete prompts or private reasoning; job-log filenames do not assign message roles. The coordination example establishes no shared memory across runs (§§IV-B–C).
- **Analyst inference:** Analyses restricted to available logs may suffer selection bias because missingness has several unresolved causes. The discovery procedure also does not establish exhaustive coverage of all gh-aw workflows (§§II-A, II-C).
- **Authors’ stated generalization limit:** Broader behavioral claims require systematic sampling and validation beyond the illustrative cases (§V).

## Open research questions
- **How often do run conclusions agree with actual task completion?** The paper distinguishes these concepts without measuring agreement. Next experiment: manually validate a stratified sample against resulting repository artifacts and compare judgments with run conclusions (§V).
- **Which failures originate in agents, policies, or infrastructure?** The aggregate failure-linked share does not attribute causes. Next experiment: annotate sampled failures using a documented taxonomy and measure annotator agreement (§IV-A).
- **When does adaptation after tool denial succeed?** A selected trace shows adaptation but supplies no population-level recovery estimate. Next experiment: identify denial events, annotate subsequent actions, and verify resulting outputs (§IV-B).
- **How does missing log coverage affect findings?** Missing archives have unresolved causes. Next experiment: compare observed metadata for runs with nonempty, empty, and unavailable archives, then test sensitivity of behavioral estimates (§II-C).

## Confidence and missing information
**Confidence: high** for the reported dataset construction and descriptive results; **limited** for generalizing from the illustrative behaviors.

Material information unavailable in the supplied text includes Table I’s actual event counts, full figure contents, systematic case-selection criteria, validated task-completion labels, comprehensive failure annotations, and complete causes of missing or empty archives. Public availability and a reproduction script are reported, but were not independently checked.
