# LuthorSQL: A One-Pass Text-to-SQL Model as System 1 for a Slower LLM Agent

> [← Daily summary](../2026-11-16.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.17780) · [arXiv](https://arxiv.org/abs/2611.17780)


## One-sentence takeaway

LuthorSQL combines a parallel slot-filling SQL generator with confidence-based agent routing, reducing hosted-model costs in several held-out evaluations, although accuracy preservation depends on the dataset and deployment setup (§§6.1–6.4; Appendix G.5).

## Problem and motivation

Hosted text-to-SQL agents can achieve high accuracy but incur recurring costs, latency, and external exposure of organizational queries. The authors ask whether a local model can answer routine questions and defer uncertain cases while retaining the stronger agent’s accuracy (§1).

The identified gap is a fast local parser whose confidence can support useful deferral. A second concern is evaluation validity: public benchmark performance may partly reflect memorized SQL rather than database reasoning (§§1–2).

## Approach and contributions

- **Parallel structured generation:** An OmniSQL-7B backbone with a LoRA adapter predicts bounded query-plan slots in one generator pass. Slots select schema items and grounded literals; a deterministic compiler constructs joins over the foreign-key graph (§§3.2–3.4).
- **Candidate generation and validation:** Factorized scores support lazy enumeration of up to 32 distinct plans without additional generator passes. Candidates execute read-only, and a second adapter, VALHARD, scores their complete SQL. Training uses execution-checked hard negatives (§§3.5–3.6).
- **Confidence cascade:** The margin between the highest-scoring distinct result groups determines whether to answer locally or call an agent. The selected threshold is 3.0. Claude Code experiments pass candidates to the agent; the successful fresh-set plain-API configuration forwards only the question (§4; Appendix G.5).
- **Evaluation assets and diagnostics:** The authors report dialect-transfer experiments, schema-free memorization probes, renamed-schema tests, and a newly constructed post-cutoff evaluation set. Code, adapters, and the fresh dataset are reported as released (Appendices F–I).

The contribution is this combination and its evaluation; slot filling, foreign-key join inference, validators, and model cascades have precedents acknowledged by the authors (§2; Appendix L).

| Accuracy preservation does not hold universally | On BIRD dev, threshold 3.0 yields **81.55%**, versus **84.49%** for always using Opus with candidates. The later question-only API test on RESERVED saves **35.3%** but loses **2.0 accuracy points**, **p = 0.03**. | Table 13; §6.3 |

The evidence supports useful cost reductions and effective confidence-based selection in the tested settings. It does **not** establish general accuracy equivalence: nonsignificant differences have wide intervals, some settings show losses, and no cascade result is available on BIRD’s hidden test set. The hidden-test accuracy and subsecond latency also come from different evaluation sets.

## Limitations and validity risks

**Author-stated limitations:**

- The bounded grammar misses complex SQL and unseen templates. Evaluation is English-only; the cascade agent is tested only on SQLite (p. 9).
- DECISION and RESERVED are held out from adapter training, but their databases occur in the backbone’s fine-tuning data. RESERVED also influenced earlier System 1 development and checkpoint selection (Appendices E, H).
- DECISION routing uses gold-derived grammar coverage, and some handoff questions receive empty candidate lists. This can flatter exploratory results; held-out cascade tests avoid gold-based routing (§4; p. 9).
- Validator hard-negative categories were chosen after inspecting DECISION errors, making its measured gain there potentially optimistic (p. 9).
- Held-out evaluations contain relatively few database clusters, results vary across runs, and the first RESERVED run fails its registered success criteria (§6.3; p. 9).
- Costs use list prices applied to logs, not invoices. Claude Code session overhead materially affects savings; the initial candidate-handoff API cascade actually increases cost (Appendix G.5).
- The fresh set is easier than BIRD, relies on LLM generation and review, and receives only a limited manual spot-check. Renaming cannot exclude recall of query structure (p. 9; Appendix G.3).
- Registrations use internal records rather than independent timestamps; some are first committed with results. Execution accuracy on one database can accept semantically wrong queries (§2; Appendix G.6).

**Analyst inference:** The broad “same accuracy” framing is stronger than the full evidence supports. Deployment-specific cost behavior and observed accuracy losses make confidence-threshold transfer a central unresolved risk.

## Open research questions

- **Can routing adapt to changes in the stronger agent’s advantage?** BIRD dev shows that a useful System 1 confidence signal does not guarantee a transferable cascade threshold. Test threshold calibration on new databases against a fixed threshold under an explicit accuracy-loss budget (Figure 3).
- **Can broader SQL coverage improve local answering without weakening confidence?** Grammar gaps are substantial, while a tested larger grammar fails to improve DECISION performance. Evaluate targeted grammar extensions on separately held-out complex-query families (Table 4; §3.2).
- **Do savings persist on harder, independently reviewed fresh data?** The fresh set is relatively easy and mostly LLM-reviewed. Repeat the API comparison on human-authored, fully reviewed questions over new databases, reporting database-level intervals (Appendix G.3).
- **Is the laptop configuration operationally practical?** The quantized run preserves aggregate accuracy on a partial sample, but sustained latency and complete evaluation are unavailable. Measure full-set latency, memory, energy, and routing behavior on consumer hardware (Appendix E).

## Confidence and missing information

**Confidence: medium.** The supplied text provides extensive methods, results, and candid validity disclosures, but supports conditional rather than universal conclusions.

Material missing information includes hidden-test labels explaining the dev–test gap, hidden-test cascade results, complete laptop performance measurements, independently timestamped registrations, full human validation of the fresh set, and actual deployment invoices. Reported code and model releases were not independently inspected.
