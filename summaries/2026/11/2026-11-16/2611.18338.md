# MEM-SQL: Memory-Empowered Text-to-SQL

> [← Daily summary](../2026-11-16.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.18338) · [arXiv](https://arxiv.org/abs/2611.18338)


## One-sentence takeaway

On HARE’s history-derived requests, MEM-SQL improves mean execution accuracy while reducing generation cost through layered SQL memory and selective schema access, but composing several historical queries remains difficult.

## Problem and motivation

Repeated questions over the same database can reuse verified joins, calculations, and schema mappings. The authors argue that independent-question benchmarks obscure this opportunity and do not distinguish whole-query adaptation from partial reuse. They address both how to evaluate historical reuse and how to select sufficient evidence without repeatedly consulting large schemas (§§1–3).

## Approach and contributions

- **HARE benchmark:** 1,600 requests derived from 823 verified queries across Spider, BIRD, Spider 2.0, and BEAVER. Six primitive and six composite categories annotate retained evidence and permitted edits. Construction checks execution, question–SQL agreement, and reuse preservation (§3).
- **MEM-SQL memory and retrieval:** Stores parameterized whole queries, reusable `SELECT` blocks, and domain-to-schema concepts. Requirement-specific retrieval atoms search each layer; a layer qualifies only when every assigned atom exceeds its similarity threshold (§4.2).
- **On-demand Schema Linking (OSL):** Consults schema when no layer qualifies or the generator declares retrieved evidence insufficient, followed by SQL validation and bounded repair. Transfer experiments separate its efficiency benefits from memory-dependent accuracy effects (§§4.2.3, 6).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Accuracy and cost improve together | Across six backbones on 1,600 HARE requests, authors report mean EX rising from 37.1% for Direct Generation to 50.0%, with 76.6% fewer input tokens and 68.8% lower latency on average. | Abstract; §5.2; Table 1 |
| Main-table leadership depends on linking policy | MEM-SQL beats all memory baselines using unconditional schema linking on every backbone. With OSL, Gemini4-Argon A-MEM reaches 58.6% EX versus MEM-SQL’s 57.5%. | Tables 1, 7 |
| Templates make the largest layer contribution | With OSL fixed, removing templates costs 5.3 EX percentage points on average across six backbones. Removing components costs 3.7 points on composite requests versus 1.1 on single-category requests. | §5.3.2; Table 2 |
| Retrieval atoms improve source coverage | On 240 calibration questions, source-linked micro recall is 94.58% with layered atoms versus 56.67% without atoms; flat retrieval reaches 96.25% but returns 16.48 items/question versus 10.26. | §5.3.1; Table 3 |
| Multiple-source reuse remains weak | MEM-SQL’s mean EX falls from 56.7% on single-source requests to 29.7% on multiple-source requests across six backbones. These are different request subsets. | Abstract; §5.4.2; Table 6 |
| OSL’s cost benefit transfers more consistently than accuracy | Averaged over backbones, each of three memory baselines saves at least 60% of input tokens and 34% of latency under OSL; BIRD-History loses EX on five of six backbones. | §6; Table 7 |

The evidence supports efficient reuse when new requests resemble verified history, particularly rephrases and parameter changes. It does not establish universal superiority over other memory designs under matched linking policies. Retrieval coverage also does not guarantee correct composition: §5.4.2 reports failures even when all historical sources are retrieved. Latency comparisons are valid within backbones because serving conditions differ (§5.1).

## Limitations and validity risks

- **Author-stated:** HARE excludes schema drift; memory remains static; execution accuracy can penalize formatting differences and accept queries that return correct results for unintended reasons (§7).
- **Author-observed:** Composite requests often retain incomplete evidence without triggering schema consultation. Aggregation and grouping remain major failure sources (§§5.4–5.5).
- **Analyst inference—evaluation scope:** Requests are generated from known historical queries and filtered for successful, nonempty execution. Generalization to naturally occurring workloads, irrelevant history, or empty-result requests remains untested (§3.3).
- **Analyst inference—annotation validity:** Appendix A.2.2 acknowledges examples departing from category rules, while the review prompt permits some structural template changes. Category purity therefore warrants independent auditing.
- **Analyst inference—comparison and cost:** Table 1 changes both memory design and linking policy. Offline memory-building cost and its amortization are not quantified in the reported per-request metrics.
- **Reporting ambiguity:** §5.2 reports 95.4% memory completions, whereas §5.4.1 reports 4.3% escalations; their relationship is not explicitly reconciled. Statistical uncertainty and repeated-run variation are not reported.

## Open research questions

1. **Can escalation detect composition failures?** Many incomplete composite requests remain on the memory route (§5.4). Compare the current gate with an explicit requirement-to-evidence verifier, measuring EX and escalation cost.
2. **Can synthesis improve after successful retrieval?** Multi-source failures persist with complete source recall (§5.4.2). Hold retrieved evidence fixed and compare direct generation with explicit intermediate-composition planning.
3. **How should memory handle changing definitions?** Static memory and absent schema drift leave this unresolved (§7). Introduce controlled schema and business-rule changes, then test update and retirement policies.
4. **Do gains survive natural workloads and total-cost accounting?** HARE is history-derived and reports online costs. Evaluate chronological user logs while including memory construction and maintenance costs.

## Confidence and missing information

**Confidence: high** in the described method and reported HARE results; broader deployment conclusions remain uncertain.

Material missing information includes public code/data release status, statistical uncertainty, repeated-run stability, offline construction costs, an independent human annotation audit, and evaluation under natural query histories or changing schemas.
