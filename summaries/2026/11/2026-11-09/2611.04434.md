# Sketchpad: certified exact arithmetic with a small vision-language model

> [← Daily summary](../2026-11-09.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.04434) · [arXiv](https://arxiv.org/abs/2611.04434)


## One-sentence takeaway

Sketchpad certifies a small vision-language model’s local arithmetic steps by exhaustively checking a finite set of views, yielding correctness at arbitrary input lengths conditional on the runtime and execution path—not a guarantee for interpreting whole problems (§§3, 8).

## Problem and motivation

Sampled arithmetic accuracy cannot guarantee correctness on unseen inputs, while conventional calculator tools perform the arithmetic outside the network. The authors ask whether a pretrained model can perform arithmetic itself with a finite, checkable correctness guarantee. Their key restriction is that each step reads only bounded external memory, with no history carried between steps (§1).

## Approach and contributions

- **Finite-view arithmetic execution.** A rank-16 LoRA adapter teaches Qwen3.5-0.8B to map three rendered cells plus an operation token to arithmetic outputs. A conventional runtime lays out operands, writes model outputs and controls execution, but computes no result digit itself (§2).
- **Conditional certification.** Lean proofs connect correctness on reachable views to correctness of every reference run, establish robustness under bounded logit perturbations, and characterize composition. A counterexample shows that finite tests alone cannot generally certify unrestricted history-reading decoders (§3; Appendix A).
- **Deployment and composition.** The authors enumerate all arithmetic views on the deployment device and compose the procedures into a symbolic algebra runtime (§§3–5).
- **Dialogue integration.** A scalar adapter gate restores the base model when disabled; a separately trained dialogue adapter learns when and how to invoke the sheet, with incomplete preservation of word-problem reasoning (§6).

The paper explicitly builds on earlier finite-state verification ideas; its claimed distinction is training and certifying a pretrained vision-language model’s arithmetic procedures on the deployment path (Methods, “Related work”).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Finite verification supports arbitrary-length execution | Equality with reference runs follows from correctness on every reachable view; concrete runtime correctness and view coverage remain assumptions. The converse additionally requires injective writes. | §3, Theorem 1; Appendix A |
| Deployment certificate passes | All 2,446 views pass on Apple M4 WebGPU with a 16-bit decoder; minimum margin is 3.02 logits, sufficient for per-logit perturbations strictly below 1.51. Full checking takes 3.5 minutes. | §3; Fig. 3 |
| Tested batching preserves outputs | Random partitions covering every view at batch sizes 2, 4 and 32 for the arithmetic adapter show maximum logit movement of 1.09; these checks sample batch compositions. | §3; Methods, “Certification” |
| Browser arithmetic succeeds | 200/200 exact: 50 each of division, square roots, gcd, and signed sums/differences. Median times are respectively 7.0, 9.8, 7.0 and 2.0 seconds; 184/200 meet the 12-second target. | §4; Methods, “Procedures and timing” |
| Arithmetic comparison favors Sketchpad | On 220 pre-registered problems—sums of 10–1,000 digits and products of 2–20-digit operands—Sketchpad gets 220, GPT-6.1 Sol 217, Claude Opus 5.5 216 and Gemini 4 Argon 207. Sketchpad runs in batched PyTorch; API baselines receive a 32,768-output-token budget and one run per problem. | §4; Methods, “Baselines” |
| Algebra checks detect injected faults, incompletely | Textbook route rejects 200/200 planted incorrect roots and 185/200 runs with one corrupted arithmetic result; the remaining 15 corruptions leave the answer unchanged. | Dialogue invocation improves, but reasoning retention fails | Held-out invocation precision/recall: 0.994/0.989 versus 0.971/0.809 for the prompted base model. Uncertainties are paired standard errors. | §6; Methods, “Dialogue fine-tuning” |

The strongest evidence is the combination of exhaustive local checks and conditional proofs, rather than the sampled problem scores. It establishes agreement with reference execution under the stated assumptions. It does not certify runtime implementation, natural-language translation, all batch compositions or arbitrary hardware. Dialogue benchmarks execute sheet calls using an exact reference implementation rather than the deployed model (Methods, “Dialogue fine-tuning”).

## Limitations and validity risks

- **Author-stated certification boundary:** concrete layouts, reachable-view coverage and reference procedure correctness are not formalized in Lean (§3; Appendix A).
- **Author-stated deployment boundary:** a new GPU requires a full certificate, while the client defaults to checking only the lowest-margin tenth. Batch checks do not bound every composition (§8; Methods, “Certification”).
- **Author-stated end-to-end gaps:** word-problem translation remains uncertified, and fresh GSM8K results fail the retention criterion. Algebra checks do not establish that every root was found; fixed-point expansion checks can miss cancelling errors (§§6, 8).
- **Author-stated scope:** inputs use fixed glyphs; algebra covers low-degree univariate polynomials and linear systems of up to three equations (§8).
- **Comparison uncertainty:** each baseline runs once per problem, and the authors caution that differences of a few answers are within sampling variation (Methods, “Baselines”).
- **Analyst inference:** the comparison supports arithmetic reliability under these settings, but does not establish an efficiency advantage over conventional exact arithmetic; no such measured baseline is supplied.

## Open research questions

1. **Can the concrete runtime be verified?** Its correctness and view coverage remain assumptions. A next experiment could formalize division and square-root layouts and prove that every reachable view belongs to the certified tables.
2. **Can numerical robustness cover every supported batch?** Current checks sample compositions. A next study could derive conservative execution-path error bounds and test them across devices.
3. **Can dialogue reasoning be retained alongside certified arithmetic?** Fresh GSM8K performance declines despite strong invocation scores. A next experiment could compare training recipes on untouched word problems, separating translation errors from subsequent reasoning errors.
4. **Can algebra checks become complete within the supported scope?** Current checks have stated gaps. A next experiment could add exact coefficient-identity and root-completeness checks, then measure fault detection and latency.
