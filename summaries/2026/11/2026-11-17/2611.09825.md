# BitDecoding-FP4: Native FP4 KV Cache Decoding via Algorithm-System Co-Design

> [← Daily summary](../2026-11-17.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.09825) · [arXiv](https://arxiv.org/abs/2611.09825)


## One-sentence takeaway

BitDecoding-FP4 uses native FP4 for both attention products on quantized GQA cache pages, and the authors report that its NVFP4 variant stays within 0.5 average accuracy points of BF16 KV on two Qwen3 models while delivering 2.4–3.0× the peak per-GPU serving throughput on B300 at 64K–128K input lengths (Table 1, Figure 10).

## Problem and motivation

The key–value (KV) cache grows with context length and concurrency and is repeatedly read during autoregressive decoding, straining GPU memory capacity and bandwidth. The authors identify a trade-off in existing 4-bit methods: standard NVFP4 can sharply degrade long-context accuracy, while vector-codebook methods incur lookup and reconstruction costs. Native FP4 attention also introduces query rounding, probability-scale underflow, and key outlier problems. As matrix multiplication gets faster, serial softmax reductions and probability quantization can become the kernel bottleneck (§§1–2, §4.1).

## Approach and contributions

- **Query and probability quantization.** Dual-residual quantization encodes the query and its first-pass rounding residual as two separately scaled FP4 tensors. For NVFP4 probabilities, the method combines exponent rescaling with a calibrated switch between two block-scale rules to reduce E4M3 underflow (§§3.1–3.2).
- **Key quantization.** The recipe combines an offline per-head key mean, a shared Hadamard rotation of queries and keys, and a two-candidate block-scale search to reduce outlier error within the token-wise layout required by native FP4 score computation (§3.3).
- **Decode kernel and serving backend.** Transposing the score tile lets warp threads reduce across keys and reuse intermediate maxima for probability quantization. The kernel stacks both query terms in one matrix multiply-accumulate (MMA) and sums their scores in FP32 before softmax. A device-side control kernel manages paged FP4 storage alongside BF16 sink and recent tokens in vLLM (§§4.1–4.3).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Near-BF16 average accuracy | On Qwen3-4B and Qwen3-30B-A3B, respectively, NVFP4 averages 67.27% and 72.74% across seven benchmarks, versus 67.69% and 73.15% for BF16 KV. MXFP4 averages 66.70% and 72.60%. Both FP4 variants exceed the FP8 KV averages on these models. | Table 1, §5.2 |
| Lower cache footprint on large models | Against BF16 KV, NVFP4 reduces the 355B FP8-weight GLM-4.7 cache from 71.88 to 20.27 GiB at 200K tokens, with average accuracy within 0.4 points. For 770B FP8-weight Hy4-preview with sparse MLA, the 1M-token cache falls from 90.46 to 34.41 GiB, and reported accuracy stays within 0.12 points across three tasks. | Table 2 caption, §5.2 |
| Faster decode attention kernels | At 128K context across batches of 1–64, peak NVFP4 kernel speedups over BF16 KV are 2.99× and 2.72× on B300 and 4.01× and 3.96× on RTX PRO 5000, for Qwen3-4B and Qwen3-30B-A3B respectively. | §5.3, Figure 9 |
| Faster end-to-end serving | At 256K context, NVFP4 lowers per-request time per output token from 7.74 to 4.28 ms on Qwen3-4B and from 6.66 to 4.34 ms on Qwen3-30B-A3B versus BF16 KV. On B300 with 2K output tokens and up to 64 concurrent requests, peak per-GPU throughput is 2.4–3.0× the BF16 KV baseline across the two models at 64K input with TP=1 and 128K input with TP=2. | Table 1, §5.3, Figure 10 |
| Quantization and kernel changes address measured bottlenecks | With NVFP4 keys, the residual query reduces the query term’s share of mean squared logit error from 60% to about 1%. At batch 64 and 128K on B300, transposed softmax gives a reported 1.91× pure-kernel speedup in the ablation, and stacking the query terms keeps the accuracy recipe’s overhead within 4%. | §3.1, Figure 3, §5.4, Figure 12 |
| RL rollout quality tracks BF16 KV | The authors report that NVFP4 closely follows BF16 KV on mean@4 validation accuracy during DAPO-style post-training on both Qwen3 models with BF16 weights, while standard TRT-LLM-NVFP4 degrades accuracy. | §§5.1–5.2, Figure 8 |

The experiments support a joint accuracy and throughput gain in the tested Qwen3 serving configurations. At high concurrency, the throughput result includes the benefit of avoiding cache-capacity pressure and preemption. Accuracy varies by task despite the close averages, and the sparse MLA experiment establishes cache savings while leaving latency unmeasured in the reported results.

## Limitations and validity risks

- **Author-stated scope.** Hy4-preview uses a fixed 2,048-token active window, so the authors omit latency speedup. Its MLA implementation uses FP4 for content scores, BF16 for positional scores, and an FP16 context product over dequantized latents (§5.2, Appendix G).
- **Author-stated comparison limits.** SAW-INT4 latency is omitted because it runs on SGLang while the Table 1 alternatives run on vLLM. TurboQuant is evaluated with its mixed-precision setup disabled, so the comparison covers its all-layer quantized configuration (Table 1, §5.1).
- **Analyst inference.** Serving results are specific to B300 and two Qwen3 models. The 64K and 128K runs use different tensor-parallel degrees, so context length alone cannot explain any difference between their throughput curves (§5.1, Figure 10).
- **Analyst inference.** The fine-grained key ablations use teacher-forced KL on Qwen3-4B. Appendix A checks that the proxy ranks four configurations consistently with MRCR accuracy, leaving component-level effects on free-running generation across models uncertain (Appendices A and F).

## Open research questions

1. **How much of the serving gain comes from faster attention versus fewer preemptions?** Figure 10 combines both effects. Run matched workloads first under a concurrency cap that fits both caches, then sweep concurrency through each cache’s capacity limit.
2. **How well does offline calibration transfer across checkpoints and workload distributions?** Appendices B–C give detailed calibration comparisons mainly for Qwen3-4B. Compare transferred settings with per-checkpoint recalibration on held-out long-context and reasoning workloads, measuring both downstream accuracy and probability underflow.
3. **Can sparse MLA use native FP4 for the context product and still reduce latency?** Appendix G identifies incompatible scale axes for the shared latent cache, and §5.2 provides no MLA latency result. Benchmark a second cache layout alongside runtime requantization and the paper’s FP16 context path, measuring accuracy, total cache footprint, and decode latency.

## Confidence and missing information

**High** for the described method and the main Qwen3 results, which are supported by Table 1 and explicit experimental settings. The supplied text omits the body of Table 2 and numerical plot data for the RL and serving curves. It also leaves run-to-run uncertainty for the main accuracy, throughput, and RL comparisons unspecified.
