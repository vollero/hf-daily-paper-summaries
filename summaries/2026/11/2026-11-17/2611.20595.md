# Invariant-Aware Harness Enforcement to Protect LLM Agents from Silent API Failures

> [← Daily summary](../2026-11-17.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.20595) · [arXiv](https://arxiv.org/abs/2611.20595)


## One-sentence takeaway

On AgentOrchBench’s six target faults, SilentGuard reduced wrong counts from 74.0% to 1.7% across seven open-weight models, chiefly by withholding suspect values and abstaining, while clean accuracy held at 84.9% (§5.2, Tables 2–3).

## Problem and motivation

An API can return HTTP 200 and a plausible count even when it ignores a filter or misreads a condition. An agent can then repeat that count as fact. The authors identify two gaps in existing safeguards: a response can look internally consistent without answering the request, and an agent can still report a value after receiving evidence that it is suspect (§§1–2, 5.2).

## Approach and contributions

- **Runtime verification and enforcement.** SilentGuard tests filtered counts by querying a condition’s complement and the count with that condition removed. It also checks list membership, duplicates, and totals, validates documented parameter names, and uses contracts mined from clean traces where available. After one re-check, it withholds values that still fail an exact check and warns on failed learned checks in the reported runs. A final answer gate accepts only checked counts (§3, Table 1, Appendix B).
- **Controlled comparisons.** The authors vary whether the agent or judge receives consistency evidence, whether the agent has explicit permission to abstain, and whether the harness blocks the value (§5.2, Table 2).
- **Measurement and benchmark.** The paper probes public research APIs for silent failures and introduces AgentOrchBench, a synthetic REST benchmark with persistent server-side faults and exact ground truth (§§4, 5.1, Appendix A.1).

Only learned checks were available, so SilentGuard re-checked and warned. | §5.2, Table 4, Appendix D Table 15 |

The controlled comparisons support harness enforcement when a check produces usable evidence. On persistent target faults, most of the reduction in wrong counts came through abstention. The live-API study shows that rejecting an invalid parameter can also help agents rewrite queries and recover correct answers. The external workflow results measure re-checking and warnings, leaving the benefit of exact enforcement on those workflows open.

## Limitations and validity risks

- **Author-stated.** Internally consistent faults can pass the count identity, and a filter the agent omits is outside the check’s reach. Missing values, estimated or changing totals, and unsupported negation can undermine the count check. List checks have limited visibility into records the API omits (Limitations, Appendices B, G, and I).
- **Author-stated.** Most fault types were injected into local services. Blind retry performed better on short-lived faults, and learned checks reduced clean success on ToolMaze. The frontier extension covered one vendor and fewer comparison arms, and internal traces and hash records are unavailable for those runs (§5.3, Limitations).
- **Analyst inference.** The live bad-documentation study deliberately used filter names already known to be ignored, so the observed improvement does not estimate the benefit under an ordinary production mix of faults. The reviewer baseline also used the agent’s own model, whereas the cited method uses a separate reviewer, which limits the comparison with that original setup (Appendices A.2 and C).

## Open research questions

1. **Can the harness verify that the query preserves the user’s requested conditions?** Some replayed queries were internally consistent after the agent dropped or rewrote a condition. Compare a task-to-query semantic check with API consistency checks on held-out query-string tasks with annotated filters (Appendix A.2).
2. **Can count checks remain reliable on changing data or fields with missing values?** The paper assumes two-valued filters and reports errors associated with changing totals. Compare two-way and three-way partitions on live and snapshot-backed queries, measuring false alarms and missed faults (Limitations, Appendix B).
3. **Can independent verification recover more answers at the same error rate?** Same-API auto-repair released wrong counts marked as verified on unseen faults. Test a fallback backed by an independent source and compare its risk–coverage curve with abstention on held-out count and list faults (§5.4, Table 6, Appendix G).

## Confidence and missing information

**High** for the reported benchmark comparisons. The supplied text describes the protocol, grading, and key results, but some referenced tables appear only as captions or summaries, leaving full per-model and per-fault cells unavailable. Internal-run traces and hash records are unavailable, and the study does not establish production fault prevalence or the performance of enforced checks on writes.
