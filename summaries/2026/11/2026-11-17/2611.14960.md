# Termination Lag: Coding Agents Solve Early but Stop Late

> [← Daily summary](../2026-11-17.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.14960) · [arXiv](https://arxiv.org/abs/2611.14960)


## One-sentence takeaway

In the core SWE-bench settings, coding agents spent a median of 35–60% of steps after their first benchmark-passing patch in runs that finished successfully, while 1–8% of runs that ever reached a passing patch ended with a failing one across the settings analyzed for regressions (§§4.2, 5).

## Problem and motivation

Final-patch scoring hides when an agent first solves a task and whether it later loses the fix. This makes it hard to assess stopping behavior and the cost of continued work. The authors identify a gap in systematic measurement of the interval between first benchmark correctness and termination, while recognizing that agents need some verification because they cannot see the official benchmark tests (§§1, 2.2–2.4).

## Approach and contributions

- **Trajectory measurement.** Record the repository diff after each agent step and evaluate each distinct patch offline with the official benchmark procedure in isolated containers. Agents receive no feedback from this evaluation (§3.5).
- **Stopping metrics and oracle reference.** Measure the first passing step, the steps from there to termination, and their fraction of the full run. Use a retrospective oracle that stops at the first passing patch to estimate the steps that ideal stopping could save (§§3.6, 4.2).
- **Empirical characterization.** Measure first-edit correctness, classify post-fix activity from tool traces, and track whether benchmark correctness persists, is lost and recovered, or is lost at submission (§5).

| Finding | Evidence / setting | Location in paper |

| Lag persists under a second framework | On Qwen3-Coder and Verified, OpenHands and mini-SWE-agent solve 43.8% and 32.4% of tasks, respectively. Among solved runs, median lag is 16 and 12 steps, with median normalized lag of 35% and 37%. | Appendix A.3.1, Table 4 |

| Continuing can lose a passing patch | Across settings reported for this analysis, 61–96% of runs that ever pass remain passing throughout, and 1–8% finish with a failing patch. | §5, Table 3 caption |

The trajectories establish when patches pass the benchmark and how much work follows. The authors’ oracle estimates potential step savings with hindsight. Whether an agent can realize those savings using only evidence available during execution, and what savings would follow in latency or compute, remains untested.

## Limitations and validity risks

- **Author-stated.** Each task was run once, and transfer beyond the evaluated models, benchmarks, and frameworks is uncertain. Runs hitting step or context limits are counted at their final step, affecting 1–4% of solved runs per setting. Steps approximate compute cost, action labels are rule-based, and Seed-OSS on Pro has few solved tasks (Limitations).
- **Analyst inference.** The framework comparison uses one model–benchmark pair and different tool interfaces and prompts. Its solved-run medians also condition on success under each framework, so they do not isolate a framework effect (Appendix A.3.1, Table 4).
- **Analyst inference.** Benchmark pass status cannot resolve whether later verification or edits improve patch quality on criteria the benchmark does not score (§§3.5, 5).

## Open research questions

1. **Which evidence available during a run supports safe early stopping?** The oracle uses hidden tests. Compare stopping rules based on agent-visible test and build results with ordinary termination and the oracle on held-out tasks, measuring solve rate, steps, tokens, and latency (§§1, 4.2).
2. **When does additional verification improve patch quality?** The paper measures activity and benchmark pass status. Compare first-passing and final patches with independent tests and blinded review, then vary the verification budget to estimate its effect (§5).
3. **How stable is lag across repeated runs and frameworks?** Each task was run once, and the second framework was tested on one model–benchmark pair. Repeat matched tasks across seeds and frameworks under aligned budgets and report both within-task variation and final solve rates (Appendix A.3.1, Limitations).

## Confidence and missing information

**High** for the central descriptive findings reported in the prose and visible table entries. It also supplies no repeat-run uncertainty estimates, full action-labeling rules, or release information for the logging code and trajectories.
