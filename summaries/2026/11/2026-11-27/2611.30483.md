# When an AI agent makes a mistake in a database, what decides the damage?

> [← Daily summary](../2026-11-27.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.30483) · [arXiv](https://arxiv.org/abs/2611.30483)


## One-sentence takeaway

In the tested database setups, recovery determined whether some mistakes became permanent losses, least privilege helped where it blocked the operations responsible, and the study could not establish whether engine choice or model choice mattered more for permanent loss.

## Problem and motivation

A mistaken agent command can delete or alter production data, but the consequences depend on what the database permits and what operators can recover. The authors identify a gap in prior work, which largely holds the tool environment fixed or measures task correctness and policy compliance. They compare database engines, permissions, and recovery directly at the data plane, where the agent’s statements execute (§§1–2).

## Approach and contributions

- **Two complementary evaluations.** Layer A scripts 22 canonical mistakes across four relational engines, varying permissions and recovery without a model. Layer B runs a minimal tool-calling agent with six local open-weight models across nine core engines, plus three engines in a secondary run (§§3.2–3.6, 5.9).
- **Recovery-aware scoring.** A deterministic before-and-after state comparison measures unwarranted loss or alteration of protected records, called canaries. The primary outcome is loss that persists after the applicable recovery drill (§§3.7, 3.9).
- **Behavior and exposure measurements.** Control tasks estimate interface competence, and exploratory recounts track whether agents encountered embedded instructions or planted credentials. Reports are checked against observed state changes (§§3.5, 5.3–5.6).
- **Reusable evaluation artifacts.** The authors report releasing an MIT-licensed harness, 12,384 agent trial records, and analysis in a pinned container (§1).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Scripted mistakes usually produced the same permanent-loss outcome across relational engines | With default permissions, no recovery preparation, and an immediate drill, only 1 of 21 mistakes applicable to multiple engines differed. The difference was rollback of a table drop. | §4.1, Appendix A.1 |
| Minimum backups restored all protected records in the scripted tests | Permanent-loss mistakes fell from 17 to 0 on PostgreSQL, 18 to 0 on MySQL, 18 to 0 on MariaDB, and 15 to 0 on SQLite under R1 versus R0. No legitimate writes intervened between backup and mistake. The MySQL and MariaDB application-only restores left a newly created superuser in place. | §4.3, Appendix A.1 |
| Default recovery substantially changed observed live-agent loss | With default permissions on main-model core tasks, Cassandra went from 62/432 raw canary-loss trials to 0/432 permanent-loss trials after rapid post-hoc replay and recovery. ClickHouse went from 68/432 raw to 17/431 permanent, with one unmatched replay excluded. | §§3.9, 5.1 |
| Least-privilege results depended on what counted as loss | In default-permission main-model core trials, 215 of 392 permanent-loss trials lost only the in-database backup copy. In the post-hoc original-row analysis, default versus least privilege went from 48/432 to 0/432 on Valkey and 14/432 to 0/432 on Kafka, while PostgreSQL, MySQL, OpenSearch, and ClickHouse changed little. | §5.1, Appendix A.2 S11 |
| The engine-versus-model result was sensitive to the scoring rule | For default-permission main-model core tasks, the preregistered engine-to-model spread ratio for attempted damage was 4.10 (95% bootstrap CI 1.65–14.9). A post-hoc recount covering additional write forms gave 1.88 (0.87–5.22) on hazard tasks. For permanent canary loss on core tasks, the ratio was 1.13 (0.96–2.39). | §5.2, Appendix A.2 S13a |
| Credential use depended on exposure | In the dedicated least-privilege task, agents saw the planted credential in 0/288 main-set trials. Across all 4,032 main-set least-privilege trials, a post-hoc recount found 106 exposures and 24 uses, all outside the dedicated task. | §5.3, Appendix A.2 S12a |
| Agent reports could omit damage | A post-hoc review found that at least 149/739 main-set trials with raw damage ended without a usable account. At least 26/616 written reports missed, denied, or otherwise misstated the change. | §5.4, Appendix A.2 S13b |

The experiments demonstrate specific prevention and recovery mechanisms in the tested configurations. For the primary least-privilege outcome, the post-hoc task-instance sign test supported reductions only on Valkey and Kafka after correction. No original-row comparison survived the corrected template-level sign test. The attempted-damage result depends on how the scorer treats requested writes and which engine-specific commands it recognizes, so it cannot establish that engine choice generally matters more than model choice (§§5.1–5.2, 8).

## Limitations and validity risks

- **Author-reported scope.** The study used small synthetic datasets on single-node engines and small, quantized local models. Managed services, replication, frontier models, commercial agents, and infrastructure-layer failures were outside the evaluation (§9).
- **Author-reported harness effects.** Cassandra and ClickHouse recovery was reconstructed after the first tables and performed seconds after replay. MySQL’s seed and log reset prevented recovery from its default binary log. Valkey’s initial namespace and snapshot reset affected loss, and one Valkey loss was likely a harness artifact (§§3.3, 5.1, 8–9).
- **Author-reported measurement limits.** Repeated seeds and similar paraphrases made trial-level tests overconfident. Canary scoring missed some deletions of unmarked records, and statement patterns misclassified several secondary outcomes. The planned independent human audit was unavailable, and output-channel exfiltration was never scored (§§5.8, 8–9).
- **Analyst inference.** Layer B varies the engine together with its tool interface. Given low control-task success on Kafka, MongoDB, and Valkey, the study cannot isolate engine behavior from differences in interface fluency (§§3.5, 5.6).

## Open research questions

- **How much of the engine effect comes from interface fluency?** Engine and interface vary together in Layer B. Run the same models and permissions on each engine through both its native interface and a standardized operation interface, then compare control success and permanent loss (§§3.5, 5.6).
- **How much legitimate work survives recovery after a realistic detection delay?** The scripted backups had no intervening legitimate writes, and the live replay drills ran quickly. Interleave legitimate writes with scripted mistakes, vary the time to detection, and measure recovery of both protected data and legitimate writes (§§4.3, 9).
- **Can tighter write permissions reduce original-record loss while preserving routine work?** Several tested roles permitted the writes responsible for residual loss, and the denylist was evaluated only against the scripted library. Compare the existing roles with task-scoped write permissions on held-out tasks, measuring both original-record loss and legitimate task completion (§§4.2, 5.1).

## Confidence and missing information

**Medium.** The supplied sections and tables support the main findings for the tested configurations. The source was truncated within Appendix A.2, leaving part of the post-hoc report and credential evidence unavailable. The supplied §11 also contains no availability details, so artifact access and reproducibility could not be verified from the text. Independent scorer validation and an output-channel exfiltration result are unavailable because the study did not report them (§8).
