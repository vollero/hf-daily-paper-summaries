# A CPU Inside an LLM: Zero-Gradient Compilation of Exact Circuits into Pretrained Weights

> [← Daily summary](../2026-11-20.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.26450) · [arXiv](https://arxiv.org/abs/2611.26450)


## One-sentence takeaway

The paper shows that a zero-gradient weight graft can execute bounded arithmetic and Boolean circuits inside pretrained language models, while numerical precision, prompt syntax, and tokenization still affect whether the model returns a correct final answer (§§3–6).

## Problem and motivation

Pretrained language models can lose accuracy on exact arithmetic embedded in prose. External interpreters interrupt decoding, while prior circuit compilers discussed by the author largely target purpose-built models. The gap is how to add deterministic computation to an existing checkpoint without gradient updates or external execution, while controlling normalization drift and preserving language generation (§§1–3).

## Approach and contributions

- **Analytical primitives.** Two-layer Mellin-GLU quadrature recovers ratios despite RMSNorm rescaling. Architecture-specific routing moves values across tokens through RoPE attention or GatedDeltaNet. Axis-aligned width extension compensates for normalization changes, and differential readout handles tied embeddings. The paper derives conditional finite-precision bounds for these components (§3, Theorems 3.2–3.4).
- **Declarative compiler.** A five-stage compiler inspects the backbone and tokenizer, schedules and allocates circuit operations, and emits sparse checkpoint patches. It synthesizes signed arithmetic, three-literal Boolean evaluation, and five-bit majority and parity. Arithmetic outputs use the backbone’s canonical numeric tokens (§4, Appendix G.1).
- **Sparse execution.** A factorized sidecar runs the circuit at higher precision while allowing the pretrained backbone to use lower precision. The paper benchmarks this implementation against dense materialization (§5, Table 3, Appendix G.4).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Reference grafts achieve high arithmetic-prefix exactness | On 1,200 unseen signed arithmetic prompts with operands up to six digits, BF16 ALU-prefix accuracy was 99.17% for Granite and 100% for Qwen. Both reached 100% in FP32. Strict non-decimal accuracy was 90.75% and 99.50%, respectively. | Table 4, §5 |
| Grafts improve inline resumption over the reported LoRA baseline | Granite and Qwen reference grafts reached 98% and 100% on Inline-50, respectively. Same-backbone LoRA trained on 12,800 examples reached 0% fluent inline continuation on both backbones. | Tables 4–5, §5 |
| Automated patches show an accuracy and sparsity trade-off | For six-digit synthesis, automated patches reduced active nonzeros by 19.5% on Granite and 5.6% on Qwen relative to hand-scheduled patches. Qwen’s FP32/BF16 ALU-prefix accuracy was 97.0%/95.7% versus 100%/100% for the reference. The Granite rows use different prompt suites. | Table 18 |
| The compiler extends beyond arithmetic | Both backbones achieved 100% on 1,728 three-literal Boolean prompts. The five-bit majority/parity evaluation reported 64/64 correct under randomized BF16 normalization scales. | Table 6, Appendix G.1 |
| Language scores meet the frozen noninferiority margins | All 14 preregistered BF16 evaluations passed across the two backbones. On 4,392 pooled reasoning items, base-to-graft accuracy changed by +0.46 percentage points for Granite and +0.23 for Qwen against a 0.75-point margin. The study separately tested long-context PubMedQA and 2,048-token SWE-bench negative log-likelihood. | Tables 7 and 23 |
| Sparse execution reduces memory and prefill latency | At batch size 1 on A100, memory fell from 13.55 to 7.89 GiB for Granite and from 19.09 to 10.65 GiB for Qwen versus ragged dense grafts. Prefill at 2,048 tokens was 2.67× and 1.96× faster, respectively. | Table 3, Appendix G.4 |

The strongest evidence concerns bounded circuits in the tested checkpoints. An exact arithmetic prefix can still be followed by extra digits or an echoed chunk after the circuit hands generation back to the model. Likewise, the language tests support retention within their prespecified margins on the evaluated benchmarks. They leave broader language behavior and other deployment settings open (Table 4, Table 15, Appendix E.4).

## Limitations and validity risks

- **Author-stated scope.** The reference arithmetic patches cover bounded formats and restrict multiplication by operand degree. Unbounded inputs and data-dependent loops exceed the single-pass design. Gemma receives a Boolean audit, with full arithmetic left open (§§3, 4.3, 6).
- **Author-reported failure modes.** BF16 can flip carries in Granite. Bare prompts can lead to decimal suffixes or chunk echoes, and some beginning-of-sequence-free formats cause parser abstention. Direct circuit quantization fails in the tested uniform INT8/INT4 settings, and raw FP16 can overflow (Theorem 3.2, Table 6, Appendices B and D).
- **Analyst inference.** Granite’s automated and reference rows in Table 18 differ in prompt mix, so their accuracy gap cannot be attributed to automation alone. The reported absence of false triggers also applies to the sampled suites, which vary in size depending on whether boundary and Boolean cases are included (Tables 6, 11, and 18).

## Open research questions

1. **Can the compiler match hand-scheduled accuracy at lower sparsity cost?** Table 18 shows a Qwen accuracy gap and uses different prompt mixes for Granite. Evaluate both patch types on identical inputs, calibration, padding, and kernels, and score parsing and ALU execution separately.
2. **Can the model end a bare numeric answer cleanly while still resuming prose?** The failure traces show that extra digits can appear after correct computation. Test a tokenizer-aware answer-boundary mechanism on matched bare and prose prompts, measuring strict accuracy and inline continuation (Table 15, Appendix E.4).
3. **How far does the compiler transfer across architectures?** The Gemma audit establishes Boolean execution after architecture-specific adjustments, while full arithmetic remains open. Compile the same arithmetic specification on Gemma and measure correctness and language retention while ablating each adjustment (§4.3, §6).
