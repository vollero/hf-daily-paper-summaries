# Embeddings vs. Grep: Rethinking the Dense Advantage in Code Search

> [← Daily summary](../2026-11-20.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.20455) · [arXiv](https://arxiv.org/abs/2611.20455)


## One-sentence takeaway

On RepoPremium, whole-file BM25 narrowed the dense retrieval lead, LLM-generated identifiers erased the remaining lead in point estimates across all four Python core pools, and fixed lexical–dense fusion improved on dense retrieval in a preregistered holdout (Figure 1, Tables 2–3).

## Problem and motivation

Code-search benchmarks report large gains over BM25, while coding agents can localize changes using tools such as `grep`. End-to-end agent scores cannot isolate retrieval quality, and the authors argue that existing retrieval benchmarks leave several explanations entangled: curated query wording, older code, chunking that disadvantages BM25, and inconsistent treatment of edited tests as relevant files (§§1–2).

## Approach and contributions

- **RepoPremium benchmark.** Rank files within a pinned repository from a natural-language change description. The benchmark combines curated issues, raw PR text from different time windows, a multilingual extension, and a matched comparison of raw PRs with LLM rewrites of the same changes. The authors report releasing queries, file labels with test flags, pinned commits, a boilerplate stripper, and evaluation harnesses (§3, Table 1, Appendices G–H, O).
- **Evaluation and query diagnostics.** Compare dense encoders against chunked and whole-file BM25, rescore under different relevance rules, and measure how the rarity of tokens shared with the first gold file relates to the dense lead. The authors use LLM query expansion and anchor ablations as experimental interventions with existing methods (§§2, 4, 5.1–5.5).
- **Held-out pipeline comparisons.** Test fixed reciprocal rank fusion against per-query routing in a preregistered lockbox, then compare search tools in a separate coding-agent localization experiment (§§5.3, 5.6–5.7, Appendices F, Q).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Whole-file BM25 narrows the dense lead | With source-file labels and the canonical dense encoder, switching BM25 from 1,000-character chunks to whole files cuts the Cur-Pre nDCG@10 lead from +0.121 to +0.034. Against whole-file BM25, raw-pool leads are +0.059 to +0.125, with the advantage concentrated in Recall@10. | §5.1, Figure 1, Tables 2, 11 |
| Test labels favor dense retrieval | On the full Raw-Post pool, counting edited tests as relevant raises the canonical encoder’s nDCG@10 lead over whole-file BM25 from +0.059 to +0.136. | §5.1, Appendix B.3 |
| Generated anchors close the remaining Python gap | On source-file labels, expanded whole-file BM25 beats the canonical encoder on original queries by 0.081 nDCG@10 on Cur-Pre, with a 95% interval excluding zero. Its raw-pool leads of 0.054–0.062 have intervals that include zero. The field ablation attributes the gain to identifiers, APIs, and error terms. | §5.2, Table 2, Appendix B.5 |
| Raw wording increases the lead in matched tasks | On 351 tasks with the same corpus and source-file labels for both views, raw PR wording raises the dense-over-BM25 nDCG@10 lead relative to an LLM rewrite by +0.091 for jina-code-0.5b and +0.111 for Qwen3-Embedding-0.6B. Both intervals exclude zero. | §5.5, Appendix O, Table 18 |
| Fixed fusion improves on dense retrieval and the router misses its criterion | On 539 lockbox queries across 91 repositories, fusion with plain or expanded whole-file BM25 improves over dense alone by +0.019 and +0.045 nDCG@10 on released labels, and by +0.027 and +0.062 on source-file labels. The router gains +0.005 over always fusing, with an interval that includes zero. | §5.3, Table 3, Appendix F |
| The agent search-tool comparison is unresolved | With qwen35-122B fixed on 96 held-out tasks in the clean rerun, four search setups score within about 0.04 exact match on the final diff’s file set. Every paired difference includes zero. | §5.7, Appendix Q.1, Table 21 |

The experiments establish that changing BM25’s indexing window, the relevance rule, or the query text can materially change the measured dense lead. The raw-pool expansion results leave room for a small dense advantage, and the generator may draw on prior repository knowledge. The lockbox supports fixed fusion over dense alone. The extra gain from adding generation to fusion disappears when repositories are weighted equally. The agent experiment measures file localization, and fix correctness remains unmeasured (§5.2, Appendices E–F, Q).

## Limitations and validity risks

- **Author-stated.** The core covers ten Python repositories, and each cross-language raw PR slice uses one repository. BM25’s window was selected on evaluation queries in the core analysis. Expansion gains depend on the generator. Gold labels come from one change, and function- and line-level targets are untested (§5.1, Limitations).
- **Author-stated.** The shared-token rarity diagnostic uses the first gold file and was selected on the exploratory slices. Its preregistered test had the predicted direction but an interval covering zero. Token replacement can also remove task meaning, leaving the mechanism unresolved (§5.4, Appendices E, N).
- **Analyst inference.** The core filters favor changes to a few existing source files, limiting transfer to changes that add files or touch many modules. The post-cutoff PR comparisons also leave encoder exposure to repository code unresolved because the indexed snapshots can predate the cutoffs (§3.2, Appendix B.1).
- **Analyst inference.** Exact reproduction from released queries may differ for some BM25 runs because the authors scored unredacted text and removed email addresses before release (Appendix G).

## Open research questions

1. **How much does expansion rely on prior repository knowledge?** Post-release PRs address exposure to the changes, while familiarity with the repository remains possible. Compare a frozen generator on repositories first made available after its release and on matched older repositories, with the same retrieval protocol (§5.2, Appendix E).
2. **Can a query signal reliably improve on fixed fusion?** The tested routers missed their held-out criteria, and the gold-dependent rarity statistic was weak per query. Preregister a router using query and retrieval-list features, then test it against fixed fusion on a larger repository-disjoint pool (Appendices F, N, P).
3. **Do retrieval gains improve repair correctness?** The agent study scores edited-file agreement without running tests. Randomize search tools at a fixed model and budget, then measure both localization and test-verified repair on clean held-out tasks (Appendix Q).

## Confidence and missing information

**High** for the reported comparisons in their stated settings. Several key tables are supplied as captions without numerical bodies, so exact confidence bounds and some per-arm scores are unavailable. The supplied text also omits the exact generation prompt and the direct code and data release links described in Appendix H.
