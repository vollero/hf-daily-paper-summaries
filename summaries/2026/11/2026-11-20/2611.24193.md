# WM^MLLM: Turning MLLMs into World Models

> [← Daily summary](../2026-11-20.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.24193) · [arXiv](https://arxiv.org/abs/2611.24193)


## One-sentence takeaway

WM^MLLM uses a multimodal language model to plan and check updates to a revisioned panorama built from one image, enabling exact same-revision revisits and pixel-preserving edits outside the committed region.

## Problem and motivation

In an interactive world, users expect to find their edits intact when they return and to build on them in later requests. The authors argue that video world models can lose these changes because they synthesize the view again on return. Among the explicit-state systems they survey, the authors identify a gap in combining MLLM planning, object editing, exact return, and checks before edits enter the state (§1, §2.3, Table 1).

## Approach and contributions

- **Revisioned world state.** The system stores a panorama, native-resolution patches, scene relations, and revision history. GPT-6.1-sol maps requests and optional boxes to operations and checks candidate updates. GPT-Image proposes views, and Sol-H3 presents transitions. Rotations and revisits render stored state without calling the image generator (§1, Fig. 2).
- **Local edit regions selected after generation.** The MLLM compares the source view and the proposal to locate the object’s old and new footprints and any accompanying effects. The system aligns the proposal against stable background, blends the edit into the panorama, and checks for pixel changes outside the allowed region (§1, Fig. 2).
- **Navigation and editing in the same world.** The system combines revisits, exploration, object edits, subject placement, and environmental changes. Figure 3 illustrates a relighting that persists through a walk away and back and is retained in a later object edit (§1, Fig. 3).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Led the reported environment-recovery comparisons | On MBench-A, highest mean on all four recovery metrics against six baselines under the same evaluator. Epipolar was 91.5 versus 0.1–74.0. Camera round-trip completion was 85.3% versus 0.4%–50.9%. | Abstract, §1 |
| Led the reported editing comparisons | Best value in all 15 CompBench metric columns against 15 baselines. Individual values are unavailable in the supplied text. | Abstract, §1 |
| Post-generation region selection improved local-edit completion | In a blind evaluation of 112 local edits, completion was 83.0% with the region selected after generation versus 34.8% with the region predicted before generation. | Abstract, §1, Contributions |
| Audited revisits and accepted local edits satisfied the pixel-level checks | Across 258 WBench and MBench-A items, all 46 revisits recovered the earlier view exactly, and all 97 local edits that passed the check preserved every panorama pixel outside the allowed region. | Abstract, §1, Contributions |
| Earlier edits persisted in a sequential demonstration | The authors report that one world retained every earlier change over 21 sequential requests. | §1, Contributions |

The reported comparisons support better scene recovery and editing performance in the evaluated settings. The pixel checks establish exact same-revision replay and preservation outside the committed region for the audited cases. They leave open how often proposed edits pass, how tightly the selected region tracks the requested change, and how well persistence holds across many worlds and longer sessions.

## Limitations and validity risks

- **Author-described scope.** Exact return is tied to the same revision. The locality result applies to edits that pass the commit check, and Figure 3 shows a failed turn that preserved the prior state (Abstract, §1, Fig. 3).
- **Analyst inference.** Preserving pixels outside the chosen region leaves room for unintended changes inside it. Region size and collateral changes within the region would help assess semantic locality (Fig. 2).
- **Analyst inference.** The reported pre-versus-post selection comparison supports the region-selection design, but the supplied text gives no separate estimates for the roles of alignment, blending, and commit checks. The benchmark summaries also omit per-baseline scores and uncertainty estimates, limiting interpretation of the reported leads (Abstract, §1).

## Open research questions

- How often do users get a correct local edit on the first attempt? The locality audit covers accepted edits. Evaluate all requests with independent judgments of intent fulfillment and report acceptance, retry, and failure rates.
- How much do alignment, blending, and commit checks each contribute? The reported comparison varies when the region is selected. Hold proposals fixed, vary each component, and measure edit completion and collateral changes.
- How well does persistence hold across varied worlds and longer sessions? The reported 21-request sequence covers one world. Run scripted sessions across diverse seed images with overlapping edits, intervening navigation, and repeated checks of prior changes.

## Confidence and missing information

**Medium.** The supplied text explains the core design and states the headline outcomes, but ends at Table 1 in §2.3. It lacks the full results tables, metric definitions, per-baseline scores, blind judging protocol, edit acceptance and retry rates, runtime and cost measurements, and code or asset release details.
