# FINCOSMOS: An Open-World Evaluation Paradigm for Agents in Finance

> [← Daily summary](../2026-11-11.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.07464) · [arXiv](https://arxiv.org/abs/2611.07464)


## One-sentence takeaway

FINCOSMOS evaluates financial agents through hidden user requirements, independently acquired Web data, and program-checked backtests, finding no accepted deliveries across 150 initial sessions despite simulated-user approval in 35 (§§3, 5.1–5.2).

## Problem and motivation

Financial research agents can produce convincing reports while implementing the wrong strategy, using unverifiable data, or introducing look-ahead bias. The authors argue that existing benchmarks suppress these failures by specifying the request completely, supplying curated data, or enforcing chronology within a benchmark-controlled environment (§1).

The proposed gap is evaluation of the entire delivery workflow when agents must clarify intent, obtain data, and maintain temporal correctness themselves. The authors’ claim that FINCOSMOS is the first framework to combine these conditions is supported by their discussion of prior work, but cannot be independently established from the supplied text (§§1–2).

## Approach and contributions

- **Generative tasks with hidden requirements.** A seeded grammar combines stock selection, market timing, portfolio construction, risk control, execution, and transaction costs. The authors estimate approximately 3.8 million combinations before parameter selection and freeze ten tasks for evaluation (§3.2).
- **Interactive requirement elicitation.** An LLM simulator adopts one of three personas and discloses strategy details when the agent asks or proposes a conflicting choice. It functions as an examiner of a hidden specification rather than a faithful model of individual investors (§§2.2, 3.3).
- **Verification of delivered artifacts.** Agents acquire their own data and submit reports, code, and supporting tables. The evaluator uses 45 dimensions, including 15 vetoes, combining semantic judgment with checks of chronology, strategy fidelity, and independently reconstructed performance. Acceptance additionally requires user satisfaction and complete grading (§3.4).
- **Benchmark assets and feedback experiments.** The authors report releasing the frozen tasks, generator, evaluator, and live leaderboard, and demonstrate repeated-task learning using persistent memory (§§1, 5.5).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Initial acceptance is zero | Four coding agents and one tool-free model each run three independent sessions on ten tasks: 0/150 accepted. | §§4.1–4.2, 5.1 |
| Partial quality separates some systems | Quality on a 0–100 scale: Codex 37.2, Claude Code 37.1, Kimi Code 22.3, Gemini CLI 22.2, tool-free model 20.2. Codex versus Claude Code: paired task-level permutation test, p=0.99. | §5.1; Table 3 caption |
| User approval misses failures | All 35/150 user-approved sessions fail a program check. Using only LLM-judged vetoes would accept 17/150 sessions, versus none under the full rule. | §5.2 |
| Failures concentrate at workflow endpoints | Among 120 coding-agent sessions, sequential survivors are 25 after strategy fidelity, 15 after the data cutoff, 14 after signal/fill chronology, and zero after return recomputation. | §5.3; Table 5 |
| Elicitation remains incomplete | Coding agents elicit 54–64% of initially unstated requirements; delivered strategies mismatch 66–83% of requirements that remain unstated. | §5.3 |
| Human validation supports, but does not fully vindicate, evaluation | In 60 sampled failed sessions, experts attribute the first decisive error to agents in 53, the simulator in three, and the evaluator in four. Judge–expert agreement on four semantic vetoes across 30 calibration sessions is κ=0.87. | §5.4 |
| Repeated practice achieves task-specific acceptance | Claude + Memory eventually passes all ten practiced tasks: 506 sessions total, median 34.5 per task, range 12–132; none passes initially. | §5.5; Table 6 |

These findings establish substantial delivery failures under the tested rubric and resource limits. They do not establish that financial agents always fail, that the benchmark captures every financial validity problem, or that repeated-task learning transfers to unseen strategies. The learning experiment demonstrates eventual acceptance on practiced tasks, rather than reliable first-attempt performance.

## Limitations and validity risks

**Author-stated limitations:** The benchmark contains ten frozen tasks with three initial sessions per system and covers long-only US equities with a fixed-cost model. Shared model ancestry between simulator, judge, and an evaluated agent creates residual bias risk. Most turns hit the time limit; program checks cannot prove every figure is genuine; and feedback scores can reveal hidden-strategy information across attempts (§6).

**Analyst inferences supported by the text:**

- **Resource limits affect interpretation:** 70% of coding-agent turns reach the 300-second limit, so zero acceptance measures performance under a constrained workflow (§5.1).
- **Learning attribution is unresolved:** The supplied experiment does not report a matched repeated-practice control without memory updates or held-out-task transfer evaluation. It therefore cannot isolate memory’s contribution from additional attempts and task familiarity (§§4.2, 5.5).
- **Acceptance is sensitive to strict completeness requirements:** Removing audit and process-completeness vetoes would accept two sessions, although their reconstructed returns still disagree with their reports (§5.2).
- **Human validation is sampled:** Expert attribution covers 60 sessions, and semantic-judge calibration covers four vetoes on 30 sessions (§5.4).

## Open research questions

- **Does learned verification behavior transfer to unseen strategies?** Only practiced-task acceptance is demonstrated. Freeze the learned memory and evaluate newly generated seeds against an unadapted control (§5.5).
- **How much does additional execution time improve trustworthy completion?** Time frequently binds, but longer-turn results are absent. Repeat the same tasks with increased turn budgets and compare acceptance and failure categories (§5.1).
- **How sensitive are results to the simulator and judge family?** Shared-family bias remains acknowledged. Cross simulator and judge families while retaining program checks and blinded expert audits (§6).
- **Can structured elicitation improve end-to-end delivery?** Clarification coverage correlates with quality, but causality is untested. Compare ordinary interaction with a component-based clarification protocol under equal resource budgets (§5.3).
