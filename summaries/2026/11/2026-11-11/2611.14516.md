# TorchCurves: Differentiable Parametric Curves

> [← Daily summary](../2026-11-11.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.14516) · [arXiv](https://arxiv.org/abs/2611.14516)


## One-sentence takeaway
TorchCurves provides composable, differentiable B-spline and Legendre curve primitives in pure PyTorch, with timing results showing practical performance in some settings and substantial overhead in others.

## Problem and motivation
The author identifies a software gap: applications repeatedly implement learnable curves within specialized models rather than using a common abstraction. TorchCurves makes scalar-to-vector curves reusable across continuous feature embeddings, Kolmogorov–Arnold networks (KANs), and functional regression, while allowing gradients through both inputs and coefficients (§§1–2).

## Approach and contributions
- **Unified curve interface:** Represents curves as weighted sums of B-spline or Legendre basis functions. Coefficients can be trained directly or supplied by another network (§3.1).
- **Three API levels:** Trainable curve modules, reusable basis modules with stored buffers, and stateless functional operations support different model compositions (§3.1).
- **Vectorized implementation:** Uses classical Cox–de Boor and Clenshaw algorithms in pure PyTorch, with loops over polynomial degree but none over batch, curve, or output dimensions. B-splines use a custom autograd function (§4).
- **Composition examples and timing evaluation:** Demonstrates embeddings, KANs, and monotone auction-response functions, then benchmarks evaluation and KAN training (§§3.2, 5). The contribution is software abstraction and integration; the underlying evaluation algorithms are established.

## Evidence and main results
All ratios below are median TorchCurves time divided by median reference time; lower is faster.

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Small spline workloads can incur large overhead. | CPU, inference only: ratio **20** versus SciPy for curve count C=1, output dimension D=1, batch B=1, coefficients K=4. Medians use five measurements. | Fig. 2, p. 8 |
| Some larger spline workloads are faster. | CPU, inference only: ratio **0.56** versus SciPy for C=64, D=1, B=2048, K=64. | Fig. 2, p. 8 |
| Legendre performance also depends on workload. | CPU, inference only: ratios **2.3** for C=1, D=1, B=1, K=4 and **0.087** for C=64, D=16, B=256, K=64, versus NumPy. | Fig. 3, p. 9 |
| KAN training has substantial wins and losses. | CPU ratio **8.8** at K=8, hidden width W=128, B=1024; GPU ratio **0.26** at K=64, W=32, B=1024, versus EfficientKAN. Float32 eager execution, generated data, MSE, Adam, fixed grids; architectures and parameter counts differ. | Fig. 4, p. 10 |
| Numerical correctness and gradients were checked, according to the author. | Comparisons against SciPy/NumPy and PyTorch numerical gradient checks in float32 and float64; no numerical error summaries supplied. | §4, p. 6 |

The results establish workload-dependent timing on the reported laptop, rather than uniform speed superiority. KAN timings measure idiomatic implementations with different architectures and parameter counts, so they do not isolate implementation efficiency. No downstream predictive-quality results are reported. The author’s explanation that small-workload overhead and larger-workload parallelism drive performance is explicitly a conjecture (§5).

## Limitations and validity risks
- **Author-stated:** No custom hardware kernels; degree-dependent Python loops can reduce efficiency, especially for high-degree Legendre curves (§4).
- **Author-stated comparison boundary:** KAN architectures, parameter counts, and initialization differ between libraries (Fig. 4).
- **Analyst inference:** Timing generalization is limited by evaluation on one laptop and restricted CPU affinity; other hardware and execution modes remain untested (§5).
- **Reporting inconsistency:** Section 5 specifies KAN architecture `[16, W, W, 1]`, whereas Figure 4 specifies `[32, W, W, 1]`. The actual input width is unresolved.
- **Analyst inference:** Application examples establish composability, but do not demonstrate accuracy, calibration, or training convergence benefits (§3.2).
- **Reproducibility gaps:** The supplied text does not specify the generated-data distribution, optimizer hyperparameters, timing variability, or quantitative correctness tolerances. API examples also contain inconsistent shape annotations (§3.1).

## Open research questions
1. **How much of the KAN timing difference comes from architecture?** The benchmark uses unequal models. Compare mathematically matched layers with matched parameter counts and initialization.
2. **Do curve primitives improve application quality?** Embedding and auction examples lack empirical evaluation. Test predictive accuracy and auction-probability calibration against explicit application baselines.
3. **How does performance transfer across hardware and execution modes?** Only one machine and eager execution are reported. Repeat the timing grid on additional CPUs/GPUs and compare eager with compiled execution.
4. **How do degree and input mapping affect numerical behavior?** Correctness checks are described without error distributions. Measure value and gradient errors across degrees, mappings, and boundary inputs.

## Confidence and missing information
**Confidence: medium.** The API design and selected timing ratios are directly supported, but broader efficiency conclusions are constrained by unequal KAN comparisons and inconsistent architecture reporting.

Material missing information includes downstream accuracy results, quantitative numerical-error reports, timing dispersion, generated-data details, optimizer hyperparameters, and resolution of the KAN input-width discrepancy.
