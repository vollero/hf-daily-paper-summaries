# SpecEngineeringBench: Evaluating Coding Agents as Autonomous Specification Engineers

> [← Daily summary](../2026-11-25.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.32973) · [arXiv](https://arxiv.org/abs/2611.32973)


## One-sentence takeaway
On a requirements-driven benchmark of Python repositories with multiple known defects, seven coding agents produced mostly valid tests, but only 26.36% of tests on average distinguished defective from repaired snapshots, and just 2.00%–7.84% of evaluable multi-file defects met the benchmark’s localization criterion (§§3.2–3.3, Tables 3 and 5).

## Problem and motivation
Prerelease testing requires agents to infer expected behavior from product requirements, decide where to investigate, and substantiate defects with executable evidence. The authors argue that supplying issue reports, designated targets, or a single known bug bypasses much of that exploratory work (§1, Figure 1, Table 1).

## Approach and contributions

- **Benchmark dataset.** The authors curate 100 instances from 78 open-source Python repositories across 16 application categories, with 531 recorded defect occurrences and 4–15 per instance. Each instance supplies a product requirements document (PRD), an unrepaired snapshot, and a configured Docker environment (§§2.1–2.3, Table 2, Figure 2).
- **Two independent evaluation tasks.** Task 1 runs submitted tests against defective and repaired snapshots to score validity, defect discrimination, and coverage. Task 2 separately asks agents to execute probes and submit evidence-backed reports, then scores their locations against reference fixes at file, function, and hunk granularity (§§2.1–2.2, Appendix B).
- **Empirical comparison.** The paper evaluates seven model–harness configurations, analyzes failure patterns, and compares agent-authored with repository-provided tests for one configuration on the same instances (§§3.1–3.6).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Valid tests and broad coverage often leave defects unexposed | Across seven agents in Task 1, mean Head Pass Rate was **91.47%** and mean Fail-to-Pass Rate was **26.36%**. Head Pass Rate pools test counts within each system, while Fail-to-Pass Rate averages per-instance fractions. Mean change-focused coverage was **80.48%**, measured on repaired snapshots. Even in the **80–100%** coverage bin, model mean Fail-to-Pass Rates ranged from **24.24% to 37.82%**. | §2.2, §3.2, Tables 3–4 |
| Reports recover files more readily than finer locations | Across seven agents in Task 2, mean localization recall was **78.11%** for files, **51.29%** for functions, and **51.88%** for hunks. Hunk matching allows a three-line tolerance. | §2.2, §3.2, Table 3 |
| Multi-file defects are rarely fully localized | Across agents, **33.14%–49.04%** of evaluable reference bugs met the distinct-bug criterion. Rates were **40.63%–59.05%** for single-file bugs and **2.00%–7.84%** for multi-file bugs. Credit requires all reference files and function symbols and more than half the reference hunks. | §2.2, §3.3, Table 5 |
| Authored tests raise average recall while lowering precision | For GPT-5.6-Sol with Codex on the same 100 instances, authoring tests increased instance-averaged recall by **4.99, 2.77, and 2.69 percentage points** at file, function, and hunk levels. Precision fell at all three levels, and the median paired recall change was zero at each level. | §3.6, Table 7 |

The results show that passing the repaired snapshot and reaching changed code are weak proxies for whether tests distinguish the two snapshots. The authors’ trajectory review identifies assertions based on observed implementation behavior and premature stopping at visible failure sites as recurring explanations (§3.5, Appendix D). Task 2 scores agreement with recorded fix locations. Independent replay of report evidence and the correctness of findings outside the reference set remain unestablished (Table 1, §2.2).

## Limitations and validity risks

- **Author-stated scope.** The benchmark covers Python repositories, and the authors identify additional languages and agent-generated specifications as future extensions. The defect-type analysis covers five systems on 86 annotated instances. Fourteen replacement instances await annotation, and cohorts overlap and are scored against each instance’s full reference set (§5, Figure 3, Table 6).
- **Analyst inference.** The stricter all-files and all-functions requirement makes multi-file bugs harder to score as localized as their reference scope grows. The observed gap therefore combines diagnostic difficulty with the effect of the success criterion (§2.2, Table 5).
- **Analyst inference.** Model rankings characterize the tested model–harness pairs. The design leaves model and harness effects unresolved, and the paired testing comparison supports a recall–precision tradeoff for only one configuration (§3.1, Table 7).
- **Reporting ambiguities.** Appendix A’s Task 1 prompt mentions “test entry inferences” and information about entry functions and ranges, leaving unclear what guidance was supplied in practice. Section 3.6 also gives two rounded values for the function-precision decline, **1.60** and **1.61 percentage points**, with Table 7 using **1.60**.

## Open research questions

1. **Can explicit PRD-derived assertions improve defect discrimination?** The trajectory analysis identifies assertion problems, but the study does not isolate the effect of how assertions are derived. Compare standard prompting with a requirement-to-assertion checklist under matched budgets and measure Fail-to-Pass Rate and coverage (§3.5, Appendix D).
2. **Can cross-component tests improve multi-file localization?** Table 5 measures the localization gap without testing a tracing intervention. Compare standard exploration with a workflow that traces failures through callers and component boundaries, and report both partial location recall and distinct-bug localization (§3.3, Table 5).
3. **Does the recall–precision tradeoff generalize across agents?** The paired comparison covers one model–harness pair. Repeat it across agents on the same instances with matched budgets and independently replay submitted evidence (§3.6, Table 7).

## Confidence and missing information
**High** for the benchmark design and headline descriptive results. The supplied text does not give exact per-run budgets, run-to-run variability, a detailed protocol and denominators for the failure-mechanism review, or independent adjudication of findings outside the reference set. The exact Task 1 entry guidance also remains unclear.
