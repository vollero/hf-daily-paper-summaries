# Don&#x27;t Sleep, Keep Watch: Proactive Perception for Computer-Use Agents

> [← Daily summary](../2026-11-25.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.28947) · [arXiv](https://arxiv.org/abs/2611.28947)


## One-sentence takeaway

NightWatch uses a lightweight screen watcher to interrupt obsolete reasoning, cancel stale actions, and end waits when the interface is ready, reducing desktop latency with comparable task success and improving dynamic-web success for the larger of two tested agents (§§4.1–4.3).

## Problem and motivation

Computer-use agents typically take a screenshot, reason, act, and wait for a fixed interval. During reasoning, a dialog or layout change can invalidate the planned action. After dispatch, a short wait can expose an unfinished transition, while a long wait can waste time or miss transient feedback. The authors identify a gap in passive approaches such as AOI’s keyframe buffering and PUSV’s pre-dispatch checks, which leave ongoing reasoning running after the screen has changed (§§1–2).

## Approach and contributions

- **Timing formulation and measurement.** The authors make observation timing a decision of the agent harness and define a wall-clock ledger for idle waiting and time lost to premature observations or stale actions (§3.1, Appendix E).
- **Event-triggered harness.** NightWatch answers a fixed bank of questions using recent screenshots, region crops, and action text when available. Threshold rules interrupt and restart reasoning after relevant changes, void invalid pending actions, and wake the agent when the interface appears ready (§§3.2–3.3, Figure 2).
- **Trained watcher and artifacts.** NightWatch-0.8B is fine-tuned on independently generated desktop trajectories and synthetic interfaces. Training combines teacher and gold labels, including a hindsight label based on whether significant screen changes follow. The paper reports releasing code, weights, and training data (§1, §3.4, Appendix C).

The authors report statistically significant paired reductions in desktop non-reasoning time for both agents (§4.2, Appendix E). The web success gain is a point estimate in the supplied text, and desktop success parity is descriptive. The comparisons establish performance under the tested harnesses and input settings. The screen-change measures indicate improved timing, with semantic action validity still unmeasured directly (Appendix E).

## Limitations and validity risks

- **Authors’ limitations.** Restarting reasoning cannot speed up the agent or supply missing task capabilities. Fast-changing games and notifications can invalidate a fresh observation before dispatch, while persistent desktop failures often end with the agent submitting an incorrect result (§5, Appendix H).
- **Analyst inference on comparison scope.** AOI’s DOM list was disabled, audio-dependent web tasks were excluded, and the web judge differs from the original evaluation. The results apply to the shared protocol used here. The desktop pixel-only comparison also disables interrupt and void and uses a single run, so it provides an approximate attribution of desktop gains to wake (Appendices D and F).
- **Analyst inference on measurement.** Significant pixel changes can be benign, and hindsight settledness labels use a finite pixel-change window. Direct semantic labels would clarify how much the proxy gains reflect valid actions and ready interfaces. Agent API cost excludes local watcher compute, leaving total deployment cost uncertain (§3.4, Appendices C, E, and F).

## Open research questions

1. **At what interface speed do interruptions stop helping?** Appendix H identifies failures when the interface changes faster than the agent can respond. Sweep event duration and agent inference latency independently in a controlled GUI and measure success, restarts, and target validity.
2. **How well does pixel-based settledness predict semantic readiness?** Training and evaluation both use screen-change proxies. Compare watcher decisions with instrumented readiness events and human annotations on delayed loads, ambient animations, and silent pauses (§3.4, Appendices C and E).
3. **How much of the wake gain comes from hindsight supervision and calibration?** The reported fine-tuning comparison bundles training choices. Ablate hindsight labels, the Brier term, and temperature scaling individually, then measure early wakes, wait time, and success with the same controller (§§3.4, 4.4).

## Confidence and missing information

**Confidence: high** for the method and headline results explicitly reported in the prose. The supplied text omits the full numerical cells of several results tables, including exact success scores for individual watcher alternatives and the full run-level variability for main comparisons. It also provides no web success significance test or all-in deployment cost that includes local watcher compute.
