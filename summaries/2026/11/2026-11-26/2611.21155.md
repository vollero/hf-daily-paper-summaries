# Edit Recommendation: Can LLMs Anticipate Edit Requests from Users, and When?

> [← Daily summary](../2026-11-26.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.21155) · [arXiv](https://arxiv.org/abs/2611.21155)


## One-sentence takeaway

On EditRecBench, the best of eight LLMs matched the user’s actual next edit request in 47% of test cases with five guesses, while a learned gate raised pass@5 among shown test cases by 12–25 percentage points across predictors at thresholds set to show 20% of development cases (Table 1, Figure 3).

## Problem and motivation

The paper asks whether a chat assistant can anticipate how a user will ask to revise its latest artifact. A matching suggestion could save the user from typing the request. The author identifies a gap between general next-prompt prediction and predicting a specific revision, where success depends on identifying both what the user wants changed and how (§1, Appendix A).

## Approach and contributions

1. **EditRecBench and a matching criterion.** The author curates 12,298 examples from WildChat-4.8M with chronological splits. An LLM judge decomposes each actual request into atomic target-and-change requirements. A prediction matches if it satisfies every requirement and introduces no conflict (§2, §3.1, Figure 2).
2. **Benchmark and failure analysis.** The paper compares eight LLMs with shuffled and stock-request baselines and reports results separately for requests that introduce information absent from the conversation (§3, Table 1).
3. **Selective suggestion gating.** A LoRA-tuned Qwen3.5 decision model scores whether any of the five generated requests will match, using the conversation and the candidate list. Training uses majority-vote judge labels for the list overall and auxiliary labels for individual candidates (§4, §5.1).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Prediction quality varied widely | On the chronological test split, eight LLMs scored 10–47% pass@5. gpt-6.1-sol led at 47% (95% bootstrap interval 45–50%). Shuffled, generic stock, and popular stock requests scored 2%, 11%, and 17%, respectively. The union of predictor matches covered 61% of test cases at pass@5. | Table 1, §3.2 |
| Requests with new information were harder | On test, gpt-6.1-sol reached 57% pass@5 without new information and 18% with it. Every evaluated LLM scored lower on the new-information subset. | Table 1, §3.3 |
| The trained gate ranked matches better than the baselines | With five candidates per test case, the Qwen3.5-4B gate averaged 0.690 AUROC on predictors seen in gate training and 0.675 on held-out predictors, versus 0.587 and 0.583 for the strongest baseline in each group. | Tables 2–3, §5.2 |
| Higher pass@5 came with fewer suggestions and missed matches | Thresholds set to show 20% of development cases raised pass@5 among shown test cases by 12–25 percentage points over showing all cases. For gpt-6.1-sol, test pass@5 rose from 47% to 62%, suggestion frequency fell by 72%, and 37% of all matches were retained. | Figure 3, §5.2 |
| The generated candidates helped the gate | With conversation context and predictor identity alone, the Qwen3.5-4B gate averaged test AUROC of 0.579 for seen predictors and 0.567 for held-out predictors, versus 0.690 and 0.675 with the candidates included. | Appendix H, Tables 9–10 |
| The judge agreed with one human annotator on most audited pairs | Agreement was 93 of 100 pairs (Cohen’s κ = 0.86), with the audit balanced between judge-labeled matches and non-matches. | Appendix F, Table 7 |

The evidence supports offline prediction of some actual edit requests and shows that the gate can concentrate matches among the cases it selects, including for predictors held out from gate training. The author describes some requests as inherently hard to anticipate. The observed subgroup gap supports that interpretation, while the 61% empirical ceiling measures coverage by the tested predictors and leaves the attainable ceiling unknown. Effects on user effort and satisfaction remain unmeasured.

## Limitations and validity risks

- **Author-stated.** The gate runs after candidate generation, so withholding suggestions still incurs generation cost. The paper reports a weaker context-only gate and includes no user study (Limitations, Appendix H).
- **Analyst inference.** The curated sample favors clear, mostly English requests with sufficiently long artifacts and an observable revised version. Because the benchmark assumes the next turn is an edit request, it leaves open how often a gate would show irrelevant suggestions on ordinary chat turns (§2.2, Appendix E, Figure 8).
- **Analyst inference.** The same LLM judge supplies gate training labels and the offline match criterion. The single-annotator audit supports the criterion, with limited evidence about whether other annotators would make the same judgments (§§3.1, 4.2, Appendix F).
- **Analyst inference.** The context-only ablation tests the value of supplying candidates. The paper reports no ablation isolating the effect of the per-candidate auxiliary targets (§4.2, Appendix H).

## Open research questions

1. **Does gating reduce user effort in live chat?** The offline benchmark conditions on an edit being requested. A randomized study could compare gated, always-shown, and hidden suggestions across ordinary chat turns using time to submit a revision, suggestion use, and user ratings.
2. **Can a cheap first stage reduce generation cost while preserving useful matches?** The tested context-only gate ranked matches less effectively. An experiment could use it as a conservative first stage, run the full gate on the remaining cases, and compare latency and match retention at equal display coverage.
3. **How much do per-candidate labels contribute to gating?** The reported models use both list-level and per-candidate targets. Train otherwise identical gates with and without the auxiliary targets and compare test AUROC and pass@5 at equal coverage for held-out predictors.

## Confidence and missing information

**High** for the reported offline comparisons and their evaluation settings. The supplied text gives no live-user outcomes, evaluation on ordinary turns without an edit request, multi-annotator validation, or isolated estimate of the auxiliary targets’ contribution. It reports code availability, while access to trained gate weights is unconfirmed.
