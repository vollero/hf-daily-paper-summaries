# PyRUA-Dex: Learning Programmatic Policies for Dexterous Bimanual Manipulation with Coding Agents

> [← Daily summary](../2026-11-26.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.33144) · [arXiv](https://arxiv.org/abs/2611.33144)


## One-sentence takeaway

PyRUA-Dex uses coding agents to develop and refine frozen Python policies without robot demonstrations, outperforming the reported trained baselines in aggregate on Bench2Dex and DexJoCo and demonstrating selected tasks on one real bimanual platform.

## Problem and motivation

High-quality demonstrations for multi-fingered robots are scarce because video retargeting is imprecise, teleoperation lacks force feedback for the operator, and exoskeleton collection is hard to scale. The authors identify a gap between robot programs that receive little robustness testing and online agents that spend model tokens in every episode. They ask whether coding agents can develop a task policy once and have it run independently across perturbed layouts. (§1)

## Approach and contributions

- **Frozen, task-specific Python policies.** Each program measures the scene, runs ordered stage functions, and can retry failures within the episode budget. A shared library exposes perception and control primitives across robot hands. Policies can call visual segmentation and use fingertip feedback where available, while language-model calls and simulator progress signals are confined to development. (§§3.1–3.2, Appendix A)
- **Parallel exploration followed by refinement.** Agents use simulator resets and shared memory to discover skills. A distilling agent evaluates and combines successful code into a task library and candidate policy. Refinement uses randomized layouts to diagnose and repair bottleneck stages, with held-out counts guiding selection and separate test layouts for final evaluation. DexJoCo supplies episode success as its only development feedback. (§§3.3–3.4, 4.5)
- **Real-to-sim-to-real development.** The authors calibrate a simulator to the physical robot, execute frozen programs on hardware, and use observed discrepancies to update the simulator before the next refinement round. They also distill a reusable piano-playing skill. (§§3.5, 5)

The simulation results establish an aggregate lead over the reported trained baselines and a gain from the refinement pipeline as a whole. The online comparison uses the same underlying model with different development and execution protocols, so it cannot isolate the effect of freezing the policy. The hardware runs establish feasibility on the reported platform. The validation counts quantify reliability in simulation, while repeated-trial hardware reliability remains unknown.

## Limitations and validity risks

- **Author-stated.** The programs struggle with sustained force and slip control. Bench2Dex tactile sensing is coarse, so the programs rely mainly on joint lag to infer contact. Stages that never succeed remain an exploration problem. Development is per task, and hardware reliability was assessed in calibrated simulation rather than through repeated physical trials. (§6, Appendix D.1)
- **Analyst inference.** The exploration-only comparison measures refinement as a package. It leaves the independent contributions of bottleneck-first selection, shared memory, and tactile sensing unresolved. (§§3.3–3.4, 4.3)
- **Analyst inference.** The absence of time and token caps during development limits what can be concluded about performance under matched development resources. The online comparison also differs in how each system accesses development feedback. (§§4.1, 4.4, Appendix A)

## Open research questions

- **Can learned contact controllers improve sustained manipulation?** The paper identifies force and slip as failure modes. Compare otherwise identical staged programs with threshold-based contact, learned contact controllers, and improved tactile simulation on pouring and assembly. (§6)
- **Does bottleneck-first refinement outperform other stage-selection strategies?** The reported comparison evaluates refinement as a package. Compare bottleneck-first, fixed-order, and random stage selection under matched layout and token budgets. (§§3.4, 4.3)
- **Do task libraries transfer beyond piano?** The demonstrated reuse stays within one task family. Seed development on held-out manipulation tasks with related libraries and compare success and development cost against empty-library runs. (§§5–6)
- **How well does simulated validation predict hardware reliability?** The physical experiments show selected executions. Run repeated trials over matched randomized layouts in simulation and on hardware, then compare success rates and failure modes. (§§5–6)

## Confidence and missing information

**High** for the reported benchmark aggregates and the broad method. The supplied text leaves open the exact refinement procedure when DexJoCo provides only binary success, the degree of episode matching behind the Bench2Dex online comparison, variation across independent policy-development runs, repeated hardware success rates, and which task artifacts are included in the linked repository.
