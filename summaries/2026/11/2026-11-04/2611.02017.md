# Switch-SWE: Do Coding Agents Hold Focus When Switching Between Unfinished Tasks?

> [← Daily summary](../2026-11-04.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.02017) · [arXiv](https://arxiv.org/abs/2611.02017)


## One-sentence takeaway
Switch-SWE reports an average 11.5-percentage-point resolution drop across seven coding-agent configurations when unfinished tasks are interleaved, while task-aware history routing and state memory recover 5.5–15.5 points on two OpenCode models (§§4.1, 5.3).

## Problem and motivation
Coding agents may need to resume unfinished work after handling other requests. Preserving code does not necessarily preserve requirements, decisions, or submission scope. The authors identify a gap in repository-level benchmarks: they do not directly isolate repeated resumption after advancing other unfinished tasks in the same conversation and repository (§§1–2).

## Approach and contributions
- **Matched evaluation setting:** Each focus task receives identical requirements, verifier, checkout layout, and focus-stage budgets in uninterrupted and switched runs. Switching inserts work on four other unfinished tasks; each task retains a separate checkout (§3.1).
- **Benchmark:** Switch-SWE contains 200 focus tasks from 19 Python repositories and 400 matched session specifications. Requirements derive from issue, pull-request, and review histories, with separately recorded benchmark-authored behavioral extensions where needed (§§3.2–3.5, C.3).
- **Behavioral evaluation:** Final focus patches are scored with held-out fail-to-pass and pass-to-pass tests. Locality comparisons, computation accounting, and illustrative trajectories characterize resumption (§§3.4, 4, E).
- **Resumption Context Manager (RCM):** An OpenCode plug-in routes relevant interaction history and maintains task-specific requirements, progress, and pending-work summaries. Auxiliary calls count toward the execution budget (§§5.2–5.3, F).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Switching consistently reduces resolution | Seven configurations, each evaluated on 200 matched focus tasks: mean gap **11.5 percentage points**, range **6.0–15.0 points**. | §4.1; Table 1 caption and accompanying prose |
| Absolute performance and gap must be considered together | DeepSeek-V4.1-Flash/OpenCode falls from **46.5% to 31.5%**; GLM-5.3/OpenCode achieves the highest switched resolution, **43.0%**, with a **6.0-point** gap. | §4.1 |
| Far interruptions associate with larger gaps | Across configurations, mean gaps are **8.1 points near** versus **14.9 points far**; each group contains **100 different focus tasks**. | §4.2 |
| Switched sessions process substantially more tokens | Full switched runs use **4.5–11.1×** uninterrupted tokens; resumed substantive focus stages alone use **1.41–2.95×** a full uninterrupted session’s tokens. | §4.3; accounting in §B.5 |
| Routing and memory improve switched completion | On 200 tasks per model, routing adds **11.0 points** for DeepSeek and **3.5 points** for GLM; memory adds another **4.5** and **2.0 points**, respectively. Full RCM gains are therefore **15.5** and **5.5 points** over native OpenCode. | §5.3 |
| Traces illustrate requirement loss and submission confusion | Click’s switched artifact preserves later factory behavior but misses earlier literal-default requirements; Moto’s switched run fails to produce an applicable focus patch after broadening submission scope. | §§E.2–E.3 |

The paired results support a resumption deficit under this specific interleaving protocol. They do not isolate its mechanism: additional work, longer history, context management, and termination or submission failures all contribute to the setting. Locality is an association, and the illustrative traces do not establish failure-mode prevalence.

## Limitations and validity risks
- **Author-stated:** Near and far groups contain different focus tasks, preventing a causal interpretation of locality (§4.2).
- **Author-stated:** Aggregate token accounting cannot separate repeated history processing from output differences and native context management; full-session ratios include interruption work (§4.3).
- **Analyst inference:** Generalization beyond Python, separate checkouts, four interruptions, and focus-only scoring remains untested here. The protocol does not evaluate shared-file conflicts or overall multi-task success (§3).
- **Analyst inference:** RCM evidence covers two models in OpenCode. The routing condition also changes compaction behavior, so its gains do not isolate history filtering alone (§§5.2–5.3).
- **Analyst inference:** Each task-condition pair is evaluated once; uncertainty estimates and repeated-run variability are unavailable. Selection used earlier diagnostic-cohort outcomes, but their selection effect is not quantified (§§3.3, B.4).
- **Reporting ambiguity:** Timeout continuation descriptions differ between §4 and §B.2. The abstract says code is available, while the reproducibility statement describes a planned public release.

## Open research questions
1. **Does locality itself affect resumption?** Different focus cohorts leave this unresolved (§4.2). Evaluate each eligible focus task with both near and far interruptions.
2. **Which context intervention drives improvement?** Routing shares a compaction intervention, and memory adds another component (§5.2). Compare filtering, compaction instructions, and memory in a factorial ablation.
3. **How does interruption load change reliability?** The benchmark fixes four interruption tasks (§3.1). Vary task count and return spacing while measuring both focus resolution and completion across all tasks.

## Confidence and missing information
**Confidence: medium.** The supplied text clearly supports the main design and reported results, but omits the bodies of Tables 1–5 and 7–8. Material gaps include complete configuration results and versions, statistical uncertainty, failure-category counts, detailed RCM resource overhead, exact diagnostic-cohort selection criteria, an unambiguous timeout policy, and confirmed artifact-release status.
