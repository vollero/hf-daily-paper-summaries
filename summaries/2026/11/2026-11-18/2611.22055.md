# Weight-Space Programming Doesn&#x27;t Need Transformers

> [← Daily summary](../2026-11-18.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.22055) · [arXiv](https://arxiv.org/abs/2611.22055)


## One-sentence takeaway

In gradient-free weight-space programming for ARC science questions, three LLMs independently built sparse fact tables that outscored the fixed architectures they wrote, and an author-designed lookup variant ran up to 17× faster than a two-layer Transformer matched by nonzero count on one RTX 3090 (§§3–4, 6.3).

## Problem and motivation

Weight-space programming asks an LLM to write the weights of a separate target model without gradient training or fitting on data. The authors ask whether architectures designed for gradient optimization and GPU execution are suitable for this regime, where the writer needs to locate and revise the weights responsible for errors. They identify a gap in prior work that fixed the target architecture and studied what could be written into it (§§1, 3.2, 9).

## Approach and contributions

- **Architecture comparison.** Three LLMs receive ten labeled ARC examples each and an isolated sandbox. The authors compare freely designed models with released architectures written from random initialization and a small supplied Transformer. Multi-generation runs select parents using held-out validation accuracy (§2, Appendix A).
- **Convergent design and controls.** All three writers compile explicit knowledge into sparse concept tables and score options using the best-matching rows. The authors test whether a single row per option preserves accuracy, how many predictions change after deleting a line, and how the written models compare with BM25 over their own source text (§§3.1–3.3, 5, Appendix C).
- **Fixed-read associative memory.** The authors design a forward pass that combines a first-order concept table with directly addressed rows keyed by concept pairs. The writer supplies the vocabulary, knowledge files, and build script. Each question reads 120 pair-table rows and performs one concept-table product, keeping work independent of fact count for a fixed concept vocabulary (§3.4).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Free design improved ARC accuracy across all three writers | Best reported free-design result was 54.4% on the 3,530 four-option ARC test questions, from Claude Opus 5.5 generation 5. Fine-tuned Qwen3.5-0.8B reached 82.1% on the same test, using 3,358 labeled training questions versus ten examples per writing run. | §2, Table 3 |
| A written table beat a much larger released model | Claude Opus 5.5’s first-generation free design reached 50.8% ARC test accuracy with 0.94M counted parameters. The same writer’s validation-selected Qwen3-1.7B, written from random initialization, reached 48.7% with 1.72B parameters, about 1,800× as many under the paper’s accounting. | Table 3, Appendix A |
| Predictions often depended on a small number of rows | For Claude’s first-generation free design, one best fact per option gave 49.1% ARC test accuracy versus 50.8% for the full model. Deleting a sampled line changed 0.5–1.8 test answers on average across Claude’s four table runs, versus 4.8 answers in one written Transformer and 38% of answers in another, whose build used a shared random stream. | §5.1, Tables 4–5 |
| BM25 exposed differences in how the models used written knowledge | On ARC, written two-layer Transformers fell below stemmed BM25 over their own artifacts in 20 of 23 runs, while table models exceeded it in 21 of 24 runs across the three writers. | Appendix D, Table 15 |
| Direct lookup improved GPU speed | Claude’s author-designed memory runs reached 49.6–52.8% ARC test accuracy over five generations. CUDA-graph timing at the first- and fifth-generation sizes was 18 ms for 3,530 questions on one RTX 3090, in batches of 64. The fastest input treatment for a two-layer Transformer matched by nonzero count was 7× and 17× slower, respectively. | §6.3, Fig. 1(b), Tables 7 and 16 |
| Transfer was strongest to similar science questions | Both Claude table designs, run unchanged, reached 47.7% and 50.1% on four-option SciQ at generations 1 and 5, respectively. Across those same table runs, OpenBookQA accuracy was 30.3–36.1% and MMLU was near 25% chance. | §7.2, Table 23 |

The evidence supports sparse tables as an effective architecture for the tested gradient-free writing protocol, with direct lookup addressing the cost of scanning every fact. The BM25 results are consistent with the authors’ interference explanation, although the compared runs can differ in what the writers chose to encode and how they read it. The accuracy results establish an advantage over the tested written baselines, while fine-tuned pretrained models retain a substantial lead on ARC. The GPU result covers forward-pass timing with inputs already encoded and on-device (Appendix E).

## Limitations and validity risks

- **Author-stated.** The main models recall explicit facts and learn no representations of their own. SciQ free-answer generation reads out stored answers, and the authors report no multi-step fact composition in the main QA models (§§7.3, 8).
- **Author-stated.** The observed convergence could reflect retrieval’s familiarity to the writers. The speed advantage also depends on concept-vocabulary size, and GPU timing uses one hardware model (§§5.2, 6.4, 8).
- **Analyst inference.** The line-deletion comparison captures compiler behavior as well as architecture. A shared random stream amplified changes in one Transformer, and vocabulary edits accounted for much of the disruption in some table runs. These tests support locality for the sampled implementations (§5.1, Tables 5 and 14).
- **Analyst inference.** The overlap and deletion controls address detectable textual copying from written artifacts. The writers’ pretraining exposure remains unknown, so those controls leave other forms of benchmark familiarity unresolved (Appendix D, Table 13).

## Open research questions

1. **How much of the table advantage comes from the reader itself?** Writers can produce different knowledge files for different architectures (§5.2). Compile one fixed fact corpus and vocabulary into sparse and dense memories, match storage budgets, and compare accuracy, BM25, and edit locality.
2. **Can written memories compose facts reliably?** The ARC models largely retrieve explicit facts, and the SciQ generator returns stored answers (§8). Compare a fixed lookup reader with a bounded multi-hop reader on held-out questions whose answers require combining facts supplied separately.
3. **Does the speed advantage hold for end-to-end inference across hardware?** The reported GPU comparison uses one RTX 3090 with pre-encoded inputs, and concept-vocabulary size affects the crossover (§6.4, Appendix E). Benchmark multiple devices and batch sizes while including tokenization and input preparation and varying vocabulary size on real tasks.

## Confidence and missing information

**High** for the central ARC results and their stated measurement conditions. The supplied text provides the main comparisons and protocol, but several tables appear only as captions or prose summaries. Missing material includes the full numerical rows for the open-answer comparisons and generation-by-generation lineages, the exact token and wall-clock caps for individual writing runs, and the writers’ benchmark exposure during pretraining.
