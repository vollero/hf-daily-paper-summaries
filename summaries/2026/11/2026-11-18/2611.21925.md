# DNeo: Your Parallel Draft Model Needs Better Target Feature Encoding

> [← Daily summary](../2026-11-18.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.21925) · [arXiv](https://arxiv.org/abs/2611.21925)


## One-sentence takeaway

DNeo combines coordinate-preserving target features, memory of rejected drafts, and a fused causal head to commit more tokens per speculative round and decode Qwen3-4B up to 20.7% faster than DFlash-2 in the main single-request evaluation (§5.2).

## Problem and motivation

Autoregressive LLM decoding requires a target-model pass for each generated token. Parallel speculative drafting proposes a block in one pass, but the speed gain depends on how many tokens verification commits before the first rejection and how much each round costs. The authors identify three weaknesses in existing feature encoders: dense projections mix hidden-state coordinates, uniform layer selection overlooks more useful states, and memoryless drafters discard features already computed for rejected proposals. Existing causal heads also impose limits on how the drafter corrects predictions using preceding tokens (§§1–3).

## Approach and contributions

- **MoFA and layer selection.** Mixture-of-Features Attention learns one softmax weight per selected target layer and combines matching hidden-state coordinates. The layer-selection rule retains the first target layer and samples the rest from the second half (§§4.1, 4.5).
- **Rejection memory.** The next draft cross-attends to target features from the entire rejected suffix of the preceding round. It shares the prefix encoder and key/value projections and uses states already computed during verification (§4.3).
- **Fused causal head and leaner attention.** DNeo combines DSpark’s low-rank correction with DFlash-2’s context-aware scoring in a shared latent space, then applies corrections across the vocabulary. The backbone removes masked-block self-attention, retains cross-attention to prefix and rejection features, and reuses DFlash-2’s two-tap causal convolutions (§§4.2, 4.4, Table 1).

| Headline speed and concurrency gains | The introduction reports up to 30% faster generation than DFlash-2 on Qwen3-4B chain-of-thought workloads and 16% higher throughput at batch size 32. The cited H100 figure labels the block size as 15. | §1, Fig. 1 |
| Throughput gains depend on serving setup | In Transformers serving, DNeo delivered up to 58% higher aggregate decode throughput than DFlash-2 at batch size 32. The throughput section also reports DNeo within 0.1% of autoregressive throughput at batch size 64. Table 3 specifies one H100, temperature 1, block size 16, and the six-benchmark suite. | §5.3, Table 3, Fig. 1 |
| MoFA supplied the largest component gain | Independent ablations with the same layer-selection rule attributed gains of 0.651 TPF to MoFA, 0.331 to the reused convolutions, 0.217 to the fused head, and 0.182 to rejection memory. In a separate 50,000-rollout encoder comparison, a coordinate-restricted projection beat dense encoding by 0.423 TPF and came within 0.3% of MoFA. | §§5.4–5.4.1, Tables 4–5 |
| Layer selection improved at fixed feature budgets | On DSpark with MoFA, selecting 5 to 15 target layers raised TPF from 2.481 to 2.516 under DNeo’s rule, while uniform selection went from 2.467 to 2.447. | §5.4.4, Fig. 7 |

TPF measures expected committed tokens per speculative round. The ablations support the authors’ explanation that preserving coordinates improves draft quality in the tested setup. Serving results show when the extra committed tokens offset round cost. At temperature 0, DNeo’s TPF advantage over DFlash on GPQA and MTBench was insufficient to make DNeo faster (§5.2). The paper grounds losslessness in the verification rule (§2). The supplied text provides no separate empirical output-equivalence test and leaves the precise relationship between the Figure 1 and Table 2 speed maxima unclear.

## Limitations and validity risks

- **Author-stated.** Rejection memory makes each draft depend on the previous verification outcome. The authors require on-policy rollouts to avoid a train–test mismatch. MoFA’s tested design assumes equal hidden widths. The paper proposes a key/value projection adaptation for unequal widths and supplies no evaluation of it (§§4.1, 4.3).
- **Author-stated.** The authors leave parallel-drafter scaling laws open and note that gains in the additive ablation may depend on component order (Appendices A.1, A.3).
- **Analyst inference.** One target model and one GPU type limit what can be concluded about transfer. Decode-only timing leaves end-to-end request latency, including prefill, unresolved. EAGLE-3 uses official weights, so the shared-training comparison applies to the parallel drafters (§5.1, Table 2, Appendix A.6).
- **Analyst inference.** The restricted projection supports the residual-mixing explanation under the tested rollout budget. Whether dense encoding closes the gap with longer training remains open (§5.4.1).

## Open research questions

1. **Does late-layer selection transfer across target models?** The reported sweep uses one target. Repeat it on several target models at matched feature counts and compare TPF and gate weights (§5.4.4).
2. **Can dense encoding catch up with longer training?** The coordinate-restriction comparison is reported at a fixed rollout budget. Train dense, restricted, and MoFA encoders at several matched budgets and compare TPF and encoder cost (§5.4.1).
3. **How much of the rejected suffix is worth retaining?** The reported rejection comparison changes both feature coverage and how features enter the drafter. Hold cross-attention fixed, vary the number of retained rejection states, and measure TPF and round latency across concurrency levels (§5.4.3).

## Confidence and missing information

**Medium.** The architecture and main directional findings are explicit. The supplied text omits most table cells and numerical figure traces, so exact per-benchmark and per-backend values, run-to-run uncertainty, and settings behind some headline maxima cannot be verified. It also gives no DNeo code or checkpoint release details, empirical output-equivalence measurements, or direct measurements substantiating the full-drafter footprint claim.
