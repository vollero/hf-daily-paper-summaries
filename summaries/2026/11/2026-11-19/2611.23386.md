# Chorus: Shared N-gram Embeddings with Layer-wise Adaptation

> [← Daily summary](../2026-11-19.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.23386) · [arXiv](https://arxiv.org/abs/2611.23386)


## One-sentence takeaway

Chorus reuses one set of token and n-gram tables with layer-specific adaptation, reaching 0.9229 validation bits per byte on ClimbMix with 1.2B added parameters versus 0.9258 for FactorEngram and 0.9273 for Engram with 9.6B each (§3.1, Fig. 1).

## Problem and motivation

Hashed n-gram tables let language models add capacity while reading only a few rows per token. Giving each layer its own tables increases memory use or forces layers to split a fixed row budget, increasing hash collisions. The authors identify a gap between separate tables, which cannot share learned entries, and simple sharing, which gives layers the same embedding despite their different computational roles (§1).

## Approach and contributions

- **Shared lookup and refinement.** Chorus combines a token embedding with hashed bigram and trigram embeddings, then applies context-dependent gating and a causal convolution. It computes the refined vector once per token position for reuse at the input and in selected layers (§2, Fig. 2).
- **Layer-specific reads.** At every other layer, the incoming hidden state determines a channel-wise rescaling of the shared vector. A layer-specific projection and per-head gate adapt the result before it is added to attention values (§2, Eq. 4).
- **Memory-efficient training.** The authors apply the existing Ember optimizer to hashed n-gram tables and test its compatibility with several table designs (§§2, 3.2). They also evaluate how Chorus scales with table size and whether its gains carry across datasets and backbone sizes (§3.1).

| Downstream gains, strongest on factual recall | FineWeb, 18-layer 133M backbone, 60M tables, three seeds. Across 22 DCLM tasks, Chorus averaged 0.1240 ± 0.0016, about 0.0030 above TN-gram. The evidence supports a validation-loss advantage for the tested Chorus configurations at matched added-parameter budgets. The scaling sweep compares complete recipes, including different table optimizers. Table 3 shows that Chorus also leads the tested designs when the optimizer is held fixed at 76M. The reported 99.2% saving applies to table optimizer state, and its paired quality comparison was run at a smaller table size. The downstream pattern is consistent with the authors’ factual-recall interpretation. Their proposed phrase-association mechanism remains untested.

## Limitations and validity risks

- **Authors.** Evaluation covers dense backbones up to 133M parameters. Larger models and other architectures remain untested. Downstream gains appear concentrated in language prediction and recall, with no statistically significant differences on CommonsenseQA or Dyck languages (§3.1, Appendix D).
- **Authors.** At the largest table size, temporary update buffers and hardware-constrained table placement reduce Chorus’s peak-memory advantage. Ember also worsens FactorEngram’s validation loss in the optimizer comparison (§3.2, Table 3, Appendix B.1).
- **Analyst inference.** The one-seed scaling sweep, ablations, and order sweep leave uncertainty about the stability of individual margins and the best n-gram order. The fixed-budget split-table ablation tests a practical allocation trade-off. It cannot isolate learned cross-layer reuse from the effect of giving each read access to a larger pool (§3, Fig. 5, Appendix C.2).

## Open research questions

1. **Does the quality advantage persist on larger backbones?** The largest tested backbone has 133M parameters. A next experiment would repeat matched-budget comparisons on larger dense Transformers and report validation BPB, training time, and peak memory across seeds (Appendix D).
2. **How much of the scaling gain comes from the architecture versus the optimizer?** The large-table sweep couples architecture and optimizer, while the crossed comparison uses 76M tables. A next experiment would cross architecture with optimizer at several larger budgets and measure BPB and peak memory (§3.2, Appendix B.1).
3. **Do hash collisions explain why longer n-grams help at larger budgets?** The order sweep uses one run per setting, and the collision explanation is tentative. A next experiment would vary hash layouts at fixed parameter budgets, measure collision rates, and repeat the order sweep across seeds (§3.3, Fig. 6, Appendix C.2).
