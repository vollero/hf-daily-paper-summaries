# QDA: Closed-Loop LLM Quantization Design with Agents

> [← Daily summary](../2026-11-19.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.23388) · [arXiv](https://arxiv.org/abs/2611.23388)


## One-sentence takeaway

QDA uses a coding agent, a fast proxy score, and selective long-generation checks to design quantization recipes that improved mean benchmark accuracy over the strongest tested public recipes by 0.9–2.2 percentage points across three precisions on four reasoning LLMs while retaining existing serving kernels (Table 2, §6.2).

## Problem and motivation

The best post-training quantization (PTQ) recipe depends on the model and target precision. Quantization reduces serving memory and compute costs, but choosing how to combine methods, tune their settings, and select calibration data still requires trial and error. The authors identify two barriers to automating that work: full reasoning evaluations take 23–86 GPU-hours per checkpoint on the main suite, and methods from separate codebases often require architecture-specific porting (§§2.1, 3.1–3.3).

## Approach and contributions

- **Closed-loop recipe design.** A coding agent proposes and revises ordered PTQ recipes under a GPU budget. It can generate calibration data, write refinement code, and refine a public checkpoint. The target format and serving kernel constrain the search (§§4.1, 6.4).
- **Scoring and generation checks.** The evaluator computes next-token KL divergence on hidden traces from the original model, caching its top 128 probabilities per position and pooling the remaining probability mass. The evaluator scores the served checkpoint, and the agent runs selected candidates on long problems to detect loops and truncations that fixed-trace scoring can miss (§§4.2–4.3, 5.2).
- **Composable PTQ infrastructure.** A common checkpoint interface supports 21 methods, with model-derived layer relationships, kernel-aware quantization, and batched GPTQ solves for MoE experts. A harness schedules GPU jobs and isolates the reference traces and test benchmarks from the agent (§§5.1–5.3, Table 8).

The experiments support QDA’s average accuracy advantage under the reported search budgets, benchmarks, and serving configurations. The ranking test and truncation example show why KL is useful for screening and why free-running checks matter. The quantified throughput result covers one model and precision. The other configurations support the authors’ broader efficiency claim through reuse of existing kernels.

## Limitations and validity risks

- **Authors’ observations.** KL can disagree with benchmark accuracy and can miss failures that emerge during long generation. The fixed recipe was derived from QDA searches, so the authors flag its dependence on those runs (§§4.2–4.3, 6.3).
- **Analyst inference — limited replication.** Search replication and component ablations center on Qwen3.6-35B-A3B. The other main model–precision pairs and the NVFP4 demonstration each use a single search, leaving run-to-run variability uncertain there (§6.1, Tables 2–5).
- **Analyst inference — bundled comparisons.** ModelOpt changes the toolkit, search workflow, and candidate-scoring protocol together. The infrastructure variant also changes several components, and greedy and ASHA use predefined recipe spaces. These comparisons leave the separate effects of the evaluator, generation checks, scheduler, and agent flexibility unresolved (Tables 4–5, Appendix E).
- **Analyst inference — architecture and deployment scope.** GLM-5.3-Flash required an adapter and library extensions, and the explicit throughput benchmark covers one configuration. Effort and performance on other architectures and serving stacks remain uncertain (§5.1, Appendix D).

## Open research questions

1. **How much do long-generation checks improve checkpoint selection?** The paper gives a failure example and search-log observations. An equal-budget ablation could compare KL-only search with KL plus generation checks across several model–precision pairs, measuring held-out accuracy, loops, and truncation (§§4.3, 6.4).
2. **How much flexibility does the coding agent need to outperform predefined search?** Table 5a compares workflows with different recipe and data-generation capabilities. A matched-budget experiment could give both search types the same candidate space, calibration pool, and submission rules, then separately enable custom data and code.
3. **How stable are the gains across search budgets and agents?** The main suite uses one agent and one budget, with repeats concentrated on one model. Repeated searches with several agents and budgets could estimate how accuracy and variability change with compute (§6.1, Appendix E).

## Confidence and missing information

**High** confidence in the reported comparisons for the stated settings. The supplied text contains the main tables and evaluation protocol. It omits raw search logs and per-run results outside the reported summaries, full prompt and recipe artifacts, uncertainty estimates for most model–precision pairs, and release links confirming availability of the QDA library, evaluator, or harness.
