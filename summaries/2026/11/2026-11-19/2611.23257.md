# StatePortal: Agentic Checkpoint Synthesis for Testing Deep States in Interactive Software

> [← Daily summary](../2026-11-19.md) · [Relationship graph](relationships.md) · [Hugging Face](https://huggingface.co/papers/2611.23257) · [arXiv](https://arxiv.org/abs/2611.23257)


## One-sentence takeaway

On DeepStateBench, synthesized checkpoints raised Agent S3’s end-to-end completion from 0% to 10.4% under the same pixel policy, while StatePortal reached 27.5% by also executing the target action through an application hook (§5.1.1).

## Problem and motivation

Deep-state GUI tests exercise behavior that requires a long sequence of prerequisite interactions. Repeating that sequence across commits costs time and model calls, and navigation errors can compound before the behavior under test is reached. Self-rendered engines often lack the DOM or accessibility tree that conventional GUI automation uses. The authors identify a gap between approaches that assume an existing fixture or platform-specific state access and test generators that leave construction of the required starting state unresolved (§§1, 6).

## Approach and contributions

1. **Checkpoint synthesis task.** Given a natural-language functional test and read-only source access, produce a versionable checkpoint with the starting state, restoration payload, bounded transition, and predicted assertions. Hidden grading is independent of those predictions (§2, §3.3).
2. **StatePortal agent.** An onboarding agent binds or builds a per-application hook and declares its capabilities. A synthesis agent then uses one bounded repository exploration to generate both the starting state and the transition. The hook restores the checkpoint in a running application (§3, Figure 2).
3. **Hybrid evaluation.** Hidden programmatic checks and a screenshot-based vision-language model judge must both pass at the Start and Goal gates. The authors calibrate the visual judge against blinded model annotations (§4.3).
4. **DeepStateBench.** The authors report releasing 61 tasks across 10 applications. Each task requires constructing the Start and executing the target behavior under a common evaluation protocol (§4, §7).

## Evidence and main results

| Finding | Evidence / setting | Location in paper |
|---|---|---|
| Checkpoint seeding improves pixel-agent completion | Across 61 tasks, three registered models, and three seeds, with 549 trials per configuration, cold vs. seeded Agent S3 reached Start on 7.8% vs. 36.6% and completed 0% vs. 10.4% end to end. Mean tokens fell from 408.3k to 163.8k per trial. | §5.1.1, Table 2 |
| Generated transitions improve completion after restoration | In the same registered study, StatePortal reached Start on 38.4% of trials and completed 27.5% end to end (95% CI 19.3–36.1%), versus 36.6% Start and 10.4% end to end for seeded Agent S3. | §5.1.1, Table 2 |
| Frozen checkpoints usually reproduce their verdicts | With model calls disabled, 98.90% of 1,361 replays of 112 checkpoints reproduced the original verdict (95% CI 96.8–100%). All 328 replays of originally accepted checkpoints agreed. The two replay sessions ran on one host. | §5.1.2, Appendix B.24 |
| The visual gate catches controlled faults missed by state checks | The hybrid grader rejected 77 of 80 controlled visual faults (96.25%) that passed the programmatic check by construction. On the full 200-sample calibration set, the judge achieved 96.0% strict accuracy against a blinded cross-model reference. | §4.3, Table 12 |
| Checkpoints distinguish some known buggy and fixed builds | In the single-seed study of 11 real issues whose registered tests passed on both builds, StatePortal separated 7 of its 8 comparable tasks using a defect-aware pixel score. That score also separated 4 of 26 same-version control pairs (15.4%). | §5.2, Appendix B.21, Table 24 |
| Synthesis ablations favor the full configuration descriptively | On all 61 tasks with gpt-5.6-terra and seed 0, the full method completed 19 tasks, versus 14 without source exploration, 17 with a schema-only contract, and 13 without assertion prediction. None of the paired differences reached significance after Holm correction. | Appendix B.24.1, Tables 28–29 |

The cold-versus-seeded comparison isolates the effect of checkpoint seeding under a fixed pixel policy. The seeded-pixel versus StatePortal comparison supports the benefit of generated transitions on this task mix, where many transitions use source APIs. It leaves pixel-path coverage unresolved. The replay metric measures agreement with the original verdict, including failures. The calibration measures agreement with model labels and detection of controlled faults, while the real-repair diagnostic measures separation where the visual footprint of the fix is already known.

## Limitations and validity risks

- **Authors’ stated limits.** Task admission requires deterministic transitions on observable, controllable state. StatePortal uses source APIs for 50 of 61 target actions, bypassing the UI input path and limiting which input-path defects those trials can trigger (§4.2, Appendix B.1).
- **Authors’ stated limits.** The real-defect study uses a single seed and a grader-side mask derived from known fixes. Two OpenRA tasks could not be scored for version discrimination because of viewport mismatch. The authors treat the results as descriptive (Appendix B.21).
- **Authors’ stated limits.** Hidden checks observe only registered properties, and a read-only or idempotent operation may already satisfy the Goal at Start. The joint-versus-delegated diagnostic is unpaired, and the component ablations cover one model and one seed (Appendices B.3, B.19, B.24.1).
- **Analyst inference.** Agreement with other VLMs leaves human agreement on subtle rendering failures unresolved. Two sessions on one host also leave portability across machines and rendering configurations untested (§4.3, Appendix B.24).

## Open research questions

1. **How much of the transition advantage survives when both methods use the same input path?** The benchmark favors tasks with a callable semantic surface. A follow-up could hold the restored checkpoint fixed and compare pixel, native-input, and source-API execution on tasks that support all three, including seeded input-path defects (§4.2, Appendix B.1).
2. **How reliably do checkpoints separate buggy and fixed builds across repairs and seeds?** The current diagnostic is narrow and shows false separation on same-version controls. A follow-up could preregister a larger repair set, standardize capture geometry, repeat across seeds, and report matched-pair coverage alongside false separation (§5.2, Appendix B.21).
3. **How portable are frozen checkpoints across runtime environments?** The replay sessions shared one host. A follow-up could replay the same artifacts across hosts and rendering configurations, tracking restoration success, verdict agreement, and frame identity separately (§5.1.2, Appendix B.24).
